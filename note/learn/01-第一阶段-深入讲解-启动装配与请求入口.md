# 第一阶段深入：启动装配与请求入口

你现在的感觉是正常的：第一阶段的“宏观鸟瞰”只能让你知道城市地图，但还不能让你会在城市里走路。要更掌握这个项目，第一阶段还要补三件事：

1. 一个服务是怎么启动起来的。
2. 启动工程为什么能加载 `01zhaocai-end` 里的业务代码。
3. 一个请求大概怎么从网关走到 Controller。

下面用 `scm-cloud-srm` 作为样例讲。SRM 是供应商管理服务，它依赖的公共能力很多，适合作为入门样板。

## 1. 先把项目想成“三层装配”

这个项目不是简单的“一个服务目录里放所有代码”。它更像组装电脑：

```text
03 启动工程：机箱 + 电源按钮
01 业务模块：CPU、内存、硬盘、显卡
Nacos 配置：插线板和外部参数
```

也就是说：

```text
03zhaocai-start/scm-cloud-starters-web/scm-cloud-srm
  负责启动 scm-srm-web 这个服务

01zhaocai-end/scm-srm-all
  负责提供 SRM 业务代码

Nacos global-config.yaml
  负责提供数据库、Redis、网关、公共参数等配置
```

你如果只看 `03/scm-cloud-srm`，会觉得代码很少；这是因为它主要是启动壳。真正的 Controller、Service、Mapper 大多在 `01/scm-srm-all`。

## 2. 先看启动配置：服务叫什么、从哪取配置

先看：

```text
03zhaocai-start/scm-cloud-starters-web/scm-cloud-srm/src/main/resources/bootstrap.yml
```

这个文件告诉你三件事：

```text
server.port = 8130
server.servlet.context-path = /scm-srm-web
spring.application.name = scm-srm-web
spring.profiles.active = dev
```

含义是：

- 这个服务默认启动在 `8130` 端口。
- 服务自己的根路径是 `/scm-srm-web`。
- 注册到 Nacos 里的名字是 `scm-srm-web`。
- 默认环境是 `dev`。

再看：

```text
03zhaocai-start/scm-cloud-starters-web/scm-cloud-srm/src/main/resources/bootstrap-dev.yml
```

这个文件告诉你：

```text
Nacos 地址：10.0.54.19:8848
namespace：scm-jdsn
group：common
shared-configs：global-config.yaml
```

Nacos 可以理解成“服务通讯录 + 配置公告栏”。服务启动时，一边把自己登记到通讯录，一边从公告栏读取公共配置。

所以 SRM 启动时大概会做：

```text
读取 bootstrap.yml
  -> 知道自己叫 scm-srm-web，端口 8130

读取 bootstrap-dev.yml
  -> 知道去哪个 Nacos

连接 Nacos
  -> 注册自己
  -> 拉取 global-config.yaml

启动 Spring 容器
  -> 装配业务代码和公共组件
```

## 3. 再看 POM：这个服务到底装了哪些能力

看：

```text
03zhaocai-start/scm-cloud-starters-web/scm-cloud-srm/pom.xml
```

你不用逐行看，先抓几类依赖：

```text
spring-cloud-starter-alibaba-nacos-discovery
spring-cloud-starter-alibaba-nacos-config
spring-boot-starter-data-redis
mysql-connector-java
scm-cloud-dependencies-orm
scm-cloud-dependencies-oauth2
scm-share-cache-web-jar
scm-share-mq-web-jar
scm-share-seq-web-jar
scm-share-workflow-web-jar
scm-srm-web-jar
```

这些依赖翻译成人话就是：

- `nacos-discovery`：我能注册到 Nacos，也能发现别人。
- `nacos-config`：我能从 Nacos 拉配置。
- `redis` / `cache`：我能用缓存。
- `mysql` / `orm`：我能访问数据库。
- `oauth2`：我能识别登录授权信息。
- `mq`：我能使用消息队列。
- `seq`：我能使用统一编号/序列能力。
- `workflow`：我能接工作流。
- `scm-srm-web-jar`：把 SRM 自己的 Web 业务代码装进来。

这里最关键的是 `scm-srm-web-jar`。看到它，你就要马上跳到：

```text
01zhaocai-end/scm-srm-all/scm-srm-web-jar
```

## 4. 最关键：启动类如何装配业务代码

看：

```text
03zhaocai-start/scm-cloud-starters-web/scm-cloud-srm/src/main/java/com/pcitc/scm/srm/starter/SrmApp.java
```

你重点看这些注解：

```text
@SpringBootApplication
@EnableDiscoveryClient
@ComponentScan
@Import
```

术语解释：

- `@SpringBootApplication`：Spring Boot 启动入口，表示“从这里启动整个服务”。
- `@EnableDiscoveryClient`：启用服务发现，让服务能注册到 Nacos。
- `@ComponentScan`：告诉 Spring 去哪些包下面找组件。
- `@Import`：手动导入其他配置类，像把一箱箱零件搬进 Spring 容器。

`SrmApp.java` 里最重要的是 `@Import`。它导入了这些配置类：

```text
SrmWebConfig
Oauth2WebConfig
MqWebConfig
CacheWebConfig
MdmFeignWebConfig
WorkFlowWebConfig
WebUserWebConfig
XxljobExecutorWebConfig
AimWebConfig
RuleWebConfig
ContractFeignWebConfig
```

你可以把它理解为：

```text
启动 SRM 服务时
  不只是启动 SRM 自己
  还把认证、缓存、MQ、工作流、用户上下文、定时任务、Feign 客户端等能力一起装进来
```

这也是为什么这个项目看起来模块多：每个服务都是“业务模块 + 一堆公共能力”的组合。

## 5. `SrmWebConfig` 才是真正把业务代码扫进来的地方

继续看：

```text
01zhaocai-end/scm-srm-all/scm-srm-web-jar/src/main/java/com/pcitc/scm/srm/webconfig/SrmWebConfig.java
```

这里重点看：

```text
@ComponentScan(basePackages = {
  "com.pcitc.scm.srm.*.controller",
  "com.pcitc.scm.srm.apply.*.controller",
  "com.pcitc.scm.srm.**.service.impl",
  "com.pcitc.scm.srm.company.mq",
  "com.pcitc.scm.srm.xxljob",
  "com.pcitc.scm.srm.*.config"
})

@MapperScan(basePackages = {
  "com.pcitc.scm.srm.*.repositories",
  "com.pcitc.scm.ubm.*.repositories"
})
```

这段话非常重要。它说明：

- Controller 会从 `com.pcitc.scm.srm.*.controller` 这些包里找。
- Service 实现会从 `com.pcitc.scm.srm.**.service.impl` 找。
- Mapper/Repository 会从 `com.pcitc.scm.srm.*.repositories` 找。
- MQ 消费者、定时任务、配置类也会被扫进来。

所以你以后找接口，不要在 `03/scm-cloud-srm` 里面死找。要去：

```text
01zhaocai-end/scm-srm-all/scm-srm-company/src/main/java/.../controller
01zhaocai-end/scm-srm-all/scm-srm-apply/src/main/java/.../controller
01zhaocai-end/scm-srm-all/scm-srm-common/src/main/java/.../controller
```

## 6. 一个真实请求怎么拼出来

以 SRM 供应商查询为例，本地代码里能看到接口：

```text
01zhaocai-end/scm-srm-all/scm-srm-company/src/main/java/com/pcitc/scm/srm/company/controller/CompanyController.java
```

里面有类似：

```text
POST s/business/srm/company/queryCompanyList
GET  s/business/srm/company/getDetail
```

结合 `bootstrap.yml` 的：

```text
server.servlet.context-path = /scm-srm-web
```

如果直接访问 SRM 服务，路径大概是：

```text
http://localhost:8130/scm-srm-web/s/business/srm/company/queryCompanyList
```

但正常前端不会直接打 SRM 服务，而是先打网关。网关再根据路由配置转发到 `scm-srm-web`。

完整理解方式是：

```text
浏览器
  -> 前端 Vue
  -> 网关 scm-gateway-web
  -> Nacos 查找 scm-srm-web 的实例地址
  -> 转发到 SRM 服务
  -> CompanyController
  -> CompanyServiceImpl
  -> CompanyMapper / Repository
  -> MySQL
```

这里的 Nacos 服务发现像通讯录：网关只需要知道服务名 `scm-srm-web`，不用写死这台服务具体在哪台机器、哪个 IP。

## 7. 网关在入口做了什么

看后台网关启动配置：

```text
03zhaocai-start/scm-cloud-starters-web/scm-cloud-gateway/src/main/resources/bootstrap.yml
03zhaocai-start/scm-cloud-starters-web/scm-cloud-gateway/src/main/resources/bootstrap-dev.yml
```

它默认：

```text
server.port = 9900
spring.application.name = scm-gateway-web
Nacos = 10.0.54.19:8848
shared-configs = global-config.yaml
```

再看网关核心代码：

```text
01zhaocai-end/scm-gateway-all/scm-gateway/src/main/java/com/pcitc/scm/gateway/filter/GatewayRewriterFilter.java
```

这个过滤器会做几类事：

- 解析 Cookie 或 Authorization 里的 Token。
- 根据配置判断哪些路径不需要登录。
- 处理请求路径。
- 生成 `SCM_X_TRACK` 这类请求追踪 ID。
- 给请求加网关标记。
- 检查用户会话活跃状态。

过滤器可以理解成门口安检：请求不是直接进业务服务，而是先被检查、补充信息、改写路径，再放行。

再看：

```text
01zhaocai-end/scm-gateway-all/scm-gateway/src/main/java/com/pcitc/scm/gateway/config/GatewayConfig.java
```

这个类使用：

```text
@ConfigurationProperties(prefix = "scm.gateway.config")
```

说明很多网关规则来自配置项 `scm.gateway.config`。这些配置本地不一定完整，因为大概率在 Nacos 的 `global-config.yaml` 里。

## 8. 为什么你会觉得“看了还不掌握”

因为第一阶段只看服务名和端口是不够的。真正掌握这个项目的第一阶段，要能说出这条链：

```text
scm-cloud-srm/pom.xml
  -> 依赖 scm-srm-web-jar

SrmApp.java
  -> @Import(SrmWebConfig.class)

SrmWebConfig.java
  -> @ComponentScan 扫描 SRM Controller/Service
  -> @MapperScan 扫描 SRM Repository

CompanyController.java
  -> 暴露具体接口

bootstrap.yml
  -> 定义服务名、端口、context-path

bootstrap-dev.yml
  -> 定义 Nacos 地址、namespace、公共配置

GatewayRewriterFilter.java
  -> 请求进业务服务前先过网关过滤器
```

你能把这条链讲出来，才算不是只停留在“知道有很多服务”的层面。

## 10. 第九项这些文件分别干什么

第九项列出的文件不是孤立的，它们是在描述一条“服务从启动到接收请求”的主线：

```text
bootstrap.yml
  -> 定义服务自己的身份

bootstrap-dev.yml
  -> 定义开发环境下去哪里拿外部配置

pom.xml
  -> 定义这个服务装了哪些业务包和公共能力

SrmApp.java
  -> 真正启动 Spring Boot 服务，并导入配置类

SrmWebConfig.java
  -> 告诉 Spring 去哪里扫描 SRM 的 Controller / Service / Mapper

CompanyController.java
  -> 真正暴露 HTTP 接口

GatewayRewriterFilter.java
  -> 请求进业务服务前，网关先做统一处理
```

### 10.1 `bootstrap.yml`：服务自己的身份证

文件：

```text
03zhaocai-start/scm-cloud-starters-web/scm-cloud-srm/src/main/resources/bootstrap.yml
```

它回答的问题是：这个服务“我是谁，我跑在哪里，我的接口根路径是什么”。

你重点看：

```text
server.port = 8130
server.servlet.context-path = /scm-srm-web
spring.application.name = scm-srm-web
spring.profiles.active = dev
```

翻译成人话：

```text
我这个服务叫 scm-srm-web。
我默认跑在 8130 端口。
我的接口统一带 /scm-srm-web 前缀。
我默认使用 dev 环境。
```

所以如果不经过网关，直接访问 SRM 某个接口，大概会是：

```text
http://localhost:8130/scm-srm-web/具体接口路径
```

它和后面文件的关系是：

```text
bootstrap.yml 给服务定身份
  -> SrmApp.java 按这个身份启动服务
  -> Nacos 里也用 spring.application.name 识别这个服务
```

### 10.2 `bootstrap-dev.yml`：开发环境的外部配置入口

文件：

```text
03zhaocai-start/scm-cloud-starters-web/scm-cloud-srm/src/main/resources/bootstrap-dev.yml
```

它回答的问题是：开发环境下，这个服务去哪里找 Nacos，去 Nacos 里拿哪些配置。

你重点看：

```text
Nacos 地址：10.0.54.19:8848
namespace：scm-jdsn
group：common
shared-configs：global-config.yaml
```

Nacos 可以理解成“服务通讯录 + 配置公告栏”。

它做两件事：

```text
服务注册：
  SRM 启动后告诉 Nacos：我叫 scm-srm-web，我现在活着。

配置拉取：
  SRM 启动时从 Nacos 拉 global-config.yaml 这类公共配置。
```

所以你在本地文件里不一定能看到完整数据库、Redis、网关路由配置，因为很多配置是在 Nacos 里。

它和后面文件的关系是：

```text
bootstrap-dev.yml 告诉服务去哪个 Nacos
  -> 服务启动后注册到 Nacos
  -> 网关后续才能通过 Nacos 找到 scm-srm-web
```

### 10.3 `pom.xml`：服务的装箱清单

文件：

```text
03zhaocai-start/scm-cloud-starters-web/scm-cloud-srm/pom.xml
```

它回答的问题是：这个服务启动时，把哪些业务包和公共能力装进来。

你重点看几类依赖：

```text
scm-srm-web-jar
scm-share-cache-web-jar
scm-share-mq-web-jar
scm-share-seq-web-jar
scm-share-workflow-web-jar
scm-cloud-dependencies-oauth2
scm-cloud-dependencies-orm
mysql-connector-java
spring-boot-starter-data-redis
spring-cloud-starter-alibaba-nacos-discovery
spring-cloud-starter-alibaba-nacos-config
```

翻译成人话：

```text
scm-srm-web-jar：
  SRM 自己的 Web 业务代码入口。

scm-share-cache-web-jar：
  缓存能力，通常对接 Redis。

scm-share-mq-web-jar：
  消息队列能力。

scm-share-seq-web-jar：
  编号/序列号能力。

scm-share-workflow-web-jar：
  工作流能力。

scm-cloud-dependencies-oauth2：
  登录认证、Token 相关能力。

scm-cloud-dependencies-orm：
  数据库访问能力。

nacos-discovery：
  注册到 Nacos。

nacos-config：
  从 Nacos 拉配置。
```

这里最关键的是 `scm-srm-web-jar`。看到这个依赖，你就要知道真正 SRM Web 业务代码在：

```text
01zhaocai-end/scm-srm-all/scm-srm-web-jar
```

它和后面文件的关系是：

```text
pom.xml 把 scm-srm-web-jar 放进 classpath
  -> SrmApp.java 才能 import SrmWebConfig
  -> SrmWebConfig 才能扫描 SRM 业务代码
```

`classpath` 可以理解成 Java 程序启动时能看到的一堆类和 jar。某个 jar 不在 classpath 里，代码里就没法直接使用它。

### 10.4 `SrmApp.java`：服务启动入口

文件：

```text
03zhaocai-start/scm-cloud-starters-web/scm-cloud-srm/src/main/java/com/pcitc/scm/srm/starter/SrmApp.java
```

它回答的问题是：这个服务从哪里启动，启动时导入哪些能力。

你重点看：

```text
@SpringBootApplication
@EnableDiscoveryClient
@Import(...)
```

含义：

```text
@SpringBootApplication：
  告诉 Spring Boot：从这里启动服务。

@EnableDiscoveryClient：
  启动后注册到 Nacos，让别人能发现我。

@Import：
  手动导入一堆配置类，把 SRM、缓存、MQ、认证、工作流等能力装进服务。
```

这里最关键的是：

```text
@Import(SrmWebConfig.class)
```

它说明：

```text
SrmApp.java 自己不扫描所有 SRM 业务代码。
它是通过导入 SrmWebConfig，
再由 SrmWebConfig 去扫描业务包。
```

它和后面文件的关系是：

```text
SrmApp.java
  -> @Import(SrmWebConfig.class)
  -> SrmWebConfig 开始生效
```

这就是 `03zhaocai-start` 能启动 `01zhaocai-end` 里业务代码的关键。

### 10.5 `SrmWebConfig.java`：SRM 业务代码的装配说明书

文件：

```text
01zhaocai-end/scm-srm-all/scm-srm-web-jar/src/main/java/com/pcitc/scm/srm/webconfig/SrmWebConfig.java
```

它回答的问题是：SRM 的 Controller、Service、Mapper 到底从哪些包里加载。

你重点看：

```text
@ComponentScan(...)
@MapperScan(...)
```

`@ComponentScan` 的意思是：告诉 Spring 去哪些包下面找 Controller、Service、配置类。

它扫描了类似：

```text
com.pcitc.scm.srm.*.controller
com.pcitc.scm.srm.apply.*.controller
com.pcitc.scm.srm.**.service.impl
com.pcitc.scm.srm.company.mq
com.pcitc.scm.srm.xxljob
```

所以 SRM 的接口、业务实现、MQ 监听、定时任务，都是从这里被装进来的。

`@MapperScan` 的意思是：告诉 MyBatis 去哪里找数据库 Mapper。

它扫描了类似：

```text
com.pcitc.scm.srm.*.repositories
com.pcitc.scm.ubm.*.repositories
```

Mapper / Repository 可以理解成“数据库访问层”。Controller 不直接写 SQL，而是通过 Service，再通过 Mapper 去访问数据库。

它和后面文件的关系是：

```text
SrmWebConfig.java
  -> 扫描 com.pcitc.scm.srm.*.controller
  -> CompanyController.java 包名匹配
  -> CompanyController 被注册成 HTTP 接口入口
```

### 10.6 `CompanyController.java`：真实业务接口入口

文件：

```text
01zhaocai-end/scm-srm-all/scm-srm-company/src/main/java/com/pcitc/scm/srm/company/controller/CompanyController.java
```

它回答的问题是：供应商公司信息相关接口具体暴露在哪里。

它负责供应商公司信息相关接口，比如：

```text
queryCompanyList
getDetail
queryCompanyInfoById
saveCompany
queryCompanyBanksByCompanyid
```

你第一遍只看这些注解：

```text
@PostMapping
@GetMapping
```

例如你看到：

```text
@PostMapping("s/business/srm/company/queryCompanyList")
```

说明它暴露了一个 HTTP POST 接口。

结合 `bootstrap.yml` 里的 context-path，直接访问路径大概是：

```text
/scm-srm-web/s/business/srm/company/queryCompanyList
```

它和前面文件的关系是：

```text
SrmApp.java
  -> 导入 SrmWebConfig

SrmWebConfig.java
  -> 扫描 com.pcitc.scm.srm.*.controller

CompanyController.java
  -> 因为包名匹配，所以被 Spring 加载成接口入口
```

现阶段不要急着看方法体。你先把“这个接口是什么路径、属于哪个模块、谁把它扫描进来”搞清楚。

### 10.7 `GatewayRewriterFilter.java`：网关入口安检

文件：

```text
01zhaocai-end/scm-gateway-all/scm-gateway/src/main/java/com/pcitc/scm/gateway/filter/GatewayRewriterFilter.java
```

它回答的问题是：请求进入业务服务前，网关统一做了什么。

过滤器可以理解成“入口安检”。请求进业务服务前，它先处理一遍。

它大概做这些事：

```text
解析 Cookie / Token
判断是否需要登录
处理请求路径
处理切换公司信息
生成请求追踪 ID
给请求加网关标记
检查会话是否活跃
```

所以一个请求不是直接打到 `CompanyController`，而是：

```text
前端
  -> 网关 scm-gateway-web
  -> GatewayRewriterFilter 处理请求
  -> 网关根据路由和 Nacos 找到 scm-srm-web
  -> 转发到 SRM
  -> CompanyController
```

它和其他文件的关系是：

```text
bootstrap-dev.yml
  -> SRM 注册到 Nacos

网关
  -> 通过 Nacos 找到 scm-srm-web

GatewayRewriterFilter.java
  -> 在转发前处理请求

CompanyController.java
  -> 接收最终转发过来的业务请求
```

### 10.8 最终把它们串成一句话

你可以这样记：

```text
bootstrap.yml 让 SRM 有身份；
bootstrap-dev.yml 让 SRM 连上 Nacos；
pom.xml 把 SRM 业务 jar 和公共能力装进来；
SrmApp.java 启动服务并 import SrmWebConfig；
SrmWebConfig 扫描 Controller、Service、Mapper；
CompanyController 提供真实接口；
GatewayRewriterFilter 在请求进入业务服务前做统一处理。
```

你现阶段不用深挖方法体。第一阶段真正要掌握的是：服务启动信息、外部配置、依赖装配、业务扫描、请求入口这五件事。

## 11. 第一阶段深入后的验收标准

你能回答这些问题，就说明第一阶段真的过关：

1. 为什么 `scm-cloud-srm` 目录里业务代码很少？
2. `scm-srm-web-jar` 起什么作用？
3. `SrmApp.java` 里的 `@Import` 为什么重要？
4. `SrmWebConfig.java` 里的 `@ComponentScan` 和 `@MapperScan` 分别扫什么？
5. 为什么数据库配置本地不一定找得到？
6. 一个前端请求为什么先过网关，而不是直接进 SRM？
7. 网关如何知道 `scm-srm-web` 在哪里？

这部分如果你能讲明白，后面第二阶段“服务职责与边界”就会顺很多。
