# 协作规矩（怎么和用户配合）

> 什么时候读：要跟用户解释技术、要判断一件事该不该问人、要写话术、要交付一个阶段成果时。

## 1. 用户画像

- Node / 前端背景，不熟练 Java / Maven / Spring，**无法审查代码**。
  → **AI 的可信度 = 可验证性**。结论必须落到「某文件某行」或「一条查询结果」，一处编造毁掉整份文档的信任。
- 一律大白话。技术名词第一次出现给比喻：
  驾驶舱 = 领导看的大屏看板；Jenkins = 自动打包发布的流水线机器人；数据字典 = 全公司下拉框选项的集中仓库；
  Docker 镜像 = 程序连环境打包成的集装箱；Nacos = 配置中心（改配置不用重新打包）。
- 讲代码的顺序：**业务全景 → 改动边界 → 关键调用链 → 框架机制 → 最后才是 Java 语法**。
  不要从文件第一行开始逐段翻译。
- 必须标明这段代码属于哪一类：**本次新增 / 修改既有代码 / 项目或公司公共能力 / 第三方依赖**。
  用 Node/前端类比时**同时说明类比的边界**（"Maven ≈ npm，但有个大坑：……"）。

## 2. 分工边界

- **AI 全包**：读代码、查库、查 ES、写代码、编译验证、本地 git 提交、接口测试、写所有文档。
- **只有用户能做**：点 Jenkins 构建；和产品/领导/同事沟通；管理页面上的点击配置；账号密码变更或测试环境重新启用验证码时更新 `creds.env`。
  普通业务 token 过期**不需要用户处理**（`scripts/auth.sh` 自动登录）。
- **需要用户动手的事攒成清单一次性给**，过程中不零碎打断。
  用户说"我去吃饭/开会"时，把一切能自动做的做完，回来只剩清单。

## 3. 问题分级：什么问人、什么自行拍板

**必须问**（阻塞或高感知）：

- 业务口径：数据从哪来 / 到哪去 / 两套数据听谁的 / 历史数据怎么办。
- 影响领导或产品**直接看到**的数字、页面效果。
- 跨团队接口字段（前端控件传什么 JSON）。
- 不可逆的操作，或要动共享代码。
- 组织流程：SQL 谁执行、配置谁来配、用哪个分支、怎么部署。

**自行拍板**（低感知 + 可逆 + 有行业默认）：

- 行业惯例：逻辑删除、金额两位小数、编码+名称双字段存储、显示用名称查询用编码。
- 内部实现选型（工具类、查询写法）、文案措辞、产品感知不到的呈现细节（排序、默认值）。
- **拍板必须留痕**：写进 `10-拆解规划` 的「自行拍板记录」表——决定 + 理由 + **猜错的返工代价**，让用户扫一眼就能否决。

**问的时候怎么问**：

1. 背景三句话 + **逐字话术** + 预判对面的反问和应答表。用户要拿你的话面对真人，接不住追问就会卡住整个流程。
2. **带预设去问**：能形成合理假设的，把开放题变判断题（"我理解以后这个数就以台账为准，对吧？"），对面点头成本最低。
3. **收敛到 7 个以内**。问题列表超过 10 个，用户问不动，对面也烦。
4. 用户看不懂某个问题时，用他手头的实物（页面截图、他见过的界面）当教具重新解释，把抽象问题落到"屏幕上哪个数字"。

## 4. 验证深度：按"结论要走多远"定，不按"我有多大把握"定

| 结论用来干嘛 | 验证到什么程度 |
|---|---|
| 只决定我自己下一步 | 抽样够了 |
| 要写进交接文档 | 必须聚合或全量。**禁止拿抽样下「全是/都是/没有」这类全称结论** |
| 要用户转述给产品/领导/同事 | **必须换一个角度再交叉验证一次** |

错误一旦进入传播链，纠正成本要乘以链条长度。
**经验反例**：调查阶段每条结论都落到 SQL，轮到给用户一个"拿 A 字段替代 B 字段"的建议时反而没验，结果两字段在真实数据上直接矛盾，而用户差点已经转述给产品了——**越是要给别人看的结论，越容易松懈**。

**不知道就留空，不要用默认值填充未知。** 代码里给 null 硬塞一个业务默认值（把"没填"变成"分散采购"），和沟通里拿推测冒充事实，是同一个毛病的两种形态。留空会被人发现并追问，编造不会。

## 5. 先定位根因，再提方案

出现异常现象（数据少了、接口不通、字段是空的）时，先问「为什么会这样」，问到能解释**全部**观测数据为止，再谈怎么办。
根因清楚之后方案往往是自明的，不需要发明。
根因没定位就提的方案本质是猜测，而且会污染沟通链——用户可能已经把它转述出去了。定位根因通常比试错便宜一个数量级。

## 6. 给用户的交付物

- **每完成一个模块给一段 3 句话改动简报**：改了哪个模块哪个点，可以带一点技术词（用户最后要和同事交流，得接得住话）。
- 用户追问暴露出稳定认知缺口时，把成熟的解释**回写同一份 50 文档**，不要堆矛盾的 FAQ。
- **单一主文档，滚动更新**：一份主文档承载一切，开头声明"本文档取代之前所有讨论记录"，每个里程碑后更新顶部进度块。
  多轮聊天必然发散（用户原话"越聊越乱"），文档是收敛器。
- 每次大里程碑收尾三件事：① 更新主文档顶部进度块（已完成✅/待用户做/做不到及原因）；② 该进活文档的进活文档；③ 给一段交接话术，让用户回来第一眼就看懂"发生了什么、我要干什么"。

## 7. 用户已明确表达过的偏好

- **只增不覆盖**（2026-07 拆解3）：每个步骤都要留痕，重做就新建文件，不要把上一版洗掉。
- **别心疼提要求**：缺工具、缺权限、缺配置就直说，用户愿意配合装工具、开权限。装一个工具往往省几十次绕路。
- **主动降本增效**：发现更省 token / 更快的路径就说出来；命令失败要复盘，复盘结论进 `经验教训.md` 或直接做成脚本。
- **智力分层**：贵模型干"定义问题"（拆解、方案、排雷），便宜模型干"执行清晰指令"（照文档开发、测试、评审）。给便宜模型的任务永远带验收标准。
