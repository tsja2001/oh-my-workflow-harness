# 代码库地图（代码怎么组织、怎么构建发布）

> 什么时候读：要找某个功能的源码在哪、要判断改动落在哪一层、要理解为什么本地编译不过、
> 要搞清楚 Jenkins 和 `mvn deploy` 分别产出什么的时候。
> 系统运行态看 [系统地图.md](系统地图.md)；本地怎么跑起来看 [本地运行手册.md](本地运行手册.md)。

## 1. 三层结构（先记住这一张图）

```
启动层  03zhaocai-start/scm-cloud-starters-web/scm-cloud-<业务>
        └─ 只是"启动壳"：主类 + Dockerfile + 打 fat jar，业务代码一行没有

业务层  01zhaocai-end/scm-<业务>-all
        └─ 真正的业务源码（Controller/Service/Mapper/Model），一个仓几十个 Maven 模块

公共层  01zhaocai-end/scm-cloud-parent → scm-cloud-bom → scm-cloud-assemblies / scm-cloud-dependencies
        01zhaocai-end/scm-assemblies-all/scm-share-*
        └─ 版本管理、框架封装、共享组件。改这里 = 影响全公司，属于共享代码
```

**运行时是"启动壳把业务 jar 拉进来跑"**，不是文件夹处理请求。
所以：改业务逻辑 → 改 `01`；改端口/启动参数/Dockerfile → 改 `03`；改公共能力 → 改公共层（**要单独提交、单独说明**）。

## 2. 顶层工作区

| 目录 | 是什么 | git |
|---|---|---|
| `01zhaocai-end/` | 后端业务源码 + 公共组件的**容器目录** | **每个子目录各自是独立 git 仓**，顶层不是 |
| `02zhaocai-front/` | 前端仓集合（30 个当前 + `scm-vue-all/` 下 26 个同名旧仓） | 同上 |
| `03zhaocai-start/` | 启动工程 | 同上 |
| 其余（`docs/` `ai-docs/` `scripts/` `skills/` `AGENTS.md`…） | **本文档仓库**，无 remote，只有本地提交 | 顶层这一个 |

**最常见的翻车**：在 `01zhaocai-end` 里直接 `git show origin/test`，会落到顶层文档仓并报"无此引用"。
必须 `git -C 01zhaocai-end/scm-<业务>-all ...` 或先进子仓。

## 3. 版本坐标与 Nexus

- 统一 `groupId` = `com.pcitc`，父级链：`scm-cloud-parent` → `scm-cloud-bom` → 各业务仓 / 启动壳。
- 两类版本：
  - `1.0.0-JDSN-SNAPSHOT`（plain）—— 各团队日常发布，**这是漂移的来源**
  - `1.0.0-JDSN-TEST-SNAPSHOT` —— Jenkins test 构建产物，不污染生产版本号
- 私服：`http://nexus.jdsn.com.cn/repository/maven-public/`（解析到 `10.0.54.19`），**是 http**。
  - 本机 Maven 是 **3.8.7**，3.8+ 默认封锁 http 仓库 → 编译时要用临时 settings 中和封锁
    （把 blocker 的 `mirrorOf` 改成 `dummy-block-nothing`，用 `-s` 传入，**不改用户全局配置**）。
  - Nexus 证书 `*.jdsn.com.cn` 已于 2026-06-16 过期，https 走不通，只能用 http。**需运维换证。**

### 跨团队 SNAPSHOT 漂移（本项目最重要的一条工程事实）

私服上 plain `1.0.0-JDSN-SNAPSHOT` 坐标里的跨团队包，**版本经常比本地源码旧**。
后果：**本地全量 `mvn compile` 本来就是坏的**，好几个现有文件自己就编不过。这正是**同事从不本地编译**的原因。

→ 我们的任务不是修好全量编译，而是**证明自己的新代码是健全的**：`bash scripts/jc.sh`（见 [本地运行手册](本地运行手册.md)）。
→ 判定规则：报错文件全是别人的现有文件 = 漂移，与你无关；报错在你的新文件里 = 你的问题。

## 4. Jenkins 与 `mvn deploy` 产出的是两种东西

| | 产出 | 给谁用 | 谁能做 |
|---|---|---|---|
| `scm-<模块>-all-<env>` | **jar 发到 Nexus** | 别的模块编译时依赖它 | Jenkins（用户点） |
| `scm-<模块>-web-<env>` | **Docker 镜像推 K8s** | 真正跑起来的服务 | Jenkins（用户点） |
| `mvn deploy` | jar 发到 Nexus | 同 `-all` | **手动**，属红线，交用户/同事 |

**公共层的 7 个"地基仓库"在 Jenkins 里没有任务**，只能手动 `mvn deploy`。
所以改了公共组件，链路是：`mvn deploy` 新 jar 到 Nexus → 重建依赖它的中间层 → 再点业务模块的 `-web` 打镜像。**缺一步 Pod 里还是旧码。**

真实案例（2026-07-22）：`scm-share-aim-spring` 在 Nexus 上的 jar 停留在 2023-04-18，字节码仍含 fastjson 1.x 的
`TypeUtils.getClassFromMapping`，运行时抛 `NoSuchMethodError`——**编译期看不出来，只有跑起来才炸**。
看到 `NoSuchMethodError` 的排查套路：先怀疑"Nexus 上的 jar 是旧的"，而不是怀疑自己的代码。

## 5. AIM：跨服务调用的四段寻址

公司自研的服务间调用机制（`scm-share-aim-all`），不是标准 Feign。

- 调用方给一个**四段地址**（形如 `<模块>-<服务名>-<方法名>-<参数JSON>`），由 AIM 解析并路由到目标服务的方法。
- 目标方法靠 `@TypeMapping` / `@MethodMapping` 注册，**注解必须贴在接口上**（贴实现类上注册不到）。
- XXL-JOB 的 `simpleJobHandler` 就是通过这套寻址调业务方法的，任务参数形如
  `source-centralizedProcurementReportService-syncCentralizedProcurementData-{}`。
  **注意：公共执行器按 `-` 切割参数**，所以参数里不能带 `-`（日期带 `-` 会被切坏，只能传 `{}`，补跑改走手动接口）。
- 代价：调用关系在编译期看不见，IDE 点不进去，改接口签名不会报错只会运行时炸。
  完整讲解见 `docs/需求/03采集管理业业务统计报表/52-公司工程体系扫盲-cc.md` 第一部分。
