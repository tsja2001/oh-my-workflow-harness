# 团队规矩（公司/团队的硬约定）

> 什么时候读：要开分支、要提交、要进 test、要发 uat/prod、要配字典或导出模板、要写新接口路径时。
> 活文档：核实过的新规矩当场追加（带日期 + 工具代号）。旧条目被推翻就直接改写或删除，不留矛盾。

## 1. 分支

- **新需求开工先判分支关系，禁止机械地一律从 `prod` 开。** 只检查本需求涉及的仓库：
  `bash scripts/git-release.sh audit --fetch <仓库...>`。
  - **同源模式**（`origin/prod` 同时是 `origin/test`、`origin/uat` 的祖先）：feature 从最新 `origin/prod` 开；保持 feature 独立，不能把 `test`/`uat` 合回 feature，之后才能沿用同一提交序列逐级交付。
  - **分叉模式**（任一仓不满足上条）：feature 从本需求实际依赖的最新 `origin/test` 开；UAT、prod 分别从各自目标环境最新基线开交付分支，只搬 test 验收冻结的提交。source/order/procurementScheme 已实查属于这种模式；从 prod 开再 MR 到 test 会夹带 prod 独有历史。
  `test` 只是测试部署分支，**不在 test 上直接写代码**。
- **未上线功能的补丁**：跟随原 feature 分支，或从当前 `test` 基线切干净子分支（prod 上没有那些文件，盲目从裸 prod 切会缺文件）。
- **环境分支不能反向污染开发分支**：不把 `test`、`uat`、`prod` merge/rebase 回 feature；否则下一级 MR 会把环境历史一起带过去。
- merge 会带进 prod/uat 大段无关历史时：`merge --abort`，改用目标环境基线交付分支 + `cherry-pick <冻结清单中的提交>`。原提交号写进发布清单，不用 `-x` 给提交信息追加正文。
- **命名像人写的**：参考团队现有风格（同事惯用拼音/缩写 + 姓名缩写，如 `prod-20240821zhq`、`prod-chun0518`）。
  **一个大需求只开一个长期分支**，其下所有修改共用它（台账相关就叫 `feature/taizhang-yang`，用户姓氏后缀 `-yang`）。
  交付分支必须带需求和环境，如 `jicai-cockpit-uat-yang`、`jicai-cockpit-prod-yang`；不要用含义过宽的 `jicai-uat-yang`，也不要一个小改动开一个新分支。
- **同事名下或同事长期维护的分支只读**（2026-08-05 用户要求）：可比对、可作历史参考，禁止追加自己的提交。
  已经误提交的要先迁出，并把同事分支恢复为远端原样。

## 2. 提交

- 只写一行：`feat: 简短表述` 或 `fix: 简短表述`。功能与功能合并用 `feat:`，修复与修复合并用 `fix:`。
  禁止 `feat(模块):`、多段正文、要点清单、完成情况汇总、`Co-Authored-By`。例：`feat: 增加坑口台账`、`fix: 修复导出时间`。
- **提交粒度 = 发版粒度：一个提交 = 一件能独立上线的事。** 不同发版节奏的东西分开提交，宁可多几个小提交。
  反例：一个紧急口径修复和一批没验收的新功能写进同一个提交，产品催上线时拆不开，只能终止合并重来。
- **只按路径暂存**：用 `git add <本需求文件...>`，不用 `git add -A`/`git add .`。工作区有 Fastjson 等其他需求未提交修改时，开发和交付使用独立 `git worktree`，不靠肉眼躲文件。
- 推送前固定三查：`git status --short --branch`、`git log --oneline <目标基线>..HEAD`、`git diff --stat <目标基线>..HEAD`。
- **test 验收通过立刻冻结发布清单**：每仓记录开发基线、按顺序的业务提交号、净变更文件、明确排除项、SQL/配置/任务和验证结果。可先运行
  `bash scripts/git-release.sh manifest <仓库> <开发基线> <feature>` 生成骨架。冻结后新增修复必须先回 test 复测，再更新清单；本地未推送、未进入远端 test 的提交不能直接越级进 UAT。
- 受保护分支上已推送的提交，不为了"好看"改历史；用普通 merge/revert 修正。必须重写时只能 `--force-with-lease`，且要用户明确同意。
- **同一段代码不要两边都写。** 要么 AI 写、用户只 review，要么用户写、AI 只 review。两边各写一版必然大面积冲突（本工作流出过一次，3 文件 20 处冲突标记，只能 `merge --abort` 重来）。
  AI 改完文件要**立即提醒用户 reload 编辑器**（AI 写文件和用户编辑器保存会互相覆盖，已发生两次）。

## 3. 发版链路：test → uat → prod

三个环境是**一级一级往上推**的，越往上用户能自己做的越少。

### test（日常开发环境）

- 开发直连 test 库改数据、AI 直接调 test 接口，随便测。
- feature 合进 `test` 分支 → 用户点 Jenkins → 部署到 K8s test；修复继续落原 feature 或干净补丁分支，不在 test 直接写。
- 业务验收通过后先冻结发布清单，再开始准备 UAT；**禁止把整个共享 `test` 合到 `uat`**。
- 字典、导出模板、菜单在 test 上自己配（页面地址见 §5）。

### uat（预生产，要走审批）

**后端**
1. 在独立 worktree 中从最新 `origin/uat` 拉需求专属交付分支，按冻结清单顺序 `cherry-pick` 业务提交；**不复制 test 整棵文件树，不带环境配置**。
2. 提 MR 前运行 `bash scripts/git-release.sh check --fetch <仓库> uat <交付分支>`；再按清单核编译/构建、允许文件、明确排除项和配置动作。
3. 用户推送 → 到 GitLab 发起 MR，目标分支 `uat`，**审核人：兰宇**。能选择时不 squash；平台强制收口时，把 UAT 合并/收口提交号补回发布清单。
4. 合并后用户点 Jenkins 的 uat 任务重启。
5. **在 uat 重做一遍 test 上做过的所有配置**：数据字典、导出模板、菜单、定时任务，并执行需求文件夹 `sql/` 中的 UAT SQL。

**前端**
1. 同样从最新 `origin/uat` 准备只含业务代码的干净分支；路由按本需求逐段搬，不能把 test 整个 router 文件覆盖过来；**不要带 `public/statics/config.js`、依赖锁或其他页面路由**。
2. MR 目标 `uat`，审核人兰宇。
3. Jenkins 重启。

### prod（生产环境 AI 不碰；本地交付分支可准备）

- UAT 验收通过后再次冻结清单；prod 代码不得临时加一刀，发现问题先回 feature/test 验证。
- **只有实查确认整条 UAT 差异都属于同一发布窗口时**，才由兰宇直接 `uat → prod` 提/合 MR。
- 共享 UAT 含其他未上线内容或历史已分叉时，默认安全方案是：从最新 `origin/prod` 开需求专属 prod 交付分支，搬入 UAT 已验收的同一逻辑提交，逐文件对比 UAT 验收版，再由用户推送并提 MR 给兰宇。禁止整条 `test → prod`。
- 配置和 SQL 交负责人在生产执行，运维部署；AI 不查写 prod 库、不点生产 Jenkins。前端生产任务为 `scm-vue-statics-pro`，模块按「页面模块 → 工程」逐项交接。

### 发版纪律（重要，开发过程中就要做）

正式发版时 **SQL 和字典/导出模板配置都要交给负责人执行**，所以开发过程中执行过的每条 SQL、每个字典项、每个模板配置**必须存档**：
放本主题文件夹 `sql/`，按序号分文件——①DDL 建表 ②必需配置数据（字典/导出模板 INSERT）③演示/初始数据（**单独文件**，标注「是否上生产待确认」）。
凡是空表会让前端页面/大屏难看的场景（尤其驾驶舱），要备几条演示数据；**演示数据进不进生产是高感知问题，必须问**。

## 4. Jenkins 与部署

- 入口 `http://jenkins.jdsn.com/`（构建按钮**只有用户能点**）。
- **后端两段式**：`scm-<模块>-all-<env>` = 编译并发 jar 到 Nexus → 成功后触发 `scm-<模块>-web-<env>` = 打镜像推 K8s。
  只看上游绿灯不够，要分别确认两段的实际构建号。
- **前端**：`scm-vue-statics-<env>`（带 `PROJECT` / `GIT_BRANCH` 参数，是共享 Job，`lastBuild` 可能是别人的）；
  `scm-vue-statics-only-test` 只部署静态资源，加了静态资源才需要跑，跑完再随便部署一个 `scm-vue-statics-test`。
- 帮用户核对参数：`GIT_URL` 指向目标仓库、`GIT_BRANCH` 是不是 `test`、`VERSION` 带不带 TEST 字样（不带会污染生产版本号）。
  scm-source-all 的固定参数：`GIT_BRANCH=test`、`VERSION=1.0.0-JDSN-TEST-SNAPSHOT`。
  还要确认该任务**会重新构建你改的模块**，不是只拉旧 jar。
- **部署完立刻主动对账，不要等产品来问。** 部署成功只说明代码上去了，不说明数据对。
  小技巧：设计一个**从返回值就能判断新旧代码的验收点**（"返回 5 条说明还是旧代码，返回 35 条才是新的"），用户不懂代码也能自己确认部署生效。
- 7 个"地基仓库"（`scm-assemblies-all` 等公共 jar）**在 Jenkins 没有任务**，只能手动 `mvn deploy`——这属于红线 3，交给用户/同事做。

## 6. 写代码时必须遵守的几条平台约定

- **接口路径：网关不剥前缀**，Controller 必须自己把完整路径写进 `@PostMapping`，形如 `e/business/source/<业务>/<方法>`（对外）或 `obs/business/source/...`（对内）。
  **反例**：`scm-source-chase` 里旧的 `TradeDataReportController` 用 `/api/trade-data-report/...`，这种路径**网关根本路由不到**（实测 404），只是同事留的本地调试入口，新接口别照抄它。
  另注：往网关发一个不存在的路径可能返回 `{"status":true,"code":"000000","data":"ok"}`，**别把这个当调用成功**，要看返回内容是不是你接口自己的。
- **鉴权模型**：平台是 `permitAll` 白名单 + `anyRequest().authenticated()`，即**登录就能调**；菜单权限只管导航栏显隐。
  所以没配菜单也能先用 `scripts/api.sh` 把接口测通。
- **改接口要防字段越权**：modify 时把流水号/创建人/创建时间/删除标记置 null 再 `updateById`，防止前端传值覆盖。
- **建新表**：通用字段（`create_by`/`update_by`/`delete_sign`/字符集/主键类型）照抄现有同类表——先 `SHOW CREATE TABLE` 两三张再动手，建完 `DESC` 验证。
- **写新代码先读满样板**：至少读 Controller / ServiceImpl / Model / DTO / 编号生成 各一个现成文件，模仿到结构、注解、命名、注释密度。新代码应该看起来像同一个人写的。

## 7. 编译口径

- **同事从不本地编译**——跨团队 SNAPSHOT 漂移，全量 `mvn` 编译本来就是坏的。**永远不要求修好全量编译。**
- 报错文件全是别人的现有文件 = 环境漂移，与你无关；报错在你的新文件里 = 你的问题。
- **可免编译**（说明理由即可）：只改注解字符串里的 SQL 文本、纯文档/SQL 脚本/配置、不新增 import 的字面量修改。
- **必须隔离编译**：新增 `.java` 文件、新增 import/依赖、改方法签名、跨模块引用 → `bash scripts/jc.sh <仓库目录> <改过的.java...>`。
- 向用户解释的话术：「本地整体编译失败不是我们代码的错——代码库里私服 jar 比源码旧，好几个现有文件自己就编不过。这正是同事'从不本地编译'的原因。我把咱们的新文件对着真实依赖单独编译，零报错。」

## 8. 数据库口径

- 开发直连 **test** 库（凭据在 `creds.env`）：业务库 `scm_source_test`、字典/组织库 `scm_ubm_test`、订单库 `scm_order_test`、调度库 `scm_xxljob_test`。
- **prod 库不碰**（红线 3）。uat 库可读、写操作要先说清楚。
- **不凭页面名称猜表名**，也不套用别的表的字段名——查之前先 `SHOW CREATE TABLE`。历史上因为猜字段翻车过多次（字典表真实字段是 `dict_type_code`/`dict_code`/`dict_name`/`dict_status`，不是 `type_code`/`dict_value`；导出模板在 `scm_ubm_test.scm_simple_template/_sub`，排序字段叫 `sort_name`、分组字段叫 `group_code`）。

## 9. Excel 导出与平台模板

- **普通列表/台账导出默认必须使用平台导出模板**：复用分页接口，后端接 `@ExportRequestTransfer`，前端传 `exportRequest`、`exportTemplateCode`、`exportFileName`。禁止另写一套 Java 字段列表或 EasyExcel 表头。
- 只有平台模板表达不了的场景（多行/合并表头、公式、图片、固定复杂样式、多 Sheet 等）才允许例外；必须在需求 `10-拆解规划` 写清原因、影响和验收方式，不能为了省配置退回硬编码。
- AI 不需要让用户去页面逐列点。test/UAT 新建模板优先运行 `scripts/export-template.sh apply`，由它调用和页面相同的保存接口，让目标环境生成 ID、审计字段和事务；**直接 INSERT 只是接口不可用时的受控兜底，不能宣称与页面保存完全相同**。
- 每个模板以需求目录 `sql/00-导出模板定义.json` 为机器可读源文件；环境 SQL、执行前备份和回滚脚本仍放同一 `sql/`，不得只存在聊天记录或目标数据库。
- `template_code` 必须在前端请求、后端注解、模板主表、模板明细四处完全一致；`field_name` 绑定接口最终 JSON 字段，不绑定数据库列。日期/字典/枚举优先绑定格式化或描述字段（如 `xxxStr`、`xxxDesc`）。
- 模板主表和明细必须启用且未删除；编码、分组保持一致；明细排序必须是唯一连续数字。序号列使用 `INDEX`，新模板统一放在排序 `0`，其余列从 `1` 开始。
- 页面新增不会传主表/明细 ID，后端使用目标环境的 `ASSIGN_ID` 生成；test 和 UAT 的生成器可能不同。禁止手写英文业务 ID、UUID、跨环境复用 ID，禁止把“正 19 位”当成所有环境的固定规则。
- 创建/修改审计必须记录真实授权操作人和实际执行时间；禁止复制任意同事、伪造“系统”或照抄旧 SQL 时间。`delete_sign=0`、`data_version=1` 是新建初值，修改已有模板不得重置创建信息。
- test 可在用户授权的开发任务内配置；UAT 写入前必须当次说清楚；prod 只准备定义、SQL、回滚和验收清单交负责人，AI 不执行。
- 验收至少包含：DB 主子表反查、模板详情接口、实际下载 XLSX、列顺序/日期/金额/字典描述/空值、列表与导出筛选对账、test/UAT 语义差异。**只看接口 JSON 或只看数据库均不算完成。**
- 平台字段模板目前不表达表头颜色、字体等样式；有样式要求必须在拆解阶段确认。详细字段、SQL 兜底和检查命令见 `skills/enterprise-dev-workflow/references/export-template-playbook.md`。
