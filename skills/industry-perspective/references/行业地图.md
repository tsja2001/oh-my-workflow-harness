## 二、S2P 赛道：标准拆解 + 他在哪一段

这条链在全球教材和厂商产品里拆法基本一致：

```
Spend Analysis         支出分析：先搞清钱花在哪         ← 他没有
Category Management    品类管理                        ← 他没有
┌── S2C (Source-to-Contract) ──┐
  Supplier Management  供应商准入/绩效/风险             ← 有
  eSourcing (RFx)      询价/招标/竞价                  ← 【他的系统主体】
  Contract Management  合同                            ← 隔壁系统
└──────────────────────────────┘
┌── P2P (Procure-to-Pay) ──────┐
  Catalog / Punchout   目录采购                         ← 云采商城
  Requisition → PO → GR → Invoice Match → Payment      ← 在 SAP / 财务共享
└──────────────────────────────┘
```

**结论：他的系统是 S2C 为主的平台，右半边在 SAP 和财务共享里。**
这解释了「为什么定标之后就交出去了」——**不是设计不完整，是标准分工。**

## 三、中国招投标法域 ★解释他系统里最"莫名其妙"的模块

中国是**两套并行法律体系**，很多人搞混：

| | 《招标投标法》 | 《政府采购法》 |
|---|---|---|
| 管什么 | 工程建设项目为主 | 政府部门用财政资金采购 |
| 谁适用 | **国企、大型工程 ← 他们** | 政府机关、事业单位 |
| 主管 | 发改委系统 | 财政部系统 |

**关键法条：**
- 《招标投标法》(1999)——依法必须招标的项目，公告应在**国家指定媒介**发布
- 《必须招标的工程项目规定》(国务院 16 号令, 2018)——**金额门槛**：施工单项约 400 万+、重要设备材料约 200 万+、勘察设计监理等服务约 100 万+，或项目总投资 3000 万+
- 《电子招标投标办法》(2013, 八部委令)——**定义了三级平台架构**
- 《评标委员会和评标方法暂行规定》——评标专家**原则上从专家库随机抽取**

**三级平台架构（钥匙级知识）：**

```
行政监督平台   ← 发改委等主管部门看
     ↑
公共服务平台   ← 国家级/省级，信息汇总与交换
     ↑          【中国招标投标公共服务平台 = CEB】
交易平台       ← 实际干活
                【他们的招采平台在这一层】
```

**由此可解释的系统特征：**

| 他系统里的东西 | 法律来源 |
|---|---|
| `scm-source-cebpubservice` 模块、「国招平台录入/发布/查询/报表」菜单 | 交易平台向公共服务平台报送，是法定义务 |
| 金额到了必须走招标 | 16 号令的门槛 |
| 专家随机抽取(12)/指定(13)，**指定必须审批** | 暂行规定要求原则上随机 |
| 评委匿名、监标人 | 防串标，监管与审计要求 |
| 中标公示期 | 对应 standstill period |

## 七、中国软件产业结构

**七类公司**：①互联网大厂 ②通信设备(华为/中兴) ③传统管理软件(用友/金蝶/浪潮)
④系统集成商(中软国际/东软/神州数码/太极/软通，**按人天卖**) ⑤行业垂直龙头(恒生/广联达/中控/卫宁)
⑥信创国产替代(达梦/麒麟/统信/东方通/海光) ⑦新一代 SaaS(帆软/北森/销售易/e签宝)

**为什么长不出 SAP/Salesforce（四条，第一条最硬）：**
1. **人力成本结构相反**——美国雇人贵，买标准 SaaS 是省钱；中国自养团队/找集成商往往比买产品便宜。**用户的岗位就是这条经济规律的直接产物。**
2. 大客户不接受标准品，甲方话语权强，改一次分叉一次，SaaS 退化成外包
3. 中小企业付费意愿低、存活期短，订阅模型不成立
4. 历史上「软件是硬件/服务的赠品」的惯性

**结果：中国软件业的钱大部分变成「人天」而不是「许可证」。人天不产生复利，产品才产生。**

**信创**（迟早会碰到，提前知道有价值）：
应用(用友/金蝶←SAP/Oracle)、中间件(东方通/宝兰德←WebLogic)、数据库(达梦/人大金仓/OceanBase←Oracle)、
OS(麒麟/统信/openEuler←Windows/RHEL)、芯片(鲲鹏/飞腾/龙芯/海光←Intel)。
**→ 这是「MySQL 特有语法写多了会出事」的一个非常现实的理由。**

### OpenViking 机制三件套

1. **`viking://` 虚拟文件系统**：`resources/`（外部资料）、`user/{id}/{memories|resources|skills|peers}`、`memories/preferences/`
2. **L0（~100 tok 一句话）/ L1（~2k 大纲）/ L2（全文）**，写入时生成，**每个目录自己也有 L0/L1**
3. **目录递归检索**：向量只负责"先拉开哪个抽屉"，拉开后老实读文件全文；每次留可回放轨迹
   ＋ 会话结束**异步**抽取用户偏好和 Agent 经验写进长期记忆

官方数字（自测，别当基准）：输入 token 降 34.3~91.0%、延迟降 58~66%；LoCoMo 上三个 agent 从 24~57% 提到 80~83%；τ²-bench 零售 +6.87pp、航空 +11.87pp。跑分用豆包 2.0 Pro + 豆包 embedding。

### ★ 最有效的讲法：他的仓库就是手工版 OpenViking

| OpenViking | 他仓库里的 |
|---|---|
| `viking://` 目录树 | `ai-docs/` `skills/` `docs/需求/` `scripts/` 这个分法本身 |
| **L0 标签** | **`AGENTS.md` §3 索引表的左列**（写的是"什么时候该开"，不是"里面有什么"——**方向就是对的**） |
| 渐进式披露 | `CLAUDE.md`「按需查，不要开工前通读」 |
| L0→L1→L2 三级 | **skill frontmatter 的 `description` = L0（~800tok），`SKILL.md` 正文 = L1（~4k），`references/` = L2（~12k）——这次会话里真实跑了一遍，是最好的演示** |
| `memories/preferences/` | `references/校准记录.md` |
| 会话自动沉淀 | `SKILL.md`「聊完必须回写校准记录」（**人写规则逼 AI 手工做**，它是程序自动做） |
| `skills/` | 他的 `skills/`（**连名字都一样**） |

**差别只在自动化和规模**：17 个文件手写一张表够用；500 个文件那张表本身就没法读了。

### 两种失败模式（讲这块必给，他反馈最好的一段）

- **RAG 的失败 = 噪音**：捞回一堆废话，但要的那条大概率也在里面，模型还有机会自己筛
- **Agentic Search 的失败 = 盲区**：L0 标签写歪 → **整个子树永远进不去，不报错、无征兆，只表现为"AI 好像不知道这事"**
- **→ 所以 `AGENTS.md` §3 索引表是他这套结构的单点故障。** 这是这一轮对他最有实操价值的结论

其他代价：慢（翻三层=至少三轮模型调用）、贵（轮数吃掉单次省的 token）、依赖模型够聪明（弱模型翻目录会迷路，RAG 至少保底）。

### 商业面（"穿越周期"那类）

- **AGPLv3 是商业策略不是技术选择**：自己用随便，包成 SaaS 卖就必须开源改动 = **反白嫖条款**，专防其他云厂商。同一套路：MongoDB 换 SSPL、Elastic 换 ELv2、Redis 2024 改协议，全是被 AWS 逼出来的。**→ 他们是国企子公司，法务对 AGPL 通常直接禁用，这条大概率把 OpenViking 挡在门外。**
- **Open Core 引流**：上层 OpenViking 免费，底下 VikingDB + 豆包模型收费
- 火山引擎 = 字节的云，2021 年才对外，比阿里云晚十年，只能靠 AI 这个新变量重新洗牌
- Viking 线时间轴：2019 VikingDB 内部支撑全业务 → 2023 公有云商业化 → 2024 VikingDB/知识库/记忆库三产品 → 2025-10 开源 MineContext → 2026-01 开源 OpenViking
- **star ≠ 采用率**：33.6k star 是真的，但 star 是最容易被运营的指标，字节开源运营力度历来大

## 十一、企业架构成因框架（2026-08-28 新增）★ 解释"这套系统为什么长成这样"

**起因**：他问「集团这么大的项目为什么由数科负责、为什么全外包、为什么冀东先用上 SRM、为什么不能移植、为什么还有 SAP」。
**这类问题的通用解法：给 5–6 个正交维度各起一个正式名字，再叠成一张图。** 他对"多维框架 + 把他放进去定位"反馈一贯很好。

### 六个维度（这次用的那套）

| 维度 | 核心术语 | 一句话 |
|---|---|---|
| **合规** | 《招标投标法》/ 三级平台架构（见 §三） | **合规驱动的系统天然集中，经营驱动的系统天然分散** ← 本轮最强的一条 |
| **组织** | `Centralized` / `Decentralized` / **`Federated IT`**；`pave the cowpaths` | 大集团 IT 只有三种形态，联邦式的经典失败模式就是"总部慢一拍，BU 早买好了" |
| **并购** | **`PMI`（Post-Merger Integration）** | IT 整合在并购里永远排最后，5 年起步，很多集团永远做不完 |
| **数据** | **MDM Implementation Styles**：Registry / Consolidation / **Coexistence** / Centralized | 不统一主数据是算过账的决策，不是懒 |
| **交付** | **`Branch-per-Customer`** ↔ Single-instance Multi-tenant；`Vertical Solution`；`Buy-then-Build` | 中国 To-B 的默认交付形态，代价是 divergence 分叉 |
| **集成** | `Point-to-Point` → **`ESB`/`Hub-and-Spoke`** → `API Gateway`+`iPaaS`+`API-led Connectivity` | **ESB 在国企不死，因为它解决的是治理不是效率** |

### 多租户三档（把厂商的方案报价翻译成标准语）★复用性最高

AWS SaaS Factory 的 **Silo / Bridge / Pool**（微软叫 `Deployment Stamps`）。
**任何厂商说"给你复制一套出来"，就是 Silo；说"加一层组织维度"，就是 Pool；说"我不是传统多租户"，就是承认自己在 Silo/Bridge。**

| 档 | 隔离 | 每加一客户成本 | 能否统一升级 |
|---|---|---|---|
| Silo | 最强 | 线性增长 | 不能 |
| Bridge | 中 | 中 | 很难 |
| Pool | 靠权限 | 趋近零 | 能 |

从 Silo 演进到 Pool 的标准路径：**`Strangler Fig Pattern`**（绞杀榕，Martin Fowler 2004）——
影子表 → 双写 → 灰度路由 → 旧路枯萎。**它要跨预算年度，所以在一年期项目里永远不会被提出来。**

### 模板推广为什么会失败

**`Template Rollout` / `Core Model`**（SAP 全球部署方法论）的两个硬前提：
`Core Model Freeze`（模板冻结，各单位不许乱改）+ `Fit-to-Standard`（业务迁就系统）。
**中国甲方基本不接受 Fit-to-Standard**——这是 Buy-then-Build 路线的根源，也是"厂商拿别家成功案例来说服你"时最该反问的一句。

### ERP 并存不是没整合好

**`Postmodern ERP`（Gartner 2014）**：核心 ERP 只留财务记账，周边用 `best-of-breed` + 集成。
**`Two-tier ERP` / `Multi-instance`**：总部重型 ERP + 子公司轻量 ERP，靠接口对账。**这是被推荐的策略，前提是接口标准化。**

### 外包的真实代价（三个词）

`Bus factor`（公交车系数）、`Knowledge transfer gap`（知识没转移）、`Version drift`（版本漂移）。
合起来叫 **`Software Entropy`**（软件熵增）——**交付验收那天是这套系统状态最好的一天。**

### 国企 IT 子公司的商业模型

`Captive IT Subsidiary` + `Chargeback`（内部结算）。
**关键洞察：这类公司的收入单位是"人天"，所以它的技术判断天然带商业动机。**
（实例：录音 50 里"你用 ABI 的话，对不起，你得多报人工"——那不是技术态度，是商业模式在说话。）

## 十二、"我们是不是很烂"——架构复杂度的对照系（2026-08-28 新增）

**起因**：他问「东拼西凑 / 是不是局部最优解 / 高效私企怎么做 / 国际同复杂度公司也这样吗 / Anthropic·Notion 是不是赏心悦目」。
**这是自我怀疑型提问，也是他第一次主动点名要外部对照组。**

### 四个必用的锚（缺一个都不成立）

| # | 名字 | 出处 | 用来回答 |
|---|---|---|---|
| 1 | **Big Ball of Mud** 大泥球 | Foote & Yoder, PLoP **1997** | 「东拼西凑」的正式名字。**论点是它到处都是因为在经济上理性**，不是骂人 |
| 2 | **Law of Requisite Variety** 必要多样性定律 | W. Ross Ashby, *Introduction to Cybernetics*, **1956** | 「是不是注定的」——**控制系统的多样性必须 ≥ 被控系统的多样性**。管 11 套规则就至少要有 11 套规则的表达能力。**数学，不是设计** |
| 3 | **Essential vs Accidental Complexity** | Fred Brooks, *No Silver Bullet*, **1986** | 把复杂度拆成「删掉软件也还在的」和「自己造出来的」，**只有后者可优化** |
| 4 | **DORA 四指标** | *Accelerate*（Forsgren/Humble/Kim），DORA 现属 Google | 把「高效」从感觉变成可测量：部署频率 / 变更前置时间 / 变更失败率 / 恢复时间 |

### 真实翻车案例表（讲「国际大公司也一样」时最有说服力，全部可 Google）

| 年份 | 公司 | 事件 | 量级（**公开报道，引用前自核**） |
|---|---|---|---|
| 1999 | **Hershey** 好时 | SAP + Siebel + Manugistics 同期上线，万圣节订单发不出去 | 股价一度跌约 8%，损失以亿美元计 |
| 2000 | **Nike** | i2 供应链系统上线事故 | 约 1 亿美元；CEO Phil Knight 名言 *"This is what you get for $400 million, huh?"* |
| 2018 | **Lidl** 德国折扣超市 | 放弃自 2011 年起的 SAP 项目（eLWIS） | 投入约 **5 亿欧元**，最终推倒 |
| 2010s | **GE** | 全球 ERP 实例整合项目 | 起点是**数百个 ERP 实例**【量级，公开报道】，整合做了很多年 |

**共同点：翻车的不是"没上系统"，是"想一次性统一"。** → 这正好对上 `§十一` 的 Template Rollout 两个硬前提。

### Anthropic / Notion 为什么看起来赏心悦目——三个原因，没一个是"工程能力强"

| # | 原因 | 证据 / 说法 |
|---|---|---|
| 1 | **问题空间小得多** | Notion 的核心业务对象**只有一个：block**（递归结构，段落/页面/数据库行都是 block）。工程博客 *Herding Elephants: Lessons Learned from Sharding Postgres at Notion*（2021，从单库切到 32 物理分片 / 480 逻辑分片；2023 还有一次再分片）——**注意他们分的是一张表** |
| 2 | **能拒绝需求** | **Product vs Project** 的根本差别。Notion 可以说"不支持"，用户走人就走人；甲方项目不能对一个二级集团说"你的四级品类我不支持" |
| 3 | **年龄** | Anthropic 2021 成立、Notion 2013/2016 起步，**还没到被自己历史绑架的年龄**。同龄同规模的正确对照组是 **Salesforce**（1999，如今 MuleSoft/Tableau/Slack/Heroku 数据模型各不相通）和 **Amazon**（2002 年那份广为流传的 *API Mandate* 备忘录，据 Steve Yegge 2011 的 Google Platforms Rant 描述——**Amazon 从未官方确认，标推断**——正是因为内部一团乱麻才强制的） |

**→ 一句话反直觉：架构整洁度的第一决定因素不是工程能力，是「能不能拒绝需求」。**

### 高效私企怎么做采购系统（真实对照组）

| 公司 | 做法 | 关键点 |
|---|---|---|
| **华为** | 1998 年起请 IBM 做 **IPD / ISC** 变革，投入以十亿计、跨十几年 | 任正非「**先僵化、后优化、再固化**」= 中文版的 **Fit-to-Standard**。**顺序是先理业务再上系统** |
| **美的** | 自己用出来之后成立 **美云智数**（2016）对外卖 | **这次来谈 SRM 的就是它**。产品是"自己趟过一遍"的副产品 |
| **宁德时代 / 比亚迪** | 制造业强供应链，SRM 是刚需 | 品类/物料天然统一（单一主业），没有并购拼图问题 |
| **字节 / 阿里 / 腾讯** | 采购系统相对简单 | **约束不同**：非国企（无招投标法强制）、采购占营收比例低、组织单一法人主体为主 |

**→ 反直觉：这些公司的优势不在架构图，在"先把业务流程统一了再上系统"的顺序，而这个顺序在并购型集团里几乎不可能实现。**

### 「整洁」的代价被转移到哪了

**通用性（generality）和贴合度（fit）此消彼长。** Ariba/SAP 那种"整洁"产品，落地时定制率一样 40–60%，
**Ariba 的大型实施项目常见 12–18 个月**【量级】——代价没消失，转移到了**实施阶段**。
（对照：美云自称定制率 40%，见 `0827开会/10-会议解读与格局推演-cc.md`。）

### 真正的瓶颈往往不在架构，在"配置没代码化"★ 本轮最实用的一条

DORA 的 **Lead Time for Changes** 里，企业软件的大头常常不是写代码，是**环境间的配置搬运**。
判据：**同一批配置（字典/导出模板/菜单/定时任务/SQL）要不要人工做三遍（test/uat/prod）？**
要 → 瓶颈在这，不在微服务拆得好不好。
相关术语：**Configuration as Code**、**Environment Parity**（12-Factor App 第 10 条 dev/prod parity）、**Configuration Drift**。
