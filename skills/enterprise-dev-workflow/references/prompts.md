# 各阶段提示词库（跨 AI 工具通用，直接复制粘贴）

> 用途：用户按成本用不同 AI 干不同阶段（统筹/拆解=强模型，开发=中档，测试/评审=便宜模型）。
> 阶段之间**只靠文档交接、不靠会话记忆**。把对应提示词整段贴给目标 AI，替换 `<主题名>` 等占位符即可。
> 设计原则：不假设模型能力强——每个提示词都把"读什么、产出什么、文件叫什么、放哪里、不许做什么"写死。

## 通用头部（每个阶段提示词都已内嵌，单独使用时贴在最前）

```text
你在 WSL 工作区 /home/t/projects/work-wsl（Windows 侧 UNC: \\wsl.localhost\ubuntu-24.04\home\t\projects\work-wsl）。
动手前先读完仓库根 AGENTS.md —— 那是唯一必读入口，里面有红线、任务分级、文档命名规范，
以及"遇到什么事翻哪一份"的索引表。其余文档按那张索引表按需查，不要通读 ai-docs/。
不确定有没有现成工具时，先看 ai-docs/工具箱.md，别自己拼 curl / javac / mysql 命令。
```

## P0 快速任务：查东西 / 改几行（任意模型）

```text
先读 AGENTS.md。这是一个<查任务/小改>，按 §2 任务分级来，不要走完整需求流程、不要小题大做。
任务：<一句话>
规则：
- 查任务：只给结论 + 证据（文件:行 / 查询结果），不写任何文档。
- 小改：用所属大需求的长期分支（不要新开分支）；遵守提交纪律；收工在 ai-docs/工作日志.md 顶部追加一条
  （≤4 行：日期 工具｜干了什么｜分支/提交｜坑）；属于某主题的话顺手更新该主题主文档进度块；
  给用户一段 3 句话改动简报（可带术语 + 一行解释）。
```

## P1 需求拆解（建议：最强模型）

```text
【任务】对「<主题名>」做需求拆解。
【先读】AGENTS.md + docs/需求/<主题名>/00-* 下全部输入文件；如有旧讨论记录也通读提取。
【照做】skills/enterprise-dev-workflow/SKILL.md 的 Phase 1~2：逐条翻译表、找代码样板（每条路径 ls 核实）、
清楚/模糊二分、问题收敛到 7 个以内并配逐字话术。判定标准见 ai-docs/协作规矩.md §3，
低感知可逆的事项自行拍板并在"自行拍板记录"表留痕。
【产出】写两份文档到 docs/需求/<主题名>/：
- 10-拆解规划-<工具代号>.md（模板：references/doc-templates.md 模板1，含"自行拍板记录"表）
- 10-待确认问题-<工具代号>.md（模板2）
【禁止】不写代码、不改库；样板路径没核实过的不许写进文档；同名文件已存在时新建带轮次后缀的文件，不要覆盖。
【收尾】告诉用户：去问谁、问什么（逐字话术）、答案写到 10-问题答复.md。
```

## P2 开发执行（建议：中档模型）

```text
【任务】按已定稿方案开发「<主题名>」。
【先读】AGENTS.md + docs/需求/<主题名>/ 的 10-拆解规划、10-问题答复（若无答复文件先停下问用户）。
【照做】SKILL.md 的 Phase 4~7：开工侦察探针（数据类需求必跑 scripts/fieldcheck.sh）→ 建表并把 SQL 存档到
本主题文件夹 sql/ → 照样板写码 → 按 ai-docs/团队规矩.md §7 分级编译（新增文件必须 bash scripts/jc.sh）→
Phase 7 干净提交（分支策略见 ai-docs/团队规矩.md §1）。
【产出】写两份文档到 docs/需求/<主题名>/：
- 20-开发交接-<工具代号>.md（模板6：改了什么/分支提交号/编译证据/遗留事项/下一步）
- 20-接口文档-<工具代号>.md（模板7：接口清单 + 可直接跑的请求示例）
并更新 10-拆解规划 顶部进度块。
【禁止】不改与本主题无关的现有代码；共享代码改动必须单独提交；凭据不进提交；push 要用户当次点头。
【收尾】给用户"需要你做的清单"（点 Jenkins、找人配菜单等），一次性列全。
```

## P3 接口测试（建议：便宜模型）

```text
【任务】独立测试「<主题名>」已部署到 test 的接口。你没有任何前情记忆，一切以文档为准。
【先读】AGENTS.md + docs/需求/<主题名>/ 的 20-接口文档、20-开发交接。
【怎么测】先跑 bash scripts/auth.sh doctor，再用 bash scripts/api.sh 逐个调接口；token 过期由脚本自动处理。
按真实链路顺序：新增→查列表→详情→修改→再查→删除→再查不可见。每一步记录：请求、响应原文、判定（通过/失败+原因）。
边界也要测：空参数、不存在的 id、超长字符串、重复提交。必要时用 bash scripts/dbq.sh 查库核对数据落库是否正确。
【独立思考】不要默认开发文档说的都对；响应和文档不一致时如实记录不一致，不要替开发圆场。
【产出】docs/需求/<主题名>/30-测试报告-<工具代号>.md（模板8：环境信息/用例表/bug清单/结论）。
【禁止】不改任何代码；发现 bug 只记录不修复（修复是开发阶段的事）。
```

## P4 代码评审（建议：便宜模型）

```text
【任务】独立评审「<主题名>」的代码改动。你没有任何前情记忆，用挑剔的眼光通览全局。
【先读】AGENTS.md + docs/需求/<主题名>/ 的 20-开发交接（拿到分支和提交号）。
然后在对应公司仓库里：git show <提交号> 看完整 diff；再读改动文件的完整内容，和它模仿的样板文件做对比。
（查别的分支用 git show <分支>:<路径>，严禁 git checkout <分支> -- .）
【评什么】1) 正确性：空指针/边界/事务/逻辑删除是否遵守全局配置；2) 一致性：和样板的注解/命名/结构是否一致；
3) 安全：SQL 注入、字段越权（modify 是否置空流水号/创建人/删除标记）、凭据泄漏；
4) 影响面：是否动了共享代码、会不会影响别的功能。
【独立思考】每个发现给"文件:行 + 问题 + 建议改法 + 严重程度(阻塞/建议/吹毛求疵)"。没把握的标"存疑待验证"。
【产出】docs/需求/<主题名>/30-评审报告-<工具代号>.md（模板9）。
【禁止】不直接改代码；不要为了显得有产出而编造问题——没问题就明说没问题。
```

## P5 临时文档（任意模型）

```text
【任务】就「<主题>」写一份说明文档给用户看。
【先读】AGENTS.md + docs/需求/<主题名>/ 下相关文档。
【产出】docs/需求/<主题名>/90-临时-<主题>-<工具代号>.md。大白话，新名词给比喻，结论给证据（文件:行/查询结果）。
【禁止】不改代码不改库；不确定的事标"未核实"，禁止写成既成事实。
```

## P6 代码复盘与理解交接（建议：强模型）

```text
【任务】对「<主题名>」执行代码复盘与理解交接。目标是让接手者获得可验证的系统模型和最低独立维护能力，
不是逐文件翻译源码。
【先读】AGENTS.md + 该主题 00/10/20/30 全部文档；按 SKILL.md Phase 9 执行。
【先定档】按业务影响、不确定性、耦合和证据复杂度选轻量/标准/深度档；重点深挖 1~3 条关键链路，机械样板只做摘要。
【只读基线】默认不改代码/数据库、不切分支、不 rebase。脏工作区用 git log/show/diff 或独立 worktree。
明确历史基线与最终基线，识别合并/回滚/重复补丁。
【事实核实】按需互证需求、Git、最终代码、数据库/配置、消费者、任务/消息、部署和运行结果；
分别标明预期、已实现、已配置、已部署、已验证。事实、设计推断和建议分开。
【分析与教学】区分本次代码、既有/共享代码、项目能力、公共组件和第三方依赖；先建业务/系统模型，
再追代表场景的控制流、数据流、状态流和失败/回退。按业务→系统→框架/平台→语言语法解释，
用用户熟悉的 Node/前端技术类比并说明类比边界（背景见 ai-docs/系统地图.md、ai-docs/代码库地图.md）。
【产出】docs/需求/<主题名>/50-代码复盘与学习-<工具代号>.md（模板10）。多个独立业务对象分开写。
【验收】包含简短复述、关键边界/待确认项和定位练习；接手者应能讲清一条主链路并重新找到证据。
【禁止】不把代码存在当运行生效，不把历史提交当最终状态，不把局部扩展当端到端支持，不猜作者意图，
不把理解交接冒充代码评审，未经授权不实施修复。
```

## P7 线上排查（任意模型）

```text
【任务】排查「<症状一句话>」。
【先读】AGENTS.md，然后用 skills/diagnose-scm-project/SKILL.md 的场景命令，全程只读。
【怎么查】症状驱动，别先猜模块：
  bash skills/diagnose-scm-project/scripts/project.sh doctor
  再按症状选 trace api / trace page / diagnose release / diagnose api / diagnose runtime / diagnose task / compare config。
需要单项细节时才下沉到 platform.sh。
【产出】结论 / 直接证据 / 判断 / 还缺的证据 / 下一步（需要用户或运维执行的写操作）。
若要动代码或数据，停在这里，转 P1 或 P2，不要顺手改。
如果这次排查值得留档：docs/需求/<主题名>/10-根因调查-<工具代号>.md。
【禁止】不触发 Jenkins 构建、不重启/伸缩/删除 K8s 资源、不发布 Nacos 配置、不启停任务、不写 MySQL/ES。
```

## 工具代号约定

`cc`=Claude Code；`codex`=Codex；`oc`=OpenCode；其他工具用小写短名。
**没有工具后缀 = 用户自己写的文件。**
同阶段重做**新建文件不覆盖**（加轮次或子题后缀），并在开头写一行"本文取代 xx，取代原因：yy"。
