# 企业需求 AI 代开发工作法（需求 → test 验证 → 理解交接）

> **前置**：仓库根 `AGENTS.md` 是必读入口（红线、任务分级、文档规范、索引）。**本文不重复它的内容。**
> 公司规矩查 `ai-docs/团队规矩.md`，怎么跟用户配合查 `ai-docs/协作规矩.md`，有什么工具查 `ai-docs/工具箱.md`。
> **本文只回答一件事：怎么把一个需求从"看不懂"推到"线上验证通过"。**
> 需求涉及 Excel 导出或导出模板时，必须同时完整读取 `references/export-template-playbook.md`，它是本流程的强制子流程。

## 什么时候用

- 用户不懂当前项目的语言/框架/业务，无法独立审查代码，也可能无法本地跑起整套系统。
- AI 负责全部技术执行；用户负责组织接口——拿着 AI 整理的问题去问真人，把答案带回来。
- 典型环境：几十个微服务、本地跑不起来、提交到 test 由 Jenkins 部署到 K8s、菜单/权限/字典/导出模板靠数据库或管理页面配置。

**成功标准不是"代码写完"**，而是：链路（配置/代码 → test → 部署 → 接口验证）真正跑通；
需要接手时，用户能说清核心逻辑、重新找到证据、具备最低独立维护能力。

## 三条工作流层面的铁律

（通用铁律见 AGENTS.md §1 和 `ai-docs/协作规矩.md`，这里只补流程特有的。）

1. **单一主文档，滚动更新。** 用一份主文档承载一切，开头声明"本文档取代之前所有讨论记录"，每个里程碑后更新顶部进度块。
   多轮聊天必然发散（用户原话"越聊越乱"），文档是收敛器。
2. **改动集中、影响可控。** 新增和修改现有文件都允许，以代码自然简洁为准，但改动要收拢，别东改一点西改一点。
   **共享代码**（别人也在用的逻辑）单独成一步、单独提交、等业务口径书面确认后再动。
   拆解阶段若用户给了项目组其他人的需求文档，先做**冲突面分析**（还有谁会动同一批文件/表）写进主文档。
   ——安全垫的本质不是"不改老文件"，而是影响面可见、可回退、能向同事解释。
3. **配置、代码、Git 历史三者都要可解释。** "最终代码一样"不等于交付合格；
   还要说得清配置为什么放这里、字段为什么这么填、提交为什么这样进 test、出问题怎么回退。

## 全流程地图

| 阶段 | 目标 | 产出（段号见 AGENTS §5） | 用户参与 |
|---|---|---|---|
| 1 需求拆解 | 看懂需求、找到代码样板、分清"清楚/模糊" | `10-拆解规划` | 读文档 |
| 2 问题收敛 | 模糊点压成最少问题、按"问谁"分组、配话术 | `10-待确认问题` | 拿去问人 |
| 3 答案回收 | 答案写回文档、方案定稿 | `10-问题答复`（用户写）+ 主文档 v2 | 带答案回来 |
| 4 开工侦察 | 30 秒探针确认数据/基线/推送/编译/鉴权可行 | 主文档里的"今天能到哪"表格 | 无 |
| 4.5 配置侦察 | 字典/导出模板/菜单/权限/静态文件的页面、API、库表互证 | 配置核查表 | 可能点管理页面 |
| 5 开发 | 照样板写代码 + 建表/配置 | 代码 + `sql/` + 配置记录 | 无 |
| 6 编译验证 | 证明"自己的代码"没问题 | 编译通过记录 | 无 |
| 7 干净提交 | 单个干净提交进 test，可回溯可撤销 | `20-开发交接` | 无 |
| 8 部署验证 | Jenkins 构建、接口测通增删改查链路 | `20-接口文档` + 验收清单 | 点构建 |
| 9 复盘交接（按需） | 还原事实、建立系统模型、交还维护能力 | `50-代码复盘与学习` | 跟读、追问、复述 |

阶段 1 之前：如果之前有零散的讨论记录（和其他 AI 聊的、笔记），先通读提取有效信息，然后在主文档里声明取代它们。

## Phase 1 需求拆解

1. 通读需求原文，做**逐条翻译表**：`| 产品原话 | 大白话翻译 | 谁来做(后端/前端/配置/无需开发) |`。
   注意识别"无需开发"项——"业务员每天 10 点前完成录入"是对人的要求，不是系统功能。
2. **为每个要做的功能找现成样板**。搜业务关键词（"台账/ledger"）、搜功能形态（分页 Controller、导出注解、编号生成 seq）。
   产出对照表：`| 要做的功能 | 样板文件路径 | 像到什么程度 |`。**每条路径都要 `ls` 确认存在。**
   照样板写代码风格不跑偏，别人看不出异常，也最不容易出错。
3. **二分法**：切成"现在就清楚、可以直接开发"（通常是纯新增的 CRUD+导出）和"有模糊点、动了会影响现有功能"（通常是和已有系统对接的部分）。
   前者先行，后者等确认。**这是防止"越聊越乱"的核心手段。**
4. 产出主文档 v1（模板见 references/doc-templates.md）：第一部分大白话写给用户，第二部分技术执行计划写给 AI。

自检：样板路径全部验证存在？每条需求都有"谁来做"？清楚/模糊二分完成？

## Phase 2 问题收敛

判定标准、话术要求、收敛到 7 个以内的理由 —— 全部见 `ai-docs/协作规矩.md §3`。本阶段只做三件事：

1. 按那套标准把模糊点筛一遍，能自行拍板的写进主文档"自行拍板记录"表（决定 + 理由 + 猜错的返工代价）。
2. 剩下的按"问谁"分组（产品/领导 ｜ 后端同事 ｜ 前端同事），每个配逐字话术 + 对面可能的反问和应答表。
3. 用户看不懂某个问题时，用他手头的实物（页面截图、他见过的界面）当教具，把抽象问题落到"屏幕上哪个数字"。

自检：问题 ≤7 个？每个都有话术？每个都标了问谁？默认值都写进文档了？

## Phase 3 答案回收

1. 逐条写回主文档并打 ✅；**口径变化立即同步修改技术方案**（"定时任务取消改实时计算"要马上改掉原定时任务设计）。
2. 对用户转述的答案做**技术含义翻译**并复述确认（"同事说不用定时任务，意思是驾驶舱打开时现算，规则上仍满足'显示前一日'"）。
3. 答不上来的标"待确认"，评估是否阻塞：不阻塞的先干，阻塞的圈出来。

自检：主文档有"确认结果汇总表"？每个答案都标了 ✅ 或待确认？方案与最新口径一致？

## Phase 4 开工侦察（先探后诺）

**总原则：任何"我假设 X 成立"的地方，只要验证成本 < 5 分钟，就不要假设，直接验。**
探针不能只探环境——**数据类假设和基线类假设错得更频繁、发现得更晚**（等产品在群里问"为什么没数据"才发现）。

1. **需求字段体检（数据类需求必做，优先级最高）**：需求里凡是拿来**筛选、统计、分组**的字段，开工前先跑
   `bash scripts/fieldcheck.sh <表> <字段> [库]`，看填充率、取值分布、**有值/无值各自的时间窗口**。
   判读：**填充率 < 50% 是红灯，必须问人，不能默默按原口径写代码**；
   有值窗口很窄而无值窗口横跨全部历史 = 字段是后加的、录入功能可能还没发版，用它筛会漏掉全部历史；
   取值里出现字典外的值 = 存的是另一套编码，页面下拉框筛不出来。
   **真实教训**：某报表需求指定按"采购业务分类"筛选，全表 311 单只有 7 单有值（录入入口上线 10 天后又被注释掉），
   做出来的报表几乎是空的，产品验收时才暴露，返工三轮。**这条探针 30 秒，能省掉整条返工链。**
2. **数据源要扒到真实落点**：产品给的往往是**页面接口**，不是数据在哪。顺着接口往下扒到最终库表，并确认那里**真的有数据**。
   反例：需求指定的两个查询接口读的 ES 索引在 test 文档数是 0，真实数据在上游 MySQL 源表里——照原文实现会一条都同步不出来。
3. **Git 基线核对 + 环境连通性：一条命令**
   ```bash
   bash scripts/doctor.sh --fetch
   ```
   它一次性给出：工具链版本、凭据齐不齐、test 库和 ES 通不通、**每个公司子仓当前在哪个分支、脏不脏、有没有落后远端**。
   反例：在比已部署 test 少两个提交的本地分支上开发了一轮，合回去才发现，白做——这条就是专治它的。
4. 推送权限（`ssh -T`）、目标分支存在（`git ls-remote --heads`）等 doctor 没覆盖的再单独探。
5. 产出"今天能到哪"诚实表格：`| 环节 | 能否完成 | 说明 |`。做不到的明说依赖谁。

自检：每一项都实测过（不是推断）？承诺的目标都有探针背书？**需求里每个筛选字段都体检过了？**

## Phase 4.5 配置类功能侦察（字典 / 导出模板 / 菜单 / 权限 / 静态文件）

企业系统里很多需求不是纯代码，而是"代码 + 平台配置 + 数据库配置"的组合。遇到这几类**不要直接写代码**，先做配置侦察
（SQL 思路见 references/env-playbook.md，页面地址见 `ai-docs/团队规矩.md §5`）。

1. 从用户给的页面 cURL 确认网关、模块、接口路径和当前登录环境。
2. 在代码里搜对应接口，定位 Controller/Service/Mapper，确认页面调的是哪个服务。
3. 在数据库里定位配置表，**不凭页面名称猜表名**：字典至少确认分组/类型/值三层；导出模板确认主表/字段明细表；菜单权限确认菜单/资源/角色关系。
4. 确认环境库：test / uat / prod / mall 变体可能不同，不要只查一个库就下结论。
5. 判断已有配置能否复用：编码稳定、业务域匹配、状态启用、`delete_sign` 有效、必要时确认缓存刷新机制。
6. 页面新增后**必须从数据库反查验证**。

涉及 Excel 导出时额外执行：

1. 先判定是不是普通列表/台账导出；是则默认复用平台字段模板，不能另写 Java 字段列表。复杂样式等例外必须写进拆解文档。
2. 四点对齐：前端 `exportTemplateCode`、后端 `@ExportRequestTransfer`、主模板编码、明细编码完全一致。
3. 在需求 `sql/` 保存 `00-导出模板定义.json`，先跑 `scripts/export-template.sh validate`；字段、ID、审计、SQL 兜底规则见 `references/export-template-playbook.md`。

自检：配置核查表填了吗？每个配置项都有库表证据？说明了需不需要后端代码配合？导出模板定义、四点编码和复杂样式边界都确认了吗？

## Phase 5 开发（照样板 + 改动集中）

1. **先建表后写码**：新表通用字段照抄现有同类表，建完 `DESC` 验证。SQL 按**生产重放包**标准存进 `sql/`（细则见 `ai-docs/团队规矩.md §3`）。
2. **读满样板再动笔**：至少读 Controller / ServiceImpl / Model / DTO / 编号生成 各一个现成文件，模仿到结构、注解、命名、注释密度。
3. 写代码顺序：DTO → Model → Mapper → Service 接口 → 编号生成器 → ServiceImpl → Controller。
4. 平台约定（接口路径、防字段越权、鉴权模型）见 `ai-docs/团队规矩.md §6`。
5. 新建导出模板优先使用 `scripts/export-template.sh apply` 调用页面同款接口；直接 SQL 只作受控兜底。环境 SQL/回滚仍必须进入需求 `sql/`，不能只改目标库。

自检：`git status` 只有本需求的改动？每个文件都有对应样板？建表 SQL 已存档？导出模板定义、回滚和目标环境反查结果齐了吗？

## Phase 6 编译验证

编译分级和判定规则见 `ai-docs/团队规矩.md §7`，命令和三个坑见 `ai-docs/本地运行手册.md §2`。
本阶段唯一的额外要求：**向用户解释清楚"编译失败但不是我们的错"这件事**（那正是同事从不编译的原因），并给出自己文件零报错的证据。

## Phase 7 干净提交

分支策略、提交格式、提交粒度、推送前三查 —— 全部见 `ai-docs/团队规矩.md §1~2`。
**不要机械套用 merge 或 cherry-pick**，先侦察这个仓库的真实历史再决定：

1. 确认 `git status` 只含自己的改动；确认 `.gitignore` 覆盖构建产物。
2. 看 `origin/test`、`origin/uat`、`origin/prod` 的 `--first-parent` 历史，判断团队习惯（test/uat 主要靠 `Merge branch 'feature/xxx'` 接收？prod 主要由 uat 合入？）。
3. 进 test 前先模拟 `merge --no-commit --no-ff`：只带自己的改动 → 按团队习惯 merge；会带入 prod/uat 大段无关历史 → `abort` 后改用 `cherry-pick -x`。
4. 危险操作前建本地 `backup/...` 分支和 `.patch` 补丁。
5. 多仓库工作区：确认在正确的子仓库里提交（顶层目录可能根本不是那个 git 仓库）。

自检：开发分支已推？test 进入方式能解释给同事听？diff 只含本需求？回退命令写清楚了？

## Phase 8 部署与验证

1. 用户点 Jenkins。帮他核对参数、确认会重新构建你改的模块（细则见 `ai-docs/团队规矩.md §4`）。
2. 接口测试：先 `bash scripts/auth.sh doctor`，再用 `scripts/api.sh` 按真实链路顺序测——
   add（看返回流水号）→ 列表 → 详情 → 修改 → 再查（看变更与发布时间）→ 删除 → 再查（不可见）。
   只有登录路径/网关/验证码机制变化导致自动登录失败时，才让用户 Copy as cURL 核对请求形态（**不得把其中 token/Cookie 写进文档或提交**）。
3. 出一份接口文档（模板见 doc-templates.md）：接口清单 + 请求体示例 + 预期结果 + 链路验收标准。
4. 明确"今天到不了"的部分及依赖（前端页面、菜单岗位配置在别人手里），写进主文档进度块。
5. **部署完立刻主动对账，不要等产品来问**（细则见 `ai-docs/团队规矩.md §4`）。
6. **数据类需求（报表/统计/同步）的验收重心是对账，不是"跑通"** —— 这类需求的缺陷密度不在代码里，在数据里：
   - 数量对账：库里按同一口径查出来的行数 = 写入条数（差额要能逐条解释）
   - 幂等：同一区间重跑，总数不变
   - **权限字段和时间字段的空值率**：一为空整行会被数据权限和时间筛选吃掉，页面上彻底看不见**而且不报错**，最阴险
   - 编码类字段是否落在字典取值范围内（不在范围 = 列表能显示但下拉框筛不出来）
   - 主键唯一性和碰撞面：主键撞了就是静默丢行 + 金额少算
   - 空值时代码有没有**编造值**
   - 分页/导出上限：ES 默认 10000，多来源汇总很容易超，超了是静默截断
7. **导出功能必须实际下载 XLSX**：检查文件可打开、表头/列顺序、数据行数、筛选条件、日期/金额/字典描述/空值；接口 JSON 正常、模板详情正常或 HTTP 200 都不能代替文件验收。平台字段模板不表达复杂样式，有样式要求按 `references/export-template-playbook.md` 的例外流程处理。

自检：用户拿到了照着跑的命令？验收标准可勾选？进度块已更新？数据类需求做过对账（不只是"接口通了"）？导出是否真的打开过 XLSX？

## Phase 9 代码复盘与理解交接（按需触发）

适用于 AI 生成代码接手、遗留模块交接、跨服务/配置改造、复杂回滚历史、事故复盘，或用户明确要求学习。
它不是代码评审的替代品：`30-评审报告` 负责挑问题，`50-代码复盘与学习` 负责让接手者形成可验证的系统认知。
**默认只读**，不改代码/数据库、不切换或变基用户分支；若同时要求修复，先完成事实边界，再转入开发动作。

1. **先定档、再抓主线**：单仓库单链路用轻量档，常规跨代码/数据/配置用标准档，跨服务、异步/状态机、迁移或事故用深度档。
   优先深挖 1~3 条高价值关键链路；机械 DTO、重复 CRUD 和稳定样板只做映射表，不逐文件翻译。
2. **建立双基线**：脏工作区不切分支，优先 `git log/show/diff/blame` 或独立 worktree。
   分别确定历史从哪里开始、最终要解释哪个版本，识别 merge/cherry-pick/rebase/revert/重复补丁。
3. **分清五种状态**：每个重要能力分别写 预期 / 已实现 / 已配置 / 已部署 / 已验证。
   **代码存在不等于运行生效，历史提交不等于最终状态。** 事实、对设计原因的推断、未来建议必须分开。
4. **标清归属和边界**：区分本次新增、修改既有/共享代码、项目能力、公司公共组件、第三方依赖。
5. **先建模型后读代码**：先给业务目标、参与者、系统/数据边界、关键状态和改动插入点，再按真实触发场景追控制流、数据流、状态流；
   同步请求之外，按需追异步消息、任务、缓存、重试、幂等、补偿、迁移和回滚。
6. **端到端核实**：对"通用、自动、实时、兼容、可扩展"这类结论，从数据模型、接口、业务逻辑、配置/任务、消费者/页面、导出和运维逐层验证，
   **不能用单层成立代替全链路成立**。
7. **分层教学、滚动修正**：业务目的 → 系统位置 → 关键链路 → 框架/平台 → 语言语法。
   用户贴局部代码时先直接回答再补上下文；稳定解释回写同一份 50 文档，结论改变时修正原章节而非堆矛盾 FAQ。
8. **验收**：用户能讲清一条主链路、指出关键边界，并能从 Git/IDE/日志/数据库重新找到证据。

自检：抓大放小了吗？历史与最终版本分开了吗？五态是否混淆？覆盖了失败/回退或说明不适用？推断是否明确标注？
