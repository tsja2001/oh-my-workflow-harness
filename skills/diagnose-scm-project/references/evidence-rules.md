# 证据规则

## 先定义问题，再取证

一次诊断先写清楚四件事：环境、入口（页面/API/任务）、预期、实际。没有这些信息时，先用 `trace` 和模块目录缩小范围，不要把所有平台全扫一遍。

## 证据强弱

由强到弱：

1. 精确 ID 对应的数据库执行记录、HTTP 响应、K8s API 状态、Jenkins 构建 JSON。
2. 同一时间窗口内的应用日志、Pod event、Jenkins 控制台关键行。
3. 代码静态链路、配置键差异、Git 历史。
4. 页面现象和基于命名规律的推断。

低层证据不能越级变成确定结论。例如：页面空白只能证明页面没展示数据，不能证明 MySQL、ES 或同步任务中的哪一层为空。

## 常见误判

- `all` Job 成功：只证明上游构建成功，不证明 `web` Job、镜像和 rollout 成功。
- K8s Deployment 有新镜像：不证明 Pod Ready，也不证明接口已注册。
- 调度任务是 `RUNNING`：只代表任务配置启用，不代表最近一次执行成功。
- 调度页面显示失败：只证明结果失败；根因要看 `xxl_job_log.handle_msg` 的最深层原因。
- 查询窗口无记录：不等于历史上从未执行。
- Nacos 有一个 key：不证明对应 ES index/topic/schema 已存在。
- ES 有文档：不证明当前用户权限、过滤条件和字段 mapping 能查到这些文档。
- test 有数据：不证明数据由当前定时任务产生；要结合创建时间、字段形态和成功执行记录。

## 时间线

跨平台判断必须尽可能记录：

- Jenkins 构建开始时间、构建号和 revision。
- Deployment 镜像、revision；Pod 创建时间、Ready、重启次数。
- Nacos Data ID 和环境。
- 任务 ID、trigger/handle 时间、状态码。
- 数据表或索引的 count 与查询时刻。

时间对不上时，只说“相关”或“可能”，不要说“导致”。

## 输出限制

- 日志先按时间和关键词缩小，再输出；默认最多保留几十条关键行。
- 配置优先比较键路径，只有确需值时才用脱敏后的 `nacos read`。
- 不输出凭据文件、cookie、token、请求头、浏览器 storage 或 Jenkins credential 参数。
- 对失败栈保留最深层 `Caused by`、业务类/方法、任务 ID 和时间；其余噪声省略。

## 标准结论

```text
结论：一句大白话，注明“已证实”或“高概率”。
直接证据：
- 代码/路由：
- Jenkins/K8s：
- Nacos/任务/DB/ES：
判断：证据如何连成结论。
还缺的证据：没有就写“无”。
下一步：只列需要做的最小动作；写操作交给用户、运维或开发流程。
```
