# 第一部分：写给你看的

## 1. 这个需求到底是做什么

一句话：**给招采平台加一个"电子记账本"页面，再加一个每天夜里自动跑一次的"抄数员"。**

- **记账本**：业务人员每天上午把"昨天各家企业买了多少钱的钢材、电缆、润滑剂、轴承"一条条记进去。页面上能查、能筛、能新增、能改、能删、能导出 Excel。
- **抄数员**：每天夜里 12 点，系统自动把"昨天"的账目汇总一下，更新到领导看的"集采驾驶舱"大屏上。

这个需求**主要是后端的活**（正好是你负责的），前端同事负责画页面，你们通过接口对接。

## 4. 重要结论:建议分两步走(这也是对之前讨论越聊越乱的纠偏)

之前和 Codex 越聊越散，本质原因是：**把"清楚的部分"和"不清楚的部分"混在一起讨论了**。其实拆开看非常清晰：

**第一步：台账本身（增删改查+导出+权限）——需求已经很清楚，现在就可以开发。**
它就是一张独立的新表加一套标准接口，不碰任何现有功能，风险很低。不需要等任何人确认就能动工。

**第二步：每晚自动更新驾驶舱——有一个关键问题没确认，先不要动。**
驾驶舱是已经在运行的功能，它现在的数字是从**另一张已有的表**里算出来的，而且"机电公司、四大类目"这些条件是**写死在现有代码里的**。新台账的数字要怎么"掺"进去——是加到现有数字上？还是替换掉？只影响"日金额"这一个数字，还是月度、年度累计也要跟着变？——这个只有产品/领导能回答。**问清楚之前谁写代码都是瞎猜，猜错了会把领导看的大屏数字搞错，这是最不能出事的地方。**

这样做的好处：第一步开发、联调、走流程的同时，你去把第二步的口径问清楚，两边不耽误。

**先认识屏幕上的角色（对照 test 环境的"金隅集团集采管理驾驶舱"，以下分工都是从驾驶舱统计代码里核实的，不是猜的）：**

**屏幕上哪些数字和这次需求有关（每个都对过代码里的计算公式）：**

| 屏幕位置 | 数字 | 现在怎么算的 |
|---|---|---|
| 左侧"集采类目分项金额" | 钢材 23350、润滑剂 902、电线电缆 8887、轴承及备件 2132 | 系统从已有数据表自动汇总，条件写死"供应商=机电公司" |
| 右侧"集采情况分析" | 机电公司 433562 | 就是上面四个类目加在一起的口径 |
| 中间 | 日集采、月度集采、季度集采、年度集采金额、集采累计总金额 | **全集团**的总数（煤炭、办公用品也算在内），按"业务完成时间"自动算 |

顺带一提：这个驾驶舱写死的东西比想象的多——连"上线企业 485"都是直接写死在代码里的固定数字。所以"数字从哪来"这件事，产品嘴里说的和代码实际算的，未必一致，更要问。

**建议问法（对着屏幕指着问）：**

> 这些数现在是系统自动算的。以后业务员每天在新台账里手工录的金额，是**替换**这些数，还是**加进去**？
> 中间的日集采、月度、季度、年度、累计总金额是全集团的总数——要不要也把台账录的数算进去？"

**带着预设去问更高效（把开放题变成判断题）**：最可能的答案就是"替换"——既然业务员每天手工录的就是这四类的全部交易，这四个数以后以台账为准。所以可以直接这样问：

> "我理解以后钢材、电缆、润滑剂、轴承这四个数就以台账录的为准了，不再用系统自动算的，对吧？"

对方点头后，还有两个连带问题必须马上跟一句（都是"替换"方案绕不开的）：

1. **历史数据怎么办**：屏幕上这些是累计值（比如钢材 23350 万），台账是新上的、从零开始。切换后是"老数据当底数，台账往上累加"，还是"只看台账、从零重新算"？
2. **中间那排全集团的数**（日集采/月度/季度/年度/累计总金额）：它们里面包含四大类目的部分，要不要也跟着改成从台账取？不改的话，同一个屏幕上"分项数"和"总数"会对不上；改的话，要确认原来的自动数据还进不进老表，避免同一笔钱算两遍。

答案只有三种可能，听到哪种记下来即可：
1. **替换**：以后这个指标只看手填台账，原来自动算的不用了；
2. **相加**：两边加起来（要确认两边统计的不是同一批钱，否则重复计算、数字翻倍）；
3. **驾驶舱暂时不动**：台账只是独立的记录页面（那第二步定时任务就先不用做）。

**对面反问时你可以这样接：**

| 对面问 | 你答 |
|---|---|
| "现在驾驶舱数据哪来的？" | "我看了代码，是从一张已有的集采数据表按类目自动汇总的，钢材电缆这些类目和机电公司的条件是写死在程序里的。" |
| "为什么不能直接加进去？" | "怕重复算。如果手填的那笔钱系统本来也会自动统计到，两边一加数字就翻倍了。" |
| "那你打算怎么做？" | "台账页面本身我先做，不碰现有数字。驾驶舱怎么取数，您定了口径我再做那一步。" |

## 6. 关于"本地跑不起来"的开发方式，你需要知道的

先安心：**这种方式很常见**。微服务模块多的公司基本都这样——本地只写代码、保证编译通过，推到测试环境（test）去真正运行验证。你之前做 Node 时"本地起服务边改边看"的习惯，在这里换成"本地写好 → 推上去 → 在 test 环境看效果"。

对你的具体影响和对策：

1. **本地不用"运行"，但必须"编译"。** 编译 = 让电脑检查代码语法和引用有没有错，几分钟的事，不需要连数据库。这是提交前唯一的本地质量关卡，绝不能省。要求执行 AI 每次改完必须编译通过才算完。
   - 编译需要：JDK 1.8、Maven、并且**在公司网络里**（依赖包要从公司内部服务器 nexus.jdsn.com.cn 下载，在家没连 VPN 可能装不上依赖）。第一次编译时如果报错下载失败，就是网络问题，找同事问 VPN/内网。
2. **小步提交。** 一次提交只干一件事，提交说明写清楚。万一 test 环境出问题，容易定位是哪次提交引起的，也容易撤回。
3. **注意：`work-wsl` 这个大目录本身不是一个 git 仓库**，里面每个项目（如 `scm-source-all`）才是独立仓库。提交要分别在对应项目目录里做，别在最外层提交。
4. **验证路径**：代码推 test 分支 → Jenkins 上点部署 → 用接口文档页面（Knife4j）手动调接口，或等前端页面好了在页面上点 → 出错了在 K8s 上看日志。**建议找同事带你完整走一遍这个流程，走通一次以后就都会了。** K8s 你现在只需要会一件事：找到自己服务的日志在哪看（详见第 8 节部署科普）。
5. **数据库是绕不开的。** 这次要建新表、配菜单权限字典，就算代码全对，这些配置没进数据库，页面照样看不见、导出照样是空的。所以第 5 节 B-2 那个问题（SQL 谁执行）必须问。

## 8. 部署科普：Jenkins + K8s 到底是怎么回事（照仓库里的部署脚本讲的，不是猜的）

仓库里有现成的部署脚本（`03zhaocai-start/scm-cloud-starters-web/Jenkinsfile` 和 `Dockerfile`），下面的流程是照脚本核实的。

**四个角色，一条流水线：**

- **Jenkins**：自动打包发布的"流水线机器人"，是个网页。你告诉它"发布哪个服务、用哪个分支"，剩下全自动。
- **Docker 镜像**：把编译好的程序连同运行环境打包成一个标准"集装箱"。
- **Harbor**：公司内部存集装箱的仓库（脚本里有公司自己的仓库地址）。
- **K8s（Kubernetes）**：运行、管理这些集装箱的"码头调度系统"，公司几十个微服务都跑在上面。脚本里还提到了 **KubeSphere**——K8s 的图形化网页控制台。同事说的"在 K8s 上看报错"，大概率就是在 KubeSphere 网页上点进你的服务看日志，**不用敲命令，会点网页就行**。

**你每次发布的完整动线（脚本里五个步骤写得明明白白）：**

1. 代码合到 test 分支，推到远程；
2. 打开 Jenkins 网页，找到你服务对应的构建任务（你改的是 scm-source 相关模块，对应服务应该是 scm-cloud-source，具体任务名和同事确认），选分支，点"构建"；
3. Jenkins 自动执行：拉代码 → Maven 编译 → 打 Docker 镜像 → 推到 Harbor → 部署到 K8s，全自动；
4. 到 KubeSphere/K8s 页面确认服务起来了、启动日志没报错；
5. 用接口文档页面或前端页面验证功能。

**提示**：同事之前给过两个表格（`docs/同事给的项目相关文档/` 下的"git代码模块对照表.xlsx"和"商城模块部署0918.xlsx"），名字看起来就是"哪个代码模块对应哪个 Jenkins 任务"的对照关系——**去问之前先打开看看**，可能一半问题已有答案。

**问部署时照这个清单问（5 句话问完）：**

1. "我改的是 scm-source-all 里的模块，Jenkins 上对应哪个构建任务？构建时要选什么参数（分支、版本号）？"

## 3. 新表设计

表名：`sc_collection_daily_amount_ledger`（独立新表，不复用 `sc_source_collection`，避免污染现有驾驶舱数据源）。

| 字段 | 类型 | 说明 |
|---|---|---|
| `ledger_id` | varchar(64) | 主键，MyBatis-Plus `ASSIGN_ID` |
| `ledger_no` | varchar(32) | 流水号，唯一 |
| `execute_unit_id/code/name` | varchar(64/64/200) | 集采执行单位 |
| `category_code/name` | varchar(64/100) | 集团集采类目（字典） |
| `statistic_date` | date | 统计日期 |
| `purchase_company_id/code/name` | varchar(64/64/200) | 采购企业 |
| `tax_amount` | decimal(18,2) | 交易金额（含税/元） |
| `bu_code/name` | varchar(64/100) | 所属板块（后端按采购企业查询带出） |
| `publish_time` | datetime | 最新发布/修改时间 |
| `publish_by` / `publish_by_name` | varchar(64/100) | 最新发布/修改人 |
| `create_by/create_by_name/create_time` | 通用 | 与项目现有表通用字段保持一致（以样板表为准） |
| `update_by/update_by_name/update_time` | 通用 | 同上 |
| `delete_sign` | int | 逻辑删除标记，默认 0 |
| `data_version` | int | 乐观锁 |

索引：唯一 `uk_ledger_no(ledger_no)`；普通 `idx_statistic_date`、`idx_execute_unit(execute_unit_code)`、`idx_purchase_company(purchase_company_code)`、`idx_category(category_code)`。
**不要**对"执行单位+类目+日期+采购企业"加唯一约束（产品示例中存在同维度多行）。

## 4. 接口设计

路径风格沿用 `/e/business/source/...`（登录态业务接口）。类名建议 `CollectionDailyAmountLedger*`。

| 功能 | 路径 | 说明 |
|---|---|---|
| 分页查询/导出 | `POST /e/business/source/collectionDailyAmountLedger/queryPageList` | `@DataRequestTransfer(exportValue={@ExportRequestTransfer()})`，入参 `DefaultPageBean<CollectionDailyAmountLedgerDTO>`，不加 `@RequestBody` |
| 新增 | `POST .../add` | 录入后即发布：写 `publish_time`/`publish_by` |
| 修改 | `POST .../modify` | 可改执行单位/类目/统计日期/采购企业/金额/板块；每次更新 `publish_time`/`publish_by` |
| 删除 | `POST .../delete` | 逻辑删除（`delete_sign=1`） |
| 详情 | `POST .../detail` | 修改弹窗回显 |
| 按采购企业带出板块 | `POST .../queryCompanyBelongBu` | 内部调 `OrgManagerFeignService#queryByOrgCode`，返回 `buCode/buName` |

查询条件（与需求逐一对应）：`ledgerNo`（模糊）、`executeUnitCode`（组织控件）、`buCode`（字典）、`purchaseCompanyCode`（组织控件）、`beginStatisticDate/endStatisticDate`（日期区间，含边界）、`categoryCode`（字典）。所有查询恒带 `delete_sign = 0`。

保存校验：执行单位、类目、统计日期、采购企业、金额必填；金额 `BigDecimal`、≥0、两位小数；采购企业保存时后端调组织接口校验存在并覆写 `bu_code/bu_name`；类目编码校验在字典中存在。

导出字段及顺序（与需求一致）：流水号、集采执行单位、集团集采类目、统计日期、采购企业、采购金额（含税）、所属板块、发布时间、创建人。

## 5. 流水号生成

格式 `JCRJE-yyyyMMdd-NNN`（3 位流水，按天重置）。照抄 `GreenChannelCodeSequence` 新建 `CollectionDailyLedgerCodeSequence`：`getPrefix()` 返回 `"JCRJE-"`，`getCenterStr()` 返回当天 `yyyyMMdd-`，`getSuffixLength()` 返回 3，`getSeqDate()` 按当天零点（与样板一致）。默认按**录入日期**生成（与样板行为一致）；若用户确认按统计日期，则 `getCenterStr()` 改用统计日期并同步调整 `getSeqDate()`。`ledger_no` 唯一索引作并发兜底，插入冲突时重试。

## 7. 驾驶舱对接（2026-07-08 口径已确认，方案更新）

**定时任务取消**。同事确认：不用每晚定时算，驾驶舱查询时**实时从台账表汇总**即可，规则上符合需求"显示前一日数据"的逻辑。

确认的口径：四大类目**只看台账，历史数据不要**（替换）。具体改法：

1. 修改 `SourceCollectionMapper#queryCategoryAmount` 中钢材（1501）、润滑剂（1701）、电线电缆（2302）、轴承及备件（2502）四个 SELECT 分支：数据来源从 `sc_source_collection` 改为新台账表 `sc_collection_daily_amount_ledger`，条件 `delete_sign = 0 AND statistic_date < CURDATE()`（即只统计"统计日期≤昨天"的已发布数据，满足"7月2日看7月1日"的需求规则）。煤炭、办公设备、办公文具三个分支**不动**。
2. 右侧"集采情况分析"的机电公司行（`querysituA` 中 `situA2`）口径 = 四大类目加总，逻辑上应同步切换到台账，否则分项与机电公司行对不上——**动手前和用户确认一句**。
3. 中间 `queryCenterHeader` 的全集团总数（日/月/季/年/累计）**保持不动**（待领导口径，需求原文未写明）。
4. 注意 `collectionShow` 字典开关：为 `1` 时驾驶舱走上述实时 SQL，否则读缓存表 `sc_collection_data`。开发前先查 test 库确认开关状态；若走缓存表路径，需同步处理对应数据项的写入或确认 test 环境开关为实时模式。
5. 不使用 XXL Job，也禁止 Spring `@Scheduled`。
