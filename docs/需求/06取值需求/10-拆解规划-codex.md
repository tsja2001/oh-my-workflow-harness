## 一、先说结论

### 1. 后端开发放哪里

本需求新增的“首页汇总取值接口”放在：

`01zhaocai-end/scm-source-all/scm-source-chase`

原因很直接：

- 前置需求 03 的统一 ES 模型、ES Repository，以及 FP/ZC/MT/JD 四路同步代码都在这个模块；
- 本需求只是继续对同一个 ES 索引做筛选和求和，放在这里改动最小；
- 接口路径应使用网关能识别的 `e/business/source/...`，不能照抄旧的 `/api/...` 本地调试路径。

建议新增独立的首页查询类，不把查询逻辑塞进已有同步类：

```text
scm-source-chase
└─ com.pcitc.scm.source.chase
   ├─ controller/CentralizedProcurementPortalController.java
   ├─ service/CentralizedProcurementPortalService.java
   ├─ service/impl/CentralizedProcurementPortalServiceImpl.java
   └─ vo/centralizedProcurementPortal/*.java
```

现有 `CentralizedProcurementReportService` 继续只负责“把五路明细写进 ES”；新 Service 负责“从 ES 汇总首页数字”。写入和读取分开，后面维护时不会把两种职责搅在一起。

### 2. 前端开发放哪里

页面已存在，不新建首页：

`02zhaocai-front/scm-vue-hpc/src/views/procurementPortal`

路由也是现成的：

`/hpc/index.html#/procurementPortal`

当前页面各块已经摆好，但数据主要来自 `data.js` 假数据，类目圆环甚至使用了随机数。本期工作是接真实接口，并删除“接口失败仍显示一组看起来很真的假数”这种兜底。

### 3. ES 和定时任务怎么分工

采用“**定时任务更新明细 ES，打开页面时由 ES 实时汇总**”：

```text
业务库/台账
    │ 每天定时同步
    ▼
统一 ES 明细索引
    │ 页面请求时 size=0 聚合
    ▼
首页汇总接口
    │
    ▼
HPC 集采门户首页
```

不再增加第二套“首页汇总表 + 首页汇总定时任务”。当前 ES 已是为统计准备的扁平明细，直接聚合即可；再存一份汇总结果只会增加数据延迟和对账难度。

用户已补充确认：

- 前置《集采管理业务统计报表》代码已经在 `test`；
- 当前有其他开发，不能切换本地分支；
- 寻源侧 FP/ZC/MT/JD 的新定时任务尚未配置。

本次研究全程没有切换公司代码分支。开发时应等当前工作结束后，以**包含 03 代码的 test 基线**继续，不要从当前旧分支直接写。

## 二、这套业务到底在干什么

前置需求 03 做的是一张“统一流水账”：把不同系统里已经成交、下单、入库或台账发布的钱，整理成统一字段后放进同一个 ES 索引。

| 数据来源 | 代号 | 业务含义 | 谁写入统一 ES |
|---|---|---|---|
| 非平台录入 | FP | 企业在绿色通道补录的交易 | Source / `scm-source-chase` |
| 招采平台 | ZC | 招标、询价等平台公示成交 | Source / `scm-source-chase` |
| 云采平台 | YC | 云采订单 | Order / `scm-order-report` |
| 煤炭 SAP | MT | 煤炭入库/收货明细 | Source / `scm-source-chase` |
| 机电四大类台账 | JD | 机电执行的集采日金额台账 | Source / `scm-source-chase` |

本需求 06 不再回五套原表分别计算，而是从这张统一流水账做汇总。

之所以公式里要减三笔，是为了去重：

```text
企业可能在 FP/YC 录了一次
机电或煤炭官方台账又在 JD/MT 录了一次
                     │
                     ▼
统一 ES 里看起来是两笔
                     │
                     ▼
保留 JD/MT 官方记录，减去 FP/YC 的重复记录
```

这解释了三个扣减项：

1. 减 FP 中“机电公司 + 四大类”；
2. 减 FP 中“北分 + 水泥板块”的煤炭重复数据；
3. 减 YC 中“机电公司 + 四大类”。

## 三、已经确认的业务口径

### 1. 公共时间规则

- 所有累计起点均为 `2026-01-01 00:00:00`，不再使用“7 月 1 日”；
- 查询结束时间为查询日前一天，不包含查询当天；
- 实现时统一使用北京时间的左闭右开区间：`[开始日 00:00, 查询日 00:00)`；
- “当日交易额”页面文案改为“日交易额”；
- 金额取含税金额 `taxTotal`，除以 10000 后按万元显示，保留两位小数；
- 百分比保留两位小数，分母为 0 时返回 `0.00`。

### 2. 集采资格

一条交易满足下面任意一个条件，就属于“统计期间的集采交易金额”：

```text
isCentralized = 1
或者
purchaseType ∈ {集团集采、二级集团集采、区域集采}
```

这个筛选天然包含招采平台 ZC，不需要单独给 ZC 加白名单。

### 3. 月、季、年集采交易额

对月、季、年分别换时间范围，计算公式一致：

```text
调整后集采交易额
= 满足集采资格的全部来源交易额
- FP 中满足集采资格的“机电公司 + 四大类”
- FP 中满足集采资格的“北分 + 水泥板块”
- YC 中“机电公司 + 四大类”
```

注意：YC 扣减是否也必须满足“集采资格”，产品补充公式里没有写，已列入待确认问题。

### 4. 各集团规模

先在同一公式上加 `buCode` 条件，再做三项去重；不能先算集团毛额，再按全平台比例摊扣减。

| 展示集团 | 板块编码 |
|---|---|
| 水泥集团 | BU002 |
| 地产集团 | BU006 |
| 新材产业化集团 | BU005 |
| 投资物业集团 | BU007 |
| 冀东发展集团 | BU004 |
| 天津建材集团 | BU008 |
| 直管单位 | 除以上六个编码外的全部板块 |

每组交易率：

```text
该组调整后年度集采交易额 ÷ 平台总交易额 × 100%
```

用户对 C7 的理解是对的：如果 FP/YC 和 JD/MT 两份重复记录都带相同 `buCode`，在每个板块内部减掉 FP/YC 后，保留 JD/MT 的一份即可。当前 test ES 的 561 条数据都有 `buCode`，所以技术上可以计算。开发时还要对缺失或非法板块编码报警，防止以后数据质量下降。

### 5. 品类和专项

- 六个一级品类全部读取统一 ES，不直接查原始台账；
- 办公用品及设备：YC 年度金额减 YC 中“机电公司 + 四大类”的金额；
- 煤炭日/月/季/累计：从 MT 按相应时间范围求和，供应商/类目限制仍待确认；
- 钢材日/月/季/累计：`dataSource=JD AND categoryCode=1501`，只改变时间范围；
- 坑口指标、煤价趋势、钢价趋势和钢材主流品种指标，本意是首页和驾驶舱共享同一份已发布台账数据，不应由两个前端各算一遍。

## 四、现有数据能不能支撑公式

2026-07-30 对 test 统一 ES 做了只读核查。以下数字只用于看字段是否可用，不是产品验收基准。

### 1. 当前数据规模

| 来源 | 条数 |
|---|---:|
| MT | 503 |
| FP | 35 |
| ZC | 11 |
| YC | 7 |
| JD | 5 |
| 合计 | 561 |

当前五路数据已经能汇到同一索引，且 561 条都有 `buCode`。这说明“按集团汇总”在结构上可行。

### 2. 已发现的数据红灯

#### 供应商编码不是同一种东西

统一字段都叫 `supplierCode`，但各来源实际含义不同：

- FP 多数存统一社会信用代码；
- ZC 常见是交易平台 `JYJT...` 编码；
- YC 常见是 MDM/SAP `CN...` 编码；
- MT 当前 503 条全部没有写入 `supplierCode`，虽然原表里有；
- JD 当前存的是执行单位代码 `JDGS`。

以“唐山冀东机电设备有限公司”为例，系统里同时能找到：

- 公司 ID：`SCM00002105`
- 平台公司编码：`JYJT0002472`
- MDM 编码：`CN13000363`
- 统一社会信用代码：`911302300759817983`

所以产品只说“按 SCM 编码筛”仍不够，必须说清楚到底是哪一套编码。不能用供应商名称模糊匹配代替，否则改名、简称和分公司都会造成错账。

#### FP 的关键字段缺失较多

当前 ES 的 35 条 FP 中，有 26 条没有 `isCentralized` 和 `categoryCode`。原表全量体检也显示：

- `is_jc` 填充率约 10.3%；
- 明细 `category_code` 填充率约 6.6%。

缺这两个字段时，既判断不了它是否属于集采，也判断不了它是不是机电四大类。代码不能凭名称猜，必须确定补数或排除规则。

#### 类目 2502 存在父子级问题

产品给的是父类 `2502 轴承及备件`，但当前 ES 实际出现的是 `250201`，没有精确的 `2502`。需要确认“2502 是否包含所有下级类目”。

## 五、接口设计

### 1. ES 金额总览接口

建议一个接口一次返回页面全部金额卡片，避免前端打开页面发十几个请求：

```http
GET /gateway/e/business/source/centralizedProcurementPortal/overview
```

前端默认不传日期，后端按服务器北京时间，以当天为查询日、统计到昨天。若测试阶段需要历史对账，可在非生产调试入口增加指定 `queryDate` 的能力，不建议让普通前端用户随意改统计日。

建议响应结构：

```json
{
  "asOfDate": "2026-07-29",
  "core": {
    "monthAmount": 0.00,
    "quarterAmount": 0.00,
    "yearAmount": 0.00,
    "platformAmount": 0.00,
    "centralizedRate": 0.00
  },
  "groups": [
    {
      "buCode": "BU002",
      "name": "水泥集团",
      "amount": 0.00,
      "rate": 0.00
    }
  ],
  "categories": {
    "coal": 0.00,
    "steel": 0.00,
    "lubricant": 0.00,
    "cable": 0.00,
    "bearing": 0.00,
    "office": 0.00
  },
  "coalTransaction": {
    "dayAmount": 0.00,
    "monthAmount": 0.00,
    "quarterAmount": 0.00,
    "cumulativeAmount": 0.00
  },
  "steelTransaction": {
    "dayAmount": 0.00,
    "monthAmount": 0.00,
    "quarterAmount": 0.00,
    "cumulativeAmount": 0.00
  }
}
```

金额字段返回数值，不返回已经拼好“万元”“%”的字符串；单位和中文文案由前端展示，方便图表继续计算。

### 2. 驾驶舱共享数据

现有接口：

```text
/e/business/source/source/cockpit_collection_data_kengk
/e/business/source/source/cockpit_collection_data_mt
/e/business/source/source/cockpit_collection_data_gc
```

当前真实情况：

- `kengk` 仍从旧缓存表 `sc_collection_data` 读取，煤炭坑口台账已有查询能力但此前因交付延期被撤回接线；
- `mt/gc` 也主要读旧缓存，数据仍停留在 2024-12 至 2025-11；
- 价格趋势台账已有维护代码，但还没有形成“发布后 → 驾驶舱/首页共同读取”的完整链路。

因此“复用接口”不等于前端直接接上就完成。若本期包含趋势和坑口更新，还要把这些接口的数据源改成已发布台账，并让驾驶舱与 HPC 首页共同消费同一后端结果。具体是否纳入本期，需产品确认。

## 六、定时任务配置

代码在 test，不代表每天会自动产生新数据。只读检查 test 调度中心后确认：

- 订单中心 YC 任务已存在：  
  `order-centralizedProcurementReportService-syncCentralizedOrderToEs-{}`
- 寻源侧没有找到本报表的四个新任务。

需要在“寻源模块”执行器下配置四项，统一使用公共 handler `simpleJobHandler`：

```text
source-centralizedProcurementReportService-syncCentralizedProcurementData-{}
source-centralizedProcurementReportService-syncZcData-{}
source-centralizedProcurementReportService-syncMtData-{}
source-centralizedProcurementReportService-syncJdData-{}
```

定时任务只负责把前一天新明细同步进 ES，不负责预计算首页。具体 cron 要避开上游数据入库时间，并错峰运行；开发完成后由用户在管理页面配置和启用，AI 准备逐项参数及验收步骤。

## 七、开发顺序

### 阶段 A：先补数据合同

1. 产品/数据负责人确认供应商规范编码和两个准确值；
2. 确认 2502 的父子类匹配；
3. 确认平台总交易额和扣减项的完整口径；
4. 确认 FP 缺字段如何处理；
5. 确认趋势/坑口台账是否属于本期。

### 阶段 B：统一 ES 数据修正

1. 新增一个语义明确的规范供应商字段，例如 `supplierMdmCode`，不要直接覆盖各来源含义不同的 `supplierCode`；
2. MT 同步时补写原表已有的北分供应商编码；
3. FP 根据确认的主数据映射补规范供应商编码；
4. 必要时修正类目和集采字段来源；
5. 对 2026-01-01 起历史数据补跑；
6. 加数据质量检查：时间、金额、板块、来源、类目、规范供应商编码。

### 阶段 C：首页汇总接口

1. 建立统一时间范围工具；
2. 封装“集采资格”和“三项去重”公共过滤器；
3. 使用 ES `size:0` + `sum/filter` 聚合，一次请求完成核心、集团、品类和专项金额；
4. 统一万元、精度、零分母处理；
5. 写接口测试和公式对账用例。

### 阶段 D：前端接入

1. `procurementPortal` 页面调用 overview；
2. 替换 `data.js` 里的业务假数据；
3. 去掉 `Math.random()`；
4. 接口失败显示 `--` 或明确错误态，不保留假业务金额；
5. 补“日交易额”展示；
6. 根据产品范围接入坑口/价格趋势共享接口。

### 阶段 E：调度和验收

1. 配置并手动执行四个寻源同步任务；
2. 检查五来源当日都有预期增量；
3. 按月、季、年、板块、类目抽样和 ES 明细对账；
4. 验证空数据、跨季度、1 月 1 日、分母为 0；
5. 验证接口失败时前端不会显示假数。
