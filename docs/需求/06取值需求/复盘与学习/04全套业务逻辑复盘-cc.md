# 序：这份文档的主线是什么

你让我"按我的逻辑、我的主线"讲。那我先把主线亮出来，后面所有章节都是在展开这一句话：

> **这一整套东西，本质上是在回答一个考核问题：「金隅冀东集团今年的集中采购，做到了多少？占比多少？各个二级集团分别做了多少？」**

围绕这一个问题，公司做了三件事，正好就是你这三个需求：

| 需求 | 干的事 | 一句话本质 |
|---|---|---|
| **01 + 02 台账** | 造了 4 个录入页面 | **把系统外的采购行为，请人手工"补进来"** |
| **03 统计报表** | 造了 5 条搬运管道 + 一个 ES 货架 | **把散在 5 个系统里的采购数据，统一成一种格式堆到一起** |
| **06 取值** | 造了门户首页 + 改造 3 个驾驶舱接口 | **站在货架前按口径加总，做成给人看的数字** |

再往下一层，这套设计要解决的是**三个天然矛盾**。你只要抓住这三个矛盾，整个系统的所有"怪规矩"就都解释得通了：

1. **数据是散的** —— 采购行为发生在 5 个不同的系统/渠道里，格式、字段、时间口径全不一样。
   → 解法：**ES 统一货架**（第五章）
2. **账是重的** —— 同一笔钱，企业自己报一遍，官方台账又报一遍，堆到一起就虚高。
   → 解法：**三笔扣减（去重）**（第七章 §7.2，这是整个 06 需求里最有业务味的一段）
3. **码是乱的** —— 同一家公司，在 4 个系统里有 4 个不同的编号，没有一个"通天下"的码。
   → 解法：**每一路各用各自的码筛**（第七章 §7.6）

读完这份文档，你应该能做到：**看着首页上任何一个数字，倒着说出它是哪个人、在哪个页面、点了什么按钮、经过哪张表、走了哪条管道、被什么条件筛过、最后怎么加出来的。**

## 1.2 什么叫"集采"，公司为什么盯这个数

**集中采购（集采）**：本来一百家成员企业各买各的钢材，现在集团说：都别自己买了，统一由机电公司去谈、去买，然后分给你们。

为什么要这么干？三个原因，从强到弱：

1. **压价**。一百家分散买，谈判筹码小；集中成一个大单，供应商必须让价。这是集采最直接的经济动因。
2. **合规**。国资背景的企业，采购是纪检审计的重点。集中到少数几个执行单位、走统一平台留痕，比一百家各自签合同好管得多。
3. **数据**。集中之后，集团才知道自己一年到底买了多少钢、什么价，才有下一年的谈判底气。

**【推测】** 而"集采率"（集采金额 ÷ 平台总交易额）几乎肯定是一个**自上而下的考核指标**——国资委考核集团、集团考核二级集团。这解释了 06 首页的两个设计：
- 为什么首页最显眼的位置放"年度集采率"；
- 为什么第二块非要按二级集团排名（**排名 = 考核压力**，把六个集团的集采率并排放在领导面前）。

> 这就是为什么 06 需求里所有口径都要"问产品/问领导"再落笔。**这不是一张报表，这是一张成绩单。** 分子分母算错，等于给谁多记/少记了一笔绩效。

## 1.3 于是产生了一个技术难题

集团要算"集采率"，但**采购行为本身分散在五个完全不同的地方**：

| 渠道 | 采购发生在哪 | 数据长什么样 |
|---|---|---|
| 招采平台（ZC） | 自家的招投标系统 | 寻源单 → 方案 → 定标 → 中标供应商 → 中标物料，五张表串起来 |
| 云采（YC） | 云采商城下单 | 订单 + 订单物料，在**另一个微服务、另一个库** |
| 非平台录入（FP） | 线下买的，事后补录 | 绿色通道主单 + 物料明细 |
| 煤炭 SAP（MT） | 根本不在这套系统里，SAP 每天推流水 | 采集表，一行一条收发流水 |
| 机电台账（JD） | **压根没有系统**，人工每天填 | 一行一条日金额 |

五种格式、五套字段、五个时间口径、五套供应商编码。**要算一个总数，必须先让它们长成一个样子。** 这就是 03 需求存在的全部理由。

# 第三章 五个数据源头：钱从哪来

这一章是"数据从哪里录入"的正面回答。每一路我按同一个模板讲：**谁在什么页面干了什么 → 落到哪张表 → 什么条件才能进货架 → 一条业务变几条记录 → 时间轴用哪个字段 → 供应商怎么标识 → 有什么坑 → 为什么这么设计。**

## 3.1 ZC 招采平台 —— "正规军"

**这是公司采购的主流程，也是整个招采系统的立身之本。**

| 项 | 内容 |
|---|---|
| **业务场景** | 需要公开采购的项目，走完整招标流程 |
| **人在哪操作** | ① 采购方案编制 `#/procurementSchemeMgt/procurementPlanPreparation`<br>② 选一种寻源方式：招标 `/biddingManagement`、询价 `/enquiryManagement`、竞争性谈判 `/competitiveNegotiation`、竞争性磋商 `/competitiveConversation`、单一来源 `/singleOrigin`<br>③ 定标方案审批 `#/approveMgt/calibrationScheme`<br>④ 公示 |
| **源表链路** | `sc_source`（寻源单）→ `sc_scheme`（方案，带"是否集采"）→ `sc_deal_result`（定标方案）→ `sc_deal_detail`（中标供应商）→ `sc_deal_product`（中标物料） |
| **进货架条件** | `state=127`（**已公示**）且 采办方式 ∈ {101 招标, 102 单一来源, 103 询价, 104 竞争性谈判, 105 竞争性磋商} 且 `final_time`（公示时间）在同步区间内；定标方案**只取审批通过且编制时间最新的一份**；供应商 `is_win_bid=1` |
| **粒度** | 一家中标供应商 × 一条中标物料 = 一条 ES 记录 |
| **时间轴** | `final_time` 公示时间 |
| **供应商编码** | `company_code` 体系（机电公司在这路是 `JYJT0002472`） |
| **是否集采** | `sc_scheme.is_collection`，**这一路是唯一有真实 0/1 值的来源** |

### 为什么这么设计（重点）

**① 为什么时间轴取"公示时间"，而不是签合同、付款、收货？**

因为**公示 = 这笔采购在法律和纪检意义上"落地"的时刻**。招投标流程里，公示是对外宣告"这个项目由谁中标、多少钱"，公示期一过就不可翻案。取公示时间意味着：

- **口径唯一、不可争辩**。合同签订可能拖几个月，付款可能分期，收货可能跨年——只有公示时间是一个确定的、公开的、单一的时点。
- **和考核周期对得上**。集团要问"今年做了多少集采"，答案应该是"今年定下来多少"，不是"今年付了多少钱"。

**② 为什么"竞价"（106）不算？**

需求明确排除了竞价方式。**【推测】** 两个可能的原因：竞价通常用于小额零星采购，不构成"集中采购"的业务实质；或者竞价模块本身就不产生标准的定标方案数据。这是产品拍的板（`13-问题答复-cc.md` 已确认"只有这 5 种"），**记住结论就行，但知道有这个边界，将来产品说"竞价也要算"你就知道要动哪里**。

**③ 为什么定标方案要"只取审批通过且最新的一份"？**

因为一个采购方案可能被定标好几次（第一次定标被否、重新定标）。如果全都取，同一笔钱会被算好几遍。**这是数据同步里最经典的一类问题：业务表保留了全部历史版本，统计只能认最终版本。**

**④ 主键为什么设计成"方案编号 + 标段号 + 供应商编码 + 物料编码"？**

这是 03 期一个被真实数据打脸后修正的设计。**【已验证】** 方案 `12870012-XJ-2026-0001` 的物料 `260101010002` 被三家供应商分标（江苏鱼跃 300 / 中国工艺 100 / 唐山明诚 670.9）。如果主键只用"方案编号+物料编码"，这三行会互相覆盖，金额从 1070.9 变成 300。

> **业务含义**：招标里一个物料被"分标"给多家供应商是常态（分散风险、平衡产能）。**主键必须包含"标段"和"供应商"两个维度，才能表达真实的商业结构。**

## 3.2 FP 非平台录入（绿色通道）—— "补丁"

**这是整套系统里业务含义最微妙的一路，也是最容易出数据质量问题的一路。**

| 项 | 内容 |
|---|---|
| **业务场景** | 企业因为各种原因**没走招采平台**就把东西买了（紧急采购、独家供应、小额零星、历史合同延续），事后必须补录进系统 |
| **人在哪操作** | 录入：`#/supplier/increasedList`（非平台采购业务录入）<br>审批：`#/approveMgt/increasedListApprove`（非平台采购业务审核）<br>查询：`#/dynamicPage/source/fpt` |
| **源表** | `sc_supplier_green_channel`（主单）+ `sc_supplier_channel_projects`（物料明细） |
| **进货架条件** | `approve_status=101`（**审批通过**）且 采购业务分类 ∈ {101 集团集采, 102 二级集采, 103 区域集采} **或为空**（只排除明确选了 104 分散采购的）且 `update_time` 在区间内 |
| **粒度** | 一单 N 条物料 = N 条 ES 记录 |
| **时间轴** | `update_time`（审批结束时间） |
| **供应商编码** | **统一社会信用代码** `three_in_one_id_code`（机电公司在这路是 `911302300759817983`） |
| **是否集采** | 主单 `is_jc`，**可以为空** |

### 为什么这么设计（重点）

**① "绿色通道"这个名字本身就说明了业务意图。**

它不是一个采购工具，它是一个**合规兜底通道**。业务上一定会有"来不及走流程但必须买"的情况，如果系统不给出口，人就会在系统外买完然后彻底不录——那集团就永远看不到这部分钱。所以设计上是：**先放你买，但事后必须补录、必须审批。**

这直接解释了两件事：
- **为什么时间轴取"审批结束时间"而不是"实际采购时间"**：因为实际采购时间是当事人自己填的、不可信；审批结束时间是系统盖的章，跑不掉。
- **为什么必须 `approve_status=101` 才进货架**：没审批通过的补录 = 一面之词，不能进考核口径。

**② 为什么"采购业务分类为空"的也放进来？**

这是 03 期第四阶段改的（提交 `16c275723 fix: 非平台录入不过滤采购业务分类为null`）。原因是同事的一句话：

> "这个字段是前段时间新增的，还没发版，能把空的也显示出来吗？"

**【实测确认】** 那时 `sc_supplier_green_channel` 311 条里只有 7 条有这个字段值，全集中在 2026-06-24~06-30。典型的**"字段新加了，但录入功能还没上线"** 状态。

> 💡 **这是你以后做统计需求最该带走的一条经验**：需求里拿来当筛选条件的字段，**开工前必须先做"字段体检"**（`scripts/fieldcheck.sh`）。填充率低于 50% 就是红灯——不是你写错了，是这个字段还没被业务真正用起来。按它筛，你会得到一张空报表，然后花三天排查一个不存在的 bug。

**③ 由此产生的一个业务口径问题（已闭环，但值得记住）**

放开分类过滤后，FP 从 5 行变成 35 行，其中 **26 行的"是否集采"是空的**。这就出现一个哲学问题：**"没填是否集采"，到底算不算集采？**

产品的答复是：**空的不计入集采**（但仍进货架、仍算进"平台总交易额"）。这个决定是对的，理由：

- **统计口径的第一原则是"宁可少算，不可多算"**。这是一张成绩单，虚高比偏低危险得多。
- 空值不是"否"，是"不知道"。把"不知道"记成"是"，等于替业务做了决定。

代码上也做了对应的修正：`resolvePurchaseType()` 原来写的是 `isJc == 1 ? "集团集采" : "分散采购"`——这会把 26 条"不知道"硬写成"分散采购"。改成了**空就留空**。

> 一张《集采管理业务统计报表》里，"是否集采"列空着、"采购业务类型"列却写着"分散采购"——**自相矛盾且是凭空编的**。这种"用默认值填补未知"的坏味道，在做统计类需求时要格外警惕。

## 3.3 YC 云采 —— "商城"

| 项 | 内容 |
|---|---|
| **业务场景** | 云采商城下单，类似企业版京东：标品、在线比价、直接下单，不走招标 |
| **人在哪操作** | 采购方：`#/buyerCenter/myOrder`（订单管理）；供应商侧：订单列表 |
| **源表** | `to_order` + `to_order_product`（库 `scm_order_test`，**不同的库、不同的微服务**） |
| **进货架条件** | `order_status NOT IN (2,7,8,9,10,11)`（排除作废/取消/关闭）且 `book_time`（下单时间）在区间内 |
| **粒度** | 一单 N 条物料 = N 条记录 |
| **时间轴** | `book_time` 下单时间 |
| **供应商编码** | **MDM 码**（机电公司在这路是 `CN13000363`） |
| **是否集采** | **固定 = 1**（产品确认：云采所有数据都是集采） |

### 为什么这么设计

**① 为什么这一路的同步代码不在你的仓库里？**

YC 的同步写在 `scm-order-all/scm-order-report`，是**同事负责的**。这不是分工偷懒，是架构约束：订单表在 order 服务自己的库里，source 服务不能跨库直连。**微服务架构下，"谁的数据谁负责往外送"是基本纪律。**

这带来一个你要知道的实操后果：**YC 没有 source 侧的手动补数接口**。FP/ZC/MT/JD 你都能自己调 `sync*` 补跑，YC 只能等每日任务或找同事。

**② 为什么云采"所有数据都是集采"？**

**【推测】** 因为云采商城本身就是集团搭的集中采购平台——上面的商品是集团统一谈过价、统一准入的供应商。**你在云采上买东西这个动作本身，就已经是"集中采购"了。** 所以不需要再打标记。

这个设定进而解释了 06 里"办公用品及设备"的口径：**办公用品 = 云采全量 − 云采里机电四大类**。云采上卖的东西大部分是办公类标品，把已经被单独统计的四大类扣掉，剩下的就是办公用品。这是一个**"用减法定义品类"** 的技巧——省得去维护一个"什么算办公用品"的类目清单。

## 3.4 MT 煤炭 SAP —— "外来户"

| 项 | 内容 |
|---|---|
| **业务场景** | **没有任何页面**。SAP 系统每天自动把煤炭采购流水推进采集表 |
| **人在哪操作** | **不需要任何人操作** |
| **源表** | `sc_source_collection`，条件 `data_source='SAP'` |
| **进货架条件** | `data_source='SAP'` 且 `final_time` 在区间内 |
| **粒度** | 一条采集明细 = 一条记录 |
| **时间轴** | `final_time` |
| **供应商** | **固定写死北分**（`CN11005095`），产品确认煤炭 SAP 永远只有北分 |
| **是否集采** | **固定 = 1** |

### 为什么这么设计（重点）

**① 为什么煤炭要单独走 SAP，不走招采平台？**

这是最有业务味的一条。**煤炭是水泥厂的命根子。** 水泥生产是高耗能行业，燃料成本占生产成本的很大一块，煤炭采购是**每天都在发生的大宗连续采购**——不是"一年招一次标"，而是"每天拉多少车、按当天价结算"。

这种业务形态：
- 不适合走招投标（一年招几百次标？）
- 天然适合走 ERP（SAP）的采购订单 + 收货过账流程
- 所以集团的做法是：**煤炭的采购权集中到北分，执行在 SAP 里，数据每天推给招采平台做统计。**

这就是为什么"MT 整路 = 北分 + 煤炭(1001) + BU002 水泥集团"，一个条件都不用加。

**② 主键为什么必须带日期？**

**【已验证】** 订单 `4500931416` 的物料 `100101000003` 从 1/9 到 1/27 共 **18 条**记录，金额各不相同。因为 SAP 推的是**按天的收发流水**，同一个订单同一个物料每天都有新的一条。

主键必须是 `订单号 + 公示日期(yyyyMMdd) + 物料编码`。**如果只用"订单号+物料编码"，503 条会被压成几十条。**

> 💡 **通用心法**：定主键之前，先问一句"**业务上什么情况下会出现第二条一样的**"。这个问题问清楚了，主键就定了。ZC 是"分标给多家"，MT 是"按天流水"，FP/YC 是"一单多物料"，JD 是"流水号天然唯一"。四种来源四种主键，全是业务结构的直接映射。

**③ 为什么有负数？**

煤炭有退货/冲销，SAP 会推负数记录。产品确认**按净额算（正的加、负的减）**。这符合会计惯例：**你退回去的煤，不该算在"今年买了多少"里。**

**④ 一个你已经踩过的坑（`02答复煤炭.md` 已详解）**

需求写"取《招采平台-报表管理-集采报表》"，但那个页面在 test 上查什么都是 0 条。**【实测】** 原因是那个页面读的 ES 索引 `index_web_collection_meta_test` 文档数为 0，而源表 `sc_source_collection` 里 SAP 数据有 507 条。

> **教训升级成方法论**：需求文档里写的"取某某报表/某某页面"，**99% 是业务口径（告诉你数据是哪块业务的），不是技术口径（不是让你调那个接口）**。往下扒到 MySQL 源表，永远比依赖别人的同步任务稳。03 期就是这么做的，所以那个页面坏了也不影响我们。

## 3.5 JD 机电四大类台账 —— "手工账"

| 项 | 内容 |
|---|---|
| **业务场景** | 机电公司每天把前一天四大类的成交金额人工填进台账 |
| **人在哪操作** | `#/businessManagementLedgerJC/dailyAmountStatisticsLedger`（集采日金额统计台账） |
| **源表** | `sc_collection_daily_amount_ledger`（**这就是 01 期做的台账1**） |
| **进货架条件** | `execute_unit_name = '机电公司'` 且 `statistic_date` 在区间内 |
| **粒度** | 一条台账 = 一条记录（主键 = 流水号 `JCRJE-yyyyMMdd-NNN`） |
| **时间轴** | `statistic_date`（统计日期，人填的） |
| **供应商** | `execute_unit_name/code`（集采执行单位） |
| **是否集采** | **固定 = 1** |

### 为什么这么设计（重点）

**① 为什么要"人工台账"？这不是开倒车吗？**

不是。这恰恰是**企业级系统最常见、也最容易被新人看不起的一类设计**。

业务现实是：机电公司的钢材采购**根本不在这套招采系统里发生**。它可能在机电公司自己的系统里、可能在 Excel 里、可能就是几个人打电话谈的。集团要考核集采率，就必须把这部分钱算进来。

三个选项：
1. 让机电公司把整套采购系统接进来 → 半年起步，跨公司协调，不现实
2. 让机电公司做接口对接 → 也要几个月，而且要机电公司配合排期
3. **给机电公司一个页面，每天人工填一个日汇总数** → 一周上线

**选 3。这就是"台账"的本质：用极低的成本，把系统外的业务纳入数字化考核。**

代价是数据粒度粗（只有日汇总，没有物料明细——所以 JD 那路的"物料编码/物料描述"是空的）、依赖人的自觉。但这是**先有数、再有精度**的正确顺序。

**② 采购方案名称为什么要拼？**

JD 没有"采购方案名称"这个概念，报表又必须有这一列，所以拼成"钢材2026-07-01的商品采购"。**MT 也一样**（`product_desc` + "商品采购"），因为 `purchase_business_name` **【实测】** 503 条全是 NULL。

> 这是报表类需求的常规操作：**统一格式意味着有些来源必须"造"出它本来没有的字段**。造的时候要遵守一条：**造出来的值必须是可解释、可回溯的**（能从数据里推出来），不能凭空编。

**③ 这一路踩过一个"写死名称"的坑（已修复，但值得完整复盘）**

**旧代码**（03 期第三阶段写的，`5906202ca feat: 煤炭机电录入`）：
```java
private static final String JD_EXECUTE_UNIT_NAME = "机电公司";                              // 常量
ledgerQuery.eq(CollectionDailyAmountLedger::getExecuteUnitName, JD_EXECUTE_UNIT_NAME);     // 同步条件
```

**问题**：需求原文写的是"集采执行单位=机电公司"，开发照着这五个字写死成了**名称匹配**。但页面上"集采执行单位"是**组织机构控件**，选出来的是集团组织树里的正式记录——`12300000 / 唐山冀东机电设备有限公司`。**组织表里根本不存在一个叫"机电公司"的单位**，所以：

- 用户从页面正常录入 → 名称永远是"唐山冀东机电设备有限公司"
- 同步条件要求名称 = "机电公司" → **一条都匹配不上，静默返回 0，不报错**

**【实测】** 拿真实数据跑这两条 SQL，差别一目了然：

| 筛选条件 | 命中条数 |
|---|---|
| `execute_unit_name = '机电公司'`（旧代码） | **0** |
| `execute_unit_code = '12300000'`（新代码） | **15** |

**✅ 已修复**：`77f00a27c fix: JD同步按机电公司组织编码筛选`（2026-08-06 16:37），分支 `feature/jd-sync-fix-yang` → merge `f9ce62da8` 进 `test`，**已推 `origin/test`**。改动就 4 行：

```diff

+ private static final String JD_EXECUTE_UNIT_CODE = "12300000";
...
```

**✅ 已验证生效**：ES 里 JD 的 15 个主键，与台账里 `execute_unit_code='12300000'` 的 15 条**一一对应**，包括今天（08-07）新录的 `JCRJE-20260807-002/003`。说明修复版已部署且同步跑通。

- **顺带一个仍待产品确认的问题**：这批台账的 `bu_code` 是页面按"采购企业"自动带出来的（**【实测】** BU005/BU007/BU008 都有），而机电公司自己属于冀东发展集团 BU004。**这批钱该记在"买家的板块"还是"执行单位的板块"？** 直接影响二级集团排名，值得问。

> 💡 **这个 bug 的普适教训，比 bug 本身值钱**：
> **凡是"按名称"做业务匹配的代码，都是定时炸弹。** 名称会变（改错别字、改全称简称、公司更名），编码不会。这就是下一章"编码+名称双存"原则的反面教材——项目里明明处处遵守（`execute_unit_code` + `execute_unit_name` 双存就在同一张表上），偏偏同步条件用了名称。
>
> 更值得警惕的是**它的失败方式是"静默"的**：查不到就返回 0，日志只有一行 `未查询到符合条件的机电四大类台账 跳过`，接口返回"同步成功，写入 0 条"。**页面上钢材品类就是 0，看不出任何异常。** 这类"沉默失败"比报错难查十倍。

# 第四章 四本台账：把系统外的业务拉进来

01 和 02 期一共造了 4 个录入页面，都挂在菜单 **"集采业务管理台账"** 下面。它们的共性和差异，是理解这套系统"人机分工"的关键。

| 台账 | 页面路由 | 表 | 谁录 | 喂给谁 | 时效 |
|---|---|---|---|---|---|
| **台账1 集采日金额统计** | `#/businessManagementLedgerJC/dailyAmountStatisticsLedger` | `sc_collection_daily_amount_ledger` | 机电公司 | **JD 那一路 → ES 货架** | 定时（明天） |
| **台账2 集采日计划统计** | `#/businessManagementLedgerJC/dailyPlanStatisticsLedger` | order 侧表 | 执行单位 | **⚠️ 谁也不喂（孤儿）** | — |
| **台账3 煤炭重点坑口日指标** | `#/businessManagementLedgerJC/coalPitDailyIndicator` | `sc_coal_pit_daily_indicator(+_item)` | 执行单位 | **驾驶舱/门户坑口图（直读）** | 实时 |
| **台账4 价格趋势维护** | `#/businessManagementLedgerJC/maintenancePriceTrend` | `sc_price_trend` | 执行单位 | **驾驶舱/门户煤价钢价图（直读）** | 实时 |

## 4.1 为什么台账1 走 ES，台账3/4 不走？

这是全套系统里**最容易搞混、也最能体现设计判断力**的一个分岔。答案在于**这两类数据的性质完全不同**：

| | 台账1（日金额） | 台账3/4（坑口价、价格趋势） |
|---|---|---|
| 数据性质 | **交易额** —— 是"钱" | **价格指标** —— 是"数" |
| 要不要和别的数据相加 | **要**（要和 ZC/FP/YC/MT 的钱加在一起算集采率） | **不要**（煤价 600 元/吨，跟谁都不相加） |
| 要不要按板块/类目/供应商切分 | **要** | 不要，就是一条时间序列 |
| 数据量 | 会持续增长，几万几十万 | 一个月几条，永远很小 |
| 所以 | **必须进统一货架，才能和别人一起聚合** | **进货架毫无意义，直接查表最简单** |

> 💡 **判断法则**：**"需要和其他数据一起做聚合运算"的，才需要统一货架；"自己就是最终答案"的，直接读源表。**
>
> 06 期把 `kengk/mt/gc` 三个接口从"读死缓存"改成"读台账"，改的就是这个——**中间那层缓存表 `sc_collection_data` 是纯粹的历史包袱**（当年大屏上线时没有真实数据源，就手工往一张表里填数撑场面），台账建好之后它就该退休了。

## 4.2 "保存即发布" 的设计意图

台账1/3/4 全都**没有独立的"发布"按钮，保存 = 发布**。代码上是 `add/update` 里直接把 `publish_time` 设成当前时间。

为什么不做草稿/审批？**【推测】** 因为这些数据的业务性质是"**日报**"：

- 时效性 > 准确性。领导要的是"今天煤价多少"，晚一天的准确数不如当天的估算数有用。
- 填的人就是唯一权威（机电公司填自己的成交额，谁审？）。
- 填错了可以改，改了立刻重新发布——**用"可修改"代替"审批"**，这是日报类数据的通用做法。

代价是**没有版本留痕**，但系统用两个机制兜底：
- `publish_time/publish_by` 记录"最后一次是谁、什么时候发的"
- **逻辑删除**（`delete_sign=1`），删掉的记录库里还在，可查可恢复

## 4.3 价格趋势台账：一个"字符串即协议"的设计

这是我认为整套系统里**最脆弱**的一处设计，你必须知道：

驾驶舱代码（`PriceTrendCockpitProviderImpl`）里**硬编码了 5 个指标名字符串**，靠字符串完全相等去匹配：

| 类目 | 指标名称（必须一字不差） | 显示在哪 | 映射字段 |
|---|---|---|---|
| 煤炭 | `煤炭月成交价格` | 煤价趋势图 - 成交价线 | `dataValue` |
| 煤炭 | `煤炭月环渤海价格` | 煤价趋势图 - 环渤海价线 | `ext02` |
| 钢材 | `钢材月成交价格` | 钢价趋势图 - 成交价线 | `dataValue` |
| 钢材 | `螺纹月成交价格` | 钢材"螺纹钢月指标" | `ext02` |
| 钢材 | `中厚板月成交价格` | 钢材"中厚板月指标" | `ext03` |

**录入的人打错一个字（含空格、全角），数据永远不显示，而且不报错。**

> **为什么会这么设计？** **【推测】** 因为这是个"临时性很强"的需求：产品要的是"煤价图上再加一条环渤海线"，而底层表是通用的 `sc_price_trend`。要么改表结构加"指标类型"字典，要么用字符串匹配。选了后者——快，但欠了债。
>
> **正确的做法**应该是：指标名做成数据字典下拉（就像"类目"那样），录入时只能选不能填。**这是一个你可以主动提给产品的优化点**，成本很低（加一个字典 + 前端改成下拉），收益是彻底消除"填错永远查不到"的静默失败。

另外还有两个隐藏规则，你不知道就会以为是 bug（下面按**代码实读**写，`PriceTrendCockpitProviderImpl.java`）：

### 规则一：图上永远只有 12 个点，窗口是"当前月之前的连续 12 个自然月"

```java
YearMonth currentMonth = YearMonth.now(BEIJING_ZONE);
YearMonth startMonth   = currentMonth.minusMonths(12);   // 起点 = 当前月 − 12
YearMonth endMonth     = currentMonth.minusMonths(1);    // 终点 = 上个月
for (int index = 0; index < 12; index++) { ... }         // 固定输出 12 个点
```

窗口是**滚动**的，每过一个月整体右移一格：

| 今天是 | 图上的 12 个点 | 当月数据 |
|---|---|---|
| 2026-08（现在） | **2025-08 ~ 2026-07** | 2026-08 **不显示** |
| 2026-09-01 起 | 2025-09 ~ 2026-08 | 2026-08 **开始显示**，2025-08 掉出去 |

**为什么不含当月？** **【推测】** 因为指标叫"**月**成交价格"——本月还没过完，就不存在"本月成交均价"这个数。和"统计截止到昨天"是同一个思路：**只展示已经收口的周期**。

**实操影响**：你今天（8 月）在页面上录一条 `2026 / 08` 的煤价，保存成功、列表能看到、**但图上没有**。这不是没生效，是要等 9 月 1 日。想立刻在图上看到效果，录 `2026 / 07`（上个月）。

### 规则二：年/月是**字符串字段**，格式不对会被静默丢弃

表结构 **【实测】**：`year varchar(10)`、`month varchar(10)` —— 存的是文本，不是数字。解析代码：

```java
int year  = Integer.parseInt(trend.getYear().trim());
int month = Integer.parseInt(trend.getMonth().trim());
return YearMonth.of(year, month);          // 失败 → 返回 null → 这条被跳过，不报错
```

> ⚠️ **本文第一版把这条写错了**（照抄了 `90-临时-业务闭环与录入实操-oc.md §3.2` 的"必须 4 位/2 位"），实读代码后更正：`Integer.parseInt` 是宽松的，**`7` 和 `07` 都能正确解析成 7 月**，前后空格也会被 `trim()` 吃掉。

真正会被丢弃的只有两种：

| 录成什么 | 后果 | 原因 |
|---|---|---|
| `七月` / `26年` / `2026-07` 这种**非纯数字** | 静默跳过 | `NumberFormatException` |
| 月份 `0` 或 `13` 这种**超范围** | 静默跳过 | `DateTimeException` |
| `7`（一位数月份） | ✅ **正常显示** | parseInt 能解析 |

那条 `year='1'` 的脏数据不是"解析失败"——它解析成了**公元 1 年**，然后被"12 个月窗口"过滤掉了。**结果一样（不显示），但原因不同**，排查时别找错方向。

> 💡 两条规则的共同点：**失败是静默的**。指标名打错、年月非数字、月份超范围、月份在窗口外——四种情况页面都不报错，就是"图上没这个点"。这就是我建议把指标名和年月都改成下拉/日期控件的原因：**把"能填错"的入口堵死，比在后端做校验更彻底。**

## 4.4 台账2 是个孤儿

`集采日计划统计台账` 录了数据，**不影响门户、不影响驾驶舱、不影响报表**，只影响它自己的列表和导出。

原因：产品原设计是拿它喂老驾驶舱的"集采计划分析"（响应率/执行率/完成率/滞后率），但 source 侧的 `queryDoRate()` 是**空实现**，没接 order 侧的 `calculateRates()`。驾驶舱那块还在读死缓存。

> **这不是 bug，是"半成品"。** 企业系统里这种状态很常见：需求砍了一半、或者排期到下一版、或者负责对接的两边都以为对方会做。**你要能一眼认出它，别把时间花在排查一个"本来就没接"的链路上。**

## 4.5 关键澄清：台账页面"能录的" ≠ 报表"会统计的"

这是最容易把人绕晕的一点：**日金额台账页面上，集采类目能选煤炭，集采执行单位能选任何组织——但门户上的"机电四大类"只认机电公司。看起来矛盾，其实是两层东西。**

### 把两件事分开

| | 台账页面（01 期造的） | JD 同步（03 期造的） |
|---|---|---|
| 是什么 | **一本通用账本**：给"集采执行单位"记录每日集采金额 | **一把筛子**：从账本里挑出符合"集团一级集采"口径的行送进 ES |
| 谁决定能录什么 | 组织机构控件（任意组织）＋ 类目字典 `collection_category`（5 个：煤炭/钢材/润滑剂/电线电缆/轴承） | 同步代码：`execute_unit_code = '12300000'` |
| 录了不符合条件的会怎样 | **正常保存**，列表能查、能导出 | **不进 ES**，门户/报表看不到 |

**页面不拦你，是有意的。** 台账页面在 01 期的定位是"集采业务管理台账"——它是给所有执行单位用的记账工具，不是机电公司专用表。**能记账 ≠ 记的每一笔都算进集团一级集采。**

### 于是台账里的每一行，实际上会走进三种命运

**【实测】** 拿今天的真实数据举例：

| 台账行 | 执行单位 | 类目 | 进 ES 吗 | 在门户上体现为 |
|---|---|---|---|---|
| JCRJE-20260807-003 | **12300000** 机电 | 1501 钢材 | ✅ 进 | 钢材品类卡 + 钢材专项 + 集采总额 |
| JCRJE-20260806-009 | **12300000** 机电 | 2502 轴承 | ✅ 进 | 集采总额（轴承卡因"2502 精确"口径仍是 0 → 实际它进了总额但没进卡）|
| JCRJE-20260709-007 | **12300000** 机电 | **1502 水泥** | ✅ 进 | **只进集采总额，不进任何品类卡**（1502 不在 CAT4 里）|
| JCRJE-20260807-001 | 10010000 冀东水泥 | 1001 煤炭 | ❌ 不进 | **什么都不体现**，只在台账列表和导出里 |
| JCRJE-20260716-002 | 11890019 中材汉江 | 1001 煤炭 | ❌ 不进 | 同上 |

### 为什么"煤炭"不能通过台账进统计（这是设计上的关键）

因为**煤炭已经有 MT 这一路了**（SAP 每天自动推北分的煤炭流水，503 条 1.41 亿）。

如果台账里录的煤炭也同步进 ES，就会出现**第四种重复账**：同一批煤，SAP 推一遍（MT）、人又在台账记一遍（JD）。而 06 的三笔扣减（D1/D2/D3）**只处理 FP 和 YC 的重复，没有"JD 煤炭"这一笔**。

所以 `execute_unit_code = '12300000'` 这个条件，**顺带就把"台账煤炭"挡在门外了**——因为煤炭的执行单位是北分，不是机电公司。**一个条件挡两件事：既限定了执行主体，又避免了和 MT 撞车。**

> ⚠️ **但这个防护是"侧面的"，不是"正面的"**。如果哪天有人用**机电公司**这个执行单位录一条煤炭台账，它会顺利进 ES（`dataSource=JD, categoryCode=1001`），进而**虚增年度集采总额**，而且不会被任何扣减抵消。
> **【实测】** 目前 12300000 名下 15 条里没有 1001，暂时没发作。**建议**：同步时再加一条 `categoryCode ∈ CAT4` 的正面限制，或者在页面上按执行单位联动限制可选类目。这是个可以提给产品/自己拍板的加固点。

### 顺带一个可以问一句的小事

类目字典 `collection_category` **【实测】** 有 5 项，但 01 期需求原文（`01台账需求.md:48`）只写了 4 个：

> 集采类目　数据字典：**钢材、电线电缆、润滑剂、轴承及备件**

而"煤炭(1001)"的字典创建时间是 `2026-07-09 16:03`，比另外四个（当天 10:47~10:48）**晚了 5 个小时**——像是配置时临时补加的。**【推测】** 可能是想让北分也能用这本台账记煤炭（作为 SAP 断供时的人工兜底），也可能只是配置时顺手加的。**值得顺口问产品一句："日金额台账的类目里为什么有煤炭？煤炭不是走 SAP 吗，这个选项是留着干什么的？"**

## 4.6 台账的"所属板块"从哪来——以及它现在为什么是乱的

这一节回答"JD 台账板块归属"那个待确认问题到底在纠结什么。

### 板块这个字段在整条链路上有多重要

回忆一下门户首页第②块"各二级集团集采率排名"：它就是把年度集采额**按每条记录的 `buCode` 拆开**。也就是说——

> **台账上那个"所属板块"下拉选了什么，直接决定这笔钱算进哪个二级集团的成绩。**

选错了，不是显示问题，是**给某个集团多记/少记了业绩**。

### 需求原本是怎么设计的

`01台账需求.md:52` 写得很清楚：

> 所属板块　根据"**采购企业**"自动带出所属板块

也就是：**谁花的钱，算谁的板块**。逻辑是通的——集团要看"水泥集团今年集采了多少"，问的是买家。而且这样和其他四路口径一致（FP/ZC/YC/MT 的 `buCode` 也都是采购企业的板块）。

### 完整的前端链路（逐层扒到底）

```
① 用户在「采购企业」下拉里搜索
        │  前端 handleUnitSearch()（防抖 0.5s）
        ▼
② POST /e/business/source/collectionDailyAmountLedger/queryOrgForSelect  {keyword}
        │  后端 CollectionDailyAmountLedgerServiceImpl.queryOrgForSelect()
        │    → Feign 调 orgManagerFeignService.queryList()  读组织主数据
        │    → 再用 Owningplate 字典把板块名换成标准名
        ▼
③ 返回 [{orgCode, orgName, belongBuCode, belongBuName}, ...]
        │
        ▼
④ 用户选中某一家 → 前端 handleFormPurchaseChange(val)
        │    formData.purchaseCompanyName = 该公司名
        │    if (unit.belongBuCode) { formData.buCode = unit.belongBuCode; ... }   ← 自动带出
        ▼
⑤ 「所属板块」下拉被填上 —— 但它仍然可以手动改（见下）
        ▼
⑥ 点「发布」→ buCode/buName 随表单提交 → 存进 sc_collection_daily_amount_ledger.bu_code
        ▼
⑦ 凌晨 03:40 syncJd → ES 的 buCode → 门户②各二级集团排名
```

### 自动带出**是生效的**，主数据也是全的（更正）

> ⚠️ **本文上一版说"这些公司在组织主数据里 belong_bu_code 是 NULL"——错了，此处更正。**
> 错因：我查的是 `ubm_organization` 表，而后端 Feign 走的是 `orgManagerFeignService`，读的是 **`ubm_organization_manage`**。两张同名前缀的表，只有后者是这条链路的真身，它的 `belong_bu_code` 是全的。

### 真正的原因：「所属板块」下拉根本没被禁用

页面代码（`dailyAmountStatisticsLedger/index.vue:147`）：

```html

```

`disabled` 写在了外层 `<a-form-model-item>` 上。**ant-design-vue 1.x 的 form-model-item 没有 `disabled` 这个属性，等于什么都没写**；里层真正的 `<a-select>` 是可编辑的，而且还专门配了 `@change="handleBuChange"` 处理手改。

所以实际行为是：**自动带出一个默认值，然后你可以随便改。**

`handleFormPurchaseChange` 里那个 `if (unit.belongBuCode)`：**只有取到板块才覆盖，取不到就保留上一次的值**。所以万一将来有公司主数据缺板块，会出现"换了采购企业、板块还留着上一家的"这种残留。现在主数据是全的，暂时不发作，但逻辑上应该写成"取不到就清空并提示"。

# 第五章 中间层：ES 统一货架

## 5.1 为什么要有这个货架

回到第一章的矛盾一：**数据是散的**。

如果不做货架，06 那个首页接口要怎么写？它得：
- 连 source 库查绿色通道主单+物料
- 连 source 库查寻源→方案→定标→中标 5 张表
- 跨服务调 order 服务查订单
- 连 source 库查 SAP 采集表
- 连 source 库查日金额台账
- 然后在 Java 里把五种结构的数据翻译成一种，再分 20 多个口径加总

**每打开一次首页做一次。** 慢、脆、任何一个上游改表就崩。

货架的做法是**把"翻译"这件事从查询时挪到写入时**：每天凌晨各路自己把数据翻译成统一格式堆进 ES，之后所有查询只面对一种格式。这叫 **CQRS / 读写分离** 的朴素版本，也是所有企业报表系统的标准解法。

**为什么用 ES 而不是再建一张 MySQL 汇总表？**
- 报表要多条件组合查（板块 × 企业 × 供应商 × 时间 × 来源 × 类目），MySQL 得建一堆复合索引且组合爆炸
- 要做全文模糊搜（供应商名、企业名），MySQL 的 `LIKE '%x%'` 用不上索引
- 06 首页要一次算出 50 多个不同过滤条件的求和，**ES 的 `filters + sum` 聚合一次请求就能全算完**（这正是 codex 把 53 次串行查询优化成 1 次的原理）

## 5.2 "字段合同"：18 个字段

这是 03 期最重要的产出——**五路数据都必须翻译成这 18 个字段**：

| 字段 | 含义 | 06 用它干什么 |
|---|---|---|
| `id` | 主键 | 幂等的基石 |
| `buCode` / `buName` | 板块编码/名称 | **按二级集团拆分的唯一依据** |
| `purchaseCompanyCode` / `Name` | 采购企业 | 数据权限过滤 |
| `supplierCode` / `supplierName` | 供应商 | **三笔扣减靠它认机电/北分** |
| `planCode` / `planName` | 方案/订单编号、名称 | 报表展示 |
| `materialCode` / `materialName` | 物料 | 报表展示 |
| `categoryCode` / `categoryName` | 类目 | **品类金额、四大类扣减靠它** |
| `taxTotal` | 含税金额（元） | **所有钱的来源** |
| `bookTime` | 公示/下单时间 | **所有时间窗的依据** |
| `isCentralized` | 是否集采 1/0 | **集采额 vs 平台总额的分水岭** |
| `purchaseType` | 采购业务类型 | ⚠️ **派生假字段，别用**（见下） |
| `dataSource` | 来源 ZC/FP/YC/MT/JD | **每一路各自的口径靠它** |

### ⚠️ `purchaseType` 这个字段的故事，值得单独讲

需求原文写：「集采 = 是否集采=是，**或**采购业务类型属于集团集采/二级集采/区域集采」。

听起来像两个独立条件。但查代码发现 `purchaseType` 是同步时由 `isCentralized` **派生**出来的：
```
isCentralized=1 → "集团集采"
isCentralized=0 → "分散采购"
空            → 空
```

**也就是说这个字段一点新信息都没有**，真正的"二级集采/区域集采"数据在系统里根本不存在。所以 06 的口径直接定成 **`isCentralized = 1`**，那个"或"字作废。

> 💡 **这类问题在需求评审时最值钱**：产品看到页面上有"采购业务类型"这一列，就以为它是一个独立维度。**只有扒到代码才知道它是派生的。** 你能把这一层讲清楚，产品对你的信任度会不一样——因为你阻止了一个"按一个假字段做分级统计"的错误需求。
>
> 同时也给未来留了口子：等真正的二级集采/区域集采业务上线，这个字段有了真值，统计口径再升级即可。**当前口径不是错的，是"当前数据条件下唯一正确的"。**

## 5.3 幂等：为什么可以放心重复跑

ES 写入用 `saveAll`，**主键相同就覆盖，不同才新增**。这意味着：

- 同一个时间区间跑 100 遍，结果和跑 1 遍一样
- 定时任务失败了，直接重跑，不用担心"是不是已经写进去一半"
- 要补历史数据，直接传 `2026-01-01 ~ 今天` 全量重跑

**幂等是所有同步任务的生命线。** 没有幂等，你每次补数前都要先想"要不要先删"，而删错了就是事故。

## 5.4 定时任务：五路的时间轴

**【实测】** 今天查 `scm_xxljob_test.xxl_job_info`，五个任务**全部已配置且已启用**（`trigger_status=1`）：

| 任务号 | 名称 | cron | 执行时间 | 手动补数接口 |
|---|---|---|---|---|
| 241 | 集采业务统计报表-非平台采购 | `0 10 3 * * ?` | 每天 **03:10** | `POST /e/business/source/centralizedProcurementReport/sync` |
| 242 | 集采业务统计报表-招采平台 | `0 20 3 * * ?` | 每天 **03:20** | `.../syncZc` |
| 243 | 集采业务统计报表-煤炭SAP | `0 30 3 * * ?` | 每天 **03:30** | `.../syncMt` |
| 244 | 集采业务统计报表-机电四大类 | `0 40 3 * * ?` | 每天 **03:40** | `.../syncJd` |
| 239 | 集采管理业务统计报表-云采 | `1 1 5 * * ?` | 每天 **05:01** | **无**（在同事的 order 服务里） |

任务参数格式：`应用名 - @TypeMapping - @MethodMapping - JSON参数`，例如 `source-centralizedProcurementReportService-syncJdData-{}`。

> ⚠️ **参数必须固定传 `{}`**：公共 XXL 执行器用 `split("-")` 切参数，而日期本身就带 `-`，**不能通过任务参数传日期**。`{}` = 同步前一天。要补跑指定区间，一律走上表最右列那个手动 HTTP 接口。

```

周二白天：03 报表页能查到了

```

# 第六章 展示层的三张脸

同一个货架，三个页面，**受众完全不同**。这是产品设计上很标准的分层。

## 6.1 03 报表页 —— 给经办人对账用

- 地址：`/procurementScheme/index.html#/reportForms/centralizedProcurement`
- 内容：15 列明细表格 + Excel 导出
- 查询条件：采购企业、所属板块、公示/下单时间区间、供应商名称
- 后端：`scm-report-all`，实时查 ES
- **有数据权限**：按登录人可见的 `purchaseCompanyCode` 过滤

**设计意图**：这是**"证据层"**。领导在驾驶舱上看到一个数觉得不对，就得有地方能一行一行看明细、能导出来对账。**任何汇总数字，都必须有一个能下钻到明细的页面兜底**——否则数字没人敢信。

**为什么这一层要有数据权限，而首页没有？** 因为明细里有供应商、金额、物料，是商业敏感信息；而首页是全集团口径的汇总数，本来就是要给所有人看的宣传数字。**颗粒度越细，权限越严** ——这是数据权限设计的通则。

## 6.2 集采驾驶舱 —— 给领导看的大屏

- 前端：`02zhaocai-front/scm-vue-all-cockpit`，页面 `procurementCatalogMgt`

- **另外 4 个块没改**：`centerHeader`（中心头部数字）、`categoryAmount`（类目分项金额）、`doRate`（计划执行率）、`situA`（情况分析）——**仍读死缓存 `sc_collection_data`，数据停在 2024-12~2025-11**

> ⚠️ **看到大屏上有些块是去年的数，不是 bug，是范围外。** 这一点验收前一定要跟产品说清楚，否则会被当成你改坏了。

## 6.3 06 集采门户首页 —— 新做的门户

- 前端：`02zhaocai-front/scm-vue-hpc`，路由 `/procurementPortal`
- 打开页面 **一次请求** `POST /e/business/source/centralizedProcurementPortal/overview`，各卡片共享这一份结果
- 后端：`CentralizedProcurementPortalServiceImpl`，一次 ES `filters + sum` 聚合算完全部数字

五大块：

| 块 | 内容 | 数据来自 |
|---|---|---|
| ① 核心指标 | 当月/季度/年度集采额、平台总额、年度集采率 | ES 聚合 |
| ② 集采规模 | 6 个二级集团 + 直管单位的交易额和交易率 | ES 聚合，按 `buCode` 拆 |
| ③ 一级集采品类 | 煤炭/钢材/电缆/润滑/轴承/办公 6 张卡 | ES 聚合，按来源+类目 |
| ④ 大宗煤炭专项 | 日/月/季/累计交易额 + 坑口指标 + 12 月煤价 | 金额来自 ES；后两个调 `kengk/mt` |
| ⑤ 钢材专项 | 日/月/季/累计 + 12 月钢价 + 螺纹/中厚板 | 金额来自 ES；后三个调 `gc` |

> **设计意图**：这是**"门面层"**。它和驾驶舱的差别是——驾驶舱是给领导在会议室大屏上看的（强调视觉冲击），门户首页是给所有员工打开系统就看到的（强调"集团在做什么、做得怎么样"）。**同样的数据，两种叙事。**
>
> 关键设计决定：**趋势/坑口块两个页面共用同一套接口，不各存一份**。这避免了"大屏说 600、首页说 580"这种最伤信任的问题。

# 第七章 口径的十个"为什么"（本文核心）

前面讲的是"数据怎么流"，这一章讲**"为什么这么算"**。这才是你说的"对业务对产品的了解"。

## 7.1 为什么起点是 2026-01-01、截止是"查询日前一天"

**起点固定 2026-01-01**：这是本年度考核周期的起点。代码里写成常量 `BUSINESS_START_YEAR = 2026` **【实测】**，而不是"当前年份"——所以 2027 年查询，年度/累计**仍然从 2026-01-01 起算**。

> ⚠️ 这是一个**有意为之但会在明年爆炸**的设计。codex 用 2027 年的日期实测验证过这个行为。跨年前必须问产品："2027 年的年度集采额，是从 2027-01-01 重新算，还是继续累计？"——两种答案都合理（前者是年度考核，后者是项目累计），**必须问，不能猜**。

**截止"查询日前一天 24:00"（左闭右开 `[起, 查询日 00:00)`）**：三个理由，一个比一个实在：

1. **数据还没到**。定时任务凌晨才跑，今天的数据要明天才进货架。统计今天 = 统计一个必然不完整的数。
2. **数字要稳定**。如果统计包含今天，上午看和下午看数字不一样，领导会问"怎么变了"。**报表的第一美德是"同一个日期，什么时候看都一样"。**
3. **符合业务直觉**。"截止昨天"是所有日报周报的通用表达。

> 由此产生一个**每月 1 号的固定现象**：当月/当季金额显示 0（因为窗口 `[本月1日 00:00, 今天 00:00)` 是空的）。**这是口径设计，不是 bug。** 提前跟产品打好招呼。

## 7.2 为什么要"扣三笔" —— 全篇最重要的一段

这是整个 06 需求的灵魂。理解了它，你就理解了这套系统的核心业务矛盾。

### 问题的产生

回到第一章的矛盾二：**同一笔钱被记了两遍**。

想象一个具体场景：

> 唐山冀东水泥（水泥集团旗下）要买 100 万的钢材。集团规定钢材必须走机电公司集采。于是：
> - **机电公司**在自己的日金额台账里录了这 100 万（→ JD 那一路进货架）
> - **唐山冀东水泥**觉得"这也是我的采购啊"，在绿色通道里也补录了这 100 万（→ FP 那一路进货架）
>
> **货架上现在有 200 万，但实际只花了 100 万。**

同样的事也发生在云采上（YC 里买了机电四大类的东西，机电台账也报了一遍）。

### 解法：保留官方账，减掉企业自报的

产品定的规则是：**JD/MT 是官方口径（执行单位报的，权威），FP/YC 里重复的部分减掉。** 于是有了三笔扣减：

| 记号 | 减什么 | 精确条件 |
|---|---|---|
| **D1** | FP 里的机电四大类 | `dataSource=FP` & `isCentralized=1` & 供应商=机电公司(`911302300759817983`) & 类目 ∈ 四大类 |
| **D2** | FP 里的北分煤炭 | `dataSource=FP` & `isCentralized=1` & 供应商=北分(`9111010577406207XG`) & 类目=1001 & 板块=BU002 |
| **D3** | YC 里的机电四大类 | `dataSource=YC` & 供应商=机电公司(`CN13000363`) & 类目 ∈ 四大类（**不加集采条件**，因为云采全是集采） |

### 三个必须理解的细节

**① 为什么保留 JD/MT 而不是保留 FP/YC？**

因为**执行单位的账更准**。机电公司知道自己一共卖了多少钢材给集团内部；而唐山冀东水泥只知道自己买了多少，还可能填错、漏填、重复填。**统计上永远优先相信"上游总账"而不是"下游分账"。**

**② 为什么 D2 必须锁死"供应商=北分"，不能用"煤炭+水泥集团"推断？**

产品 2026-08-04 明确了：**FP 里的煤炭可能来自北分以外的供应商**。也就是说水泥集团的某个厂可能自己从别的煤矿买了煤（不走北分集采），这笔钱是**真实的、不重复的**，不能减。

> 💡 **这就是"扣减条件必须写全，不能靠推断"的原因。** 少写一个条件 `supplierCode=北分`，就会把一笔真实交易当成重复账减掉——**凭空少算一笔钱**。这种错误在报表里最难发现，因为总数看起来"挺合理"。

**③ 为什么算各二级集团时，扣减也要"在集团内部扣"？**

算水泥集团的时候，减的是"水泥集团里的 FP 机电四类"，不是全公司的。这样**六个集团加起来 = 年度集采总额**，账才对得上。

而 D2（北分煤炭）**只可能扣水泥集团**（因为条件里写死了 `buCode=BU002`），算其他集团时 D2 直接返回 0。**【实测代码确认】** `d2Query()` 里固定 `BU_CEMENT = "BU002"`。

### ④ 一个"不对称"的边角（cc 已向领导提过）

- 集采额 = `Σ(是否集采=1)` − 三笔
- 平台总额 = `Σ(全部，不分集采)` − 三笔

**底数不同，扣减相同。** 严格说，如果存在一笔"非集采的机电四类重复账"，它会留在平台总额的底数里没被减掉（因为 D1/D3 带了集采条件）。

这是需求原文的写法，真实数据里几乎碰不到。**照原文写是对的**，但你要知道这个边角在哪——将来数据量上来出现偏差，你能一眼定位。

## 7.3 为什么集采率的分母是"平台总交易额"

`年度集采率 = 年度集采交易额 ÷ 平台总交易额 × 100%`

分母是**全平台所有成交额（不分是否集采）**，再减三笔重复。

**为什么这个分母是对的？** 因为集采率要回答的问题是：**"公司花出去的所有钱里，有多大比例是通过集中采购花的？"**

- 分子 = 集中采购花的钱
- 分母 = 一共花的钱
- 比值 = 集中度

如果分母只算"平台上的集采"，那这个比值永远是 100%，毫无意义。如果分母不减重复，分母虚高，集采率被人为压低。

**【实测的一个真实教训】** test 环境里曾有一条 3.6 亿的 FP 测试垃圾数据（唐山冀东机电、无类目、无集采标志）。它进不了分子（没勾集采），却全额进了分母 —— 结果集采率从应有的 **95.73%** 被压到 **27.86%**。

> 💡 **这件事的普适意义**：**分母是最危险的位置**。分子错了，那一项数字错；分母错了，页面上所有比率全错。做任何"率"的时候，先把分母的口径钉死，并且**优先排查分母里有没有垃圾数据**。
>
> 还有一个操作层面的坑：oc 当时发现**只删 ES 不够**——FP 的定时任务会从源表 `sc_supplier_green_channel` 再同步回来。**必须连源表一起处理。** 这是所有"同步型"数据的通则：ES 是副本，源表才是真身，删副本没用。

## 7.4 为什么按 `buCode` 而不是板块名称

因为**板块名称是脏的**。**【03 期实测】** 同一个 BU002，主表里的名字有"冀东水泥"、有"水泥集团"、有 NULL；BU006 的名字是"北京金隅地产开发集团有限公司"。

所以同步时的做法是：**取 `bu_code`，去 `Owningplate` 字典换成标准名再存**。查询时一律用 `buCode` 精确匹配（`termQuery`）。

> 💡 **通用原则（行业惯例，本项目处处遵守）：编码用来查，名称用来看。**
> - 编码：稳定、唯一、不会被改，适合做筛选条件和外键
> - 名称：会变（改名、合并、全称简称），适合展示
> - 所以业务表普遍**双存**：`execute_unit_code` + `execute_unit_name`
>
> **为什么名称也要存一份，不能查的时候再去字典换？** 因为**历史快照**。三年前这笔采购的执行单位叫 A 公司，今年改名叫 B 公司了——报表上应该显示哪个？多数业务场景要显示**当时的名字**。存下来就有了历史真相。

## 7.5 为什么"直管单位"是减出来的

```
直管单位交易额 = 年度集采总额 − 六个点名集团之和
```

而不是"把 BU001/003/009/010 加起来"。

**为什么？** 因为**"直管单位"的定义是"不属于那六个二级集团的所有单位"**，这是一个**开放集合**：明天新成立一个板块 BU011，用加法就会漏掉它，用减法自动包含。

**更重要的是：减法保证了"六个集团 + 直管 = 总额"这个恒等式永远成立。** 领导拿计算器一加，必须等于总数——**报表最忌讳"分项加起来不等于合计"**。

## 7.6 为什么一家公司要用四个编码去筛

回到矛盾三。机电公司这一家公司，在系统里有**至少五个身份证**：

| 编码类型 | 值 | 好比 | 谁发的 |
|---|---|---|---|
| 统一社会信用代码 | `911302300759817983` | **身份证号** | 国家工商 |
| SCM 编码（`company_id`） | `SCM00002105` | 招采系统的工牌号 | 本系统 |
| 平台码（`company_code`） | `JYJT0002472` | 金隅交易平台会员号 | 交易平台 |
| MDM 码 | `CN13000363` | 集团主数据花名册工号 | MDM 主数据平台 |
| 组织编码 | `12300000` | 集团组织机构树里的编号 | 集团组织 |

而**五路数据各自存了不同的那一个**：

| 在哪一路挑机电公司 | 用什么码 |
|---|---|
| FP 非平台 | `911302300759817983`（统一社会信用代码） |
| YC 云采 | `CN13000363`（MDM 码） |
| ZC 招采 | `JYJT0002472`（平台码） |
| JD 台账 | `12300000`（组织编码，整路就是机电公司） |

**为什么不统一？** 因为**这些数据本来就来自不同的系统，每个系统写入时只知道自己那套码**。绿色通道的表单让人填统一社会信用代码（工商信息），云采订单从 MDM 拿供应商，招采从自己的会员库拿。要统一，得让每个上游系统都去查一次主数据——那是主数据治理项目，不是一个报表需求能干的。

**所以 06 的设计是：不追求统一码，每一路各用各的码筛。** 这是**务实的妥协**，也是正确的工程判断。

### ⚠️ 一条你必须记住的铁律

> **绝对不要用 SCM 编码（`company_id`，`SCM000...`）当筛选键。**
>
> 产品 2026-08-03 确认：**每个环境的 SCM 编码是各发各的**。test 上的 `SCM00002105`，到 UAT/生产可能是别的值。写死进代码 = 上生产必然筛空。
>
> SCM 编码只能用于"人看的展示"，不进筛选逻辑。（这条已经进了我的记忆库，是这套系统里最容易犯的致命错误之一。）

另外还有个反直觉的事实：**北分根本没有 SCM 编码**。它没进"供应商主档"（它是金隅自己的单位，是在煤炭 SAP 数据里作为供应商出现的），身上只有 MDM 码 `CN11005095`。所以产品说"都是 SCM 开头"这句话，对机电成立、对北分不成立。

## 7.7 为什么"品类金额"只认机电台账那一路

③ 里的钢材/电缆/润滑/轴承四个品类，公式是 `Σ { JD & 对应类目 & 年度 }` —— **只取机电台账，不算招采/云采里的同类目**。

一开始我也觉得反直觉：招采平台上明明也有人买电缆，为什么不算？

**答案在"集团一级集采品类"这个标题里。** 这一块回答的问题不是"公司买了多少电缆"，而是 **"集团一级集中采购这个动作，在各品类上做出了多少量"**。而集团一级集采的执行单位就是机电公司（四大类）和北分（煤炭）。**别的公司自己在招采平台上买的电缆，那是分散采购或二级集采，不属于"集团一级集采"。**

所以这一块的口径其实是：**煤炭 = MT 那一路（北分执行）；四大类 = JD 那一路（机电执行）；办公用品 = 云采（集团商城）。六个品类，三个执行主体，完整覆盖了"集团一级集采"的全部形态。**

> 💡 **这就是我说的"业务理解比技术理解值钱"的例子。** 从技术角度看"钢材金额"应该是"所有来源里类目=1501 的和"，从业务角度看它是"机电公司执行的钢材集采量"。**同一个字面表述，两种口径，差之千里。**

## 7.8 为什么趋势类不进 ES（回顾）

见第四章 §4.1。一句话：**要和别人相加的进货架，自己就是答案的直接读表。**

## 7.9 为什么煤炭按净额

SAP 有退货负数，求和不过滤。理由：**SAP 记的是入库净额，会计惯例就是正负相抵**。你退回去的煤，不该算在"今年买了多少"里。

## 7.10 为什么"轴承"现在恒等于 0（一个有意思的口径变更）

这是一个**产品改口径、开发跟着改、结果数字变成 0** 的完整案例，值得复盘：

- **2026-08-04 定稿**：轴承 = `2502 及其所有子类`（含 250201）
- **2026-08-06 产品改口**：机电四大类**一律精确匹配、不含子类** → 轴承 = `2502` 精确
- **后果**：**【实测】** 当前数据里轴承只有子类 `250201`，没有精确 `2502` → **轴承金额恒为 0**
- 产品已知悉并接受

**为什么产品要改成精确匹配？** **【推测】** 因为"前缀匹配"有风险：`2502` 前缀会匹配到 `250201`、`250299`……如果将来类目树调整，某个不属于轴承的类目编码恰好以 2502 开头，就会被误算进来。**精确匹配虽然现在算不出数，但它是"确定的 0"，而前缀匹配是"不确定的数"。** 在成绩单场景下，宁可要确定的 0。

> 同理还有钢材：`1501` 精确，`1502`（水泥）、`1504`（小五金）、`15010101`（方钢）都不算。

# 第八章 招采系统的通用设计考量

前面讲的是这个需求特有的逻辑。这一章讲**跨需求的、你在任何企业采购系统里都会遇到的设计惯例**。这些是"行业常识"，懂了以后你看别的模块会快很多。

## 8.1 编码 + 名称双存

已在 §7.4 讲。**编码查、名称看、双存留快照。**

## 8.2 逻辑删除

所有业务表都有 `delete_sign`（0 正常 / 1 已删）。删除 = 打标记，不是真删。

**为什么？** 采购数据是**审计对象**。物理删除意味着"这条记录曾经存在过"这件事被抹掉了，纪检审计过不去。逻辑删除既满足了"页面上看不见"的需求，又保留了完整证据链。

**代码上的实现**：`bootstrap.yml` 里配了 MyBatis-Plus 全局逻辑删除字段 `deleteSign`，**所有查询自动加 `delete_sign=0`**，开发时根本不用写。

> ⚠️ **踩过的坑**：`sc_source_collection` 这张表**没有** `delete_sign` 字段，而库里 2792 行的 `delete_sign` 列**全是 NULL**。一旦手写 `delete_sign=0` 就一条都查不到。**用框架自动能力之前，先确认这张表有没有那个字段。**

## 8.3 字典标准化

板块、类目、状态这些"有限取值"的字段，全部走 UBM 数据字典（`scm_ubm_test.ubm_dict`）。

配置地址：`http://10.0.54.16:30370/ubm/index.html#/basicMgmt/dictionary`

**为什么？** 让业务人员能自己维护取值范围，不用改代码发版。代价是**跨环境要各配一份**（发版时 SQL 和字典项都要交给负责人执行）。

## 8.4 数据权限

03 报表页开了数据权限：按登录人可见的 `purchaseCompanyCode` 过滤。

**为什么采购系统的数据权限特别重要？** 因为采购数据里有**价格**。A 公司知道 B 公司同样的钢材买多少钱，会引发内部矛盾；供应商知道你给别家什么价，谈判筹码就没了。**所以采购系统天生是"越细的数据，权限越严"。**

顺带说一个本项目的鉴权特点（`ai-docs/工作规范与习惯.md` 已记）：**平台接口登录即可调**（permitAll 白名单 + `anyRequest().authenticated()`），**菜单权限只管导航显隐**。所以没配菜单也能用 curl 先测接口——这对开发验证很方便，但也意味着**接口层面的数据权限必须自己在代码里做**，不能指望菜单权限兜底。

## 8.5 导出模板配置化

Excel 导出的列不写在代码里，配在数据库表 `scm_ubm_test.scm_simple_template / _sub`。

配置地址：`http://10.0.54.16:30370/platform/index.html#/statics/list`

**为什么？** 产品经常要改列顺序、改列名。配置化之后不用发版。

> ⚠️ **踩过的坑（codex 2026-08-05）**：导出最终是按模板 `field_name` 从 Fastjson 对象取字符串。原始 `Date` 字段可能在 Excel 里变成 `Thu Jul ... CST ...`。**日期类问题必须实际下载 Excel 检查单元格，不能只看接口 JSON。**

## 8.6 "保存即发布" vs "审批流"

同一套系统里两种模式并存，判断标准是**这条数据会不会影响别人**：

| 模式 | 用在哪 | 为什么 |
|---|---|---|
| **审批流** | 非平台录入（绿色通道）、招采定标方案 | 涉及钱的合规性，必须有人背书 |
| **保存即发布** | 台账1/3/4 | 日报性质，填的人就是权威，时效 > 准确 |

## 8.7 幂等与补数

已在 §5.3 讲。补一条：**手动补数接口的存在本身就是一种设计**——定时任务总会失败（网络、发版、上游没数据），必须有一个"人工重跑指定区间"的口子。做同步类需求，**永远要同时提供"定时入口"和"手动入口"，两个入口汇合到同一个核心方法**（03 期就是这么做的，不维护两份算法）。

## 8.8 一个反面教材：靠字符串匹配的业务协议

§4.3 的价格趋势指标名。**能用编码/字典的地方，绝不用中文字符串做匹配键。**
