# 答复：煤炭 SAP —— 集采报表页面查不到，为什么报表里却有一堆 SAP 数据

> 对应提问：`01提问煤炭.md`
> 答复日期：2026-08-07 ｜ 工具：cc
> 全部结论都是**今天在 test 环境现查现验的**，不是翻旧文档抄的。查了：ES 索引、MySQL 源表、以及你贴的那个接口本人。

---

## 一、一句话结论

**你没理解错，逻辑是对的。**

“页面查不到” 和 “报表里有 503 条 SAP” 这两件事**同时成立且互不矛盾**，因为它们根本不走同一条路：

- 你点的那个《集采报表》页面 → 读的是 **ES 索引**，而 test 环境上这个索引是**空的（0 条文档）**，所以你查什么都查不到，跟 SAP 没关系。
- 我们做的《采集管理业务统计报表》→ **绕过了那个页面和 ES，直接读底层 MySQL 表**，所以数据一条不少。

一句话：**页面是空的，但数据是有的。我们取的是数据，不是页面。**

## 三、实测证据（今天现查的，可复现）

### 证据 1：那个接口**去掉所有筛选条件也是 0 条**

我用你贴的同一个接口在 test 上打了三枪：

| 请求条件 | 返回 |
|---|---|
| `queryTimeArr: 2026-01-01 ~ 2026-09-30` + `dataSource: SAP`（你的原请求） | `totalCount: 0` |
| 同样时间窗，**去掉 dataSource** | `totalCount: 0` |

## 四、那个页面为什么会空？（顺带查清了，跟我们无关）

看了 `CollectionMetaServiceImpl` 的推送逻辑，它是这么干的：

```java
// 只捞 es_code = '0'（意思是“还没推过 ES”）的记录，推完把 es_code 改成 1
spQuery.in(SourceCollection::getEsCode, Arrays.asList(esCodeArr));  // esCodeArr 默认 {"0"}
```

再查库：

```sql
SELECT es_code, COUNT(*) FROM sc_source_collection GROUP BY es_code;
-- es_code = 1 : 2792 条（全部）
```

**2792 条全部被标记成“已推送”了，但当前索引里一条都没有。**

推断得很清楚：历史上确实推过（`index_web_collection_meta_test3` 那 2773 条就是老索引的遗骸），后来索引名换了 / 索引被重建过，数据没跟着迁过来。而因为源表的 `es_code` 已经全是 1，**再手动跑一次推送任务也捞不到任何数据**，这个索引就再也自己补不回来了 —— 除非有人手动把 `es_code` 改回 0，或者调用时显式传 `esCodeArr=1`。

另外还有个坑：老索引 `test3` 的 mapping 里**压根没有 `dataSource` 这个字段**（`@Document(dynamic = Dynamic.FALSE)`，新加的字段不会自动建）。所以就算把服务指回 test3，你按“数据来源=SAP”筛，照样是 0 条。

> **这是 test 环境的历史遗留问题，不是我们 03/06 期引入的，也不影响我们的功能。**

## 五、这件事对 06 取值需求有什么影响

**结论：不影响首页的煤炭数字能不能算出来，但影响你在 test 上能看到什么数。**

代码里煤炭指标是这么取的（`CentralizedProcurementPortalServiceImpl`）：

```java
addMetric(metricFilters, "coal_day",       srcCat(dayStart,     todayStart, SRC_MT, CAT_COAL));
addMetric(metricFilters, "coal_month",     srcCat(monthStart,   todayStart, SRC_MT, CAT_COAL));
addMetric(metricFilters, "coal_quarter",   srcCat(quarterStart, todayStart, SRC_MT, CAT_COAL));
addMetric(metricFilters, "category_coal",  srcCat(yearStart,    todayStart, SRC_MT, CAT_COAL));  // 累计
```

即：**从我们自己的报表货架取，条件 = 数据来源 MT + 类目 1001 煤炭 + 时间窗**。走的是路线 B，跟那个空页面没有半毛钱关系。

⚠️ 但有个**验收时一定要提前说清楚**的事：

**test 上 SAP 数据只到 2026-01-27，之后再没推过新数据。** 今天是 2026-08-07，所以首页的煤炭四个数会长这样：

| 首页指标 | 时间窗 | test 上的实际结果 |
|---|---|---|
| 日交易额（查询日前一天） | 2026-08-06 | **0** |
| 月交易额（当月1日~昨天） | 2026-08-01 ~ 08-06 | **0** |
| 季度交易额（本季度~昨天） | 2026-07-01 ~ 08-06 | **0** |
| 累计交易额（2026.1.1~昨天） | 2026-01-01 ~ 08-06 | **14,121.28 万元** ✅ |

**这是数据没有，不是功能坏了。** 别到时候演示的时候被问“怎么日/月/季都是 0”答不上来。

## 七、给你留个判断方法（下次再遇到类似的）

以后再碰到“需求说取某某页面，但那个页面查不出来”，按这三步走，别急着怀疑自己：

1. **先把筛选条件全去掉再查一次**。如果不带条件也是 0 → 问题在“这个页面/这个数据源本身”，不在你的筛选条件。
2. **再去数据库看源头有没有数**。页面是页面，数据是数据，中间隔着同步任务，同步任务经常是坏的。
3. **确认我们的功能到底读的哪一条路**。需求写的“取某某报表”多数是**业务口径**（告诉你数据是哪一块业务的），不是**技术口径**（不是让你调那个接口）。往下扒到表，通常更稳。

这次三步走完，结论就是：你的理解是对的，页面是坏的，数据是好的，我们的报表是准的。
