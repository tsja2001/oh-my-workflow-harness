## 3. 同事对不上的两大疑点（按概率排序）

### ① 报表导出有权限过滤——**最上游，先查这个**（10c 调查新发现）

- UAT 配置实测：Nacos `scm-report-web-uat.yaml`（group=common, tenant=scm-jdsn-uat）`commonConfigs.source.settings.usePerssion: true`。
- 报表查询/导出（`SourceMetaQueryServiceImpl.getCentralizedProcurementPageList`，L139）在 `usePerssion=true` 时按**当前登录人角色**过滤采购企业：平台角色→全量；领导角色→本板块下属企业；公司角色→本公司。
- **实测**：用 admin 账号调 UAT 报表分页接口返回 `totalCount=0`（ES 明明 160 条）——过滤真实生效。
- **overview（首页）不做任何权限过滤，全量读 ES**。所以同事的账号若不是"平台"角色，他导出的 Excel 只是部分企业的数据，底数就和首页不一样，**怎么算都对不上**。
- test 环境那位测试没测出问题，可能他的账号权限是全量。
- 排除方法：让同事看导出的 Excel 一共多少行（全量=160 条）。

### ② 漏扣 D3（云采机电公司四大类）— 原①，仍最可能（在无权限问题时）
- 他会算出：`35,969.88 / 10000 = 3.60 万`
- 与页面差：`3.60 − 2.28 = 1.32 万`（精确 1.314028 万 = 13,140 元）
- 原因可能：报表导出的 Excel 里**供应商只有名字没有 MDM 码**，他无法识别"唐山冀东机电"对应云采里的 `CN13000363`；或者他根本没意识到要扣云采。还有一层：**导出的类目编码是 6~8 位末级码**（YC 存 `15010101`/`250201`），代码按**前缀**匹配；同事若按"类目编码=1501/1701/2302/2502"**精确**筛，会漏掉全部 YC 机电四条 → 同样漏扣 D3。
- **这是 test 环境从没出现过的坑**——test 上 YC 没有机电公司供应商（D3 恒为 0），所以前两轮对账都没暴露；UAT 同事造了云采机电公司数据后才浮出来。

### ③ 把"当月"窗口搞错了一天
- 若他把查询日当成 8-12（即他自己昨天导的表），窗口会变成 `[8-1, 8-12)`，**少算 8-12 当天的 3 条 / 3,000 元**。
- 影响很小（最多差 0.03 万），不是主要差异。
- **实测 UAT 没有 8-13 当天数据**，所以"今天才查"和"昨天查"窗口差异只在这一笔 8-12 的 3,000 元上。

### ④ 把"或采购业务类型"那句话当真
- 需求 a 原文写"是否集采=是 **或** 采购业务类型属于集团/二级/区域集采"。
- **实测 UAT 的 `purchaseType` 字段是 `isCentralized` 的派生字段**（1→集团集采、0→分散采购、空→空），两者**完全一致**，那个"或"不会多捞任何一条。所以这不是差异来源（与 test 结论一致）。
