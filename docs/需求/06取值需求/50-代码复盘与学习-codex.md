## 一、用一句话理解整个项目

这部分项目的核心是：

> 把五个业务渠道产生的交易明细，翻译成同一种格式放进 ES；报表和首页再从 ES 按不同规则筛选、汇总和去重。

可以把 ES 想成一个统一货架。FP、ZC、YC、MT、JD 是五个进货口；03 需求负责把货摆上架，06 需求负责按标签数货。

```text
FP 非平台 ─┐
ZC 招采 ───┤
YC 云采 ───┼─> 统一 ES 明细 ─┬─> 集采统计报表（查明细）
MT 煤炭 ───┤                  ├─> HPC 首页（算汇总）
JD 机电 ───┘                  └─> 对账/导出
```

## 二、五路数据分别是什么

### 1. FP：非平台录入

企业没有走完整平台采购流程，而是在绿色通道补录一笔采购。

大致链路：

```text
sc_supplier_green_channel 主单
        +
sc_supplier_channel_projects 物料明细
        ↓
scm-source-chase 同步
        ↓
统一 ES，dataSource=FP
```

一条物料明细写一条 ES。它在本需求里最麻烦，因为历史记录的“是否集采”和“类目编码”填得很少。

### 2. ZC：招采平台

这是正常走招标、询价、公示的采购。

大致链路：

```text
寻源单 sc_source
  → 定标结果 sc_deal_result
  → 中标供应商 sc_deal_detail
  → 中标物料 sc_deal_product
  → 统一 ES，dataSource=ZC
```

是否集采来自采购方案的集采标志。首页公式并不是“写死包含 ZC”，而是 ZC 记录满足集采资格后自然被统计进去。

### 3. YC：云采

云采订单在订单中心产生，所以不由 Source 仓写 ES，而由：

`01zhaocai-end/scm-order-all/scm-order-report`

写入相同 ES，`dataSource=YC`。

这说明“一个 ES 索引”不等于“只有一个服务写”。Source 和 Order 各有自己的 Model/Repository，但字段合同必须保持一致。

### 4. MT：煤炭 SAP

煤炭相关收货/入库数据先进入 `sc_source_collection`，统一报表同步时取 SAP 来源记录，写成 `dataSource=MT`。

当前代码约定 MT 是煤炭官方来源，所以去重时保留 MT，减掉企业在 FP 重复补录的北分煤炭。

### 5. JD：机电四大类台账

来自 `sc_collection_daily_amount_ledger`，取集采执行单位为机电公司的台账，写成 `dataSource=JD`。

这是钢材、电缆、润滑剂、轴承等官方统计来源。去重时保留 JD，减掉 FP/YC 中重复出现的机电交易。

## 三、统一 ES 里有什么

索引是：

`index_centralized_procurement_report_test`

核心字段可以分成五组：

| 作用 | 字段 |
|---|---|
| 唯一定位 | `id` |
| 时间与金额 | `bookTime`、`taxTotal` |
| 来源 | `dataSource` |
| 是否属于集采 | `isCentralized`、`purchaseType` |
| 汇总维度 | `buCode/buName`、`categoryCode/categoryName`、`supplierCode/supplierName` |

06 的所有时间筛选都应使用 `bookTime`。不同来源原表里的“公示时间、下单时间、入库日期、统计日期”会在同步时统一映射到它。

要特别记住：字段名字统一，不代表字段内容已经统一。现在 `supplierCode` 在不同来源的实际编码体系不一致，这是本需求最关键的数据合同问题。

## 四、为什么要减三笔

假设有一笔水泥集团采购的钢材：

1. 企业为了业务留痕，在非平台 FP 录了 100 万；
2. 机电公司在官方日金额台账 JD 又发布了 100 万；
3. 两路都进入统一 ES，直接求和会得到 200 万；
4. 公式减掉 FP 中“机电公司 + 钢材”的 100 万；
5. 最终保留 JD 的 100 万。

煤炭也是同理：

```text
FP 北分煤炭补录 + MT 煤炭 SAP 官方记录
                         ↓
减 FP，保留 MT
```

所以这不是把真实交易抹掉，而是在选择“同一笔业务以哪一路为准”。

### D2 为什么必须精确到“北分”

D2 不是“扣掉 FP 里所有煤炭”，而是扣掉产品公式定义的“FP 北分煤炭”这一整组金额。产品明确不要求再与 MT 逐笔验证。定稿条件应同时满足：

```text
数据来源 = FP
+ 是否集采 = 1
+ 供应商代码 = 9111010577406207XG（北分 FP 统一社会信用代码）
+ 类目 = 煤炭 1001
+ 板块 = 水泥集团 BU002
```

“MT 整路永远只有北分”只能用来简化 **MT 官方数据**的筛选；FP 是通用人工补录通道，不能由“煤炭 + 某个板块”推断供应商就是北分。

> **2026-08-04 产品确认：FP 里的煤炭确实可能有北分以外的供应商。**这使上面的风险从“将来可能发生”变成已确认的业务事实；修复前的 D2 查询条件因此不成立。

修复前实现有两层偏差：

1. 没有筛“供应商 = 北分”，所以水泥集团从其他供应商买的 FP 煤炭也会被当重复数据误减。
2. 分集团计算时，代码把 D2 固定的 BU002 换成“当前正在算的集团编码”；因此地产 BU006、新材 BU005 等集团的 FP 煤炭也可能被误减。按定稿，D2 只可能归属 BU002，其他集团的 D2 必须是 0。

用一组简化数据看得最清楚：

| ES 记录 | 金额 | 是否命中产品扣减条件 | 正确处理 |
|---|---:|---|---|
| MT 北分煤炭，BU002 | 100 万 | 官方数据 | 保留 |
| FP 北分煤炭，BU002 | 100 万 | 是 | D2 减掉 |
| FP 其他供应商煤炭，BU002 | 80 万 | 否（供应商不符） | 必须保留 |
| FP 地产集团煤炭，BU006 | 50 万 | 否（板块不符） | 必须保留 |

原始求和是 330 万，正确 D2 只减第二行 100 万，最终应是 230 万。修复前代码算总额时会多减第三行 80 万；算地产集团时又会把第四行 50 万减掉。

2026-08-04 已完成修复：D2 精确筛 `supplierCode=9111010577406207XG`，查询板块固定 `BU002`；计算非水泥集团时直接返回 0。目标 Java 文件隔离编译无错误，但仍需真实或受控样本验证运行命中。

当前 test ES 在核对时没有任何“FP + 集采 + 煤炭”记录，因此正确 D2 和错误 D2 现在都等于 0，数字对账自然相同。这只证明“错误分支还没被当前数据触发”，不证明条件写对了。

### 不是找一个“全系统通用编码”，而是按数据来源确认稳定识别键

同一家公司进入不同来源时，`supplierCode` 的编码体系并不相同。SCM 公司编码又会随环境变化，所以不能拿一个 `SCM000...` 写死到所有查询里：

| 去重项 | 在哪一路识别公司 | 该路实际使用的稳定键 | 当前结论 |
|---|---|---|---|
| D1 非平台机电四类 | FP | 统一社会信用代码 `911302300759817983` | 主数据和现有 FP 数据均已确认 |
| D2 非平台北分煤炭 | FP | 统一社会信用代码 `9111010577406207XG` | 产品确认；test 当前无样本，待受控验证 |
| D3 云采机电四类 | YC | MDM 编码 `CN13000363` | 主数据映射已确认；test 当前无命中是数据现状，不是口径缺失 |

`CN11005095` 是煤炭 SAP 来源里看到的北分编码，不能用于 FP。FP 同步代码把“三证合一/统一社会信用代码”写入 ES 的 `supplierCode`，产品最终确认 D2 使用 `9111010577406207XG`。

进一步核查 test 原表得到：`sc_supplier_green_channel.three_in_one_id_code` 填充率为 99.4%，因此用统一社会信用代码精确筛选在数据结构上可行；但该字段由 FP 页面人工输入，页面只校验必填和最大 50 字符，test 已出现 `123` 等脏值。代码不能改用供应商名称模糊匹配兜底，业务侧应保证北分录入时使用同一个规范代码。

当前 test 的 FP 原表与统一 ES 都没有北分煤炭样本；供应商主档、UBM 来源供应商、公共资源供应商等现有 test 表也没有查到 `9111010577406207XG`。该值为产品/主数据确认值，长度和校验位有效，但修复后仍需用一笔受控 FP 北分数据验证查询会命中。

产品已在 2026-08-04 明确：D1/D2/D3 只按各自公式条件汇总扣减，不要求与 JD/MT 逐笔验证是否真的重复。因此开发不需要订单号、合同号等跨来源判重字段；三项扣减的供应商识别口径现在全部闭环。

这里也解释了为什么开发交接里“煤炭整路 MT 都是北分，所以不需要北分编码”的结论只对一半：查询 MT 官方煤炭金额时确实不用筛供应商；但从通用 FP 通道中扣除“北分重复补录”时，仍然必须识别北分。两种用途不能合并成同一个结论。

## 五、首页各块怎么从同一套逻辑长出来

### 1. 核心金额

月、季、年只是开始时间不同：

```text
月：本月 1 日 → 查询日 0 点
季：本季度 1 日 → 查询日 0 点
年：2026-01-01 → 查询日 0 点
```

每个时间段都执行：

```text
集采资格内总额 - 三笔重复额
```

### 2. 集采率

```text
年度调整后集采交易额
────────────────── × 100%
   平台总交易额
```

平台总额是否包含非集采交易、三笔扣减是否也走年度范围，是当前还要问产品的口径。

### 3. 各二级集团

不是另做一套算法，只是在公共算法前加一个板块筛选：

```text
水泥集团 = 公共算法 + buCode=BU002
地产集团 = 公共算法 + buCode=BU006
……
直管单位 = 公共算法 + buCode 不在六个单列集团内
```

为什么 C7 可以解决：当前 JD、MT、FP、YC 明细都可以带 `buCode`，所以相同板块里的重复数据能在板块内部互相抵消。将来如果某路缺 `buCode`，那才会出现集团之和与总额对不上的问题。

### 4. 六个品类

全部从统一 ES 算，不回原始台账：

- 大宗煤炭：待确认是 `MT`，还是 `MT+北分+1001`；
- 钢材：对应类目；
- 润滑剂：对应类目；
- 电线电缆：对应类目；
- 轴承及备件：要确认 `2502` 的子类规则；
- 办公用品及设备：YC 总额减 YC 的机电四大类。

### 5. 煤炭和钢材专项交易额

煤炭：

```text
dataSource=MT + 日/月/季/累计时间窗
```

钢材：

```text
dataSource=JD + categoryCode=1501 + 日/月/季/累计时间窗
```

“日”就是昨天那一天，不包含今天。

## 六、为什么是 ES + 定时任务，但不是再做一套汇总定时

这两个概念容易混：

### 已经需要的定时任务

每天把昨天的 FP/ZC/YC/MT/JD 新明细写进统一 ES。它解决的是“货架有没有新货”。

### 页面实时聚合

用户打开首页时，后端让 ES 按时间、来源、板块、类目做 `sum`。它解决的是“当前要按什么口径数货”。

### 暂时不需要的第二套定时任务

如果再每天把月额、季额、年额提前算好并存表，会出现：

- 补历史数据后，汇总表不会自动修正；
- 产品改一条公式，要重算很多缓存；
- 页面日期和定时任务跑完时间容易错位；
- 多一份数据就多一份对账工作。

test 目前只有 561 条，ES 聚合很轻。正确顺序是先实时聚合、测性能；只有真实数据量证明慢，再考虑短缓存或汇总索引。

## 八、驾驶舱、台账和首页是什么关系

这是当前最乱的一段，可以拆成三层：

```text
台账管理页面
  负责录入、发布坑口/价格指标
             │
             ▼
后端查询接口
  负责只返回当前已发布的统一数据
       ┌─────┴─────┐
       ▼           ▼
集采驾驶舱       HPC 集采首页
```

正确目标是两个前端共享后端数据，不是 HPC 去抓驾驶舱页面，更不是两个页面各存一份。

当前并未完全达到这个目标：

- 煤炭坑口台账的查询实现存在，但驾驶舱接线此前被撤回；
- `kengk/mt/gc` 老接口多数仍读 `sc_collection_data` 缓存；
- mt/gc 缓存还是 2024-12 到 2025-11 的旧月份；
- 价格趋势台账有维护功能，但缺少清晰的发布后读取链路。

所以产品说“首页复用驾驶舱接口”，业务方向没问题，代码上仍可能需要修接口内部数据源。

## 九、代码已经写好、定时任务没配，分别意味着什么

项目里常混淆五种状态：

| 状态 | 含义 |
|---|---|
| 需求写了 | 产品希望有 |
| 代码写了 | Git 某分支里有实现 |
| 配置好了 | XXL Job、Nacos、菜单等外部配置存在 |
| 部署了 | 对应分支构建并运行到环境 |
| 验证了 | 真正产生数据且接口/页面对账通过 |

当前前置报表的准确描述是：

- 代码：已经在后端 `test`；
- YC 调度：test 已配置；
- FP/ZC/MT/JD 调度：test 尚未配置；
- ES：已有五路测试数据，说明至少做过手动同步或部分联调；
- 06 首页：仍是本次待开发内容。

因此“代码都做好了”和“每天自动更新正常”不是同一件事。寻源侧四个任务补配后，还要看任务日志和 ES 每日增量才能算打通。

## 十、开发时最值得盯住的 8 件事

1. 不切当前有其他开发的分支；开发前再确定正确基线。
2. 新首页查询写在 `scm-source-chase`，与同步 Service 分开。
3. 时间统一写成 `[开始, 查询日 00:00)`，不要拼 `23:59:59`。
4. 金额用 `BigDecimal`，不要用 `double` 算钱。
5. ES 用聚合，不把全年明细全部拉回 Java 再循环相加。
6. 供应商必须用确认后的规范编码，不用名称模糊匹配。
7. 分组时先加 `buCode` 再扣重复项，保证集团之和能和总额对账。
8. 前端接口失败显示错误态，不显示随机数或业务假数。

如果你能用自己的话回答下面问题，就算把这块业务初步摸清了：

1. 为什么统一 ES 里有五路来源？
2. FP/ZC/YC/MT/JD 分别代表什么？
3. 为什么机电四类和煤炭要从 FP/YC 里减掉？
4. 月额、季额、年额到底有什么不同？
5. 各集团金额为什么不是简单按总额比例分摊？
6. 为什么 `supplierCode` 字段存在，仍然不能直接按它筛供应商？

> 五路数据先进入统一明细；集采金额按资格筛选后减重复；时间窗决定月季年，板块决定集团；定时任务保证明细新鲜，ES 实时聚合负责按最新口径算首页；供应商和类目数据合同必须先统一，前端假数据必须清掉。
