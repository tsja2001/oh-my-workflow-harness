# Fastjson 2 日期报错 · 从零讲懂版

> 日期：2026-07-28 ｜ 工具：cc
> 用途：先让不懂技术的自己彻底看懂，再照着给懂技术的领导讲清"什么原因、为什么这么修"。
> 读法：从上往下读，别跳。全程只跟一条数据：截止时间 `2026-06-10 22:00:00`。

---

## 第 0 步：先在脑子里建一个画面——"盒子"

系统里传来传去的"一行数据"，你就想象成**一个带格子的盒子**，每个格子有标签、有内容：

```
一行寻源数据（盒子）
┌───────────────────┬───────────────────────────────┐
│ 标签               │ 格子里装的东西                 │
├───────────────────┼───────────────────────────────┤
│ source_code       │ "10930000-JC-2026-0016"  (文字) │
│ state             │ "080"                    (文字) │
│ sourceSignEndTime │ 【闹钟：2026-06-10 22:00:00】    │  ← 注意！这一格装的是"闹钟"，不是文字
└───────────────────┴───────────────────────────────┘
```

**最关键的一点**：`sourceSignEndTime` 这一格，装的是一个**"闹钟"（Java 里叫 `Date` 日期对象）**，不是一串文字。

- **闹钟**能回答"现在过没过 22:00 这个点"——因为程序后面要靠它判断"报名截止了没、按钮还显不显示"。
- 如果这一格换成**文字**"2026-06-10 22:00:00"，人看着还是那个时间，但程序问它"过没过点"，它答不上来——它只是一串字。

> 全篇你只要盯住这一格：它到底是**闹钟**还是**文字**。出事就出在这一格从闹钟变成了文字。

---

## 第 1 步：解答你的疑问——"没传入 date 啊，date 在哪？"

你看到那行代码是这样的：

```java
obj.toJavaObject(new TypeReference<Map<String,Object>>(){})
```

你说"这也没传入 date 啊"——对，**因为 date 不是单独传进来的，它一直藏在 `obj` 这个盒子里面。**

`obj` 就是上面那个盒子。盒子里那一格 `sourceSignEndTime` 装着闹钟。你在这一行代码里只看到"盒子"三个字（`obj`），看不到里面的闹钟——但闹钟确确实实在盒子里。

打个比方：我说"把这个**行李箱**复印一份"，你会问"行李箱里有护照吗？" 护照就在箱子里，只是从"复印行李箱"这句话里看不出来而已。`obj` 就是那个行李箱，闹钟（date）就是里面的护照。

**那闹钟是怎么进到盒子里的？** 往前倒一步就清楚了 👇

---

## 第 2 步：闹钟是怎么进盒子的（数据的来路）

```
① 数据库查询
   数据库里 source_sign_end_time 这一列，本来就是日期类型
        │
        ▼
② Java 从数据库读出来，装进一个"闹钟"对象（Date）
   到这里，它是货真价实的闹钟 ✅
        │
        ▼
③ 打包成"盒子"（JSONObject），准备返回给前端
   打包时，闹钟那一格【还是闹钟】——只是被放进了盒子 ✅
        │
        ▼
④ 这个盒子 = 上面代码里的 obj
```

所以到了第 1 步那行代码之前，**盒子（obj）里的 `sourceSignEndTime` 一格，装的还是闹钟**。这一路都好好的，fastjson 1.x 时代到这里也没问题。

---

## 第 3 步：出事的那一步——把盒子"复制"一份

第 1 步那行代码 `obj.toJavaObject(...)` 想干的事，其实很简单：

> "把这个盒子**复制一份**，交给专门算按钮的那段业务代码去用。"

问题就出在"复制"这个动作，**新旧版本 fastjson 复制的方法不一样**：

**fastjson 1.x（老版本）——直接搬格子**
```
原盒子                    复制出的新盒子
┌───────────────┐        ┌───────────────┐
│ 闹钟 ●         │  搬──▶ │ 闹钟 ●         │   闹钟还是闹钟 ✅
└───────────────┘        └───────────────┘
```
一格一格原样搬过去，闹钟搬完还是闹钟。所以十几年一直正常。

**fastjson 2.x（新版本）——先拍成一张纸，再照纸重装**
```
原盒子              先"拍平成一张纸"(JSON文字)         再照着纸重新装盒子
┌───────────┐      ┌──────────────────────────┐      ┌───────────────────────┐
│ 闹钟 ●     │ ──▶  │ 纸上写：                  │ ──▶ │ 文字 "2026-06-10       │
│           │      │ sourceSignEndTime:       │      │       22:00:00"        │
│           │      │ "2026-06-10 22:00:00"    │      │  ← 变成一串文字了 ❌    │
└───────────┘      └──────────────────────────┘      └───────────────────────┘
```

关键就在中间那一下**"拍成纸"**：纸上只能写字，**闹钟没法印在纸上，只能把它显示的时间抄成一行文字**。等照着纸重新装盒子时，那一格拿到的就只是文字了——**闹钟就这么变没了，变成了文字。**

> 这就是我之前说的"date 变成 string"。不是有人故意去转，是 2.x 版"复制盒子"的手法变成了"拍纸再重装"，**闹钟变文字是这道工序的副作用**。1.x 是"直接搬格子"，没这道工序，所以闹钟不会丢。

这一步的代码在**公共库** `scm-cloud-dependencies` 里（`OperListResponseTransferServiceImpl.java` 第 113 行）。

---

## 第 4 步：为什么最后会报错

复制出来的新盒子（那一格已经是文字了），被交给**算按钮的业务代码**去用。业务代码在 `scm-source` 里，它伸手去开"截止时间"这一格，心想里面是闹钟：

```java
// OperSupplierSourcePageListImpl.java 第 216 行
sourceSignEndTime = (Date) map.get("sourceSignEndTime");
//                   ↑ 硬把这一格当"闹钟(Date)"来用
```

结果开出来一看是**文字**。程序说"你让我把一串文字当闹钟使，我做不到"，当场报错：

```
java.lang.String（文字） cannot be cast to java.util.Date（闹钟）
```

报错后，这一行的操作按钮（报价、咨询、撤回等）就没算出来——**表现就是页面上列表的按钮出不来或缺一块。**

> 补一个有意思的细节：业务代码第 216 行上面，当初写代码的人自己还留了句注释 `// string 转 date`——说明他当时就隐约觉得这里在跟"文字"打交道，只是 1.x 时代恰好没出事，就没在意。

---

## 第 5 步：谁调用谁？（把整条链串起来）

一句话：**是公共库反过来"喊"业务代码，还顺手把复制好的盒子递给它。** 不是业务去调公共库。

```
① 前端请求"供应商寻源列表"
        │
        ▼
② 业务查数据库 → 拿到盒子(闹钟还在) ✅
        │
        ▼
③ 公共库(scm-cloud-dependencies)接手，要给每行补操作按钮
   → 复制盒子：fastjson 2.x 在这一步把【闹钟 → 文字】❌   ← 病根在这
   → 把复制好的盒子，递给业务的"算按钮"方法
        │
        ▼
④ 业务(scm-source)算按钮：打开"截止时间"格 → 期望闹钟，拿到文字 → 报错 💥
```

所以你会看到一个"反常"现象：**报错报在业务代码第 216 行，但真正把闹钟弄丢的，是公共库第 113 行。** 业务代码一个字都没改，是被公共库"喂"进来的盒子变了样，才崩的。

---

## 第 6 步：为什么这么修（对症下药）

病根是第 3 步"复制盒子用了拍纸重装的手法"。那就**把这一步换回"直接搬格子"**：

```java
// 公共库 第 113 行（还有第 83 行同样写法，一起改）
// 老（拍纸重装，闹钟丢）：
obj.toJavaObject(new TypeReference<Map<String,Object>>(){})
// 新（直接搬格子，闹钟原样保留）：
new HashMap<>(obj)
```

`new HashMap<>(obj)` 的意思就是"新盒子，把原盒子每一格**原样搬过来**"——不拍纸、不重印，**闹钟还是闹钟，文字还是文字，数字还是数字**，全都保持原样。对 1.x、2.x 都成立。本地已实测：换成这个写法，2.x 下截止时间那一格仍然是闹钟。

- 改的是**病根**（公共库那一步），所以下游业务不用动，一次到位。
- 唯一要留神的是：这段公共代码很多服务都在用（约 140 处），所以发布前要多挑几个接口回归一下，确认闹钟、数字、开关这些都没被改坏——稳一点。

**为什么不用那些"看着能修"的办法：**

| 别人可能提的办法 | 为什么不行（一句话） |
|---|---|
| "给日期加个格式配置" | 那只是规定"纸条上的字怎么写"，纸条还是纸条，变不回闹钟。 |
| "把报错那行删了/去掉注解" | 注解是用来给页面长按钮的，删了按钮全没；而且同类强转还有 5 处。 |
| "退回 fastjson 1.x" | 等于把当初要堵的安全漏洞又放回来，方向错。 |

## 给领导讲的话（照读，30 秒）

> "升级 fastjson 到 2.0.62 是为堵安全漏洞，必须做。升级后暴露一个 2.x 的行为变化：OAuth2 公共返回处理里，有一步要把一行数据的 `JSONObject` 复制成 `Map` 交给业务算操作按钮。fastjson 1.x 这步是直接浅拷贝，日期字段还是 `Date`；2.x 这步 `toJavaObject(TypeReference<Map>)` 会走一次序列化再反序列化，`Date` 就被写成了 `String`。下游 `OperSupplierSourcePageListImpl` 第 216 行还 `(Date)` 强转，抛 `ClassCastException`，表现是列表操作按钮补不上。
>
> 报错在业务代码，但根因在公共库那一步的复制方式。修法是把公共库第 83、113 两处的 `toJavaObject(new TypeReference<Map>)` 换成 `new HashMap<>(obj)` 浅拷贝，日期不再经过 JSON 文本、类型原样保留，1.x/2.x 都兼容。改动就两行，因为是公共组件、约 140 处在用，发布前挑几个接口回归验证一下。已用 1.2.83 和 2.0.62 对照实测复现确认。"

## 你可能被追问的三个问题（备着）

**Q：数据库存的日期出问题了吗？**
没有。数据库、查询出来、装盒子这一路，日期都是好的闹钟。是"复制盒子"那一步才把闹钟弄成文字的。

**Q：为什么以前没事，升级才出事？**
因为老版本 fastjson"复制盒子"是直接搬格子，闹钟不丢；新版本改成"拍纸重装"，闹钟才丢。业务代码十几年没动过。

**Q：改公共库风险大吗？**
改动只有两行，逻辑是"复制时原样保留类型"，本身是把行为改回更接近 1.x 的样子。风险点在于它是公共组件、用的地方多，所以我们发布前会挑代表性接口回归，确认没有连带影响再上。
