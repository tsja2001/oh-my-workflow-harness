## 0. 先记住几个大白话名词（后面都用得上）

| 名词 | 你就理解成 |
|---|---|
| **fastjson** | 一个全公司 Java 服务都在用的"翻译工具"，负责把数据在"对象"和"文本(JSON)"之间来回转。 |
| **1.2.83 / 2.0.62** | 这个翻译工具的两个版本。老版 1.2.83、新版 2.0.62。这次就是要从新版退回老版。 |
| **打包 / 编译** | 把源代码加工成服务器真正能跑的"成品件"。改了代码要重打包才生效；有时代码没改也得重打。 |
| **Nexus** | 公司内部的"仓库/应用商店"。所有打好的成品件都传到这，test/uat/prod 各环境都从这里取。 |
| **版本总闸(parent)** | 一张全公司统一的配置表，规定"大家都用哪个版本的 fastjson"。拧它一下，全公司都跟着变。 |
| **502** | 服务挂了、接口调不通时浏览器/网关报的错。用户看到就是"页面打不开、点了没反应"。 |

**一句话背景**：之前把 fastjson 从老版升到新版 2.0.62，结果毛病太多，领导决定退回老版 1.2.83。退版本这件事，麻烦就麻烦在"牵一发动全身"。

## 1. 第一件事：降级 + 打那"三个包"（你有印象、有 git 记录的）

这三个是这次改动的"地基"，我把它们里面为了适配新版而改的代码**原样撤回**，然后重新打包传到 Nexus。三个都有 git 提交记录（都是一条 `Revert` 撤回提交），所以你才有印象：

| 包（仓库） | 干了啥 | 撤回提交 |
|---|---|---|
| **scm-cloud-parent** | 把"版本总闸"从 2.0.62 拧回 1.2.83 | `9e9efe1 Revert "fastjson升级到2.0.62"` |
| **scm-cloud-dependencies** | 撤回当初为新版做的一处"字符串处理"改动 | `f6f7f0b Revert "fix: 处理FastJSON2 string问题"` |
| **scm-assemblies-all** | 撤回当初为新版补的"缺失方法"适配 | `62947d1 Revert "处理fastjson2.x缺失方法问题"` |

**为什么只推代码不够、还要打包传 Nexus？**
线上服务器跑的是**成品件里的东西**，不是 GitLab 里的源码。只把代码推上去，线上一动不动。必须：撤回代码 → 重新打包传到 Nexus → 重建服务，才真正生效。所以你"以为推完就没事了"其实只做了第一步。

这一步做完，你合理地以为回滚完成了。但接着就冒出了 502。

## 2. 第二件事：又打的"几个包"（这就是你第 3 行问的，重点！）

### 一句话：这几个包**源代码一个字都没改**，但必须用老版重新编译一遍，否则线上一直 502。

**为什么代码没改还要重打？** 打个比方：

- fastjson 里有一个功能叫 `toJSONBytes`（把数据转成字节）。
- **新版 2.0.62** 里，这个功能有一个"只填一个参数"的写法。
- **老版 1.2.83** 里，**没有**"只填一个参数"的写法，只有"填多个参数"的写法。
- 当初这些服务是在**新版环境下打包**的，打包时机器自动挑中了新版那个"只填一个参数"的写法，把这个选择**焊死在成品件里**了。
- 现在底层退回老版，成品件跑起来去找那个"只填一个参数"的写法——**老版里根本没有**——当场报错，接口就 502。

所以：**代码不用改，但凡是里面用到这个功能的成品件，都得在老版环境下重新编译一次**，让它重新挑中老版有的那个写法。这就是"又打的几个包"。因为不涉及改代码、只是重打+上传的固定命令，所以当时是**直接给你命令照敲**的。

这几个包是：

| 重打的包 | 谁在用它 |
|---|---|
| **网关 scm-gateway**（主网关 + 商场网关） | 所有业务接口都从网关走，它一坏，**全站 502** |
| **4 个消息队列适配器**（MQ ali4x / rocket4x / rocket5x / ali5x） | source、order、product、contract、ifs 等 9 个业务服务在用 |

> 还有一个坑顺带说下（不用深究）：test 环境打包时会自动把版本号改成 `TEST-SNAPSHOT`，所以网关这个包得**发两个版本号**（普通版给 uat/prod，TEST 版给 test），否则 test 拿不到。这也是当时多敲几条命令的原因之一。

**这一步做完，502 基本就都好了。** 到这里，fastjson 回滚本身在 test / uat 都验证通过了（prod 还等运维给正式发布入口）。

## 3. 第三件事：云采"不填也能提交"——原因（已重新查证，见 `06` 文档）

> ⚠️ 更正：这一节早先写的"空字符串校验绕过、改一行 isBlank 就好"的说法**是错的**，别再用。后来我从**源码 + UAT 数据库**重新查证，结论完全不同。完整实证在 [`06云采必填校验-根因实证版.md`](06云采必填校验-根因实证版.md)，这里只放白话摘要。

### 3.1 先说清楚：跟 fastjson **没关系**

它是回滚期间顺带发现的，和 fastjson 是两码事，别混一起。

### 3.2 真正的原因（一句话）

后端**根本没有"原因和计划二选一必填"这条规则**。它是**两个各自独立的开关**，两个都关着就什么都不拦：

- **开关①"是否强制关联采购计划"（planCheck）**——**按公司所属的租户(BU)配**。有 11 个租户被明确设成了"不强制"。
- **开关②"是否需要填比价原因"（needCompare）**——**按商品配**。商品不需要比价，这道就不管。

### 3.3 为什么"换个公司就不一样"（你观察到的核心现象）

我直接查了 UAT 数据库，逐一对上：

| 你测的公司 | 所属租户 | 强制关联计划? | 商品需比价? | 结果 |
|---|---|---|---|---|
| 信息技术 10930000 | BU002 | **要**(默认) | 否 | **被拦**（要计划）|
| 建筑工程 11761000 | BU004 | **不要**(被配成 false) | 否 | **能提交** |

**换公司 = 换租户 = 换"强制关联计划"开关。** 建筑工程那家(BU004)开关是关的、商品又不需比价 → 两道关卡都不管 → 直接放过。这就是"有时候拦、有时候不拦"的真相，不是玄学，也不是偶发。

### 3.4 那我之前改的那行代码呢？

我确实在 test 上改并提交过一行（`f27c3903d`，把 `null` 判断换成 `isBlank`）。**说实话，它跟你这个 bug 没关系、也修不好这个 bug**——那行属于"比价原因"关卡，只有"商品需要比价"时才会跑，而你能绕过的案例商品都是"不需要比价"的。它顶多算个顺手的小加固，不是解药。**你一直觉得"没解决"，是对的。**

### 3.5 这到底算不算 bug、下一步谁来定

系统其实是**完全按配置正确运行**的，没写错。是**"配置/业务规则"和"产品期望"对不上**：那 11 个租户的"不强制计划"是**有人明确配上去的**。所以要先让产品拍板——**这些租户当初是不是故意不强制关联计划？** 定了口径我再动手（改配置 / 加新规则 / 维持现状）。详见 `06` 文档第 5、6 节，那里有直接能念给产品的话术。
