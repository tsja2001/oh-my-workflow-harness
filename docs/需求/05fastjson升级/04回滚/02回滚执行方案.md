## 1. 必须先懂的一个真相：影响面不是"三个模块"

你说"受影响的就这三个模块"——这句话在**改代码**层面成立（回滚的代码提交确实只动这三个仓库，别的业务服务一行不用改）。但在**部署生效**层面**不成立**，原因有两个：

1. **`scm-cloud-parent` 是全公司的"版本总闸"。** 所有 Java 服务的 fastjson 版本都从它继承。把它拧回 1.2.83，意味着**之后任何一个服务重新构建，都会变回 1.x**——不是只有这三个仓库。

2. **Nexus 上每个 SNAPSHOT 只有一份，全环境共用。** 你把回退后的 parent 发上 Nexus，test / uat / prod 三套环境的服务，只要重建就都会拿到 1.x。**没法"只让 test 回退、prod 不动"**（除非改版本号，那是另一个大工程）。

> 结论：**"改哪些代码" = 三个仓库；"回退会波及谁" = 所有重新构建的 Java 服务、所有环境。** 所以下面第 3 步"重建范围"是需要拍板的决策，不是技术细节。

## 3. 四步执行

### 第一步：推送代码（三个仓库，各推各的分支）

> 推送本身**不会**触发任何构建或部署（地基仓没 Jenkins），所以这步安全。真正的"引爆点"是第二步发 Nexus。
> **每个仓库推送前先 fetch 校验**，避免踩"用落后分支覆盖同事新内容"的坑（升级时真踩过）。

```bash

# ② dependencies（dev 分支）

git fetch origin
git log --oneline origin/dev..dev        # 应只看到 1 条 Revert 提交
git log --oneline dev..origin/dev        # 应为空
git push origin dev

# ③ assemblies（dev 分支）
cd /home/t/projects/work-wsl/01zhaocai-end/scm-assemblies-all

git log --oneline origin/dev..dev        # 应只看到 1 条 Revert 提交
git log --oneline dev..origin/dev        # 应为空
```

⚠️ 分支不统一是既成事实：升级时 parent 提交在 `prod`、另两个在 `dev`，回滚跟着同分支走才能精确盖掉那次升级。手动 deploy 时也要站在这几个分支上（见下）。

### 第二步：发 Nexus（手动 mvn deploy，顺序不能反）

> **parent 必须第一个发。** 它是版本总闸，且另外两个模块编译时要继承它。先发 parent（deploy 会顺带装进本地 `~/.m2`），再发子模块，子模块才拿得到 1.2.83。

```bash

mvn -N clean deploy -s ~/.m2/settings-zc.xml

# ② 发 dependencies-oauth2（日期修复回退）
cd /home/t/projects/work-wsl/01zhaocai-end/scm-cloud-dependencies/scm-cloud-dependencies-oauth2
mvn clean deploy -s ~/.m2/settings-zc.xml -DskipTests

# ③ 发 assemblies 的两个公共模块
cd /home/t/projects/work-wsl/01zhaocai-end/scm-assemblies-all/scm-common-all/scm-common-json
mvn clean deploy -s ~/.m2/settings-zc.xml -DskipTests
cd /home/t/projects/work-wsl/01zhaocai-end/scm-assemblies-all/scm-share-aim-all/scm-share-aim-spring
mvn clean deploy -s ~/.m2/settings-zc.xml -DskipTests
```

注意：
- **不要加 `-am` / 不要在仓库根批量 deploy**：只发目标模块，避免把 Nexus 上无关模块一起覆盖成旧内容。
- 若 ③ 报"找不到 parent 或依赖"：先在 `scm-assemblies-all` 根执行一次 `mvn install -DskipTests` 把同仓库模块装到本地，再回来单独 deploy 这两个模块。
- **禁止 `bash -x` 调试 Maven**（会把 settings 里的 Nexus 凭据打印出来）。
- deploy 前务必 `git diff` 确认只有本次改动、且分支是最新的。

> ⚠️ **分水岭提醒**：第二步一旦执行完，Nexus 上就是 1.2.83 了。从这一刻起，**任何人重建任何服务（含 uat/prod）都会变回 1.x**。所以发完 Nexus 到验证完成这段窗口，要约好"别让别人去重建 uat/prod 的服务"。

### 第二步补充：编译字节码兼容 —— `toJSONBytes(Object)` 单参问题（2026-07-31 test 踩坑后新增）

> **这个问题的本质**：源码一行没改，但字节码不兼容。fastjson2 的 compat 包里 `JSON.toJSONBytes(Object)` 是一个真实的单参方法（非变参）；1.2.83 只有 `toJSONBytes(Object, SerializerFeature...)` 变参版。任何在 fastjson2 时期编译的 jar，如果源码里写了 `JSON.toJSONBytes(xxx)`，编译器都会选中单参版——生成的字节码在 1.2.83 上找不到方法，直接 `NoSuchMethodError`。

#### 关键发现：TEST-SNAPSHOT vs SNAPSHOT —— 两个版本号都要发！

> **所有 test Jenkins 流水线里都有 `mvn versions:set -DnewVersion=1.0.0-JDSN-TEST-SNAPSHOT`**，它会把项目版本改为 `TEST-SNAPSHOT`。而每个服务的 pom.xml 中，自己的业务 jar 依赖用的是 `${project.version}`，这会被 `versions:set` 一并改成 `TEST-SNAPSHOT`。所以 Jenkins 构建 test 环境时，实际拉的是 `xxx:1.0.0-JDSN-TEST-SNAPSHOT`，不是普通的 `xxx:1.0.0-JDSN-SNAPSHOT`。
>
> **结论：发 Nexus 时两个版本号都要发。** 普通 SNAPSHOT 给 dev/uat/prod 用；TEST-SNAPSHOT 给 test 用。（dev/uat 的 Jenkins 不做 `versions:set`，直接用的普通 SNAPSHOT。）

## 4. 回滚里的"坑"清单

| 坑 | 说明 | 对策 |
|---|---|---|
| 只推代码就以为回滚完了 | 线上跑的是镜像里的 jar，不是 GitLab 源码 | 必须走完发 Nexus + 重建镜像 |
| 顺序反了 | 先重建 web 再发 parent，web 拉到的还是旧 2.0.62 | parent 永远第一个发 |

| 用落后分支 deploy | 会把 Nexus 上同事的新内容覆盖成旧的 | deploy 前 fetch + 确认 diff 只有本次 |
| **🔴 toJSONBytes 单参字节码不兼容** | fastjson2 compat 的 `JSON.toJSONBytes(Object)` 是单参方法，1.2.83 只有变参版。2.x 时期编译的 jar 字节码在 1.2.83 上 `NoSuchMethodError` | 源码不用改，但含此调用的每个模块必须用 1.2.83 重编译并发 Nexus（见第二步补充） |
| **🔴 TEST-SNAPSHOT 版本号陷阱** | test Jenkins 流水线会 `mvn versions:set` 把版本改成 `TEST-SNAPSHOT`，`${project.version}` 的依赖也会跟着变成 `TEST-SNAPSHOT`。只发普通 `SNAPSHOT`，test 根本拉不到 | 凡是用了 `${project.version}` 的业务 jar（gateway 等），要同时发 `SNAPSHOT` 和 `TEST-SNAPSHOT` 两个版本 |
| **🔴 Jenkins 构建机 Maven 缓存** | `mvn install -U` 理论上强制更新 SNAPSHOT，但个别构建机可能因 updatePolicy 或本地缓存策略不刷新。Nexus jar 正确但线上仍是旧字节码 | 再 `mvn deploy` 一次 bump build 号（让 maven-metadata.xml 时间戳更新），然后 Jenkins 重建 |
