# 一、问领导 / 技术负责人（3 个，最重要）

## Q1 🔴 先上 1.2.84 止血，还是直接冲 2.x？

**为什么要问：** 这是整个方案的岔路口。技术上我推荐"先 1.2.84 再 2.x"，但"要不要多做一次发布"是管理决策。

**逐字话术：**

> "关于 fastjson 我查到一个新情况，想跟您确认下方向。
>
> 上个月我们从 2.0.62 退回了 1.2.83。当时退回去的理由是 2.x 兼容问题多。但有个事当时没有：**7 月 29 号官方发布了 1.2.84，专门修 1.x 那个 RCE 漏洞**——就是我们当初升级 2.x 想躲的那个。同一天 2.x 也发了 2.0.63，修了 2.x 那个漏洞，现在最新是 2.0.64。
>
> 现在的问题是：我们停在 1.2.83，**而且当初为了挡漏洞加的那个安全模式开关，回滚的时候也一起撤掉了**。所以现在生产是**既没打补丁、也没兜底**的状态。
>
> 我的建议是分两步：
> **第一步，先花一两天把 1.2.83 换成 1.2.84。** 我用两个版本的真实包跑过对照测试，**行为一模一样**，就是个纯安全补丁，改一个版本号，业务代码一行不动。做完漏洞就清零了。
> **第二步，再从容做 2.x 升级。** 这样就不是在赶工救火，可以老老实实一批一批验证。而且万一 2.x 又出问题，退路是 1.2.84 这个**安全版本**——上次最被动的就是退也带漏洞、不退也带漏洞。
>
> 想请您拍板：是按这两步走，还是直接一步到位上 2.x？"

**对面可能反问 → 怎么答：**

| 反问 | 应答 |
|---|---|
| "1.2.84 靠谱吗？1.x 不是不维护了吗？" | "这次官方专门为 1.x 出了补丁，release note 明确写了修的就是 1.2.68 到 1.2.83 这个漏洞，也把 2.x 那批 AutoType 加固回移到 1.x 了。而且它跟我们现在跑的 1.2.83 是同一条代码线，只差安全修复，风险比跨大版本小一个量级。" |
| "那是不是就不用升 2.x 了？" | "长期还是要升的，1.x 官方定位是维护状态。但先上 1.2.84 能把'必须马上做'变成'可以好好做'，两件事不冲突。" |
| "多一次发布是不是多一次风险？" | "1.2.84 这次发布不改任何业务代码，也不需要业务回归，只要验证包换进去了、能登录能下单就行。风险主要来自代码改动，这次没有代码改动。" |
| "为什么安全模式撤掉了？" | "回滚到 1.x 之后，那个开关是给 2.x 用的、名字都不一样，留着不起作用，所以撤了。这次我建议加回来，而且把 1.x 和 2.x 两个参数名都写上，以后不管在哪个版本都生效。" |

**为什么要问：** 如果 Q1 选了"直接冲 2.x"，那从现在到 2.x 上生产（预计 2～3 周）这段时间，生产是没有任何防护的。这个知情同意必须拿到。

**逐字话术（只在 Q1 选了"直接冲 2.x"时才问）：**

# 三、问后端同事 / 架构（2 个）

## Q7 🔴 `scm-ifs-all` 那批未提交的改动，该进哪个分支？

**为什么要问：** 我发现 `scm-ifs-all` 的工作区里躺着一批**已经改好但没提交**的代码（4 个文件 + 1 个新增工具类 `RuleInputUtil`），而且是在 **`prod` 分支**上改的。这批改动是修 IFS 规则脚本问题的，质量没问题，但直接在 prod 上改不合规。

**逐字话术：**

> "有一批修 IFS 规则脚本兼容问题的改动，之前做了但一直没提交，现在还躺在本地的 prod 分支上没动。内容是新增了一个工具类，把 4 个地方的写法换掉了。我想确认一下走法：**是从 prod 拉一个 feature 分支把它们放进去，还是跟着别的分支走？** 另外这批改动是给 fastjson 2.x 升级用的，如果我们暂时不升 2.x，这批要不要先提交着？"

**背景补充（对方追问时用）：**
> "问题是 fastjson 2.x 之后，`JSON.toJSON()` 不再把嵌套的对象递归转成 Map 了，规则脚本里 `.get("字段名")` 就找不到方法。这个工具类是把递归行为手动补回来，同时保证日期不被转成字符串。"

## Q8 🟠 规则引擎的注入点不止 IFS，其他几处要不要一起修？

**为什么要问：** 我扫出来同款写法在 `scm-platform-pipeline`、`scm-plateform-staticdata`、`scm-ubm-todo` 也有（共 5 处），上次只修了 IFS。**这就是"处理完又冒新问题"的原因。**

**逐字话术：**

> "我扫代码发现一件事：上次 fastjson 2.x 那个'规则脚本取不到字段'的问题，我们只修了 IFS，但**同样的写法在 pipeline、staticdata、ubm 待办里还有 5 处**，都是把对象塞进规则引擎那种。上次没炸可能只是刚好没跑到。
>
> 我的建议是把那个修复的工具类**上提到公共模块**（`scm-common-json`），这几处统一调用，别各写一份。这样以后新加的地方也有现成的可用。想确认两件事：一是这几处一起修您认可吗；二是工具类放公共模块，有没有别的顾虑？"

# 五、我自己拍板的（不问人，但你扫一眼，觉得不对就否决）

| 决定 | 理由 | 猜错的返工代价 |
|---|---|---|
| 目标版本选 **2.0.64** 而不是 2.0.63 | 都含安全修复，2.0.64 更新（8/2），且实测两版行为一致 | 极小，改版本号重发一次 |
| 分 4 个波次、按"雷点密度"排序 | 让上次出事的 source / IFS 排最后，前面波次先把链路验通 | 无，波次可随时调整 |
| B2 那 10 处日期强转**也要改**（上次没改） | 双保险：就算公共层哪天再退化，业务层也不会炸 | 无，是纯增强 |
| `RuleInputUtil` 上提到公共模块 | 5 个模块要用，各写一份必然走样 | 小，如果同事反对就各模块各放一份 |
| SafeMode 两个属性名都写 | 1.x 认不带 2 的、2.x 认带 2 的，写一个会静默失效 | 无 |
| 阶段 0 的 1.2.84 升级**不做业务回归**，只做冒烟 | 6 项探针实测 1.2.83 / 1.2.84 输出逐字相同，没有行为变化可回归 | 小，如果领导要求全量回归就照做，只是多花时间 |
