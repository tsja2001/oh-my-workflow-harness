# 第一部分 · 大白话

## 1.1 这次和上次最大的不同

上次的做法是"**出问题 → 查 → 修 → 再出问题**"，所以返工了很多轮，而且到最后也不确定还有没有没发现的。

这次我换了个做法：**不猜哪里会坏，而是把两个版本的行为逐项跑一遍做差集。**

我写了 112 项行为探针（序列化、反序列化、日期、数字、精度、空值、枚举、循环引用、类型转换……），用 1.2.83 和 2.0.64 的**真实 jar** 各跑一遍，然后自动对比。结果：

> **96 项完全相同，16 项有差异。**

然后我把这 16 项差异，一项一项拿到代码库里去数"我们到底用没用到"。这样得到的清单是**穷举的**，不是"想到哪查到哪"。

**代价是：我比第 1 版多找出了 3 个雷**，其中一个（DPS 流程签名）如果不修，上线后会导致流程审批对接直接失败——这种问题靠"等它炸"要好几天才能发现。

## 1.2 结论：一共 6 类断点，只有 21 处代码需要改

| | 是什么 | 处数 | 改哪 |
|---|---|---|---|
| **A** | 2.x 删了一个方法，编译过不去 | 2 | 公共依赖 |
| **B1** | 日期变字符串（上次 source 出事的） | 2 | 公共依赖 |
| **B3** | 规则脚本取不到字段（上次 IFS 出事的） | **1** | 公共依赖 ⭐ |

**其中 A / B1 / B3 三类——也就是上次真正炸过的全部——都能只改公共依赖，业务模块一行不动。**

## 1.3 关于"公共依赖做全面，别影响子模块"

你这个要求我当成硬指标做了，结果比预想的好：

**上次修 IFS 那个规则脚本问题，是在 5 个注入点逐个改的，而且漏了 5 处。** 这次我往上追了一层，发现所有规则脚本最终都汇聚到**同一个方法**：

```
scm-share-rule / QlExpressRuleEngineServiceImpl.execute(脚本, 上下文Map)
```

IFS 的 8 处、pipeline 的 5 处、invite 的 3 处、ubm 待办的 2 处、staticdata 的 2 处、ifs-batch 的 2 处——**全部 22 个调用点，无一例外，都走这一个方法**。

所以只要在这个方法里，进 QLExpress 之前把上下文做一次"恢复成 1.x 那种结构"的处理，就**一次性覆盖全部 22 处，而且以后新写的规则也自动免疫**。业务模块零改动。

> 打个比方：上次是挨个房间换灯泡，还漏了几间；这次是找到了总电闸。

## 1.4 需要改业务代码的只剩一类（N2），而且原因很硬

N2 是这次新发现的：`JSONObject` 这个对象**自己**的 `toJSONString()`，输出日期的格式在两个版本里是**反的**：

```
1.2.83 →  {"d":1780000000000}          （时间戳数字）
2.0.64 →  {"d":"2026-05-29 04:26:40"}  （字符串）
```

而**静态写法** `JSON.toJSONString(那个对象)` 两版**完全一致**。同一件事，两种写法结果不同——这就是为什么它极难靠肉眼发现。

代码里有 23 处用了实例写法。其中最要命的两处在**流程审批（DPS）对接**：

```java
String cmd5 = Base64Encoding(md5(params.toJSONString()));   // 拿它算签名
```

报文内容一变，MD5 就变，**签名校验直接失败**。这不是页面显示难看的问题，是接口直接调不通。

修法很简单也很机械：把 `x.toJSONString()` 改成 `JSON.toJSONString(x)`。**一行对一行，不改逻辑。**

## 1.5 好消息：前端基本不受影响

这是最容易全站翻车、也最难验的一项，我把真实返回链路模拟出来测了：

后端返回 → `GlobalResponseHandler` 用 fastjson 加工 → Jackson 输出给前端。逐字段对比结果：

| 字段类型 | 1.2.83 | 2.0.64 |
|---|---|---|
| Date / Timestamp | 一样 ✅ | 一样 ✅ |
| BigDecimal（金额） | 一样 ✅ | 一样 ✅ |
| Long（大数，怕丢精度的） | 一样 ✅ | 一样 ✅ |
| Integer / String / Boolean | 一样 ✅ | 一样 ✅ |
| **java.time.LocalDate 系列** | 字符串 | **对象** ❌ |

只有 `java.time` 那一类不同。而全代码库里，**声明成实体字段的 java.time 只有 4 处**，其中 2 处在工具类里（根本不进接口），剩 2 处是同一个短信 VO。

> **也就是说：升级后前端拿到的报文，除了那 1 个短信 VO 要确认一下，其余一切照旧。**

# 30 秒复述

> "这次我没有靠'边升边查'。我写了 112 项行为探针，用两个版本的真 jar 各跑一遍做自动对比——96 项一样，16 项不一样，归成 6 个原因。然后每个原因回代码里数处数。这样清单是穷举的。
>
> 结果：一共 21 处代码要改。上次真正炸过的三类问题——编译报错、日期变字符串、规则脚本取不到字段——**全部能只改公共依赖，业务模块一行不动**。特别是规则脚本那个，上次是在 5 个注入点逐个改还漏了 5 处，这次我找到了所有规则调用的唯一入口，一处收口覆盖全部 22 个调用点。
>
> 另外新查出 3 个上次没发现的问题，最要紧的是 JSONObject 输出日期格式在两版是反的，而流程审批那边拿它算 MD5 签名——不修的话上线后签名直接失效。这种问题靠等它炸得好几天才能发现。
>
> 前端基本不受影响：我把真实返回链路模拟出来逐字段比过，日期、金额、大数、布尔全都一样，只有 java.time 那类不同，而全代码库只有 4 处、其中 2 处还在工具类里。"
