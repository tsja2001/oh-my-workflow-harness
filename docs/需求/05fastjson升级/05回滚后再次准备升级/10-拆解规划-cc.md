# 第一部分 · 大白话（给你看的）

## 1.1 一句话结论

> **你问的"是不是有新版本可以不用配安全模式了"——是的，新版本出来了，而且不止一个。**
> 更重要的是我查到一件你可能不知道的事：**现在这个状态（1.2.83）是最不安全的一档**，比升级前还差。
> 所以第一步不是"怎么升 2.x"，而是**先花半天把 1.2.83 换成 1.2.84 止血**——这个改动实测和现在的行为一模一样，零兼容风险。
> 然后再从容做 2.x 升级，不用赶。

## 1.2 先说清楚现在的处境（这是最重要的一段）

一共有**两个**漏洞，别混：

| | 漏洞 A | 漏洞 B |
|---|---|---|
| 影响谁 | fastjson **1.2.68 ~ 1.2.83** | fastjson2 **≤ 2.0.62** |
| 编号 | CVE-2026-16723 | 长亭 2026-07 报的那个（FNV 哈希碰撞） |
| 当初 | 就是为了躲它，才升级到 2.x | 升上去之后才爆出来的 |
| **现在修好了吗** | **1.2.84 修好了** | **2.0.63 / 2.0.64 修好了** |

**而我们现在在哪？**

```
当前 = fastjson 1.2.83（回滚后）+ 安全模式已经被撤掉（代码里搜不到了）
     = 漏洞 A 全裸
```

我实测确认了：`scm-cloud-parent/pom.xml:65` 现在是 `1.2.83`；`03zhaocai-start` 全仓库搜 `safeMode` **0 个结果**，两个仓库都有一条 `Revert "fix: 增加fastjson安全模式配置"` 的提交。

也就是说：**回滚那一轮，把版本退回去了，也把挡漏洞的开关一起撤掉了。现在既没有新版本的修复，也没有安全模式兜底。**

> 这句话你可以直接跟领导说，不用怕，因为回滚是领导拍的板，撤 SafeMode 也是"退回 1.x 后这开关没意义了"的合理动作——**问题不在谁做错了，在于当时 1.2.84 还没出（7/29 才发布），现在出了，就有更好的选择了。**

## 1.3 回答你的第 7 行问题：安全模式还要不要配？

**分两种情况：**

- **如果走 1.2.84 或 2.0.64（都是已修复版本）→ 不用为了"救命"配了。** 那个 SafeMode 当初是"官方还没发修复包，先拿它顶着"的临时措施，现在包出了，措施可以退休。
- **但建议还是留着当"第二道锁"。** 我实测过：我们全代码库 `@type`/AutoType 主动使用 **0 处**，开了 SafeMode 对业务零影响。等于免费多一层防护，以后再爆同类漏洞也不用连夜加班。这属于建议，不是必须。

**一个实测细节**（省得以后再踩）：1.x 和 2.x 读的属性名不一样——
1.2.84 读 `-Dfastjson.parser.safeMode=true`（**不带 2**），2.0.64 读 `-Dfastjson2.parser.safeMode=true`（**带 2**）。
两个都写上最省事，写错一个不会报错、只是不生效——这种"静默失效"最坑。

## 1.4 上次为什么那么狼狈？（这次能不能不重演）

上次的三次"意外"，我这次全部找到了并且量化了。说人话：

| 上次踩的坑 | 本质 | 这次还会不会 |
|---|---|---|
| ① 编译报错：方法没了 | 2.x 删掉了一个 1.x 的方法 | **不会**。我把代码库里所有 fastjson 调用形态抽出来，用 2.0.64 真编译了一遍，**全场只有 1 个方法真的没了，就 2 处代码**，改法早就有了 |
| ② 上线后才发现：日期变成了字符串 | 同名方法，行为变了 | **不会**。已定位到唯一 2 处，且修法已实测有效 |
| ③ 又过几天：IFS 的规则脚本崩了 | 另一个同名方法，行为也变了 | **不会**。已定位到 9 个注入点（比上次多找出 4 个），其中 4 个前面的 AI 已经改好了、还差 1 个 |

**为什么上次是"一批一批冒出来"？** 因为①能靠编译器发现，②③只能等真实业务跑到那一行才炸。这次我不靠"等它炸"——我把 1.2.84 和 2.0.64 两个真 jar 拿来跑同一套探针，**把行为差异全表列出来**，再拿差异去代码库里挨个数。

## 1.5 两条路，我推荐哪条

| | 路线 A：先上 1.2.84 | 路线 B：直接冲 2.0.64 |
|---|---|---|
| 改什么 | parent 里一个版本号 `1.2.83`→`1.2.84` | 版本号 + 3 处代码 + 规则脚本回归 |
| 行为变化 | **实测零变化**（我 6 项探针逐项对跑，1.2.83 和 1.2.84 输出完全一致） | 有 3 类已知变化 |
| 修掉哪个漏洞 | 漏洞 A（现在正裸着的那个） | A + B 都修 |
| 要重新部署几个服务 | 全部（但只是重打包，代码没变） | 全部 |
| 时间 | 1～2 天 | 2～3 周（含分批验证） |
| 风险 | 极低 | 中 |

**我的建议：A 先做，B 后做，不是二选一。**

理由：现在漏洞 A 是**实打实裸着的**，而 2.x 升级不管怎么规划都要几周。用 1～2 天把最急的风险清零，剩下的 2.x 升级就从"救火"变成"从容做"，可以老老实实一批一批验证，不用再赶工上生产。

> 如果领导坚持"就要一步到位上 2.x"，也能做，方案在第三部分照样给了。但我会把"这几周窗口期漏洞 A 裸着"这件事明确写进去让领导知情。

## 2.2 1.x 和 2.x 到底差在哪（4 个版本真 jar 对跑）

实验：同一份探针代码，分别用 1.2.83 / 1.2.84 / 2.0.62 / 2.0.64 的真实 jar 编译运行。

### 表 1：日期序列化格式 —— **好消息，没差别**

| 版本 | `JSON.toJSONString(Date)` |
|---|---|
| 1.2.83 | `1780000000000` |
| 1.2.84 | `1780000000000` |
| 2.0.62 | `1780000000000` |
| 2.0.64 | `1780000000000` |

> **结论：接口返回给前端的日期格式，1.x→2.x 不会变。** 这是升级前最容易担心、也最容易全站翻车的一项，实测排除了。前端不用改，也不用担心"日期显示变了"。

### 表 2：`JSONObject` → `Map<String,Object>` —— **上次 Source 日期变字符串的根因**

| 写法 | 1.2.83 | 1.2.84 | 2.0.62 | 2.0.64 |
|---|---|---|---|---|
| `toJavaObject(new TypeReference<Map<String,Object>>(){})` | Date | Date | **String ❌** | **String ❌** |
| `toJavaObject(..., Map.class)` | Date | Date | Date ✅ | Date ✅ |
| `new HashMap<>(jsonObject)`（修法） | Date | Date | Date ✅ | Date ✅ |
| 数字 / 布尔 | 不变 | 不变 | 不变 | 不变 |

> **两条关键结论：**
> 1. **2.0.64 没有修这个行为**，升到最新版这个坑依然在，必须改代码。
> 2. **只有带 `TypeReference` 泛型的那一种写法会坏**；`Map.class` 那种写法是安全的。这一条把影响面从"19 处"砍到"2 处"。

### 表 3：`JSON.toJSON(对象)` 递归转换 —— **上次 IFS 规则脚本崩的根因**

| 数据结构 | 1.2.84 | 2.0.64 |
|---|---|---|
| 直接嵌套的 Bean 字段 | 转成 Map ✅ | 转成 Map ✅ **（一样）** |
| `List<Bean>` 的元素 | 转成 Map ✅ | 转成 Map ✅ **（一样）** |
| **`Map<String,Bean>` 的值** | 转成 Map ✅ | **保留原 Bean ❌** |
| **`Map<String,Object>` 里塞的 Bean** | 转成 Map ✅ | **保留原 Bean ❌** |
| **`Bean[]` 数组** | 转成 JSONArray ✅ | **保留原数组 ❌** |

> **这是本次研究最有价值的一条**：2.x 的行为变化**不是"全都不转"，而是只有"Map 的值"和"数组"不转**。
> 直接字段和 List 都照常。这意味着 104 处 `JSON.toJSON` 里，**绝大多数根本不受影响**——真正危险的，只有"结果被当成多层 Map 往下 `.get()` 挖"的场景，也就是规则引擎/脚本那一类。

### 表 4：SafeMode 开关

| 版本 | 认哪个属性名 | 实测生效 |
|---|---|---|
| 1.2.84 | `fastjson.parser.safeMode`（不带 2） | ✅ `ParserConfig.global.safeMode = true` |
| 2.0.64 | `fastjson2.parser.safeMode`（带 2） | ✅ 属性读到 true |

> 必须在 **JVM 启动前**设（`JAVA_TOOL_OPTIONS` 或命令行 `-D`）。放 Nacos / application.yml **读不到**——因为它是类加载时读一次的。

# 第三部分 · 分步实施方案

## 3.0 总原则（针对上次的三条教训）

1. **公共包先发、业务服务后建、一批一批来** —— 这是你自己提的，完全正确，方案就按这个搭。
2. **每一波都要有"能一眼看出新旧代码"的验收点**，不能只看 Jenkins 绿灯。
3. **每一波都留可回退点**：镜像 tag 留着，公共包发布前记下上一版时间戳。

---

## 阶段 0 · 立即止血：1.2.83 → 1.2.84（建议先做，1～2 天）

> **目标：把现在正裸着的漏洞 A 关掉。行为零变化，所以不需要业务回归。**

**改什么：** 一个字符。

```
01zhaocai-end/scm-cloud-parent/pom.xml:65
<fastjson.version>1.2.83</fastjson.version>  →  <fastjson.version>1.2.84</fastjson.version>
```

**为什么可以这么轻：** 我把 1.2.83 和 1.2.84 用同一套 6 项探针跑过，**输出逐字相同**（日期格式、Map 泛型转换、递归行为、API 存在性、SafeMode、反序列化）。1.2.84 是纯安全补丁，官方 release notes 也没有 breaking change。

**步骤：**

| # | 做什么 | 谁 |
|---|---|---|
| 1 | 改 parent 版本号，本地提交（`fix: 升级fastjson到1.2.84`） | AI |
| 2 | 推 `prod` 分支 | 用户确认后 AI 执行 |
| 3 | `mvn -N clean deploy` 发 parent 到 Nexus | AI |
| 4 | Jenkins 批量重建 test 全部 `*-web-test`（脚本复用 `../04回滚/02回滚执行方案.md` 第 6.1 节，直接改标题） | 用户点 |
| 5 | 抽 3 个服务进 Pod 验证：`jar tf /opt/app/xxx-web.jar \| grep fastjson` → 应看到 `fastjson-1.2.84.jar` | AI |
| 6 | 冒烟：登录 / 网关转发 / source 列表 / 一个导出 / 一条 MQ | AI + 测试 |
| 7 | 同流程走 UAT → 生产 | 用户 + 运维 |

**（可选，建议做）同时把 SafeMode 加回来**，作为第二道锁：

```dockerfile
ENV JAVA_TOOL_OPTIONS="-Dfastjson.parser.safeMode=true -Dfastjson2.parser.safeMode=true"
```

两个属性名都写，1.x/2.x 都能生效，以后升到 2.x 不用再改一遍。实测我们代码 AutoType 使用 0 处，开了没有副作用。

**回退：** 版本号改回 `1.2.83`，重发 parent，重建服务。或直接回滚镜像 tag。

## 阶段 2 · 公共包先发（半天）

**发布顺序不能反**（parent 是版本总闸，另两个编译时要继承它）：

```
① scm-cloud-parent                （版本号 2.0.64）
② scm-cloud-dependencies-oauth2   （B1 修复）
③ scm-common-json + scm-share-aim-spring（A 档修复 + RuleInputUtil 上提）
④ scm-ifs-* / scm-platform-* / scm-ubm-* 业务 jar（B2/B3 修复）
```

**⚠️ 分水岭提醒（这条上次写过，还是最重要的一条）：** 三个地基仓都是 `1.0.0-JDSN-SNAPSHOT`，**Nexus 上只有一份，全环境共用**。第 ① 步一发完，**任何人重建任何服务（含 uat/prod）都会变成 2.0.64**。所以：

> 发 Nexus 到 test 验证完这段窗口，必须约好：**别让人去重建 uat / prod 的服务。**

发布前每个仓库都要 `git fetch` + 确认 `git diff` 只有本次改动（上次真踩过"用落后分支 deploy 把 Nexus 上同事的新内容覆盖成旧的"）。

## 阶段 3 · 分批部署（这是你说的"防止全部署完出错得回滚"）

**test 环境按 4 个波次，每波验完再下一波。任何一波出问题，停下修，不往下走。**

### 波次 1 · 探路（2 个服务，最低风险）
```
scm-cloud-file-web-test
scm-cloud-scheduling-web-test
```
**验什么：** 这一波不验业务，验**链路本身通不通**——公共包有没有真的进镜像。
进 Pod：`jar tf /opt/app/xxx-web.jar | grep fastjson` → 必须看到 `fastjson-2.0.64.jar` + `fastjson2-2.0.64.jar`。
看不到就说明 Jenkins 缓存没刷新（上次踩过），重新 deploy 一次 bump build 号再重建。

### 波次 2 · 入口层（3 个服务）
```
scm-gateway-web-test
scm-gateway-mall-web-test
scm-auth-web-test
```
**验什么：** 登录能不能进、网关转发正常、token 正常。这两个坏了是全站不可用，所以单独一波、验透。

### 波次 3 · 一般业务（9 个服务，可以连着点）
```
scm-professor-web-test   scm-workflow-web-test   scm-fee-web-test
scm-contract-web-test    scm-devops-web-test     scm-report-web-test
scm-srm-web-test         scm-product-web-test    scm-order-web-test
```
**验什么：** 各自主流程列表 + 详情 + 一个导出 + 操作按钮显示正常。**重点看操作按钮**——B1 坏了的表现就是"列表有数据但按钮没了"，而且**接口还是返回 200**（`GlobalResponseHandler` 会吞掉异常），最阴险。

### 波次 4 · 高风险（4 个服务，一个一个来，每个验完再下一个）
```
scm-source-web-test        ← B1 + B2，上次首发故障点
scm-ubm-web-test           ← B3
scm-ubm-mall-web-test      ← B3
scm-ifs-web-test           ← B3 + 数据库模板
scm-ifs-schedule-web-test  ← 同上
```
**source 的验收点（能一眼看出新旧代码）：** 调 `/e/business/source/source/querySupplierSourcePageList`，**每一行都要有 `operList` 且不为空**。日志里不能出现 `java.lang.String cannot be cast to java.util.Date`。
**ifs 的验收点：** 跑一条京东价格变更消息，商品池状态要从 `ERROR` 走到 `FINISH`；日志里不能出现 `没有找到 ProductSkuCache 的方法：get(String)`。

### 然后：UAT 同样 4 波 → 生产同样 4 波

**生产有个前置问题**：上一轮记录显示 **Jenkins 上没有 `*-web-prod` 任务**（但 `02回滚执行方案.md` 6.5 节又列了一份 prod 任务清单，两处对不上）。**生产发布入口必须先跟运维问清楚**，已列进 `11-待确认问题-cc.md`。

## 阶段 4 · 验证与对账（每一波都做）

**四层，缺一层都不能说"这波过了"：**

| 层 | 查什么 | 命令 / 方法 |
|---|---|---|
| 1 构建 | Jenkins 绿灯 | 看流水线 |
| 2 制品 | 大 jar 里真的是 2.0.64 | `jar tf /opt/app/xxx-web.jar \| grep -E 'fastjson2?-.*\.jar'` |
| 3 进程 | 新 Pod 起来了、旧的没了；SafeMode 参数读到了 | `tr '\0' '\n' </proc/1/environ \| grep JAVA_TOOL_OPTIONS` |
| 4 业务 | 按上面各波的验收点 + 产品那份测试清单 | curl / 页面 |

**特别强调（上次的血泪）：**
- **HTTP 200 + `status:true` 不代表成功。** B1 那类错误被公共层 `try/catch` 吞了，接口照样 200，只是按钮没补上。**必须逐行看 `operList`。**
- **Jenkins 绿灯不代表 Pod 换了。** 必须看第 2、3 层。

## 3.5 回滚预案（真出事怎么办）

**分两种：**

| 出问题的范围 | 怎么退 | 多久 |
|---|---|---|
| **单个服务**（比如只有 source 崩） | K8s 回滚到上一个镜像 tag，其他服务不动 | 分钟级 |
| **公共包问题**（多个服务同时崩） | ① 把 parent 版本号改回 1.2.84 → ② 重发 parent 和公共包 → ③ 重建服务 | 小时级 |

**关键：退到 1.2.84，不是退到 1.2.83。** 1.2.84 是已修复版本，退回去不会把漏洞 A 带回生产——**这是阶段 0 先做的最大价值：给 2.x 升级准备了一个"安全的退路"**。上次回滚之所以那么被动，就是因为唯一的退路（1.2.83）本身带着漏洞，进退两难。

**开始前必须记录：** 每个服务当前镜像 tag、公共包发布前 Nexus 上的时间戳。

# 30 秒复述（你被问的时候照念）

> "我把这次升级要踩的坑提前全查了一遍。结论三条：
> 第一，**现在这个状态其实最不安全**——回滚到 1.2.83 之后，1.x 那个 RCE 漏洞又回来了，而且当初挡漏洞的安全模式开关也一起撤掉了。好消息是 7 月 29 号官方发了 1.2.84，专门修这个，改一个版本号就行，我实测过行为和现在一模一样、零兼容风险。建议先花一两天把这个做掉止血。
> 第二，**2.x 升级的雷我全部定位并量化了**：编译层面只有 1 个方法没了、2 处代码；运行层面只有 3 类行为变化、加起来 21 处，全都有实测过的修法。上次之所以一批一批冒问题，是因为其中两类只能等业务跑到才炸；这次我拿两个真 jar 对跑，把差异表列出来再去代码里数，不靠等它炸。而且我发现上次只修了 IFS，同样的问题在 pipeline、ubm 还有 5 处没修，这就是为什么处理完还会冒新问题。
> 第三，**公共包先发、服务分 4 波部署**，从最不重要的服务探路，再到网关，再到一般业务，最后才是 source 和 IFS 这两个上次出事的。每一波都有能一眼看出新旧代码的验收点，坏了只退那一波。而且因为先上了 1.2.84，万一 2.x 出问题，退路是安全版本，不会像上次那样'退也带漏洞、不退也带漏洞'。"
