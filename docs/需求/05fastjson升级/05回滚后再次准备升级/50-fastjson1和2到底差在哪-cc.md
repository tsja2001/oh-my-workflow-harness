# fastjson 1 和 2 到底差在哪，为什么会把业务代码搞崩

> 写给不熟悉 Java 的人看。所有对照数据都是拿两个版本的真实包跑出来的，不是推测。
> 实验脚本在 `verify-4versions/`，`bash wide.sh` 可以自己复现。

---

# 第一部分 · 先建立三个概念

## 1. fastjson 是干什么的

它是个**翻译官**，负责在两种形态之间来回翻：

```
Java 对象（程序里的活东西）  ⇄  JSON 文本（能存能传的字符串）
```

比如程序里有个"寻源单"对象，要发给前端，就得翻成 `{"code":"JC-0016","endTime":...}` 这样的文本。反过来，前端传上来的文本也要翻回对象。

**全公司二十几个后端服务都在用它**，一天要翻几百万次。所以它是个地基。

## 2. "对象"和"文本"的关键区别

这是理解后面所有问题的钥匙。用你熟悉的 Node 举例：

```js
const source = { endTime: new Date() }

source.endTime instanceof Date   // true —— 它是个"活的"日期对象，能比较、能加减

const copied = JSON.parse(JSON.stringify(source))

copied.endTime instanceof Date   // false
typeof copied.endTime            // "string" —— 变成一串文字了
```

**一旦经过"写成文本再读回来"这一趟，日期就不再是日期了，只剩下长得像日期的一串字。**

Java 里这个区别更要命，因为 Java 是强类型的：

| | Java 类型 | 能不能直接判断"截止了没有" |
|---|---|---|
| 活的日期对象 | `java.util.Date` | 可以，直接 `endTime.after(现在)` |
| 长得像日期的文字 | `java.lang.String` | **不行，会直接抛异常** |

Node 里你把字符串当日期用，顶多结果不对；**Java 里会直接崩**。这就是上次寻源列表按钮消失的根源。

## 3. 为什么"换个版本"能出这么多事

大多数人的直觉是：升级 = 修 bug + 加功能，老代码照跑。

fastjson 1 → 2 不是这样。它是**同一个牌子的两套内核**：方法名一模一样、调用写法一模一样，所以编译器基本不会报错——**但方法内部干的事变了**。

打个比方：还是那个翻译官，还是那个名字，人换了。你交给他同一份材料、说同一句话，他给你的东西不一样了。而你的代码是照着老翻译官的习惯写的。

这就导致：

- 编译器帮不了你（签名没变）
- 单元测试也未必发现（很多路径要真实数据才走到）
- **只有真正跑到那一行、那种数据的时候才炸**

上次之所以"处理完一批又冒一批"，就是这个原因——不是没修干净，是根本没法靠编译和静态检查把它们一次性找出来。

# 第二部分 · 六个变化点，逐个讲

这次我没有靠"边升边查"。我写了 112 项行为测试，用两个版本的真实包各跑一遍自动比对：**96 项完全一样，16 项不一样**，归成下面 6 类。

---

## 变化 1 · 有个方法被删了

**一句话**：1.x 里有个叫 `getClassFromMapping` 的工具方法，2.x 把它删了。

**这个最简单**，也是唯一一个编译器能帮你抓到的。代码里写了个不存在的方法名，编译直接过不去，打不出包。

**我们踩到 2 处**，都在公共依赖里。

**为什么它反而是最不危险的**：因为它藏不住。一编译就报错，不可能带着它上线。真正危险的是下面那些**编译得过、跑起来才出事**的。

---

## 变化 2 · 日期在中转时被变成了字符串 ⭐ 上次寻源按钮消失的元凶

**一句话**：把一行数据从"JSON 对象"倒进"普通字典"的时候，1.x 是直接搬，2.x 会先写成文本再读回来 —— 日期就在这一趟里变成字符串了。

**实测对照**：

```
准备一行数据：{ 时间: 活的日期对象, 数字: 7, 布尔: true }
然后做同一个"倒进字典"的操作 ——

fastjson 1.2.83 →  时间的类型 = java.util.Date      （还是活的）
fastjson 2.0.64 →  时间的类型 = java.lang.String    （变成文字了）

数字和布尔两个版本都没变，只有日期出问题。
```

这就是第一部分讲的 `JSON.parse(JSON.stringify(x))` 那件事——2.x 内部悄悄多做了一趟文本往返。

### 它是怎么把页面搞崩的

我们系统有个公共功能：列表接口返回之后，公共层会给**每一行**补上"报价、撤回、咨询"这些操作按钮。补按钮要先判断"这单截止了没有"，就得读那一行的截止时间。

完整链路是这样：

```
前端请求供应商寻源列表
      ↓
查数据库 —— 这一步完全正常，时间是活的日期对象
      ↓
公共层准备给每行补按钮，把这行数据倒进一个字典 ←←← 就是这里
      ↓
      1.x：时间还是日期对象  →  正常判断  →  按钮补上了
      2.x：时间变成字符串    →  下一步崩
      ↓
业务代码：拿这个时间当日期用，判断"截止了没有"
      ↓
   崩：String 不能当 Date 用
```

### 最阴的地方：接口还是返回 200

补按钮这段代码外面包了一层"出错就记个日志、别影响主流程"的保护。结果就是：

```json
HTTP 200 OK
{
  "status": true,
  "data": { "root": [ 有数据的列表... ] }     ← 数据都在
}
```

**接口是通的、数据也有，就是按钮那一栏空了。**

所以当时排查特别费劲——监控不报警、接口不报错、日志里只有一行不起眼的异常，只有用户说"我这按钮怎么没了"才发现。

> 这也是为什么这次部署验收我一再强调：**返回 200 不代表成功，必须逐行看按钮**。

**我们踩到 2 处**，都在公共依赖里（一处管单条数据的接口，一处管列表接口）。

---

## 变化 3 · 嵌套的对象不再被"拆平"了 ⭐ 上次 IFS 京东同步报错的元凶

**一句话**：把一个对象转成 JSON 结构时，1.x 会**从里到外每一层都转成字典**，2.x 只转最外面一层，里面的原样不动。

### 先解释"为什么这事很重要"

我们系统里有个**规则引擎**：一些业务逻辑不写死在代码里，而是存在数据库里的一段小脚本，运维可以随时改。IFS 对接京东、SAP、OA 那些流程，大量用了这个。

脚本长这样（这是数据库里的真实内容）：

```
detailMap = skuModel.get("detailMap");
detailObj = detailMap.get("detail");
contentStr = detailObj.get("content");
```

一层层 `.get("字段名")` 往下挖——**这种写法只对"字典"有效**。

而这些脚本是好几年前照着 fastjson 1.x 的行为写的：1.x 会把整个对象树从里到外都拆成字典，所以挖到哪一层都能 `.get()`。

### 实测对照

```
准备一个对象：商品模型 { 明细字典: { "detail" → 明细对象 }, 顶层时间: 日期 }
转成 JSON 结构之后 ——

                      1.2.83              2.0.64
最外层                 字典 ✅              字典 ✅
明细字典                字典 ✅              字典 ✅
明细字典里的那个对象      字典 ✅              还是原来那个 Java 对象 ❌
```

最里面那层，2.x 没有转。

### 于是脚本就崩了

脚本走到 `detailObj.get("content")` 时：

- 1.x：`detailObj` 是个字典 → `.get("content")` 取到值，正常
- 2.x：`detailObj` 是个 Java 对象 → 这种对象只有 `getContent()` 这种方法，**没有 `.get("字段名")` 这种用法** → 报错

线上的错误信息就是：**"没有找到 ProductSkuCache 的方法：get(String)"**。

京东价格变更的消息进来处理不了，商品池的记录卡在 ERROR 状态。

### 顺便说清楚 2.x 的真实边界（这个细节很关键）

不是"全都不转了"，我实测出来是这样：

| 数据结构 | 1.2.83 | 2.0.64 |
|---|---|---|
| 直接挂在对象上的字段 | 转 ✅ | 转 ✅ **一样** |
| 列表里的元素 | 转 ✅ | 转 ✅ **一样** |
| **字典里存的值** | 转 ✅ | **不转 ❌** |
| **数组里的元素** | 转 ✅ | **不转 ❌** |

**只有"字典的值"和"数组"出问题。** 这一条把排查范围从"全代码库 104 处"缩到了真正有风险的那一小撮，也是这次能把范围说清楚的关键。

**我们踩到的范围**：全平台 22 个用规则脚本的地方，分布在 IFS、pipeline、静态数据、工作台待办、邀请、批处理 6 个模块。

> 上次只修了 IFS 的一部分，另外 5 处一直留着。它们没炸只是因为刚好没跑到那种数据。这就是"处理完又冒新问题"的机制。

---

## 变化 4 · 同一件事，两种写法结果相反 ⭐ 这次新查出来的，不修必挂

**一句话**：把一个 JSON 对象转成文本，有两种写法。它们在 1.x 下结果一样，**在 2.x 下日期的写法是反的**。

### 实测对照（这个最好玩，也最坑）

```
准备：{ 时间: 活的日期对象, 数字: 7, 文字: "abc" }

写法A（问对象自己）：  jsonObj.toJSONString()
写法B（交给翻译官）：  JSON.toJSONString(jsonObj)

                    写法A                              写法B
1.2.83   {"t":1780000000000, ...}          {"t":1780000000000, ...}    ← 两种一样
2.0.64   {"t":"2026-05-29 04:26:40", ...}  {"t":1780000000000, ...}    ← 反了
```

写法 A 在 2.x 下输出**字符串**，写法 B 还是**时间戳数字**。

而在 1.x 时代，两种写法**没有任何区别**，所以历史上谁想怎么写就怎么写，代码里两种混着用。

### 为什么这个特别难发现

前三个变化好歹有个"故障现象"——编译报错、按钮没了、日志报错。这个不一样：

**它不报错，只是内容变了。**

程序照常运行，日志一切正常，只是发出去的报文里日期长得不一样了。如果对方系统不校验，可能几个月都没人发现；如果对方校验，就是莫名其妙的失败。

### 我们踩到最要命的一处：流程审批签名

`DPS流程审批` 对接的代码是这样的：

```java
String 签名 = Base64(MD5(params.toJSONString()));   ← 写法A
```

它把报文内容算个 MD5 当签名，对方拿同样的规则验。

**报文里只要有日期，2.x 下算出来的 MD5 就和对方对不上，签名校验直接失败。**

现象是"审批对接报鉴权失败"——你根本不会往 fastjson 上想，会先怀疑密钥错了、时钟不同步、对方改接口了。这种问题排查起来能耗好几天。

**我们一共 21 处用了写法 A**，除签名那 2 处外，还散布在：请求报文存库（8 处）、对外接口报文（IFS 一批）、MQ 消息体（1 处）、日志打印（几处）。

**改法**：全部统一成写法 B。一行换一行，逻辑不动。

严格说不是每一处都会出问题——取决于那个对象里有没有日期。但要逐处往上追数据从哪来，成本高、漏一个就是一个线上问题，所以统一换掉，把这一类风险一次性清零。

---

## 变化 5 · 新式日期类型的写法反了（我们几乎没用）

**一句话**：Java 有新旧两套日期类型。老的（`Date`）两个版本表现一样；新的（`LocalDate`、`LocalDateTime`）反了。

**实测对照**：

```
一个 LocalDate（2026年6月10日）：

1.2.83 →  "2026-06-10"        （字符串，人能看懂）
2.0.64 →  1781020800000       （时间戳数字）
```

如果这种字段出现在接口返回里，**前端页面上会显示成一串数字**。

**但我们基本没用它**。全代码库当成实体字段声明的只有 4 处：

- 2 处在一个日期计算的工具类里，压根不进接口
- 2 处在短信 VO 里，而且只做入参、从不作为返回值

所以**这条对我们影响约等于零**。查它花的时间不亏——如果我们大量用了新式日期，这就是个全站级的问题。

---

## 变化 6 · 空值会把默认值冲掉（我们没踩到）

**一句话**：字段设了默认值，如果传上来的是 `null`，1.x 保留默认值，2.x 强行冲成 0。

**实测对照**：

```
字段定义：每页条数 = 10（默认值）

传 {"每页条数": null} 进来：
  1.2.83 →  10   （保留默认值）
  2.0.64 →  0    （冲成 0）
```

**危险在哪**：分页大小被冲成 0，查询就查不出东西；某个开关默认开着，被冲成关。而且**不报任何错**，就是行为悄悄变了。

**我们没踩到**。涉及的 11 个数据对象里：

- 9 个的默认值本来就是 0 或 false —— "冲成 0"等于没变化
- 剩下 2 个：一个只在程序里 new 出来用、根本不走 JSON；一个（那个分页对象）全代码库**没有任何地方在用**

**一个补充**：字段**完全没传**的时候，两个版本都保留默认值。只有**明确传了 null** 才会被冲掉。这个区别我也测了，所以能说清楚边界。

# 第三部分 · 为什么这类问题这么难对付

把上面六条放一起看，能看出一个规律：

| 变化 | 编译能发现吗 | 有明显报错吗 | 难度 |
|---|---|---|---|
| 1 方法被删 | ✅ 能 | — | 最简单，藏不住 |
| 2 日期变字符串 | ❌ 不能 | 有异常但**被吞了**，接口仍返回 200 | 难 |
| 3 嵌套不拆平 | ❌ 不能 | 有报错，但要跑到那种数据才出现 | 难 |
| 4 两种写法结果相反 | ❌ 不能 | **完全不报错**，只是内容变了 | 最难 |
| 5 新式日期 | ❌ 不能 | 不报错，页面显示成数字 | 难 |
| 6 空值冲默认值 | ❌ 不能 | **完全不报错**，行为悄悄变了 | 最难 |

**六条里只有一条能靠编译发现，其余五条全靠"跑到才知道"。**

而"跑到"是有条件的——得刚好有那种数据、刚好走那条分支。上次生产上是一批一批冒出来的，就是这个道理：不是没修干净，是每次只有那一批数据先跑到。

## 这次换了个办法

既然靠"等它炸"不行，就反过来做：

**不去猜哪里会坏，而是把两个版本的行为逐项跑一遍，做差集。**

112 项测试 → 96 项一样、16 项不一样 → 归成 6 个原因 → 拿这 6 个原因回代码库里挨个数处数。

好处是这份清单是**穷举出来的**，不依赖"我有没有想到"。

代价是比原计划多查出 3 条（变化 4、5、6）——其中变化 4 那个签名问题，靠上线后观察大概率要好几天才能定位。

# 第四部分 · 这次怎么修的

## 一个原则：能在公共层解决的，绝不去改业务模块

修改越分散，越容易漏；漏一处就是一次线上故障。所以我把每一条都先问一遍："能不能只改公共依赖？"

| 变化 | 修在哪 | 业务模块要动吗 |
|---|---|---|
| 1 方法被删 | 公共依赖 2 个文件 | **不动** |
| 2 日期变字符串 | 公共依赖 1 个文件（2 行） | **不动** |
| 3 嵌套不拆平 | 公共依赖 1 个方法 | **不动** |
| 4 两种写法相反 | 只能改业务代码，21 处 | 要动，但是机械替换 |
| 5、6 | 核实后确认不用改 | — |

**上次真正炸过的三类（1、2、3），全部收进了公共依赖。**

## 变化 3 的修法值得单独说

这是这次做法上最大的改进。

上次的做法是：在 IFS 里找到 5 个"把对象塞给规则脚本"的地方，逐个改。结果**漏了 5 处**（在 pipeline、静态数据、工作台待办、批处理里），所以处理完还会冒新问题。

这次我往上追了一层，发现一件事：

> 全平台 22 个用规则脚本的地方，**最后都汇到同一个方法**：
> 脚本引擎的入口 `RuleEngineService.execute(脚本, 数据)`

打个比方：上次是挨个房间换灯泡，还漏了几间；这次是找到了总电闸。

所以修法变成：**在这一个入口处，把数据统一处理成规则脚本期望的样子（也就是恢复 1.x 的行为）**。

效果：
- 22 个调用点，一次全覆盖
- 6 个业务模块，一行代码都不用改
- **以后新写的规则也自动免疫**——这是最值钱的一点，等于把这个坑永久填上了

## 修完怎么验的

改完不能只说"我觉得对"。我做了三件事：

1. **编译验证**：5 个公共文件在 **2.0.64 和 1.2.83 下都编译通过，0 报错**。
   （两个版本都过，意味着万一要回滚，只改一个版本号就行，代码不用撤——这和上次要反向撤销三个仓库完全不同）

2. **行为验证**：25 项断言，而且是**直接调用改完之后编译出来的真实代码**，不是测一份副本。两个版本各 25/25 通过。重点验了：
   - 规则脚本能不能一层层 `.get()` 挖到最里面
   - 挖到最里面的日期**还是不是活的日期**（不能修好一个坑又挖一个）
   - 补按钮的时候，改动后拿到的还是不是**原来那个对象**（如果变成拷贝，按钮就写不回去了——这会是个新的静默故障，专门验了）

3. **对照实验**：编译时有几个文件报错，我把它们还原成改动前再编一次，**报错数量完全一样**，证明是环境问题不是我改出来的。

---

# 一句话总结

> fastjson 1 和 2 是同一个牌子的两套内核：**方法名没变，方法干的事变了**。所以编译器基本发现不了，只能靠真实数据跑到才暴露——上次就是这么一批一批炸出来的。
>
> 这次先把两个版本的行为逐项跑一遍做差集，把清单穷举出来（96 项一样、16 项不一样、归成 6 个原因），再回代码里数处数。
>
> 结果是：上次真正炸过的三类问题，全部能只改公共依赖解决，业务模块一行不动；业务代码只剩一类机械替换，其中流程审批签名那 2 处是不改就一定出事的。
