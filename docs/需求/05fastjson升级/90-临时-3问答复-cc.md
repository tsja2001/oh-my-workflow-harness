## Q1：改 `scm-cloud-dependencies`，只改那两处就够吗？

**结论：够。全公司代码里这种写法只有那两处，没有第三处。**

我在整个 `01zhaocai-end`（所有公司仓库）里搜了 `toJavaObject(new TypeReference<Map...`，结果只有两条命中，都在同一个文件：

```
scm-cloud-dependencies-oauth2/.../OperListResponseTransferServiceImpl.java:83   ← 单对象分支
scm-cloud-dependencies-oauth2/.../OperListResponseTransferServiceImpl.java:117  ← 数组分支
```

为什么"两处 = 全局修复"，而不是"只修了寻源"：

- 这个 `OperListResponseTransferServiceImpl` 是**公共转换器**，全项目所有带 `@DataResponseTransfer` 注解的接口（本地扫到约 **140 处**）补操作按钮时，**都必须经过它这两个方法之一**（返回单对象走 83，返回列表走 117）。
- 所以这两行是"所有列表/对象补按钮"的**唯一必经关口**。把关口上的类型损坏堵掉，等于给所有走这条路的接口一起修好。
- 两处缺一不可：只修 117，寻源列表能好；但哪天某个"返回单对象"的接口一样会在 83 犯同样的病。

**话术：** "全公司代码搜过了，这个写法只有那一个文件的两处，没有别的地方。而且这个类是所有接口补操作按钮的必经公共关口，140 处注解都走它，所以改这两处就是全局修复，不是只修寻源。两处一个管列表、一个管单对象，一起改。"

## Q2：能不能改 `JsonTransferUtil`（上次升级改的那个），加个类/方法全局解决？

**结论：不能。因为这次的 bug 根本不在 `JsonTransferUtil` 里——它是另一个仓库、另一件事。**

### `JsonTransferUtil` 到底干嘛的

它是个 **JSON 路径导航器**，就干一件事：给它一个大 JSON 和一条路径（比如 `data.root`），它顺着路径走下去，把那个节点取出来。核心就这几行：

```java
// JsonTransferUtil.java：顺着 data.root 一层层往下取，最后把节点返回
for (String path : splitArrs) { g = source.get(path); ... }
return JSONObject.toJavaObject((JSON) g, returnClass);   // returnClass 是 JSONObject / JSONArray
```

关键点：它返回的是 `JSONObject` / `JSONArray`（结构本身），**转换目标是"结构类型"，不是"无类型的 Map"，所以它不会把 Date 降级成 String**。实测也证明：数据过完 `JsonTransferUtil`，日期仍然是 `Date`（1.x、2.x 都一样）。**它是清白的。**

### 真正的爆点在别处、别的仓库

| 文件 | 所在仓库 | 角色 | 是不是本次爆点 |
|---|---|---|---|
| `JsonTransferUtil.java` | **scm-assemblies-all**（公共工具） | 走路径取 `data.root` | 否，不碰日期类型 |
| `OperListResponseTransferServiceImpl.java` | **scm-cloud-dependencies**（Web/OAuth2 框架） | 取到每一行后转 `Map<String,Object>` 补按钮 | **是**，就这一步把 Date 变 String |

两者是**不同仓库**。上次（`80e24fa`）改 `JsonTransferUtil`，是因为当时的问题是"fastjson2 删了一个旧方法"，正好那个旧方法在它里面被调用——那是**另一种病**（方法没了、编译/运行失败）。这次是"方法还在、但行为变了（Date→String）"，病灶在转换器，不在工具类。**同一次升级引出的两件不同的事，不能套用上次的修法。**

### 领导"想收敛成一个公共方法"的思路——能做，但绕不开转换器

如果目的是"别散在两处、抽成一个公共方法方便以后复用"，完全可以：把浅拷贝封装成一个工具方法（放 `JsonTransferUtil` 里当个新方法也行），比如

```java
// 可选：在 JsonTransferUtil 里加一个类型保真的转换方法
public static Map<String,Object> toTypedMap(JSONObject obj) { return new java.util.HashMap<>(obj); }
```

然后转换器两处改成 `JsonTransferUtil.toTypedMap(obj)`。

但请注意：**即便这样，调用点还是必须在转换器那两处改**——因为"把每一行转成 Map"这个动作是转换器在做的，损坏就发生在它手里。**"只动 JsonTransferUtil、完全不碰转换器就能修好"是做不到的。** 加公共方法只是把修法收纳得更整齐，不改变"必须在那两处落地"这个事实。（其实两处就两行，是否抽公共方法可有可无，不抽也不算 hack。）

**话术：** "这次的坑不在 `JsonTransferUtil` 里——它只负责按路径取数据、不碰日期类型，我读过也实测过，过完它日期还是 Date。真正把 Date 变 String 的是另一个仓库 `scm-cloud-dependencies` 里的转换器。上次改 `JsonTransferUtil` 是因为那次是'方法被删'的另一种问题，这次不一样。想把修复抽成一个公共方法当然可以，但落地点还是得在转换器那两处，绕不开。"

## Q3：现在的时间格式是什么？能不能在时间格式的"序列化/反序列化"上处理来解决？

**结论：这个思路很专业，但在**本场景**救不了——因为转换的目标是"无类型的 Map"，反序列化时 fastjson 根本不知道哪个字段该是日期，所以"日期格式"这个开关无从触发。**

### 先回答"现在的格式是什么"

fastjson 2.x 在那一步把 `Date` 写出来时，用的是它的**默认日期格式** `yyyy-MM-dd HH:mm:ss`，所以 Map 里最后存的是一串这样的字符串：`"2026-06-10 22:00:00"`（和数据库里那条数据实测一致）。

### 为什么"在格式上处理"这次不行

日期格式（`@JSONField(format=...)`、全局 DateFormat 之类）**只在"fastjson 明确知道目标字段是 Date"时才起作用**。而这次的转换目标是：

```java
new TypeReference<Map<String, Object>>() {}     // 值的类型是 Object —— 无类型
```

值槽是 `Object`（无类型口袋）。反序列化时，fastjson 看到字符串 `"2026-06-10 22:00:00"` 要放进一个 `Object` 槽，**它没有任何信息告诉它"这个字段应该是日期"**，于是原样留成 String。你把日期格式配得再漂亮，也只是决定"字符串长什么样"，触发不了"把它解析回 Date"这个动作——**问题不在格式，在于目标是无类型 Map。**

### 领导这个思路在什么情况下是对的

如果这一步转的是**带 Date 字段的具体 VO 类**（比如 `toJavaObject(SupplierSourceVO.class)`，里面声明了 `Date sourceSignEndTime`），那么"序列化/反序列化 + 日期格式"就**真的能解决**——因为 fastjson 知道目标字段是 Date，会照格式把字符串解析回 Date。

**但**这个转换器是**通用**的：它要服务 140 种不同返回结构，不可能知道每个接口具体是哪个 VO，所以只能转成通用的 `Map<String,Object>`。一旦转成通用 Map，就失去了"哪个字段是日期"的类型信息，格式化也就没了着力点。**领导的方向对，只是不适用于"通用 Map"这个具体写法。**

### 一个技术上存在、但坚决不能用的开关

fastjson 确实有办法让"往返"保留类型（写出时带类型名 `WriteClassName` + 读取时开 `AutoType`），这样 Date 能被还原。**但 `AutoType` 正是我们这次升级要消灭的那个安全漏洞（RCE）的来源**，开它等于把漏洞重新请回来，**坚决不开**。

**话术：** "领导说的'在序列化/反序列化的日期格式上处理'，思路是对的——但只在'目标类型明确是 Date'时才管用。我们这一步是把整行转成一个**无类型的通用 Map**（值是 Object），fastjson 不知道哪个字段是日期，所以日期格式这个开关根本触发不了，配了也只是改字符串长相。要让格式生效，就得转成带 Date 字段的具体 VO，但这个转换器是给 140 种接口通用的，做不到。所以根治还是回到'别做这次往返（浅拷贝）'或'读取时把字符串解析回 Date'这两条。"

> 一句话总括：**格式管的是"字符串写成啥样"，管不了"它是不是 Date"。类型信息在转成通用 Map 的那一刻就丢了，格式救不回来。**

## Q4：想写个测试验证效果——思路（暂不落代码）

领导想要一个能**跑出来看**的测试。目标是把三件事一次性钉死：

1. **复现**：fastjson 2.x 在那一步确实把 Date 变成 String；
2. **证伪 JsonTransferUtil**：数据过完 `JsonTransferUtil` 时 Date 还在（它不是元凶）；
3. **验证修复**：浅拷贝能保住 Date，且**不误伤**数字/布尔/字符串/嵌套对象。

### 测试步骤（一条直路）

```
① 构造一个"贴近真实返回"的对象：Result → data.root(数组) → 一行里放
   sourceSignEndTime = 真正的 Date、needQual = Integer、state = String、
   isPublic = Integer、再塞一个嵌套对象，用 JSON.toJSON(...) 生成 JSONObject
        │
② 用 JsonTransferUtil.getJsonPath 取到 data.root
   断言：此时这一行里的 sourceSignEndTime 仍是 Date   ← 证明工具类清白
        │
③ 对同一行分别跑两种写法：
   旧：row.toJavaObject(new TypeReference<Map<String,Object>>(){})
        断言：sourceSignEndTime 变成了 String          ← 复现 bug
   新：new HashMap<>(row)
        断言：sourceSignEndTime 仍是 Date              ← 验证修复
        │
④ 对"新写法"的结果再断言其它类型没被改坏：
   needQual 仍是 Integer、isPublic 仍是 Integer、
   state 仍是 String、嵌套对象仍是对象（Map/JSONObject）
        │
⑤ 把①~④在两套依赖下各跑一遍：fastjson 1.2.83 与 2.0.62
   预期：1.2.83 两种写法都保住 Date（解释为何历史上一直没事）；
        2.0.62 旧写法变 String、新写法保住 Date（解释坑与修复）
```

### 形式建议

- **最快**：写一个独立的 `main` 小程序，把 fastjson 的 1.2.83 / 2.0.62 两个 jar 分别放进 classpath 各跑一次（和 codex 之前的对照实验同款做法，不依赖整仓库编译）。今天就能出结果。
- **要进仓库长期留存**：放到对应模块的 `src/test/java` 下写成 JUnit 用例，断言同上。因为项目平时不做全量 mvn 编译，跑单测需要单独指定该模块，落地时再定。

### 一句纠偏（也告诉领导）

这个测试验的是**"修复效果 + 不误伤"**；其中第②步顺便就证明了 `JsonTransferUtil` 是清白的（对应 Q2）。所以**测试挂在"验证修复"上，而不是挂在"改 JsonTransferUtil 之后"**——因为按 Q2 的结论，`JsonTransferUtil` 这次不需要改。

**话术：** "测试我按这个思路搭：构造一行带日期、数字、嵌套对象的真实返回，先过一遍工具类证明它不背锅，再对同一行跑旧写法（复现变 String）和新写法（保住 Date），最后确认数字、对象都没被改坏；整套在 1.2.83 和 2.0.62 两个版本下各跑一遍对照。最快用独立小程序今天就能出结果，要留仓库就写成单元测试。"

## 补充：有人提议"在静态块里设全局日期格式"——已实测，不行（附真实输出）

有一版具体改法是在 `JsonTransferUtil` 的静态块里加：

```java
static {
    JSON.configWriterDateFormat("yyyy-MM-dd'T'HH:mm:ss.SSS'Z'");
    JSON.configReaderDateFormat("yyyy-MM-dd'T'HH:mm:ss.SSS'Z'");
    ESCAPELIST.add(".");
}
```

**用 fastjson 2.0.62 真实 jar 实测，结论：这条路不行。** 三层问题，一层比一层要命：

**① 编译层：按现在的 import 根本编译不过。**
`configWriterDateFormat` / `configReaderDateFormat` 只存在于**原生** `com.alibaba.fastjson2.JSON`；而 `JsonTransferUtil` 现在 import 的是 **compat** `com.alibaba.fastjson.JSON`，它**没有**这两个方法（`javap` 确认、`javac` 直接报 `cannot find symbol`）。

**② 效果层（最要命）：就算改用原生类真设上，报错一点没变。** 实测输出：

| 写法 | 日期最终类型 | `(Date)` 强转 |
|---|---|---|
| 现状 `toJavaObject`（不配格式） | String `2026-07-28 09:33:22.973` | ❌ ClassCastException |
| **配了全局格式后** `toJavaObject` | String `2026-07-28T09:33:23.058Z` | ❌ **照样崩** |
| `new HashMap<>(row)` 浅拷贝 | **Date** | ✅ 成功 |

设了全局格式后，日期只是**从 `2026-07-28 09:33:22.973` 变成 `2026-07-28T09:33:23.058Z`——类型仍是 String**，`(Date)` 强转照样抛 `java.lang.String cannot be cast to java.util.Date`。**用真实输出证实了：格式只管字符串"长啥样"，管不了它"是不是 Date"。**

**③ 风险层：`configXxxDateFormat` 是全局、进程级、永久的开关。**
塞在静态块里，类一被加载就把整个应用的日期读写格式全改了，且 compat / 原生两条路表现还不一致（实测中 `toJSONString` 输出的仍是时间戳，没跟着变）。等于为一个根本没解决的问题引入全应用范围的副作用，只赔不赚。

> 对照实验程序在 `/tmp/fjtest/FjTest.java`（可复跑）；这个实验同时也满足了 Q4 想要的"验证测试"——复现 bug + 证否格式改法 + 证实浅拷贝有效，一次跑全。
>
> **话术：** "我实测过了，把那两个全局日期格式设上，寻源那行 `(Date)` 强转照样报 ClassCastException，一点没解决——它只是把日期字符串换了个样子，类型还是 String。而且这俩方法在我们代码 import 的那个 fastjson 类上根本没有、编译都过不了；就算换原生类，它也是全局开关会改掉整个应用的日期行为。所以还是用浅拷贝 `new HashMap<>()`，同一个实验里它两种情况都稳。"
