**2026-08-24 按用户要求简化**：三个环境脚本统一成同一套骨架，共 7 条语句，为的是能原样交给运维执行——
`SELECT DATABASE()` 确认库 → `CREATE TABLE ... LIKE` + `INSERT ... SELECT` 备份 → 备份行数检查 →
两句 `UPDATE` 改名 → 列出钢材指标核对。`01`/`02`/`03` 只差库名和预期条数，其余逐字相同，
所以 test/uat 验过就等于生产也验过。

`04-回滚` 同步简化为「照备份表按主键 JOIN 还原」一句话，原先那套"反向 UPDATE + 时间/主键排除条件"已删除
（新代码上线后会出现天生就叫新名字的数据，反向改必然误伤；test 上 `JGQS-20260824-003` 就是实例）。

环境事实（均实测）：
- 库是 **Percona XtraDB Cluster，`pxc_strict_mode=ENFORCING`**，`CREATE TABLE ... AS SELECT` 被直接拒绝，必须拆两句。
- `dbq.sh` 走 mysql 批处理，**遇第一个错误即整体中止**，脚本报错不会执行到一半。
- 库账号 `admin@%` 对 `*.*` 全权限，**test 和 uat 都能写，库名写错就改错环境**。
- 待改行数：test **6**，uat **24**（2026-08-24 17:x 实测）；prod 未知，由运维现场截图留档。
- 两个库当前均无 `sc_price_trend_bak%` 残留表。

用户第一次手动跑 SQL 的操作手册见 `50-手把手跑SQL-cc.md`。

**执行时机是死规矩**：SQL 必须和代码在**同一个发布窗口**。三个环境都已接台账（含 prod，见 `10` 文第 3 节更正），代码和数据只要不同步，那段时间驾驶舱和集采门户的螺纹、中厚板两条曲线就是空的——**不报错、不弹窗，就是没线**。

生产如果代码发布和 SQL 执行卡不到同一时间点，**必须先让后端走"新旧名都认"的兼容写法**（`10` 文第 5 节方案 B），否则生产大屏会空一段。
