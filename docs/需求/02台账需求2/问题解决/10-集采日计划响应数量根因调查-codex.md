## 1. 结论

同事预期的 `19,025` 算错了两处：

1. 把 2026-07-31 北京分公司这一行的“当月计划总数量 `19,000`”当成了“当月响应数量”；该行实际响应数量是 `18,800`。
2. 漏掉了同为 2026-07-31 的机电公司一行，其响应数量为 `260`。

正确计算为：

```text
7 月 31 日全部有效行的响应数量 = 18,800 + 260 = 19,060
当前日期前一日的云采响应数量 = 25
累计响应数量 = 19,060 + 25 = 19,085
```

页面统计卡片显示 `19,085.00` 正确，本问题无需修改累计计算代码。

## 3. 判断

现行需求写的是“每个月最后一天的当月响应数量 + 当前月当前日期前一日的当月响应数量”，而台账允许不同执行单位分别维护，所以同一统计日期可以有多行。代码对同日全部有效行求和，符合这个口径。

本次 `60` 的表面差额不能单独解释问题，因为同事的算法同时多算了 `200`（把 `18,800` 看成 `19,000`）并少算了 `260`（漏掉机电行），净差正好是 `60`：

```text
19,085 - 19,025 = 260 - 200 = 60
```

## 4. 另行发现的数据自洽问题

需求原文还规定：

```text
响应数量 = 执行中数量 + 已完成数量 + 已滞后数量
```

但 UAT 的两条 2026-07-31 人工数据都不满足这个关系：

- 北京分公司：`18,800 != 800 + 18,000 + 200`。
- 机电公司：`260 != 255 + 255 + 20`。

这不会改变“接口为何返回 19,085”的结论，但会让按“响应率 − 执行率 − 完成率”计算的滞后率出现负数。该问题涉及历史数据是否录错、页面是否应增加录入校验两个方向，不能擅自改数据或改口径，需要产品确认后另开修复。
