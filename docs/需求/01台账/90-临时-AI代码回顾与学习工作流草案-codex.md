# 代码复盘与理解交接工作流 · 设计草案

> 日期：2026-07-13<br>
> 工具：codex<br>
> 当前状态：已从单次实践草案提升为通用设计稿；本文先定义方法论，再据此更新正式工作流。<br>
> 下一阶段：将精炼后的规则写入 AGENTS、enterprise-dev-workflow、阶段提示词、文档模板和用户习惯文档。

> 本文讨论的不是某一种语言、框架或业务，而是如何把一段由 AI、前任开发者或多人协作产生的代码，转化成接手者可验证、可解释、可继续维护的知识。示例可以来自当前项目，但规则不能依赖某个示例成立。

---

## 1. 定位：从“代码交付”走到“所有权交接”

传统开发流程通常在代码合并、测试通过、部署完成后结束。但当代码主要由 AI 编写，或者接手者不熟悉语言、框架和业务时，技术上完成不等于真正交付：接手者仍然不知道为什么这样设计、运行时走哪条路径、出问题去哪里找、哪些结论只是推断。

因此需要一个独立阶段：

> **代码复盘与理解交接**：以可核实证据重建变更的来龙去脉和当前真实状态，提炼系统模型与关键链路，并通过实操、复述和问题演练，把后续维护所需的判断能力交给接手者。

它的交付对象不是代码，而是四种能力：

1. **定位能力**：知道从入口、日志、配置或数据怎样找到相关代码。
2. **解释能力**：能说明核心数据怎样流动、关键决定在哪里发生。
3. **判断能力**：能区分既有能力与本次变更、计划与事实、可配置与已生效、局部扩展与端到端扩展。
4. **沟通能力**：能向同事说明实现范围、设计取舍、风险和待确认口径。

建议正式阶段编号与产物：

```text
Phase 9：代码复盘与理解交接
docs/需求/<需求名>/50-代码复盘与学习-<工具代号>.md
```

“50”表示它位于开发、测试、评审之后的知识交接区；它也允许独立触发，不要求目标变更一定由当前 AI 开发。

## 2. 适用场景与非目标

### 2.1 适用场景

以下情况适合触发：

- 用户需要接手 AI 生成或 AI 参与较多的代码。
- 新成员接手遗留功能、陌生模块或陌生技术栈。
- 一个需求跨多个仓库、服务、数据库、配置中心或部署环境。
- 功能经历多次补丁、合并、回滚，最终状态难以从提交说明判断。
- 代码评审发现问题，但用户还不理解问题所在的完整链路。
- 线上故障、数据异常或版本事故后，需要从变更恢复系统认知。
- 重大重构、数据迁移、技术替换前，需要建立旧逻辑基线。
- 用户需要准备技术评审、交接会议、述职或与负责人沟通。

### 2.2 非目标

本阶段默认不负责：

- 直接修复发现的问题。
- 替代正式测试或代码评审。
- 穷举解释每个文件、字段、Getter 和框架基础知识。
- 根据提交信息猜测作者真实意图。
- 为了展示工作量而输出一份无法阅读的超长源码翻译。

发现缺陷时，记录证据并转入评审/开发流程；用户明确同时授权修复时，也要先完成事实边界，再单独实施修改。

## 3. 与开发交接、测试和代码评审的关系

| 阶段 | 主要回答的问题 | 典型证据 | 产物 |
|---|---|---|---|
| 开发交接 | 改了什么、提交在哪、怎样部署回退 | Diff、提交、编译结果 | 20开发交接 |
| 测试 | 关键行为是否符合预期 | 请求响应、日志、数据库结果 | 30测试报告 |
| 代码评审 | 是否存在正确性、安全性、可维护性问题 | 完整代码、样板、静态分析 | 40评审报告 |
| **理解交接** | 当前系统怎样工作、为什么、接手者怎样继续判断 | 需求、Git、最终代码、配置、运行证据 | 50代码复盘与学习 |

四份文档可以互相引用，但不能用一份代替另一份。理解交接可以解释评审问题，却不能把“我不喜欢这种写法”包装成缺陷；也不能因为接口测试通过，就跳过对状态、配置和失败路径的理解。

## 4. 工作量分档：用复杂度决定深度

不是每个改动都值得写成完整教材。先按范围和风险分档，再决定文档长度。

| 档位 | 典型情况 | 必做内容 | 建议形态 |
|---|---|---|---|
| 轻量 | 单仓库、少量文件、单一同步链路、无配置/数据迁移 | 纵览、最终Diff、1条关键链路、风险和复述 | 短文档，省略通用语法 |
| 标准 | 常规业务需求，包含接口、服务、表、配置或前端中的两三层 | 完整核心步骤 + 1～3条代表链路 | 默认50文档 |
| 深度 | 跨仓库/跨服务、异步任务、复杂状态机、共享核心逻辑、迁移/回滚、线上事故 | 多证据互证、状态与时序、失败路径、运行态验证、决策记录 | 主文档 + 必要附录 |

升级深度的信号：

- 用户看不懂最终状态或无法判断哪个版本生效。
- 变更影响金额、权限、订单状态、结算、库存等高感知数据。
- 存在异步、缓存、定时任务、事件、重试、幂等或最终一致性。
- 同一业务规则在多个服务或多套数据源中重复实现。
- 代码和需求、配置、数据库或运行结果出现矛盾。

降级原则：机械 DTO、重复 CRUD、标准框架样板只选一个代表讲透，其余用表格概括。每一节都必须回答一个独立问题；没有新增认知价值的细节不展开。

## 5. 抓大放小：选择真正值得深挖的内容

复盘优先级由四个因素决定：

```text
业务影响 × 不确定性 × 耦合范围 × 后续复用价值
```

优先深挖：

- 决定业务口径、状态变化、金额计算、权限或数据归属的代码。
- 修改共享能力、旧链路或公共组件的插入点。
- 数据跨边界的位置：前后端、服务间、缓存与数据库、任务与消息。
- 错误后难回滚、难补偿或难观察的路径。
- “看上去通用/灵活/自动”但可能只完成一部分的设计。
- 用户之后最可能被同事追问的设计取舍。

只做摘要：

- 纯字段声明、Getter/Setter、重复映射。
- 已在项目中稳定复用且对本次行为没有特殊影响的样板。
- 不改变控制流、数据流和外部契约的格式调整。
- 对当前用户目标没有帮助的框架百科知识。

当用户追问某个局部时再按需下钻，不能用“抓大放小”拒绝解释真实卡点。

## 6. 事实模型：先区分五种状态

企业项目最常见的误判，是把“写过代码”说成“功能已经生效”。每个重要能力都要区分：

| 状态 | 要回答的问题 | 常用证据 |
|---|---|---|
| 预期 Intended | 产品或负责人想要什么 | 需求原件、确认答复 |
| 已实现 Implemented | 目标版本代码做了什么 | 最终文件、Diff、构建产物 |
| 已配置 Configured | 字典、开关、模板、权限、任务是否配好 | 配置页面、数据库、配置中心 |
| 已部署 Deployed | 哪个版本进入哪个环境 | Jenkins、镜像版本、部署记录 |
| 已验证 Verified | 运行时是否真的按预期执行 | 请求响应、日志、指标、数据变化 |

文档不能用一个“已完成”抹平这五层。无法核实的层必须明确写未知或待验证。

### 6.1 证据优先，不按记忆写结论

复盘至少从下列证据中选择适用项：

- 需求原件与确认答复。
- Git 提交、分支、合并、回滚和最终目标版本。
- 改动文件完整内容及其调用方/被调用方。
- 数据库 DDL、只读样例数据、索引和配置记录。
- 前端入口、API 契约、服务间调用、消息或任务配置。
- 构建部署记录、运行日志、接口响应、监控指标。
- 既有开发交接、测试报告和评审报告。

证据冲突时，不强行统一：并列写出“需求计划”“代码行为”“环境配置”“运行结果”，说明差异和需要谁确认。

### 6.2 事实、推断和建议分开

- **事实**：由代码、数据或运行证据直接支持。
- **推断**：对设计原因或作者意图的合理解释，必须标“推测/可能”。
- **建议**：未来可以怎样改，不能写成当前行为。

解释“为什么这样设计”时，优先引用需求、提交说明、样板和约束；没有明确记录时，只能给权衡分析，不能代替作者发言。

## 7. 通用工作流

### Step 0：建立复盘契约

确定：

- 业务主题、时间范围、目标分支/版本和涉及仓库。
- 用户目标：了解全貌、准备沟通、接手维护、评审问题还是事故复盘。
- 可用证据和权限：代码、数据库、日志、部署、外部系统。
- 只读边界以及是否允许写学习文档。
- 多个业务对象是拆文档，还是共享一份总览后分章节。

默认纪律：不改业务代码、不改数据库、不发送外部消息、不切换/变基用户工作分支。

### Step 1：建立安全的版本基线

先查看工作区、当前分支、目标分支和相关提交。脏工作区不切分支；优先使用 `git log/show/diff/blame`、远端引用或独立 worktree。

必须同时确定两个基线：

1. **历史基线**：变更从哪里开始、经历了什么。
2. **最终基线**：现在要解释的版本究竟是哪一个。

合并、cherry-pick、rebase、重复补丁和 revert 都可能让“提交号列表”失真，应按补丁内容和业务结果去重归类。

### Step 2：重建变更史与当前边界

用业务语言整理时间线，不要求用户背 hash：

| 时间/版本 | 业务变化 | 技术落点 | 当前是否保留 | 证据 |
|---|---|---|---|---|

然后把代码归属分为：

- 本次新增。
- 本次修改的共享/既有代码。
- 直接复用的项目能力。
- 公司或组织公共组件。
- 第三方框架与基础设施。

归属不是为了评价作者，而是为了让接手者知道问题该在需求代码、公共平台还是外部依赖中排查。

### Step 3：建立系统模型

在逐行读代码前，先给出最小但完整的心智模型：

- 业务目标和参与者。
- 系统边界与外部依赖。
- 入口、核心处理、持久化和输出。
- 关键数据对象及其关系。
- 重要状态、开关、缓存和异步边界。
- 本次改动插入系统的具体位置。

根据问题选择合适的图，不为画图而画图：

- 组件/服务关系用结构图。
- 请求、任务、事件用时序图。
- 状态变化用状态图。
- 表、文档、消息关系用数据模型图。
- 新旧版本差异用变更地图。

### Step 4：选择代表性关键链路

不机械按文件顺序阅读，而按真实触发场景选择 1～3 条主链路，再补失败/回退链路。

每条链路至少回答：

1. 谁在什么条件下触发？
2. 输入、身份和前置状态是什么？
3. 哪一层作出核心业务决定？
4. 数据经过哪些转换和边界？
5. 产生哪些持久化、消息、缓存或外部副作用？
6. 输出给谁，何时可见？
7. 失败、重试、回滚、幂等和降级怎样处理？
8. 如何从日志、数据或响应证明走了这条路径？

同时分别追踪：

- **控制流**：下一步调用谁、走哪个分支。
- **数据流**：字段从哪里来、怎样变、存到哪里。
- **状态流**：对象、任务或版本从什么状态变到什么状态。

### Step 5：按变更形态使用检查清单

| 变更形态 | 重点追踪 |
|---|---|
| CRUD/表单 | 字段所有权、校验、审计、事务、逻辑删除、返回契约 |
| 查询/报表/导出 | 筛选口径、聚合、分页、单位/精度、模板、数据量 |
| 配置驱动功能 | 默认值、环境差异、缓存刷新、开关范围、失效行为 |
| 跨服务调用 | 契约、鉴权、超时、重试、降级、版本兼容、错误传播 |
| 消息/事件/异步任务 | 生产者、消费者、顺序、重复、幂等、补偿、可观测性 |
| 定时任务 | 调度配置、日期窗口、漏跑/补跑、并发、时区、结果落点 |
| 状态机/审批 | 合法迁移、权限、并发、撤回、终态和旁路入口 |
| 缓存/搜索/索引 | 数据源、写入时机、一致性、失效、重建和回源 |
| 数据库/迁移 | DDL/DML、历史回填、双写/兼容期、索引、回滚和生产重放 |
| 算法/规则 | 输入域、不变量、边界、舍入、复杂度、可解释性 |
| 前端交互 | 生命周期、状态管理、请求时机、错误/空态、渲染约束 |
| 构建/部署/基础设施 | 环境变量、制品、部署顺序、健康检查、回滚和观测 |
| 重构/替换 | 外部行为是否等价、兼容层、迁移窗口、删除旧路径条件 |
| 故障修复 | 触发条件、根因、为什么原防线失效、修复覆盖面、复发监控 |

只使用与当前变更有关的清单，不要求每次全部填写。

### Step 6：分层教学，而不是堆知识点

默认顺序：

```text
业务目的 → 系统位置 → 关键链路 → 框架/平台机制 → 语言语法
```

教学规则：

- 先给结论和上下文，再解释局部代码。
- 新概念在第一次真正用到时解释，不提前写百科。
- 优先借用用户熟悉的语言或框架类比，并说明不能类比的部分。
- 一段代码至少说明“做什么、为什么在这里、依赖谁、有什么副作用/边界”。
- 标准样板讲一个代表，其余指出相同模式。
- 用户贴局部代码时，先直接回答，再向上追调用方、向下追副作用；扩展到足以解释问题就停。

### Step 7：核实端到端能力与运行状态

凡是出现“通用、灵活、自动、实时、已接入、兼容、可扩展”等评价，都要跨层验证：

```text
数据模型 → 接口契约 → 业务逻辑 → 配置/任务 → 前端/消费者 → 运维与导出
```

典型反例：表能存任意明细，不代表 DTO、校验、页面和导出支持任意数量；代码有实时分支，不代表环境开关已打开；任务方法存在，不代表调度器正在运行。

### Step 8：滚动吸收问题，修正文档模型

用户追问分为：版本/工具、语言语法、框架机制、项目公共能力、业务链路、数据设计、配置运行、风险决策等类型。

每次处理：

1. 直接回答当前问题。
2. 补一层必要上下文和设计边界。
3. 判断问题是否暴露文档缺口。
4. 若是稳定且可复用的解释，回写同一份50文档。
5. 若结论改变，修正文档原章节，不在末尾堆矛盾答案。

连续出现同类疑问，说明心智模型或解释顺序有问题，应重构章节，而不是继续追加零散 FAQ。

### Step 9：完成所有权验收

复盘不以“AI写完文档”为完成，而以接手者具备最低维护能力为准：

- 能用30秒说明目标、改动范围和当前状态。
- 能沿一条主链路说明触发、决策、数据变化、输出和副作用。
- 能区分本次代码、既有项目能力、公共组件和外部依赖。
- 能说出关键配置、失败/回退路径和至少两个已知边界。
- 能在 IDE、Git、日志或数据库中重新找到证据。
- 面对未知问题，知道先查哪一层，而不是只能再次询问 AI。

可以用复述、自测题、反向定位练习和模拟同事追问验收；用户不需要记住所有类名和快捷键。

## 8. 工具与交互原则

核心流程保持工具无关。IDEA、VS Code、数据库客户端、Git GUI 或命令行只是实现手段。

如果用户需要跟读操作，每一步写明：

```text
起点 → 操作 → 预期落点/现象 → 这一小步要回答的问题
```

工具规则：

- 阅读任务不默认 checkout、pull、rebase 或修改工作树。
- 有未提交改动时优先只读 Git 命令或独立 worktree。
- 数据库默认只读；生产环境不做探索性写操作，样例数据脱敏。
- 运行验证优先使用已有脚本、测试环境和可回滚动作。
- 无法访问某层证据时明确降低结论强度，不用猜测补齐。

## 9. 文档结构：必填骨架 + 按需章节

正式50文档不应固定成同一长度。以下六项必填：

1. 复盘范围、目标版本、证据可用性和当前五态结论。
2. 业务纵览与改动边界。
3. 业务化变更时间线。
4. 系统模型和代表性关键链路。
5. 设计取舍、已知边界、风险与待确认项。
6. 复述话术、定位练习或掌握度自检。

按需加入：

- 数据模型、表结构与真实样例。
- 配置、权限、导出、缓存和环境差异。
- 异步时序、状态机、失败与补偿。
- Git/IDE/数据库跟读步骤。
- 技术概念卡和熟悉技术栈类比。
- 评审问题解释、故障根因或迁移策略。
- 用户后续追问的滚动补充。

长度规则：

- 先用一页左右建立全景，再决定是否下钻。
- 同类样板只讲一次，重复文件用映射表。
- 源码片段只保留理解控制流、数据流或约束所需的最小部分。
- 详细 SQL、完整响应、长日志放附录或引用已有报告。
- 文档变长时增加导航和“建议阅读路线”，不要只继续堆章节。

## 10. 正式提示词草案

```text
【任务】对需求/变更「<名称>」执行代码复盘与理解交接。目标是让接手者获得可验证的系统模型和最低独立维护能力，不是逐文件翻译源码。

【先定档】根据改动范围、业务风险、耦合和证据复杂度选择轻量/标准/深度档；优先深挖高影响、高不确定、高耦合的1～3条关键链路，机械样板只做摘要。

【只读基线】先检查工作区、当前/目标版本和相关仓库；默认不改代码/数据库、不切分支、不rebase。有脏工作区时用 git log/show/diff 或独立 worktree。明确历史基线和最终基线。

【证据】读取需求原件及已有10/20/21/30/40文档；按需核对 Git、最终代码、表结构/数据、配置、前端或消费者、任务/消息、部署和运行证据。分别标明预期、已实现、已配置、已部署、已验证；事实、推断和建议分开。

【分析】恢复业务化变更时间线，识别修复/合并/回滚/重复补丁；区分本次新增、修改既有代码、项目能力、公共组件和第三方依赖。先建立系统模型，再按真实场景追控制流、数据流、状态流和失败/回退路径。对“通用/自动/实时/可扩展”等结论做端到端验证。

【教学】顺序为业务目的→系统位置→关键链路→框架/平台→语言语法。用接手者熟悉的技术作类比并说明边界。用户追问时先直接回答，再补必要上下文；成熟解释滚动回写同一文档。

【产出】docs/需求/<需求名>/50-代码复盘与学习-<工具代号>.md，使用模板10的必填骨架，复杂章节按需展开。多个相互独立的业务对象分开写；共享底层可在总览中引用。

【验收】文档必须提供简短复述、关键边界/待确认项和定位练习或自测，使接手者能重新找到证据并讲清一条主链路。

【禁止】不把代码存在当运行生效，不把历史提交当最终状态，不把局部可扩展当端到端支持，不猜作者意图，不把理解交接冒充正式评审，未经授权不实施修复。
```

## 12. 设计自检

正式落地前用以下问题检查：

- 是否适用于不同语言、框架、仓库和业务形态？
- 是否能覆盖同步、异步、配置、数据、部署和故障场景？
- 是否明确抓大放小，避免逐文件翻译？
- 是否区分预期、实现、配置、部署和验证？
- 是否区分事实、设计推断和改进建议？
- 是否与20/30/40文档各司其职？
- 是否给轻量需求保留简化路径？
- 是否能通过接手者复述和重新定位来验收？
- 是否保持只读安全边界，避免复盘过程破坏工作区或环境？

全部满足后，才适合进入正式 skill。
