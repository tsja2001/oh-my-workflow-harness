# 04 追问回答：带你读懂集采日金额统计台账要改的模块

这份文档不是直接写代码的实现清单，前一份 `02.md` 已经偏“任务拆解计划”。这一份换成学习视角：你现在不懂 Java，也不熟微服务，我会先回答“这种开发方式到底需要什么”，再带你顺着真实代码读一条流程，最后把“集采日金额统计台账”这个新需求对应到每一步。

## 1. 先回答你最关心的：后端改动是不是只在两个模块

结论：如果只说“集采日金额统计台账的后端业务代码”，主要落点确实应该是这两个模块：

```text
01zhaocai-end/scm-source-all/scm-source-source-api
01zhaocai-end/scm-source-all/scm-source-source
```

但如果说“完整交付这个需求”，不能说全部只在这两个模块。原因是这个需求不只是一个后端接口，它还牵涉菜单、权限、数据字典、导出模板、定时任务配置、前端页面。

可以这样分层理解：

```text
后端核心业务代码：
  scm-source-source-api
  scm-source-source

后端启动装配：
  scm-source-web-jar
  03zhaocai-start/scm-cloud-starters-web/scm-cloud-source
  通常不一定要改，但必须确认它们会扫描到新代码。

菜单/岗位/权限：
  scm-ubm-all 里的 rbac/basicdata 相关模块，或者由 SQL/配置在数据库里处理。

导出模板/数据字典/XXL Job：
  多半不是 Java 类里写死，而是数据库配置或调度中心配置。

前端：
  招采平台页面仓库需要新增菜单页面、查询区、列表、弹窗、导出按钮。
```

所以更准确的说法是：

```text
这次新增台账的 Java 业务主战场在 scm-source-source-api / scm-source-source；
完整上线还需要配合权限、菜单、字典、导出模板、定时任务和前端。
```

## 2. “只能上服务器测”的开发方式普遍吗

在微服务很多、基础设施很多的老业务系统里，这种情况不罕见，但它不是理想状态。

理想情况下，后端开发至少应该能做到：

```text
本地能编译
本地能跑单元测试
本地能启动部分服务或用 mock 替代外部依赖
开发环境能做完整联调
测试环境做验收
```

你现在遇到的是更现实的一种：

```text
代码能拉下来
但本地缺注册中心、配置中心、数据库、Redis、MQ、文件服务、工作流、组织机构、权限系统
所以完整服务跑不起来
只能提交后在公司开发/测试服务器上测
```

这种模式最大的风险不是“不会写 Java”，而是“你本地看不到运行时真实配置和真实数据”。比如代码里只是写了一个接口，但它启动后依赖哪个数据库、哪个 Nacos 配置、哪个网关路径、哪个权限资源，可能都在服务器环境里。

所以你不能只要“服务器账号密码”。真正应该要的是一整套能让你闭环验证的信息。

## 3. 你应该向同事要什么

按优先级列，最重要的是这些。

第一类：分支和发布流程。

```text
应该基于哪个分支开发：prod、test、dev，还是某个需求分支
涉及多个仓库时每个仓库的分支分别是什么
提交后谁合并、谁发版、发到哪个环境
数据库脚本走什么流程，是开发自己执行，还是 DBA / 运维执行
```

这很关键。因为这个工作区不是一个大 Git 仓库，而是很多仓库拼在一起。比如 `scm-source-all`、`scm-ubm-all`、`scm-cloud-starters-web`、前端仓库都有自己的 Git。

第二类：开发环境访问方式。

```text
招采平台前端地址
（下面这三个都是干什么的）
后端网关地址
Swagger / Knife4j 地址
XXL Job 调度中心地址
（同事说是用K8S部署的，说上面能看各种日志调试）
日志平台或服务器日志查看方式
```

如果同事说“只能服务器测”，你至少要能看到接口报错、日志堆栈、SQL 报错，否则你只能盲改。

第三类：账号和权限。

```text
一个有“集采管理-执行单位集采管理岗”的测试账号
一个没有该岗位的普通账号
一个能看菜单配置/角色配置的管理员账号，哪怕只读也行
```

这个需求有菜单和岗位。没有权限账号，你只能测接口，测不了“这个岗位是否能看见菜单、能不能新增修改删除”。

第四类：数据库和配置。

```text
开发库连接方式，至少要能查表结构和数据
（说的有点简单，没看懂）
菜单、岗位、角色、接口资源表在哪个库
字典表在哪个库，集团集采类目和所属板块的字典编码是什么
导出模板表怎么配
```

你可以没有生产库权限，但最好有开发库只读权限。没有只读权限，也至少要同事给你表结构和几条样例数据。

第五类：外部服务口径。

```text
组织机构控件前端返回哪些字段
（下面这三条都是什么意思，没看懂）
根据采购企业带出所属板块时，后端应该用 orgCode、orgId 还是 epecCode 查
集采驾驶舱现在展示哪些卡片，新台账金额要影响哪些卡片
每日 24:00 的任务由谁配置，JobHandler 名称有什么命名规则
```

这些不是 Java 语法问题，而是业务系统之间的约定。AI 写代码前也必须知道这些约定，否则代码可能能编译，但业务口径错。

## 4. 本地还要不要编译
（找同事确认了，本地不编译，只给服务器上提交代码，剩下的在服务器上做）
要。本地不能完整启动，不等于不用编译。

最低要求是：改了哪个 Maven 模块，就至少编译这个模块和它依赖的模块。比如这次如果只改 `scm-source-source-api` 和 `scm-source-source`，理论上至少要在 `01zhaocai-end/scm-source-all` 下跑类似：

```bash
mvn -pl scm-source-source -am package -DskipTests
```

如果改到了 `scm-source-web-jar` 或 starter，再扩大编译范围。

编译能帮你挡住这些低级问题：

```text
类名写错
包名写错
方法不存在
字段类型不匹配
缺 import
依赖模块没引入
```

它挡不住这些问题：

```text
SQL 逻辑错
权限没配
字典编码错
数据库字段不存在
Feign 调外部服务失败
驾驶舱统计口径错
```

所以正确心态是：

```text
本地编译是最低门槛，不是最终验收。
服务器联调是必要环节，但不能把所有低级错误都留到服务器才发现。
```

## 5. 先用 Node/Koa 的视角理解这个 Java 项目

你做过 Node/Koa，可以先这样类比：

```text
Controller 约等于 Koa router
Service 约等于业务 service 文件
Mapper 约等于 db model / repository
DTO / VO 约等于 TypeScript interface 或接口入参出参对象
Model 约等于数据库表对应的 entity
Feign 约等于调用别的服务的 HTTP client
```

一个典型后端请求流程是：

```text
前端点击查询
  -> 网关转到 scm-cloud-source 服务
  -> Controller 收到请求
  -> Controller 调 Service
  -> Service 拼查询条件、校验参数、调 Mapper
  -> Mapper 查数据库
  -> Service 把数据库对象转成 DTO/VO
  -> Controller 用 Result.success 包起来返回前端
```

新增“集采日金额统计台账”也会走这条线。

## 6. 先看这两个模块分别干什么

### 6.1 scm-source-source-api：放“对外能看懂的数据形状”

路径：

```text
01zhaocai-end/scm-source-all/scm-source-source-api
```

这里主要放 DTO、VO、Param、Enum。你可以理解成“接口契约层”。

比如现有文件：

```text
scm-source-source-api/src/main/java/com/pcitc/scm/source/source/api/enums/CollectionDataTypeEnum.java
```

这类文件通常不直接访问数据库，也不写复杂业务。它们更像是在定义：

```text
接口需要哪些字段
返回给前端哪些字段
查询条件有哪些字段
枚举值有哪些
```

对应到新需求，这里应该新增类似：

```text
CollectionDailyAmountLedgerDTO
```

它会包含：

```text
ledgerNo：集采日金额统计流水号
executeUnitCode / executeUnitName：集采执行单位
categoryCode / categoryName：集采类目
statisticDate：统计日期
purchaseCompanyCode / purchaseCompanyName：采购企业

publishTime / publishByName：发布时间和操作人

beginStatisticDate / endStatisticDate：查询用的开始日期和结束日期
```

注意：DTO 里通常会同时放“展示字段”和“查询辅助字段”。比如保证金台账的 `SourceDepositLedgerDTO` 里既有 `payTime`，也有 `beginPayTime/endPayTime`。这就是前端传日期范围后，后端拆成开始和结束两个条件。

## 7. 为什么这个需求落在 scm-source-source

因为现有“集采驾驶舱”相关代码已经在这个模块里。

入口在：

```text
scm-source-source/src/main/java/com/pcitc/scm/source/source/controller/SourceQueryController.java
```

里面有一个接口：

```java
@GetMapping("e/business/source/source/cockpit_collection_data_{typeCode}")
public Result<List<SourceCollectionData>> cockpitCollectionData(@PathVariable("typeCode") String typeCode) {
    return Result.success(sourceCollectionDataService.queryCollectionData(typeCode));
}
```

不用懂注解，只要看它表达的意思：

```text
前端请求 cockpit_collection_data_xxx
  -> Controller 收到 typeCode
  -> 调 sourceCollectionDataService.queryCollectionData(typeCode)
  -> 返回驾驶舱数据
```

这个接口查的是“集采驾驶舱数据”。而你的需求第 4 条写了：

```text
每日 24:00 系统按照统计日期自动取前一日的数据并自动更新集采驾驶舱
```

所以台账不是孤立列表，它和这个驾驶舱有业务关联。这就是为什么 `scm-source-source` 比别的模块更合适。

## 8. 带读现有驾驶舱流程

### 8.1 Controller：前端怎么拿驾驶舱数据

文件：

```text
scm-source-source/src/main/java/com/pcitc/scm/source/source/controller/SourceQueryController.java
```

核心接口：

```text
GET e/business/source/source/cockpit_collection_data_{typeCode}
```

`typeCode` 可以理解成前端要哪块驾驶舱数据。比如：

```text
centerHeader：中心和头部统计
categoryAmount：集采类目分项金额
situA：集采情况分析
```

对应到新需求：

```text
新台账本身应该新增自己的 Controller；
驾驶舱接口不一定新增路径，但它的统计口径可能要加上新台账数据。
```

也就是说，台账列表和驾驶舱展示是两件事：

```text
台账列表：给业务人员增删改查和导出
驾驶舱：给大屏或页面看汇总金额
```

这两个功能可以共用数据，但不能混成一个接口。

### 8.2 Service：驾驶舱有“实时汇总”和“读缓存表”两种模式

文件：

```text
scm-source-source/src/main/java/com/pcitc/scm/source/source/service/impl/SourceCollectionDataServiceImpl.java
```

它的大概逻辑是：

```text
先查字典 collectionShow
如果某个 typeCode 的开关是 1，就实时查 sc_source_collection 汇总
否则就查 sc_collection_data 表里已经保存好的结果
```

这意味着驾驶舱不是永远实时算，也不是永远读缓存，而是由字典开关控制。

对应到新需求：

```text
如果新增台账金额要影响驾驶舱，就要先确认当前环境 collectionShow 开关怎么配。

如果是实时汇总模式：
  需要让 SourceCollectionMapper 的汇总 SQL 合并新台账表。

如果是读缓存表模式：
  每日 24:00 的 XXL Job 需要把新台账汇总结果写入 sc_collection_data。

如果两个模式生产上都可能用：
  两边都要考虑，否则测试环境好用，生产可能不生效。
```

这就是为什么第 4 条需求最需要找同事确认口径。

### 8.3 Mapper：驾驶舱当前从哪张表算金额

文件：

```text
scm-source-source/src/main/java/com/pcitc/scm/source/source/repositories/SourceCollectionMapper.java
```

里面有几个方法：

```text
queryCenterHeader：查累计总金额、日集采、月度、季度、年度等
queryCategoryAmount：查类目分项金额
querysituA：查集采情况分析
```

现有 SQL 主要从这张表汇总：

```text
sc_source_collection
```

这张表对应的 Java Model 是：

```text
scm-source-source/src/main/java/com/pcitc/scm/source/source/model/SourceCollection.java
```

`SourceCollection` 里有这些字段：

```text
categoryCode / categoryName：类目
taxTotal：含税总金额
supplierCode / supplierName：供应商
purchaseCompanyCode / purchaseCompanyName：采购企业
buCode / buName：所属板块
finalTime / pullDate：完成时间或拉取日期
dataSource：来源
```

对应到新需求：

```text
你的台账也有类目、采购企业、含税金额、所属板块、统计日期。
字段很像，但它不是原来的成交数据来源。
```

所以这里有一个关键设计判断：

```text
不要直接把人工录入的台账数据塞进 sc_source_collection，除非同事明确说这张表就是集采驾驶舱统一明细表。
更稳妥是新增台账表，然后在驾驶舱汇总时明确把新台账表的数据合并进去。
```

原因很简单：`sc_source_collection` 当前看起来是从寻源、SAP、商城订单等来源汇聚来的“集采信息数据”。人工台账如果直接混进去，后续别人查原始来源、同步状态、业务 ID 时可能误判。

## 9. 带读类似台账：保证金台账

你要新增的是“日金额统计台账”，项目里已有一个比较像的“保证金台账”。

Controller：

```text
scm-source-ssc/src/main/java/com/pcitc/scm/source/ssc/controller/SourceDepositLedgerController.java
```

Service：

```text
scm-source-ssc/src/main/java/com/pcitc/scm/source/ssc/service/impl/SourceDepositLedgerServiceImpl.java
```

DTO：

```text
scm-source-ssc/src/main/java/com/pcitc/scm/source/ssc/api/dto/SourceDepositLedgerDTO.java
```

### 9.1 它的查询入口怎么写

保证金台账接口是：

```java
@PostMapping("/e/business/source/depositClaimLedger/queryPageList")
public Result<PageList<SourceDepositLedgerDTO>> queryPageList(DefaultPageBean<SourceDepositLedgerDTO> pageModel) {
    if (null == pageModel.getModel()) {
        pageModel.setModel(new SourceDepositLedgerDTO());
    }
    PageList<SourceDepositLedgerDTO> pageList = sourceDepositClaimLedgerService.queryListByPage(pageModel);
    return Result.success(pageList);
}
```

翻译成人话：

```text
前端传一个分页对象 pageModel
pageModel 里面有当前页、每页条数、查询条件 model
如果 model 为空，就给它一个空条件对象，避免空指针
然后调用 Service 查分页列表
最后用 Result.success 返回
```

对应到新需求：

```text
日金额统计台账也应该有 queryPageList。
查询条件放在 CollectionDailyAmountLedgerDTO 里。
返回 PageList<CollectionDailyAmountLedgerDTO>。
```

### 9.2 它怎么处理日期范围

保证金台账用了：

```java
@DataRequestTransfer(value = {
    @DateTransfer(root = "model", jsonPath = "payTimeArr", value = { "beginPayTime", "endPayTime" })
})
```

你不用背这个注解，只要理解它在做一件事：

```text
前端可能传 payTimeArr = [开始时间, 结束时间]
后端真正查询时用 beginPayTime / endPayTime
这个注解帮忙把数组拆成两个字段
```

对应到新需求：

```text
前端查询条件有“统计日期：开始日期 ~ 结束日期”
后端可以让前端传 statisticDateArr
再转换成 beginStatisticDate / endStatisticDate
```

这就是为什么 DTO 里要有几个看起来不是展示字段的字段。

### 9.3 Service 怎么拼查询条件

保证金台账 Service 里用的是 MyBatis-Plus 的 `LambdaQueryWrapper`。

你可以把它理解成一种“用 Java 写 SQL where 条件”的方式：

```text
如果采购企业名称不为空，就加 like purchase_company_name
如果方案编号不为空，就加 like scheme_code
如果开始时间不为空，就加 pay_time > beginPayTime
如果结束时间不为空，就加 pay_time < endPayTime
最后 order by，再分页查询
```

对应到新需求，查询条件应该类似：

```text
流水号不为空：like ledger_no
执行单位不为空：eq execute_unit_code
所属板块不为空：eq bu_code
采购企业不为空：eq purchase_company_code
类目不为空：eq category_code
统计日期开始不为空：ge statistic_date
统计日期结束不为空：le statistic_date
delete_sign = 0：只查未删除
order by publish_time desc, create_time desc
```

这就是列表查询的主逻辑。

### 9.4 它怎么把数据库对象变成前端对象

保证金台账里有：

```java
BeanUtils.copyProperties(sdc, dto);
dto.setting();
```

翻译成人话：

```text
数据库查出来的是 Model
返回前端的是 DTO
大部分字段名字一样，可以直接复制
有些字段需要格式化，比如金额、时间、状态中文，就在 setting 里处理
```

对应到新需求：

```text
金额可以保持 BigDecimal 返回，也可以增加 taxAmountStr 用于导出或展示。
发布时间可以返回 Date，也可以加 publishTimeStr。
类目、所属板块不要只返回编码，也要返回名称。
```

不过建议不要过早加太多 `xxxStr` 字段。先看前端和导出组件需要什么。

## 10. 带读增删改查参考：集采组配置

```text
queryPlanGroupDetail：详情
```

对应到新需求，建议也是这个形状：

```text
add：新增，录入后直接发布
modify：修改，更新发布时间和操作人
delete：删除，建议逻辑删除
queryPageList：分页查询，也支持导出
detail：详情，供修改弹窗回显
queryCompanyBelongBu：根据采购企业带出所属板块
```

你要重点理解“新增”和“修改”的区别。

新增时：

```text
生成流水号 JCRJE-统计日期-三位流水
校验必填字段
根据采购企业查所属板块
保存创建人、发布时间、发布人
插入数据库
```

修改时：

```text
根据 ledgerId 查原记录是否存在
校验是否已删除
允许改执行单位、类目、统计日期、采购企业、金额、所属板块
如果采购企业变了，重新带出所属板块
更新发布时间和操作人
更新数据库
```

删除时：

```text
产品写“删除本行”
技术上建议逻辑删除，也就是 delete_sign 改成 1
不要物理删除，方便追溯和排查
```

## 11. 流水号怎么理解

需求要求：

```text
JCRJE-年月日-三位流水
例如 JCRJE-20260701-001
```

项目里已有类似流水号生成类，比如：

```text
scm-source-source/src/main/java/com/pcitc/scm/source/source/seq/GreenChannelCodeSequence.java
scm-source-require/src/main/java/com/pcitc/scm/source/require/seq/RequireCodeSequence.java
```

这类类通常告诉系统三件事：

```text
前缀是什么
中间日期怎么拼
后缀流水几位
流水什么时候重置
```

对应到新需求：

```text
前缀：JCRJE-
中间：统计日期 yyyyMMdd-
后缀：001、002、003，即三位
重置：最好按统计日期重置，不是按提交当天重置
```

这里有一个容易踩坑的地方。

如果用户在 2026-07-08 补录 2026-07-01 的数据，流水号应该是：

```text
JCRJE-20260701-001
```

而不是：

```text
JCRJE-20260708-001
```

因为需求写的是“统计日期”，不是“录入日期”。

所以流水号生成类不能简单取 `new Date()` 当天日期，应该用 DTO 里的 `statisticDate`。

## 12. 组织机构控件和所属板块

需求里有两个组织机构控件：

```text
集采执行单位
采购企业
```

“控件”是前端说法。对后端来说，它最终会变成一组字段：

```text
orgId
orgCode
orgName
```

具体名字要问前端或看现有控件返回值。

所属板块的关键点是：

```text
需求写“所属板块根据采购企业自动带出”
所以后端不能完全相信前端传来的 buCode / buName
保存时最好再根据采购企业编码查一次组织机构，拿 belongBuCode / belongBuName
```

项目里组织机构相关接口在 UBM 模块，常见字段名是：

```text
belongBuCode
belongBuName
```

对应到新需求：

```text
前端选择采购企业后，可以调后端接口 queryCompanyBelongBu 做页面回显。
后端 add/modify 保存时，也要再查一次，保证入库数据可信。
```

这样即使前端传错所属板块，后端也能兜底。

## 13. 导出不是单独随便写一个 Excel 接口

这个项目已有统一导出组件。你在 `RequireController`、`SourceQueryBidController` 等地方能看到：

```java
@DataRequestTransfer(exportValue = {@ExportRequestTransfer()})
```

它的含义是：

```text
分页查询接口既可以普通查询
也可以在导出请求参数触发时，走导出组件
```

对应到新需求：

```text
日金额统计台账的 queryPageList 最好同时支持查询和导出。
导出字段顺序用导出模板配置控制。
```

需求要求导出字段：

```text
集采日金额统计流水号
集采执行单位
集团集采类目
统计日期
采购企业
采购金额（含税）
所属板块
发布时间
创建人
```

这里要注意：产品表格里列名有“交易金额（含税/元）”，导出字段写“采购金额（含税）”。开发前最好和产品确认是不是同一个字段。技术上可以都对应 `taxAmount`。

## 14. 每日 24:00 自动更新驾驶舱怎么做

启动工程 `scm-cloud-source` 已经引入了 XXL Job：

```text
03zhaocai-start/scm-cloud-starters-web/scm-cloud-source/pom.xml
03zhaocai-start/scm-cloud-starters-web/scm-cloud-source/src/main/java/com/pcitc/scm/source/starter/SourceApp.java
```

`SourceApp` 里导入了：

```text
XxljobExecutorWebConfig
```

所以这个项目不是完全没有定时任务能力。

新增定时任务建议这样理解：

```text
XXL Job 调度中心负责在每天 00:00 调用某个 JobHandler
JobHandler 里算出要刷新哪一天，默认是昨天
JobHandler 调 Service
Service 汇总台账表 statistic_date = 昨天 的数据
Service 把汇总结果写入驾驶舱相关数据，或让实时 SQL 能算到这些数据
```

对应到需求里的例子：

```text
7 月 2 日 24 点，也就是 7 月 3 日 00:00
取 statistic_date = 7 月 1 日的数据
自动更新集采驾驶舱
```

这个例子有一点业务表达上的歧义：通常“7 月 2 日 24 点”就是“7 月 3 日 00:00”。它说取 7 月 1 日，说明可能是希望在某天结束后刷新“前一自然日之前已经录完的数据”。开发前要确认到底是：

```text
每天 00:00 取昨天
还是每天 24:00 取前一天
还是因为执行单位当天 10:00 补录前一日，所以夜里刷新的是前一日
```

不要让 AI 自己猜这个口径。

## 15. 新需求从前端到数据库的完整流程

现在把“新增一条台账”串起来。

```text
用户打开“集采业务管理台账 / 日金额统计台账”
  -> 点击新增
  -> 选择集采执行单位
  -> 选择集采类目
  -> 选择统计日期
  -> 选择采购企业
  -> 前端调用后端接口带出所属板块
  -> 输入交易金额
  -> 点击保存
  -> Controller 收到 CollectionDailyAmountLedgerDTO
  -> Service 校验字段
  -> Service 根据采购企业再次查询所属板块
  -> Service 生成流水号
  -> Service 设置发布时间、操作人、创建人
  -> Mapper insert 到 sc_collection_daily_amount_ledger
  -> 返回成功
```

修改流程：

```text
用户点击某一行修改
  -> 前端调用 detail 查询详情
  -> 弹窗回显
  -> 用户修改字段
  -> Controller 收到 DTO
  -> Service 查原记录
  -> Service 校验字段和删除状态
  -> Service 更新字段
  -> 如果采购企业变化，重新带出所属板块
  -> Service 更新 publish_time / publish_by / publish_by_name
  -> Mapper updateById
  -> 返回成功
```

删除流程：

```text
用户点击删除
  -> Controller 收到 ledgerId
  -> Service 查原记录
  -> Service 把 delete_sign 置为 1
  -> Mapper updateById
  -> 返回成功
```

查询/导出流程：

```text
用户输入查询条件
  -> 前端传分页对象和 model
  -> Controller 做日期数组转换
  -> Service 拼 LambdaQueryWrapper
  -> Mapper selectPage
  -> Service 转 DTO
  -> 返回 PageList
  -> 如果请求带导出标记，则统一导出组件按模板导出 Excel
```

驾驶舱刷新流程：

```text
XXL Job 到点触发
  -> JobHandler 计算 statisticDate
  -> Service 汇总台账表
  -> 更新 sc_collection_data 或让实时汇总 SQL 合并台账表
  -> 记录日志
  -> 前端下次查驾驶舱看到新金额
```

## 17. 新增台账表该怎么理解

建议新增表：

```text
sc_collection_daily_amount_ledger
```

它就是“日金额统计台账”的数据库存储。你可以把它想成一个 Excel 表，只是每一列变成数据库字段。

核心字段应该覆盖：

```text
ledger_id：主键
ledger_no：流水号
execute_unit_code / execute_unit_name：集采执行单位
category_code / category_name：集采类目
statistic_date：统计日期
purchase_company_code / purchase_company_name：采购企业
tax_amount：交易金额
bu_code / bu_name：所属板块
publish_time：发布时间或最近修改时间
publish_by / publish_by_name：发布或最近修改人
create_by / create_by_name / create_time：创建人和创建时间
update_by / update_by_name / update_time：更新人和更新时间
delete_sign：逻辑删除标记
```

为什么要同时存编码和名称？

```text
编码用于查询和关联，比较稳定
名称用于展示和导出，方便前端直接用
如果只存名称，后续改名、重名、查询都会麻烦
```

为什么金额要用 BigDecimal？

```text
Java 里金额不要用 float/double
BigDecimal 可以避免小数精度问题
```

为什么要逻辑删除？

```text
台账数据通常需要追溯
用户点删除后列表不可见即可
真从数据库删掉，后面排查驾驶舱金额变化会很难
```

## 21. 最后用一句话总结

这次需求对 Java 新人最难的不是写几个接口，而是把“台账增删改查”“组织机构和字典”“导出模板”“权限菜单”“驾驶舱定时汇总”这几块串起来。你读代码时不要陷进语法细节，先看请求从 Controller 到 Service 到 Mapper 到表，再反过来看这个表的数据什么时候被驾驶舱使用。只要这条链路通了，后面的 Java 语法和注解都只是实现细节。
