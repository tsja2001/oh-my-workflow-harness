# 办公网络远程访问合规方案

> 日期：2026-08-21  
> 工具：codex  
> 当前状态：已将 `101需求.md` 中的 SSH、网页和远程桌面诉求拆成可向网安申请的最小权限方案；不设计流量伪装、协议混淆或绕过态势感知。  
> 下一步：用户先用第 8 节话术询问公司已有的堡垒机、VDI、零信任或远程开发能力；取得网安答复后，再针对获批产品写实施清单。

## 1. 结论

需求本身可以合理解释，但“让流量看起来正常、不容易被态势感知发现”不能成为技术目标。对网安来说，正常流量不是“像普通 HTTPS”，而是：**工具获批、责任人明确、访问范围最小、身份可核验、行为可审计、异常时能立即切断**。

结合本主题前序实测，本机的 Mihomo 单一公网 443 长连接、Tailscale 控制连接、ToDesk 保活均能在公司 WLAN 出口留下可归因的元数据；把 SSH、WireGuard 或远控协议再包进 443，只会改变外层，不会把它变成合规流量。CISA 的远程访问安全指南还明确建议避免让远程访问软件借 HTTPS 443 隐藏在普通 Web 流量中，并要求授权的远控工具通过批准的 VPN 或 VDI 使用。

所以可行方向只有两个：

1. 把工作环境搬到公司认可的开发机、云环境或 VDI，不再从办公电脑访问家庭设备；
2. 由网安批准一个**按应用开放**的访问入口，只给一名用户、一台受管办公电脑、一个目标和必要端口，并启用 MFA、日志、期限和封禁开关。

## 2. 先把三类场景拆开

| 场景 | 正确归口 | 不能混用的原因 |
|---|---|---|
| 公司访问客户机房 | 客户指定通道、项目堡垒机或双方批准的 VPN | 涉及客户资产和合同边界，不能经过家庭网络或个人云服务器 |
| 公司访问家庭开发机 | 公司批准的远程开发/零信任入口；若不批准则迁移环境 | 家庭设备和个人云服务器不受公司资产、安全基线和事件响应控制 |
| 居家访问公司电脑/系统 | 公司 VPN、VDI、RD Gateway 或堡垒机 | 这是从外部进入公司信任域，风险和审批等级最高 |

一条 Headscale/Tailscale 网络同时承载三类流量，会让权限、责任、日志和故障处置全部混在一起，网安很难批准。

## 3. 推荐顺序

| 顺序 | 方案 | 能力覆盖 | 审计接受度 | 现实判断 |
|---:|---|---|---|---|
| 1 | 公司管理的开发机/云工作区 | SSH、网页、可选桌面 | 最高 | 最推荐；把家庭文件经审批的数据通道迁入，不再访问家庭网 |
| 2 | 公司现有堡垒机、VDI 或零信任访问 | SSH、网页、桌面按产品开放 | 高 | 先问有没有现成能力，通常比申请新 VPN 节点容易 |
| 3 | 网安批准的单目标、限时例外 | 只开放已声明的 SSH/网页/桌面 | 中 | 技术上可做，但家庭设备是否允许作为目标必须由网安拍板 |
| 4 | 个人电脑加个人网络 | 仅处理个人设备和个人资料 | 对公司网络风险低 | 不得把公司代码、数据、密钥或文档带到个人环境 |
| 不采用 | Tailscale/Headscale、ToDesk、frp、ngrok、自建 VPN、SSH/WebSocket over 443、域前置或流量混淆 | 技术上可能覆盖 | 未批准时最低 | 都属于未授权远控或隧道；换端口、域名、协议外壳不改变性质 |

### 3.1 最优解：迁移工作环境

如果真正需求是“AI 能 SSH 到一台机器做开发、看几个网页”，目标不必是家里那台物理机。可以申请一台公司管理的开发机或批准的云工作区，将允许迁移的源码、依赖和测试数据放进去：

- AI 和开发人员都只访问这台受管开发机；
- SSH、调试网页和桌面都在公司控制面内；
- 家庭设备只保留个人资料，不与公司办公终端互通；
- 若只是取居家时期产生的文件，先做数据分类，再用公司批准的 Git、制品库或文件交换通道迁移，不能用远控隧道顺带搬运。

这条路牺牲的是一次环境迁移成本，换来后续不需要反复解释个人公网 IP、个人 VPS 和家庭设备的可信度。

### 3.2 次优解：按应用授权，不做全网组网

如果网安允许访问指定家庭开发机，申请的应是“应用入口”，不是“把两个局域网连起来”：

```text
一名实名用户 + 一台登记办公设备
             │
             ▼
公司批准的访问入口（MFA、策略、日志、随时封禁）
             │
             ├── SSH：只到一台主机的 22 端口
             ├── Web：只到列明的应用和端口，不提供任意 CONNECT/SOCKS
             └── 桌面：只经 RD Gateway/VDI，不公网暴露 3389
```

必须同时具备：

- 公司身份认证和 MFA，不使用多人共享账号；
- 指定办公设备、指定目标、指定端口，默认拒绝其他访问；
- 禁止家庭设备反向连接办公电脑，禁止访问或转发公司网段；
- SSH 禁止通用代理、动态端口转发和任意横向跳转；
- Web 只发布明确应用，不提供全网 HTTP/SOCKS 代理；
- 记录登录人、时间、来源设备、目标、动作结果和会话时长；日志保留期由网安定，使用者不能删除；
- 先做 30 天或一个项目周期的限时试用，到期自动失效；
- 网安拥有立即封禁入口和撤销账号的开关；
- 家庭目标机纳入补丁、恶意软件防护、独立账号和磁盘加密等最低基线。

NIST 的零信任原则是不能因为设备位于某个网络或归某个人所有就默认信任，用户和设备都应在建立会话前完成认证和授权。上述限制正是把“私人组网”改造成“每次访问都能解释和核验”。

### 3.3 远程桌面单独处理

远程桌面不能直接把家庭 Windows 的 3389 暴露到公网。若公司已有 VDI，优先使用 VDI；若批准 Windows 远程桌面入口，应由管理方使用 RD Gateway 一类网关完成 TLS、用户认证、MFA、目标授权和会话超时。微软官方文档说明 RD Gateway 可以按用户和资源分别设置连接/资源授权策略，并通过 RADIUS 接入 MFA。

如果当前只急需 SSH 和网页，建议先不申请桌面，把审批范围压到最小；以后确有图形界面需求再单独补申请。

## 4. “流量正常”应改成什么验收标准

网安真正容易接受的是可解释、稳定、低权限，而不是难识别：

| 不应作为目标 | 应改成的目标 |
|---|---|
| 像普通 HTTPS，DPI 不容易识别 | 使用已批准域名/IP，网安明确知道协议和用途 |
| 只有一个 443 长连接 | 只有列明的应用可访问，禁止任意隧道和代理 |
| 不装终端代理就看不到 | 身份、设备、目标和操作均有日志 |
| 自己掌握服务器，方便随时改 | 管理方能审批、吊销、封禁和调阅日志 |
| 家庭与公司整网互通 | 单用户、单设备、单目标、单向、限时 |

## 5. 最小申请包

不需要一上来申请“公司 VPN 增加节点”。先让网安判断公司已有能力能否承载以下最小范围：

| 字段 | 建议填写 |
|---|---|
| 业务目的 | AI/开发人员远程维护一台开发设备，执行代码、查看本机测试页面 |
| 使用人 | 仅本人实名账号 |
| 来源 | 一台登记的办公电脑 |
| 目标 | 一台明确归属的开发设备；真实域名/IP由用户私下提交网安，不写项目文档 |
| 协议 | 第一阶段仅 SSH 和列明的 Web 应用；远程桌面暂缓 |
| 方向 | 仅办公电脑主动访问目标；目标不得反向访问办公电脑或公司网段 |
| 数据边界 | 不传生产数据、客户数据、公司密钥；公司源码能否进入家庭设备必须单独确认 |
| 控制 | MFA、最小权限、日志、30 天试用、到期自动关闭、网安可随时封禁 |

## 6. 网安最可能追问的风险

| 对方可能问 | 可直接回答 |
|---|---|
| 为什么一定要访问家里设备？ | 核心是需要一台可 SSH、可运行测试网页的开发环境；如果公司能提供受管开发机，我可以迁移，不坚持必须是家庭设备。 |
| 为什么不用现有 VPN/堡垒机？ | 我目前不知道公司已有哪种能力，愿意完全改用公司批准方案，请告知入口和申请流程。 |
| 家庭设备会不会反向进公司？ | 不需要，方案必须技术上禁止反向连接、公司网段路由和代理转发。 |
| 会不会把代码或数据带出去？ | 数据边界请公司明确；未获准前不把生产/客户数据、凭据或公司源码放到个人设备。 |
| 为什么以前用了 Tailscale/Clash？ | 为远程开发自行搭建，看到安全提醒后已停止 Tailscale；现在希望按批准方案整改，不再通过改端口或套代理规避识别。 |
| 能不能先试用？ | 可以接受单人、单设备、单目标、30 天、全日志、随时封禁，试用后再评估。 |

## 7. 当前明确不要做的事

- 不恢复已停止的 Tailscale，也不改成其他自建组网软件继续试；
- 不把 SSH、RDP、WireGuard 或远控流量改包到 443、WebSocket、QUIC、CDN 或正常网站域名下；
- 不使用域前置、SNI/指纹伪装、随机端口、流量填充、低速保活等方式降低检测概率；
- 不删除本机日志、事件、配置或历史痕迹；
- 不把客户机房、家庭网络、个人云服务器和公司网络接成一个可横向访问的网；
- 不因为“设备没有公司审计软件”就推定公司允许，网络侧策略和组织制度仍然有效。

## 8. 给网安/领导的逐字话术

> 我有一个明确的远程开发需求：办公电脑需要由我本人访问一台开发设备，主要是 SSH 执行代码和查看几个测试网页，远程桌面可以先不要。我之前为方便使用过 Tailscale，自查通知后已经停止。现在不准备通过改端口、套 HTTPS 或换别的远控工具规避检测，想按公司批准方案整改。
>
> 我不是申请公司与家庭全网互通，也不要求家庭设备反向访问公司。请帮我确认公司现在是否已有堡垒机、VDI、零信任访问或受管云开发机可用。如果有，我直接迁移；如果没有，能否按“仅本人实名账号、仅一台办公设备、仅一个目标、仅 SSH 和指定网页、MFA、全日志、30 天试用、到期关闭、网安可随时封禁”的范围评估最小例外？家庭设备是否允许作为目标、公司代码和数据能否进入该设备，也请按制度明确告诉我。

若对方只回复“禁止个人设备”，继续问：

> 明白，我不再从办公电脑访问家庭设备。为了不影响远程开发，请帮我指定一个替代入口：公司受管开发机、云工作区、堡垒机或 VDI 任选现有的一种即可。我需要的最小能力只有 SSH、运行测试服务和查看网页；请告诉我申请人、审批人和所需材料，我按清单准备。

## 9. 依据与证据边界

本方案依据：

- `10-终端网络安全调查-codex.md`：本机具备被办公网出口识别 Tailscale/代理流量的条件；
- `10b-Windows监控与流量可见性调查-codex.md`：公司可按 AP、DHCP、出口元数据归因到终端，Clash 还曾面向公司局域网开放代理端口；
- `30-Windows十分钟观察分析-codex.md`：实测公司 WLAN 可见持续的 Mihomo 公网 443 外层连接、Tailscale 443 保活和 ToDesk 流量；
- [CISA《Guide to Securing Remote Access Software》](https://www.cisa.gov/resources-tools/resources/guide-securing-remote-access-software)：远程访问工具需授权、监控和日志，并建议通过批准的 VPN/VDI 使用；
- [NIST SP 800-46 Rev.2](https://csrc.nist.gov/pubs/sp/800/46/r2/final)：远程访问方案应基于威胁模型同时保护客户端、访问通道和目标资源；
- [NIST SP 800-207](https://csrc.nist.gov/pubs/sp/800/207/final)：网络位置和设备归属不产生隐式信任，用户和设备都要在会话前认证与授权；
- [Microsoft RD Gateway](https://learn.microsoft.com/en-au/windows-server/remote/remote-desktop-services/rds-plan-access-from-anywhere)：远程桌面网关提供 TLS、认证、MFA 接入、用户/资源策略和会话超时。

仍然未知、不能替网安拍板的事项：公司现有产品、允许访问个人设备与否、允许的数据类型、日志保留期、具体审批人和网络白名单流程。取得正式答复前，不部署任何替代隧道。
