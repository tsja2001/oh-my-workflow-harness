> 本文取代 `20-Windows监控观察脚本-codex.md` 中关于异常收尾能力的说明，取代原因：首次10分钟运行的外层终端被中断后，PowerShell `finally` 未得到执行机会，留下了仍在运行的 Pktmon 会话。  
> 日期：2026-08-20  
> 工具：codex  
> 当前状态：遗留会话已按精确 ETL 路径核对后停止并转换；脚本已加入独立看门狗，Bash 与三份 PowerShell 均通过语法检查。  
> 下一步：用户再次运行10分钟命令并确认 Windows UAC；完成后从 latest 指针读取结果并分析。

## 1. 本次失败的根因

用户执行的参数没有问题，命令换行也不是失败原因。实际顺序是：

1. 第一轮10分钟任务已在 `13:57:56` 成功启动 Pktmon，目标为 `%TEMP%\codex-trend-watch-20260820-135756\packets.etl`；
2. 外层终端随后中断，主体 PowerShell 没有机会进入 `finally`，因此 Pktmon 仍在后台运行；
3. 第二轮任务在 `13:58:31` 尝试启动时，Pktmon 返回“数据包监视器已启动”，脚本保护性退出，启动器当时只显示了退出码1。

Pktmon 同一时刻只有一个全局会话。第二轮退出避免了覆盖或停止来源不明的诊断会话。

## 2. 遗留会话恢复结果

恢复前先以管理员身份读取 Pktmon 状态，确认活动 ETL 路径与第一轮任务目录完全一致；只有精确匹配后才执行停止和转换。

结果目录：`%TEMP%\codex-trend-watch-20260820-135756`。

- `packets.etl`：约29 MB；
- `packets.pcapng`：约46 MB；
- 转换统计：183,361个数据包，丢弃0个；
- PCAPNG 文件头：`0A0D0D0A`；
- `recovery.txt`：保存停止、转换和匹配说明；
- 未把包正文、Cookie、Token 或其他载荷写进文档或聊天。

这一轮的元数据时间线只记录到任务中断时，不能把后续纯 Pktmon 数据误说成完整的“进程—连接—包”同步观察结果。

## 3. 脚本加固

新增 `scripts/windows-trend-watch-watchdog.ps1`，由成功启动 Pktmon 的管理员主体独立拉起：

- 等待原定截止时间再加15秒收尾宽限；
- 若主体正常完成，看到无活动会话后直接退出；
- 若主体或外层终端意外消失，只在当前活动 ETL 路径与本次预期路径完全一致时停止并转换；
- 若路径属于其他任务，明确拒绝停止并记入 `watchdog.txt`；
- `--stop` 时给主体5秒自行收尾，之后再做同样的所有权核验。

同时增加了：

- 主体每15秒输出一次进度，减少把正常等待误认为卡死；
- 启动器在管理员进程失败时读取本轮 `FatalError`，除退出码外尽量回显具体原因；
- Bash 入口把看门狗与主体、启动器一起复制到 Windows TEMP；
- Pktmon 启动冲突会报告活动 ETL 路径，不再只给笼统退出码。
