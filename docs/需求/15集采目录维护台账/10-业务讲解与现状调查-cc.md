## 0. 一句话概括

> **现在**：系统里有一张 Excel 导进来的清单，叫《集采范围台账》。谁要下单，系统拿物料去这张清单里对一下——对上了就在单子上盖个章「是否集采=是」，仅此而已。
>
> **要变成**：这张清单要变成一套**有层级、有力度、有生命周期的管控规则**——
> ① 管到更细的类目（末级）；② 说清这条规则是谁定的（集团 / 二级集团 / 区域企业）；
> ③ 说清是"硬规矩"还是"软建议"（强管控 / 弱管控）；④ 删掉的规则不再物理消失，而是变成"失效"留痕。

打个比方：现在的台账像一张**贴在墙上的采购黑名单**，只有"在不在名单上"两种状态。
改完之后它像一套**公司红头文件**——每条规定都写明「谁发的文、管哪些单位、必须执行还是可以商量、什么时候开始、什么时候废止」。

## 1. 系统现在是怎么玩的（先看懂现状，需求才看得懂）

### 1.1 这张台账在哪、长什么样

| 项目 | 事实 | 证据 |
|---|---|---|
| 页面地址 | `http://10.0.54.16:32740/mdm/index.html#/mdm/procurementCatalogMgt` | 需求原文 |
| 前端文件 | `02zhaocai-front/scm-vue-all-mdm/src/views/procurementCatalogMgt/index.vue` | 已核实存在 |
| 列表的列在哪定义 | **不在代码里**，在静态 JSON：`scm-vue-all-mdm/public/statics/json/mdm/procurementCatalogMgt.json` | 已核实 |
| 后端服务 | `01zhaocai-end/scm-source-all/scm-source-plan`（寻源-计划模块） | 已核实 |
| 后端接口 | 只有 3 个：分页查询、删除、范围校验 | `PlanController.java:466-487` |
| 数据库表 | `sc_plan_product_range`（库 `scm_source_test` / `scm_source_uat`） | `SHOW CREATE TABLE` |

**⚠️ 第一个要知道的事实：这个页面没有"新增"和"编辑"按钮。**
页面上只有四个按钮：**导入、下载导入模板、导出、批量删除**（`index.vue:14-19`）。
也就是说——**台账是靠 Excel 导入维护的**。需求里说的"新增字段、必填、可选内容"，
落到实处首先是**改那个 Excel 导入模板**，不是画一个新增表单。这一点会直接影响工作量估算。

### 1.2 现在这张表里有什么

表 `sc_plan_product_range` 一共 13 个字段：

```
range_id / product_code 物料编码 / product_name / category_code 类目编码 / category_name
bu_code 影响范围编码 / bu_name / supplier_id+code+name 集采执行单位
create_by / create_by_name / create_time
```

真实数据（我查的）：

| 环境 | 行数 | 类目编码长度 |
|---|---|---|
| test | 5 行 | **全部 4 位** |
| uat | **7343 行** | **全部 4 位** |

**4 位 = 二级类目。** 这就印证了需求里那句"目前全集团只统一到二级"——不是口号，是数据实况。

另外两个坑：
- `bu_code`（影响范围编码）存的是 **`BU002/BU004/BU006` 这种斜杠拼起来的一长串**，不是一行一个 BU。
- `bu_name`（影响范围名称）在 test 里**全是空的**——导入时压根没回填名称。

### 1.3 "是否集采"现在是怎么算出来的（这是全需求的心脏）

系统里有三个地方会问"这单是不是集采"：**采购计划、采购方案、非平台采购业务录入**。

**好消息：这三个地方调的是同一个后端接口。**

```
/e/business/source/plan/queryInProductRangeNum
```

| 调用方 | 文件:行 |
|---|---|
| 采购计划 | `scm-vue-all-plan/src/views/purchasePlan/saveOrSubmit.vue:1584` |
| 采购方案 | `scm-vue-all-procurementscheme/.../procurementPlanPreparation/basicInfo2.vue:4304` |
| 非平台录入 | `scm-vue-all-procurementscheme/src/views/supplier/increasedListAdd.vue:489` |

它现在做的事（`PlanProductRangeServiceImpl.java:119-160`）：

1. **先看你是谁**：如果当前用户所在公司出现在字典 `collection_company`（集采执行单位）里 → 直接返回"0"（不算集采）。
2. 然后**逐行**拿物料去台账里查：`物料编码相等` **或**（`类目编码相等` 且 该行没填物料编码）。
3. 返回三种结果：`"0"` 全都不是集采 / `"1"` 全都是集采 / **一串中文物料名** = 有的是有的不是，前端弹框"集采和非集采不允许同时采购"。
4. 前端拿到 0/1，写到单据上的"是否集采"字段，**并且这个字段在页面上是只读的（`disabled`）**。

**⚠️ 第二个要知道的事实：现在的匹配逻辑完全不看 `bu_code`。**
表里虽然存了影响范围编码，但校验时一个字都没用上。
所以需求 §4 说的"按 BU 决定谁执行集采逻辑"——**是全新逻辑，不是改改条件那么简单。**

**⚠️ 第三个事实：这个"是否集采"目前基本没人用。** uat 真实数据：

| 表 | 总行数 | "是否集采"有值的行数 |
|---|---|---|
| `sc_scheme` 采购方案 | 17062 | **231（1.4%）** |
| `sc_plan` 采购计划 | 27142 | **122（0.4%）** |

这意味着：**期初上线时，历史单据几乎全是空的**，指望"回写"补历史是补不出来的。

### 1.4 审批流程现在在哪配

需求 §2.2 说"改成否就走新的审批流程，向上一级审批"。这件事**大概率不在 Java 代码里**：

- 代码只是把"是否集采"当成一个**流程条件变量**丢给工作流平台
  （`SourceWorkflowAdapterBuilder.java:156 / 235 / 319`，`metaCode="isCollection"`，`metaName="是否集采"`）。
- 具体谁审、审几级，是**在工作流平台的流程模板里画出来的**，不是写在代码里的。

**但云采（商城）那边已经有一个可以照抄的先例**：
`OrderPlanPushPurchaseConsumer.java:76-89` —— 它先去查商城采购范围拿到"是否强控"，
然后按强控与否**选两套不同的流程模板**（`ORDER_PLAN_FORCE` / `ORDER_PLAN_SIMPLE`）。
所以技术路径是通的：**后端负责选模板 + 传变量，流程本身由人在工作流平台上配。**

## 3. 最绕的那一段（6.1~6.4）用例子讲

类目树长这样（这就是你贴的**图片 2**，真实数据我查过了）：

```
15 金属材料          ← 一级（2 位码）
└─ 1501 黑色金属     ← 二级（4 位码）  ← 台账现在只能填到这一层
   └─ 150101 型材    ← 三级（6 位码）
      ├─ 15010101 方钢   ← 四级（8 位码）
      ├─ 15010102 圆钢
      └─ 15010103 扁钢
```

test 环境启用中的类目：**一级 26 个、二级 204 个、三级 624 个、四级 561 个**。

> **注意：不是每个三级下面都有四级。** 624 个三级只对应 561 个四级。
> 所以"末级"不是固定的第几层——**有的类目末级是三级，有的是四级**。
> 代码判断"是不是末级"只能靠"它下面还有没有子节点"，不能靠码长。

**6.2~6.4 那三条规则其实是同一句话，只是在不同层重复了一遍：**

> **同一个父类目下面，要么整个一起管，要么就一条条列清楚，不许混着来。**

举例：
- ✅ 只在台账里维护 `150101 型材` → 型材下面的方钢、圆钢、扁钢**全部**受管。
- ❌ 台账里已经有了 `15010101 方钢`，又想再加一条 `150101 型材` → **不允许**。
  因为一旦你已经点名了方钢，就等于宣告"这一层我要逐个管"，那圆钢、扁钢也必须逐个列出来。
- 同理往上：如果你在 `1501 黑色金属` 下面维护了 `150101 型材`，那黑色金属下面的其他三级也要一条条列。

**6.1 说的是另一回事**：如果你要精确管到某个具体物料（填了"集采物料编码"），
那么这一行的"类目编码"必须写到末级——不能写个二级类目再挂个具体物料，那样口径是矛盾的。

**6.5 判重**：以前判重只看「类目编码 + 物料编码」两个字段。
以后要看「类目编码 + 物料编码 + 集采目录层级 + 影响范围编码」四个，**而且只跟"生效"的行比**。
好处是：同一个类目，集团可以定一条、某个 BU 也可以定一条，互不冲突。

## 5. 我查出来的三个"红灯"（开会一定要说）

### 🔴 红灯一：「区域」在系统里几乎是空的，而且数据是脏的

需求 §4 说"如果是区域/企业集采，录入指定的区域的组织编码"。可是：

- **组织表里一条 `organization_level='QY'`（区域级）的记录都没有。** uat 实测分布：
  `BS 企业级 613 / GS 集团·二级集团级 17 / JT 平台级 1 / 空 223`。
  也就是说 —— **区域不是组织树上的一个节点**，你没法像选公司那样"选一个区域"。
- 区域实际藏在 `belong_plate_code`（所属区域编码）这一列里，**uat 854 条组织中 622 条这一列是空的（73% 空）**。
- 已有的区域编码是自己造的、**没有统一规范**：
  - 有像样的：`TSQY 唐山区域`、`SJZQY 石家庄区域`、`JHQY 吉黑区域`、`XTQY 邢台区域`
  - 也有直接拿公司编码当区域用的：`13260000 红树林总厂`、`18000077 北京混凝土`
- **而且有明确的脏数据**（这几条我是逐行查出来的）：
  - `XTQY` 在不同行里既叫"**刑**台区域"又叫"**邢**台区域"（错别字）
  - 河北金隅鼎鑫（12650064）的 `belong_plate_code=XTQY`，但 `belong_plate_name` 写的是"石家庄区域"——**码和名对不上**
  - `SJZQY` 有"石家庄区域"和"石家庄区域采购办公室"两个名字

**结论**：区域级集采**现在无法落地**，不是代码问题，是主数据问题。这是开会第一优先级的事。

### 🔴 红灯二：整个系统里到处写死了"集采类目 = 4 位二级码"

需求要"管到末级"，但代码里至少 **8 处**在做 `categoryCode.substring(0, 4)`（截前 4 位当二级类目）：

| 文件:行 | 干什么用的 |
|---|---|
| `SourceCollectionServiceImpl.java:224` | **云采订单采集**：截前 4 位再去 `sc_plan_product_range` 查，查不到整条丢弃 |
| `SourceEnrollServiceImpl.java:1036 / 1087` | 寻源报名 |
| `QuoteServiceImpl.java:3074 / 3222 / 4693` | 报价 |
| `PqSubmitFileServiceImpl.java:371`、`QuoteImportServiceImpl.java:140` | 报价文件、报价导入 |

其中第一条最要命：**台账一旦填了 6 位或 8 位的末级类目，云采采集这条链路就会一条都匹配不上，数据静默丢失。**
（这个坑在 06_2 需求的调查文档里已经踩过一次并写进了记录。）

### 🔴 红灯三：删除现在是物理删除，加"失效时间/状态"等于改数据模型

`PlanProductRangeServiceImpl.java:100` 用的是 `deleteBatchIds`——**直接从表里删掉**。
表里也**没有 `delete_sign` 字段**。
需求 §2.3/§2.4 要"记录删除时间 + 状态改为失效"，等于把删除改成逻辑删除。
连带影响：所有读这张表的地方都要加"只读生效数据"的条件，否则失效的规则还会继续生效。
目前已知读这张表的除了台账自己，还有 `SourceCollectionServiceImpl`（两处 `selectList` 全表扫）。

## 7. 几个零碎但会绊脚的现状

- **导入模板是按"第几列"取值的**：`ProductRangeImportServiceImpl` 里写的是
  `lines.get(0)` 类目编码、`lines.get(2)` 物料编码、`lines.get(4)` 影响范围编码、`lines.get(5)` 集采执行单位。
  **新增 4 列后，如果谁还用旧模板导入，数据会整体错位落库。** 上线时旧模板必须停用。
- **导入模板文件不在代码里**，是传到 OBS 上的一个 xlsx，地址配在数据库 `scm_ubm_*.scm_staticfile`，
  编码 `planProductRangeTemplate`。改列 = 传新文件 + 改这条配置。
- **导入时硬性拦"必须是二级类目"**：`ProductRangeImportServiceImpl` 里如果类目不是二级就报错
  "物料组编码不属于二级类目"；即使填了物料编码，落库时也强行存成二级码 `midClassCode`。管到末级必须改这里。
- **导出模板 test 环境是缺的**：`planProductRangeExport` 在 uat 有（8 列），**test 里查不到**。
  而且 uat 那份有个笔误：第 3 列 `categoryName` 的标题写成了"集采物料编码"（应该是"集采类目名称"）。
  这次加 4 列时顺手修掉。
