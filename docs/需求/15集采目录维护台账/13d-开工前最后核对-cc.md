# 1. ✅ 已查实①：类目树是同一棵，用招采自己的 `mdm_material_class`

**背景**：3.1 说「类目编码参考云采【品类管理-后台类目管理】」。
电商系统的类目通常有**前台/后台两棵树**，若台账选的是云采的码、判定时拿它回招采查物料，两棵树对不上就会静默失效。所以必须核实。

**云采侧确实有两张表**（`scm_product_uat`）：

| 表 | 中文 | 条数 |
|---|---|---|
| `ic_product_category_back` | 后台类目（产品说的就是这个） | 1421 |
| `ic_product_category_web` | **前台类目（另一棵树）** | 959 |
| `scm_ubm_uat.mdm_material_class` | 招采物料类目 | 1445 |

**逐条比对结果（uat，2026-09-09）**：

| 对比项 | 结果 |
|---|---|
| 编码相同 | **1415** |
| 编码 + 名称都相同 | **1413** |
| 层级结构 | 两边都是 2/4/6/8 位严格前缀式四级树，`10 燃料 → 1001 煤炭 → 100101 烟煤` 完全一致 |

差异只有三处，全部无害：

1. **云采多 6 条，全是垃圾数据**：`111` / `22222` / `3333`，以及三条安全测试留下的注入探测串
   （`<%- 976687343+959785862 %>`、`expr 870106439 + 950662619`、`aalnrrttilbfahdjcmjf`）。
   ⚠️ 这三条是**存储型注入 payload 落库**，与本需求无关，但应转给「16安全」主题。
2. **招采多 30 条，全是「服务」和「工程」**：`3308 维修和保养服务`、`3309 租赁服务`、`3311 金融服务`、
   `36 工程`、`3601 房屋施工`、`3606 安装工程` …… 云采商城不卖服务/工程，没有这些类目是合理的。
   👉 **由此引出 §4 问题①。**
3. **同码不同名 2 条**：`3306` 云采叫「装卸服务」/ 招采叫「装卸搬运服务」；
   `3303` 云采叫「咨询服务」/ 招采叫「商务及鉴证咨询服务」。台账存编码，不影响。

**对照组**：前台类目 959 条只有 938 条能在招采找到，顶层结构也不同（还有 `1402` 父节点指向自己的脏数据）。
⇒ **产品说的是「后台类目」，是对的；若说的是前台类目，这事就真麻烦了。**

## 结论（不必再问产品）

台账类目选择器走招采现成接口：

```
POST /c/business/mdm/materialClassQuery/queryMaterialClassTreeFull
     → MaterialClassController（scm-mdm-all/scm-mdm-material）
     → mdm_material_class
```

支持选到末级（2 / 4 / 6 / 8 位都可，对应 3.1）。理由：与云采后台类目同一棵树；无需跨系统调用；
台账配完后判定集采、云采采集回单都拿这个码查 `mdm_material`，**同一棵树才不会错**。

# 2. ✅ 已查实②：3.3 要的「提单企业所属板块 / 区域」拿得到，不用改前端

3.3 要求取值时按 `物料编码 ＋ 提单企业对应的区域或二级集团` 匹配。
这是本轮最大的工程未知项——**取数路径已跑通，全在后端，前端和接口契约都不用动**：

```
CurrentUserUtil.getCurrentUser().getCurCompanyCode()        ← 登录人当前公司编码
   → orgManagerFeignService.queryByOrgCode(OrganizationManageDTO)
        POST /c/business/ubm/org/queryByOrgCode
   → OrganizationManageDTO.belongBuCode    ← 二级集团（板块），对应 collection_level=2
     OrganizationManageDTO.belongPlateCode ← 区域，        对应 collection_level=3
```

- 现成先例：`CollectionDailyAmountLedgerServiceImpl:174` 已在用 `org.getBelongBuCode()`。
- 校验接口 `PlanProductRangeServiceImpl.queryInRangeNum()` 现在只收 `productCode/categoryCode`
  （`PlanProductRangeCheckLineDTO` 就两个字段），**但它本来就在方法里取了 `CurrentUserUtil`**（判集采执行单位那段），
  所以补板块/区域**不需要改 DTO、不需要前端配合**。
- 板块名以字典 `Owningplate` 短名为准，缺失回退组织表 `belongBuName`（同上先例）。

## ⚠️ 一个坑：不要用 `sc_plan.bu_code`

`sc_plan` 表上有现成的 `bu_code 板块编码`，看着能直接用，**但 uat 实测填充率只有 1.6%**：

| 字段 | 总数 | 为空 |
|---|---:|---:|
| `sc_plan.bu_code` | 27155 | **26713（98.4% 空）** |
| `sc_plan.company_code` | 27155 | 12 |

⇒ **板块一律由 `company_code` / 登录人公司现算，不读 `sc_plan.bu_code`。**
