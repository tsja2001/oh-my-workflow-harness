# 一、🔴 先说那个硬冲突

台账表上有一个**唯一索引**：

```sql
UNIQUE KEY `range_product_idx` (`product_code`, `category_code`)
```

意思是：**同一个（物料编码 + 类目编码）的组合，全表只允许存在一行。**

这带来三个后果，每一个都能让功能做不成。

## 后果一：需求 §3.3 根本存不进去

`01c` 3.3 明确说：

> 集采目录层级不属于"集团集采"，**同一类目/物料可以属于不同的二级集团或者区域**。

翻成数据：柴机油配给冀东水泥一条、再配给混凝土集团一条——

```
第 1 行：物料=170101010186，类目=170101，层级=二级集团，影响范围=BU002
第 2 行：物料=170101010186，类目=170101，层级=二级集团，影响范围=BU003
                ↑ 这两个字段完全一样 → 撞唯一键 → 第 2 行录不进去
```

> ⚠️ **不改这个索引，§3.3 就是纸上谈兵。** 这跟"状态"功能无关，是这次需求整体的一个卡点。

## 后果二：软删除会让"重新启用"变成不可能

改成"标记失效"之后，那一行**还占着索引位置**：

```
今天：删掉柴机油那条 → 行没了 → 两个月后重新录一条一样的 → ✅ 成功
以后：标成"失效"    → 行还在 → 两个月后重新录一条一样的 → ❌ 撞唯一键报错
```

> 📌 **这个坑我们踩过。** `ai-docs/经验教训.md` 里有一条一模一样的：
> 「`serial_number` 之类的唯一索引不认 `delete_sign`——软删除的行仍占着号」。

## 后果三：导入是"裸 insert"，撞键会整批回滚

导入代码就是循环 `insert`，**没有任何判重**，而且整个包在一个事务里。
所以只要有一行撞唯一键 → 抛异常 → **整批导入全部回滚**。

## 所以真正要定的问题是

**新的唯一键应该是哪几个字段？**

老 §6.5 曾经给过答案——"类目编码 & 物料编码 & 集采目录层级 & 影响范围编码"四字段联合，
而且"只对生效数据判重"。**但那条被产品划掉作废了。**

> 🔴 **这就是待确认问题③（判重规则）的技术后果。**
> 它不是一个抽象的业务问题，是"这张表的唯一索引改成什么"这么具体。
> **这条不定，状态功能和 §3.3 都做不下去。**

# 三、诚实回答"好做吗"

| 事项 | 难度 | 卡在哪 |
|---|---|---|
| 加两列（状态、失效时间）+ 补 `update_by`/`update_time` | 🟢 半天 | 无 |
| 删除接口改成改状态 | 🟢 十分钟 | 无 |
| 列表页加状态筛选、默认只看生效 | 🟢 半天 | 无 |
| **6 处读表全部加"状态=生效"** | 🟡 一天 | 不难，但**必须一处不漏**，漏了是静默故障（不报错） |

| 期初 7343 行填状态 | 🟢 一条 SQL | 要产品点头 |

> **一句话：代码不难，难在两点——①规则没定（唯一索引改成什么）；②漏一处过滤是"不报错的错"。**
>
> 第 ② 点正是你担心的。**它的解法不是"更小心"，是"把清单列全然后逐个打勾"**——上面 B 组就是那张清单。

# 四、为什么这类改动容易出事（讲透给你听）

软删除这种改动有个特点：**做错了不会报错，只会"悄悄地不对"。**

```
真删除做错了  →  数据没了  →  马上有人喊
软删除做漏了  →  数据都在  →  规矩明明取消了却还在管人
                              → 可能几个月后才被发现
```

而且发现的时候，现场是这样的：

> 业务："我明明把柴机油那条删了啊，为什么小李的单子还是集采？"
> 你在页面上一看：状态确实是"失效"。
> ——因为漏加过滤的是**云采采集**那条链路，页面上根本看不出来。

**所以这个功能的质量，不取决于代码写得多好，取决于那张清单列得全不全。**
