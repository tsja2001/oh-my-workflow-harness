# 零、先纠正一个印象：这不是三个并列的东西

你可能以为是三个平行的入口。实际上是**一条主线 + 一个后门**：

```
【主线】
  ①采购计划  →  待采购池  →  ②采购方案  →  定标签合同
  "我要买什么"              "打算怎么买"

【后门】
  ③非平台录入
  "这笔买卖压根没走平台，事后补个记录"
```

集采管控这件事，**这三个口子必须一起堵**——堵漏一个，规矩就是摆设。

---

# 一、主线走一遍（用一个具体的人）

## 第 1 步：企业的采购员填**采购计划**

冀东水泥某个水泥厂的采购员小王，要买一批柴机油。
他进「采购计划编制」，选物料、填数量、填什么时候要，**提交**。

**提交那一瞬间，系统去集采台账查一次**：柴机油在不在集采范围里？
在 → 这张单子盖上"**是集采**"的章。

> ✅ 你说的第一句——"各个公司发布采购计划，如果是集采目录的自动列为集采"——**完全正确**。

## 第 2 步：审批通过后，每一行掉进一个"待采购池"

这一步你的描述里没有，但它是理解第 3 步的关键。

计划审批通过后，**这张单子上的每一行物料，会各自变成池子里的一条记录**。
池子里的每条记录都记着"我是从哪张计划的第几行来的"。

**池子就是计划和方案之间的中转站。** 一张计划 10 行，就掉 10 条进池子。

## 第 3 步：做**采购方案**的人从池子里挑

采购方案回答的是"**打算怎么买**"——公开招标？邀请招标？询价？找哪几家供应商？

做方案的人打开「采购方案编制」，**从池子里挑几条组成一个方案包**
（可以把好几张计划的行合并成一个方案，一起去招标，这样量大好谈价）。

> ✅ 你说的"把采购计划打包成采购方案"——**这句对**，就是从池子里挑行打包。

# 二、但"然后集中去集采吗"这句，**要改一改**

## 2.1 集采的单子，本企业**不该自己做方案**

采购方案编制页面上有一道拦截。当系统发现：

- 这张方案里的物料**都是集采物料**，而且
- 每一行**都有对应的采购计划**

它会**直接拦住你**，弹一句：

> **"集采物资采购且有计划，请联系集采执行单位组织采购"**

意思是：**这活不该你干。**

## 2.2 那该谁干？——机电公司

还记得台账上那一栏"集采执行单位"吗（`10h` §八讲过，就是"跑腿的那家公司"）？

计划审批通过、掉进池子的时候，如果这行是集采物料，
**系统会顺手在这条池子记录上写一笔"这活归机电公司"**。

然后机电公司**以供应商的身份登录系统**，在「用户中心 / 集采采购计划」这个页面里，
**筛出所有归自己执行的记录**，统一组织采购。

> 💡 这也解释了一个一直很怪的事：台账上那一列在数据库里的字段名带着 "supplier"（供应商）——
> **因为集采执行单位在这套系统里就是以"供应商"身份存在的**（机电公司在供应商库里有一条正式记录）。

## 2.3 所以两条路是这样分的

```
计划审批通过，行掉进池子
        │
        ├── 不是集采物料 → 本企业自己做采购方案 → 自己招标 → 自己签合同
        │
        └── 是集采物料   → 打上"归机电公司"的标记
                          → 机电公司在自己的页面里看到
                          → 由机电公司统一组织采购
```

**"集中"是集中在机电公司手里，不是集中在采购方案里。**

# 三、非平台录入：为什么它跟集采有关系（你问的重点）

## 3.1 它是干什么的

有些采购**压根没走这个平台**——金额太小、太紧急、或者在别的系统里做完了。
但集团要看全集团的采购总盘子，**这些"平台外"的生意也得有个账**。

「非平台采购业务录入」就是这个补录口：**在外面已经做完的采购，事后录进系统。**

## 3.2 为什么必须管它——它是唯一能绕过所有管控的口子

打个比方：

> 公司规定"5000 块以上的开销必须走报销系统审批"。
> 那"我先自己垫钱、事后填个报销单"这条路**也得管**——
> 不然大家全走这条路，那条规定就是废纸。

**非平台录入就是那条"事后填单"的路。**

如果集采管控只管采购计划和采购方案，那企业想绕开集采太容易了：

```
❌ 不管它的话：
   小王想自己买柴机油，不想走机电公司
   → 不填采购计划，直接在外面买了
   → 回来走"非平台录入"补个记录
   → 神不知鬼不觉，集采管控完全绕过去了
```

所以这个口子**必须一起堵**：非平台录入提交时，同样要去集采台账查一次、同样要盖章、
同样要按集采层级走对应的审批流。

## 3.3 它是三个口子里量最小、但最容易被漏掉的

uat 实测：

| 入口 | 单据量 |
|---|---|
| 采购计划 | 27,151 张 |
| 采购方案 | 17,075 张 |
| **非平台录入** | **163 条** |

163 条，比前两个少两个数量级。
**正因为量小、平时没人盯，做需求时最容易被漏掉**——而它偏偏是唯一的后门。

# 四、那这次开发到底改这三个地方的什么

## 4.1 今天已经有的

这三个页面**都已经**在提交时去查一次集采台账、都会盖"是否集采"的章。这部分不是新做。

## 4.2 这次要改的四件事

| # | 改什么 | 说明 |
|---|---|---|
| **1** | **查的口径变了** | 今天只按"物料编码"或"二级类目"查；改成"先按物料编码 → 找不到取末级类目 → 再往上一级"，而且还要看**影响范围**（当前公司在不在管辖范围内）和**状态**（这条规矩失效没有） |
| **2** | **章从 1 个变 3 个** | 今天只盖"是否集采"；以后还要盖"**集采目录层级**"和"**是否强管控**" |
| **3** | **章可以有条件地改** | 今天"是否集采"是锁死的；以后：默认"否"不许改；默认"是"可以改成"否"，但强管控的改了要多审一级 |
| **4** | **三个章要递给审批流** | 画审批分支的人（郭小华）要用这三个值当条件 |

## 4.3 ⚠️ 非平台录入这一处，工作量比看起来大

两个坑：

1. **它的"是否集采"字段名跟另外两个不一样**（另两个叫一个名字，它叫另一个），
   照着前两处改代码会漏掉它；
2. **它走的是一条独立的"绿色通道"审批流**，现在只往工作流递了两个变量，
   **完全没有"是否集采"**。所以这里是**新加一整组变量**，不是"再加一个"。

# 六、你只要记住这五句

1. **不是三个并列入口，是"计划 → 池子 → 方案"一条主线，加上"非平台录入"一个后门。**
2. **计划提交时盖章；审批通过后每行掉进池子；做方案的人从池子里挑行打包。**
3. **集采的活本企业不做方案——系统会拦住，交给机电公司统一组织采购。**
4. **非平台录入必须一起管，因为它是唯一能绕过前面所有管控的路。**
5. **这三处今天已经会盖"是否集采"了；这次是改口径、把 1 个章变 3 个、允许有条件修改、并递给审批流。**
