### 1.1 §6 那处变化到底意味着什么（重要）

**被划掉的 6.1～6.4 讲的是「导入台账的时候，不许你乱填」**——一套**录入期约束**：
> 你要是已经点名管了 `15010101 方钢`，就不许再加一条 `150101 型材` 把整层一锅端；这一层要么整体管，要么逐个列。

**留下的那一句讲的是「单子提交的时候，怎么去台账里找匹配」**——一套**运行期消解**：
> 拿物料编码去找 → 找不到就拿它的末级类目去找 → 还找不到就拿上一级去找 → 一直往上。

**产品是有意把设计换了，而且换对了。** 对比：

| | 作废的老设计（6.1~6.5） | 现在的新设计（那一句） |
|---|---|---|
| 思路 | **不许填出歧义**（录入时严格约束） | **允许重叠，提单子时按"越具体越优先"消解** |
| 业务维护者要做什么 | 想管螺纹钢，就得把型材下面方钢圆钢扁钢**全部一条条列出来** | 想管螺纹钢就只填螺纹钢 |
| 可行性 | **非常难遵守**，7343 条历史数据一条都不符合 | 好用 |

而且新设计是**自洽的**：二级配了一条管一片、三级又配了一条管更细——
匹配时先找三级那条（更具体），找到就停，不会再往上撞到二级那条。**重叠不再产生歧义。**

### ⚠️ 但换完之后留下两个洞（这才是要问产品的）

**🕳 洞一：判重规则跟着一起没了。**
老 6.5 定义的是「类目编码 & 物料编码 & 集采目录层级 & 影响范围编码 四个字段全同才算重复，且只跟生效的比」。
现在这条被划掉了 → **是完全不判重了吗？**
这不是理论问题：现在的匹配接口是按「只可能查到一条」写死的（`selectOne`），
**查到两条直接抛异常，三个单据页面全部提交不了**（见 §4.2）。

**🕳 洞二：横向多条命中，听谁的？**
新那句话解决的是**纵向**问题（螺纹钢找不到就往上找型材）。
**横向没解决**：同一个"螺纹钢"上，集团配了一条、水泥集团配了一条、唐山区域配了一条——三条都在这一层命中，听谁的？

**而这恰恰就是产品自己在会上问、并说要去确认的那件事**（§1 差异 2）。
所以「作废 6.5」+「留下唯一性那个问号」是同一件事的两面：**能不能并存（判重）、并存了听谁的（优先级）**。

**建议的补法**（已写进 `11b` A2 的话术）：判重仍按四字段 + 只比生效；优先级按"越具体越优先"（企业/区域 > BU > 集团）。

### 附带一个小影响：6.1 作废之后，导入不该再改写类目

老 6.1 要求"填了物料编码时类目必须到末级"。作废后允许"物料编码 + 二级类目"这种行。
按新匹配规则，先按物料编码找，找到就用，**这一行的类目编码根本用不上**，所以作废无害。
但**现在的导入代码会强行把类目改写成二级类目**（`ProductRangeImportServiceImpl.finish()` 里 `dto.setCategoryCode(data.getMidClassCode())`），
这个改写既没意义又会丢信息，**这次要一起去掉**。

## 3. 这次新查出来的三件事（都是好消息）

### 3.1 ✅ 招采自己就有一棵完整的四级类目树，还有现成的树接口和树组件

会上产品最不确定的技术问题是（14:03）：
> "这个物料编码的话，现在这块有棵树，我不知道你能不能引用还是招采到时候自己再去建棵树……我对标的话就是云采这棵树……我不知道招财那边能不能引用到它"

**答案：不用引用，招采本来就有。**

| 事实 | 证据 |
|---|---|
| 招采（UBM 主数据）有物料类别表 `mdm_material_class` | `scm_ubm_uat.mdm_material_class`，1445 条，`data_source` 全是 `mdm` |
| 它是**完整四级**的 | uat 启用中：一级 27、二级 228、三级 624、四级 562 |
| 和云采那棵树**几乎是同一份数据** | 1445 条里 **1415 条编码能对上云采**，其中 **1413 条连名称都一样**（两边都是从 MDM 主数据同步来的） |
| **招采这棵比云采还全** | 招采多出 `36 工程`（房屋施工/安装工程/装修工程…）和一批 `33xx 服务`（维修保养/租赁/工程管理…）——云采是商城只管实物商品，招采要管工程和服务 |
| 已有**树查询接口** | `POST /c/business/mdm/materialClassQuery/queryMaterialClassTreeFull`（`MaterialClassController.java:53`），另有 `materialClassMange/queryMaterialClassTreeFull` |
| 已有**前端树选择组件**，还带多选 | `02zhaocai-front/scm-vue-all/scm-vue-ubm/src/views/MaterialMgt/component/Tree2.vue:160`，勾选后返回 `{categoryCode, categoryName, purchaseType}`——正好是台账要的字段 |
| 已有**逐级向上取父级**的现成接口 | `POST /c/business/mdm/productQuery/getClassLine`（`MaterialClassServiceImpl.java:265 queryClassLine`），传一个类目码，返回它的一级/二级/三级/末级四层。**`01b` §6 那句"末级没有取上级"就是拿这个实现的** |
| 树数据是干净的 | uat 实测：无重复编码、无断链（父节点不存在）、无"启用的子挂在停用的父下面"；27 个顶级 |

**结论：**「集采类目支持选到末级」这件事，8/19 我判的是"半清楚"，**现在可以判为清楚**——数据、接口、组件三样都是现成的，只要在台账页面上把输入框换成树选择器，并把导入校验里"必须是二级类目"那个限制拆掉。

> 顺带一个对业务有用的数字：**要"管到末级"，末级一共 1166 个**（二级里有 109 个本身就是末级、三级里 495 个、四级 562 个）。
> 也就是说"末级"不是固定的第几层，**不能按编码长度判断**，只能按"下面还有没有子节点"判断。

### 3.2 ✅ 「区域」虽然主数据还是空的，但取值路径是通的

产品在会上把区域的玩法讲清楚了（18:05-20:36），和我 8/19 的判断一致：

**技术上完全可行，缺的只有数据**（见 §5.1）。

## 4. 会后重新核代码，发现的 4 个"现在就已经坏了"的地方

这些都不是需求要求的，是我这次读代码顺手撞见的。**其中前两个会直接影响本次改造能不能跑通，必须处理。**

### 4.1 🔴 混采场景下，单据点了提交会**永远卡住**（不报错也不成功）

三个页面（采购计划 / 采购方案编制 / 非平台录入）里都是这段代码：

```js
if (this.isChineseString(res.data)) {
  await new Promise((resolve, reject) => {
    this.$confirm({ title: `${res.data}数据是集采物料，集采和非集采不允许同时采购`,
      onOk() {}, onCancel() {} });     // ← 既不 resolve 也不 reject
  });
}
```

- `onOk` 和 `onCancel` 都是空的，**这个 Promise 永远不会结束**，`await` 就永远停在这里；
- 结果：**用户点"确定"或"取消"之后，什么都不会发生**，单子既不保存也不报错。
- 出处：`scm-vue-all-plan/src/views/purchasePlan/saveOrSubmit.vue:1592`、
  `scm-vue-all-procurementscheme/.../basicInfo2.vue:4313`、
  `scm-vue-all-procurementscheme/src/views/supplier/increasedListAdd.vue:499`。

**为什么本次必须一起改**：现在这个分支很少触发（台账只管 7 个二级类目）。
一旦管到末级 + 多层级，**"一张单子里有的物料是集采有的不是"会变成常态**，这个死锁就会天天出现。

### 4.2 🔴 匹配接口用的是 `selectOne`，台账一旦一个类目有多行就**直接抛异常**

`PlanProductRangeServiceImpl.java:139-144`：

```java
query.eq(PlanProductRange::getProductCode, lineDTO.getProductCode())
     .or(w -> w.eq(PlanProductRange::getCategoryCode, lineDTO.getCategoryCode())
               .isNull(PlanProductRange::getProductCode));
PlanProductRange productRange = planProductRangeMapper.selectOne(query);   // ← 命中多行会抛异常
```

- MyBatis-Plus 的 `selectOne` 命中 2 行以上就抛 `TooManyResultsException`。
- 今天没事，是因为 uat 里**每个类目只有一行**（我查过：按"纯类目行"分组，没有任何一个类目出现两次）。
- **但需求 §4 明确要求同一个类目可以有多条规则**（集团配一条、二级集团配一条、区域配一条）。
  这个改造一落地，**这个接口就会开始抛异常，三个单据页面全部提交不了**。
- 同样的坑在 `getPlanProductRange`（导入判重用的，:106-118）也有一份。

**结论：这个方法必须重写成 `selectList` + 按优先级挑一条**，不是可选项。

### 4.3 🟡 台账列表的「创建时间」列**永远是空的**（这就是产品在会上抱怨的那个）

产品原话（01:41）："当时批量导入创建时间都空着呢"。查下来**不是数据的问题，是显示的问题**：

- 库里 uat 7343 行 `create_time` **一条都不为空**；
- 但接口返回的 `createTimeStr` **全是 null**——我实测调了一次 test 的接口，三行全是 `"createTimeStr": null`；
- 原因在 `PlanProductRangeServiceImpl.java:74-82`：循环里 `new` 了一个 DTO、格式化了时间，然后**这个对象被丢掉了**，最后 return 的是 `ListCoverUtil.listCover(...)` 另外生成的一批（它只做 `BeanUtils.copyProperties`，不会把 `createTime` 转成 `createTimeStr`）；
- 前端列配的又正是 `createTimeStr`（`procurementCatalogMgt.json`）。
