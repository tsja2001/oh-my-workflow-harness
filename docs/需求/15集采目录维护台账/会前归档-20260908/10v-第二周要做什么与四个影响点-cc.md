# 第一部分 · 第一周那 4 个影响点

## 1.1 为什么会有"影响点"这回事（一句话）

```
台账（sc_plan_product_range）＝ 一本规矩册
                │
                │  有 7 处代码会翻这本册子
                ▼
   ┌────────────────────────────────────────┐
   │ 6 处是采购业务在翻（提交单子时查自己算不算集采） │
   │ 1 处是台账页面自己翻（列表分页）              │
   └────────────────────────────────────────┘

你第一周把这本册子改了三件事：
  ① 同一个物料允许写多行（以前只能一行）
  ② 删除不是真删，改成打「失效」标记（以前直接消失）
  ③ 类目能写到末级（以前只能写到二级）

→ 那 6 处翻册子的代码，是照着旧规矩写的，翻不动新册子。
```

**"保命改造"就是把这 6 处翻册子的代码改到能读懂新册子。**
它不是新功能、页面上看不出任何变化——**它的全部价值就是"改完之后，别的地方不会坏"。**

## 1.3 影响点 ① —— 同一物料允许多行之后，查规矩的代码会当场炸

### 大白话

以前册子上「一个物料只可能有一条规矩」，所以代码写的是"**给我查出那一条**"（`selectOne`）。
需求 3.3 要求同一个物料能配给不同的 BU（比如螺纹钢，冀东水泥一条、唐山区域一条）——
册子上出现两行了，代码还在说"给我那一条"，**数据库直接甩脸：你要一条，我这有两条，报错。**

### 4 处里分两种，第二种更阴

| 表现 | 位置 | 后果 |
|---|---|---|
| **当场抛异常** | `:108`、`:138` | 用户点【提交】→ 转圈 → 报系统错误。**三个采购页面全部提交不了。** 上线第一天就炸，好在一眼能看见 |
| **不报错，但随机挑一条** | `:687`、`:2034` | 这两处写了 `query.last("limit 1")` 但**没有 order by**——命中两行时，数据库返回哪条算哪条。取到的是 `supplier_code`，也就是「**这批活派给哪家集采执行单位**」。<br>**挑错了不会报错，只是这批物资被派给了错的公司。** 等业务发现，可能是一周以后 |

> 我今天把这 4 处逐个读了一遍。`10t` 里写「2 处」——那是只数了会抛异常的两处。
> **实际 4 处都得改**，后两处不改的话，多行配置这个功能等于配了也不生效（随机取）。

**顺手还发现一个空指针**：`:687` 和 `:2034` 是这样写的——

```java
PlanProductRange range = planProductRangeMapper.selectOne(query);
return range.getSupplierCode();   // ← range 为 null 时直接空指针
```

一行都没命中就崩。今天没炸是因为它只在"已判定为集采"的分支里被调；
但**加了「状态=生效」过滤之后，"判集采时是生效的、审批通过时已失效"这个时间差就出现了**，
这个空指针会被真正触发。**改的时候顺手补上判空。**

### 怎么改

`selectOne` → `selectList` + **按一个明确的优先级排序挑一条**。

### 🔴 卡在哪

**优先级到底怎么排，就是 `12c` 你写的问题 2**：

> "同一个品类上，二级集团配一条、区域也配一条，应该听谁的？
> 比如 170101 物料，冀东水泥和唐山区域都配了，具体按哪条规则走？"

**这条不定，这 4 处一行代码都写不了**——`selectList` 之后按什么排序，就是这个答案。
（~~我的建议：层级越高越优先，即 集团 > 二级集团 > 区域·企业~~
**【订正 2026-09-08：方向反了。这里问的是「一行物料命中两条规矩用哪条」，答案是「影响范围越窄越优先」= 区域·企业 > 二级集团 > 集团**，
跟 6.2 纵向的「越具体越优先」同一套心智模型。
「层级越高越优先」是另一个问题的答案——6.3「一张单子多行、表头记哪一级」，那里才是集团赢。
两件事方向相反，最容易混。详见 `13` §1.1 的 D2 / D3。】**；同层级再按创建时间取最新。)

## 1.4 影响点 ② —— 删除改成"标记失效"之后，6 处读表都要加"只看生效的"

### 大白话

以前点【删除】，那行从数据库里真的没了，所以读的时候不用管——**读到的必然是有效的**。
改成软删之后，失效的行**还躺在表里**。读的地方不加一句"只要生效的"，
**你在页面上明明把柴机油作废了，采购单据那边照样把它当集采管。**

### 为什么这条是整个第一周最容易出事的地方

**因为它漏了不报错。**

影响点 ① 漏了会当场抛异常，测试一提交就发现。
影响点 ② 漏一处——比如漏了云采采集那条——**页面上一切正常**：
台账列表里那行清清楚楚写着"失效"，业务却发现该采的还在采、该停的没停。
**你在页面上是查不出来的**，得去看定时任务的数据。

### 6 处清单（就是 1.2 表里的 2~7）

改法都一样，每处加一个条件。**改法不难，难在一处都不能漏。**

**解法不是"更小心"，是拿上面那张 7 行的表逐个打勾。** 这份清单就是给这个用的。

### 🟡 一个附带问题

失效的行，**还占不占判重的位置**？（`12c` 你写的问题 1 后半句）
—— 比如把「柴机油 + 集团集采」作废了，现在要重新录一条一模一样的，能不能录进去？

**我的建议：不占。** 失效的行就是历史留痕，不该挡着新规矩。
（否则业务会遇到"删了却录不回去"，只能找运维改库。）

## 1.5 影响点 ③ —— 类目放开到末级之后，云采采集会静默丢单

### 大白话

`SourceCollectionServiceImpl.java:224` 这一行：

```java
String midClassCode = s.getCategoryCode().substring(0,4);   // 把订单的类目码砍成 4 位
if(skuMap.get(midClassCode) != null) {                       // 拿 4 位去台账里对
```

`skuMap` 的键，是**台账里存的类目码**。
今天台账只存 4 位（二级类目），砍成 4 位刚好对得上。
台账一旦开始存 6 位、8 位的末级类目——**键是 6 位，拿 4 位去找，永远找不到。**

`if` 进不去 → 这条订单**不落库** → 该被采集进来的集采订单，一条都进不来。
**而且整个过程没有任何报错**，日志里也看不出异常，只是数据少了。

**还有一个次生问题**：`substring(0,4)` 本身，遇到长度不足 4 位或者为 null 的类目码**直接抛异常**，
一条脏数据就能把整个采集任务打断。

### 怎么改

不砍字符串，改成**用完整类目码逐级向上找**：
先拿 `170101` 去台账查，没有就退到 `1701`，再没有退到 `17`。
这也正是需求 6.2 要的匹配口径——**这一处改完，等于顺手把第二周的匹配逻辑先落一半地基。**

### ⚠️ 一个边界，今天核实出来的，别卷进来

全仓一共有 **10 处** `substring(0,4)/(0,6)` 这种写死二级类目的地方：

```
SourceCollectionServiceImpl:224    ← 只有这一处在读台账，属于本次
PlanProductServiceImpl:74          （substring(0,6)）
SourceEnrollServiceImpl:1036, 1087     寻源报名
PqSubmitFileServiceImpl:371            报价文件
QuoteImportServiceImpl:140             报价导入
QuoteServiceImpl:3074, 3222, 4693, 4705   报价
```

**除了第一处，其余 9 处都不读台账**，是寻源和报价那条线自己在切类目码。
**这次不动它们**（`10l` 当时把这 10 处并列写了，容易让人以为都要改）。

但记一笔：**末级类目这件事一旦往寻源、报价那条线流，这 9 处会跟着出同样的问题。**
这是下一期的事，现在只需要知道它存在。

## 1.6 影响点 ④ —— 数据库索引挡着第二行，而且 **test 和 uat 不一样**

### 今天新查出来的（这条 `10t` 写得不准，我订正）

```
uat  (scm_source_uat.sc_plan_product_range，7343 行)
     PRIMARY            (range_id)
     range_product_idx  (product_code, category_code)   ← Non_unique=0，是唯一索引

test (scm_source_test.sc_plan_product_range，5 行)
     PRIMARY            (range_id)
     ——没有 range_product_idx，一个唯一索引都没有
```

### 这意味着什么（这条比索引本身重要）

需求 3.3 要"同一物料配给不同 BU 存两行"。
在 **uat** 上，那个唯一索引会把第二行**直接挡回去**——存不进去。

但在 **test** 上没有这个索引，**两行随便存**。

> 🔴 **所以：你在 test 上把 3.3 这个功能测通了，到 uat 一样会失败。**
> 而且失败点在数据库，不在你的代码里——排查时容易往代码上找半天。

### 怎么改

按新的判重口径重建索引（大概率是 `(product_code, category_code, level, scope)` 这一组），
**并且 DDL 必须在 test 和 uat 两边都执行**——test 那边是从"没有"变成"有"，
不然 test 永远测不出真实行为。

### 🔴 卡在哪

**判重口径就是 `12c` 你写的问题 1**：

> "重复行怎么算？我的理解：类目 + 物料 + 层级 + 影响范围。"

**这个答案直接就是索引的列清单。** 不定，索引建不了；索引建不了，导入的判重也写不了。

## 2.2 业务上的变化：单子上从「1 个章」变成「3 个章」

### 今天

采购计划 / 采购方案 / 非平台录入这三张单子，表头上有**一个**「是否集采」的选项，
系统提交时自动盖章，而且**写死不让人改**（三处都是 `<a-radio-group ... disabled>`）。

### 改完

```
[是否集采:    ○是 ○否]   ← 按规则决定灰不灰（新）
[集采目录层级: 集团集采  ]   ← 🆕 只读
[是否强管控:   是        ]   ← 🆕 只读
```

三个章递给审批流平台，华姐用它们当分支条件：

| 分支 | 条件 | 走法 |
|---|---|---|
| ① | 集团集采 + 强管控 | **连改都不让改**，必须按集采走 |
| ② | 强管控，但改成了"否" | 走新流程，**多审一级** |
| ③ | 弱管控，改成了"否" | 走原流程（🔴 `10r` P3，文档和口头对不上，必须问） |

**「是否集采」只能"是→否"，不能"否→是"**（需求 6.5 写死的）。

### 三个页面共同的三件事

**① 加两个只读字段**（集采目录层级、是否强管控）

**② 把写死的 `disabled` 拆掉**，换成按规则动态判断：

```
默认"否"                      → 灰的，不许改
默认"是" + 集团集采 + 强管控   → 灰的，不许改（分支①）
默认"是" + 其他               → 可以改成"否"
```

**③ 修那个死掉的弹框**——三处一模一样：

```js
await new Promise((resolve, reject) => {
  this.$confirm({
    title: `${res.data}数据是集采物料，集采和非集采不允许同时采购`,
    onOk() {},        // ← 空的，永远不 resolve
    onCancel() {}     // ← 空的，永远不 reject
  });
});
```

`await` 在等一个**永远不会完成的 Promise**。
单子里既有集采又有非集采物料时，**弹框出来，点确定点取消都没反应，提交流程永远卡死，只能刷新重来。**

### 层 2 · 🔴 判集采接口改返回结构 —— **这才是第二周真正的工作量**

`queryInRangeNum` 现在返回的是**一个字符串**：

| 返回 | 含义 |
|---|---|
| `"0"` | 一行都没命中 → 整单不是集采 |
| `"1"` | 每行都命中 → 整单是集采 |
| 一串中文物料名 | 部分命中 → 触发那个死掉的弹框 |

**它只回答"是 / 否 / 混着"，不回答"哪一行命中了哪条规矩、那条什么层级、强不强"。**

但需求 6.3「取最小层级」、6.4「有强取强」，要的是**每一行各自的判定结果**：

```
每一行物料 → 各自命中哪条规矩 → 各自什么层级、强不强
                    ↓
   表头  →  层级取最小、强管控有强取强
```

**所以这个接口必须改签名**（从"返回一个字符串"改成"返回每行明细"），
**三个前端页面接收返回值的那段代码（复制粘贴的三份）都要跟着改。**

> ⚠️ **整个两周里，"牵一发动全身"的只有这一处。**
> 第一周那 4 个影响点全部是在方法内部加条件，**接口签名不变，前端一行不动**。
