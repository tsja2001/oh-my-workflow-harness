# 第一章：先搞懂"集采"这件事本身

金隅集团下面有一大堆公司：冀东水泥、地产集团、物业集团、天津建材……几百家。

假如每家公司各买各的钢材，会发生什么？
唐山这家买 200 吨，石家庄那家买 300 吨，各自去找供应商、各自谈价格。
**几百家分开谈，谁都谈不出好价钱。**

所以集团说：**钢材这类东西，不许你们自己买了，统一由集团指定的单位去买。**
这就叫**集采**（集中采购）。

于是就需要一张清单，回答一个问题：

> **"到底哪些东西是必须走集采的？"**

这张清单，就是系统里的**《集采范围台账》**。
它就是这次需求要改造的东西 —— 整个需求，从头到尾，只围绕这一张清单。

# 第二章：今天这张清单是怎么用的（讲个故事）

**唐山冀东水泥的采购员小王，要买 200 吨螺纹钢。**

他在系统里填一张采购计划，选好物料"螺纹钢"，填好数量，点**提交**。

就在点下提交的那一瞬间，系统干了一件事：

> 拿"螺纹钢"去《集采范围台账》里翻一翻 —— 找到了吗？
> 找到了 → 在这张单子上盖一个章：**「是否集采 = 是」**
> 没找到 → 盖另一个章：**「是否集采 = 否」**

然后单子就往下走审批流程了。**故事结束。**

就这么简单。这个章是系统自动盖的，**小王自己改不了**（页面上那个字段是灰的，点不动）。

## 但这里有几个说不通的地方

**说不通之一：这张清单太粗了。**

台账里现在写的不是"螺纹钢"，而是"**黑色金属**"。
"黑色金属"底下有方钢、圆钢、扁钢、角钢、槽钢、螺纹钢、钢轨……十几种。
台账里写一条"黑色金属"，**这十几种全部一网打尽**。

可业务上未必需要这样。也许集团真正想管的只是螺纹钢，其他的各公司自己买就行。
**现在做不到 —— 要么整个"黑色金属"全管，要么全不管，没有中间档。**

（顺带一提：全公司现在的 7343 条台账数据，**没有一条是细的，全是"黑色金属"这种粗颗粒**。）

**说不通之二：这张清单不说话是谁定的。**

台账里的每一条规矩，到底是**集团总部**定的，还是**冀东水泥这个二级集团**定的，还是**唐山区域**自己定的？

清单上看不出来。所有规矩挤在一起，长得一模一样。

这就带来一个很实际的麻烦：领导想问"集团层面的集采做了多少钱？二级集团层面又是多少？"
—— **答不上来**，因为系统压根不知道每笔生意归哪一级管。

**说不通之三：这张清单没有"松紧"之分。**

有些东西是死规矩，谁也不许绕（比如水泥、钢材这种大宗物资）。
有些东西是软要求，特殊情况可以变通（比如某个小类目，集采渠道正好断货）。

**现在系统里这两者长得一模一样** —— 都是自动盖章、都是改不了。
结果就是：真遇到特殊情况，小王只能在系统外面想办法，或者干脆不走这个流程。
**规矩看起来很硬，实际上很虚。**

**说不通之四：删掉一条规矩，就像它从没存在过。**

某个类目今年不集采了，管理员把这条删掉 —— **数据直接从系统里消失**。
以后谁也查不到"这条规矩什么时候废的、为什么废的"。

**说不通之五（最要命的）：清单上明明写了"这条规矩管哪些公司"，但系统看都不看。**

台账里其实有一列叫"影响范围"，写着 `BU002/BU004/BU006` 这种东西
（意思是：这条规矩管冀东水泥、冀东集团、地产集团这三家）。

但是 —— **系统在盖章的时候，这一列一个字都不看。**

也就是说：哪怕一条规矩写明了"只管冀东水泥"，
物业集团的人来买同样的东西，照样被盖上"是集采"的章。
**这一列现在纯粹是个摆设。**

# 第三章：改完之后，同一个故事会变成什么样

还是小王，还是 200 吨螺纹钢，还是点提交。

系统这次不是翻一下就完事，而是要**连问四句话**：

### 第一句："这条规矩管不管你？"

系统看一眼台账上写的影响范围，再看一眼小王是哪家公司的人。

- 台账写"管全集团" → 管你，继续
- 台账写"只管冀东水泥" → 小王正好是冀东水泥的，管你，继续
- 台账写"只管地产集团" → **不管你，这条规矩跳过**

**这一句是全新的。今天完全没有。**（就是上一章"说不通之五"那个摆设）

### 第二句："这条规矩是谁定的？"

系统在单子上盖**第二个章**：「集采目录层级」，三选一 ——

| 层级 | 意思 |
|---|---|
| **集团集采** | 总部定的规矩，全集团几百家公司都得听 |
| **二级集团集采** | 冀东水泥这一级定的，只管自己下面的企业 |
| **区域/企业集采** | 唐山区域自己定的，只管本区域几家厂 |

**这一句也是全新的。** 而且它就是上一章"说不通之二"的解药 ——
以后领导问"集团级集采多少钱"，系统能答上来了。

### 第三句："这条规矩硬不硬？"

台账上每条规矩要标明：**强管控** 还是 **弱管控**。

这个标签决定了小王能不能"抗命"，以及抗命的代价：

> **今天**：章是灰的，小王根本改不了。规矩看着硬，实际很虚。
>
> **以后**：章能改了 —— 小王确实可以把"是集采"改成"不是集采"。
> **但改动是有代价的，而且代价按松紧程度不同：**
>
> - **强管控** → 想改？行，但这张单子要**往上多爬一级审批**。
>   企业发起的，得二级集团批；二级集团发起的，得总部批。
>   **改是能改，但领导会看见。**
> - **弱管控** → 想改？改就改了，还走原来的流程，不用惊动上面。

这是整个需求里**思路最巧的一处**：
不是把门锁死，而是**给你钥匙，但用钥匙会留下记录**。
从"堵"变成"疏 + 留痕"。

### 第四句："这条规矩还有效吗？"

以后删除一条规矩，**它不会消失**，而是变成两个新状态：

- **状态**：从"生效"变成"**失效**"
- **失效时间**：记下是哪天废的

失效的规矩不再参与盖章，但**永远能查到**。

需求里有一句话叫「**管后不管前**」，意思就是：
规矩变了，只影响**以后**的新单子；已经在走流程的老单子，**不受影响，不追溯**。

# 第四章：那个"管到末级"到底在说什么

这是需求里最绕的一段（就是 6.1 到 6.4 那四条）。其实说的是一件很朴素的事。

## 先看类目是怎么分层的

系统里的物料是按树分类的，最多四层：

```
金属材料            ← 第一层
└─ 黑色金属         ← 第二层   ← 台账现在只能填到这里
   └─ 型材          ← 第三层
      ├─ 方钢       ← 第四层
      ├─ 圆钢
      ├─ 扁钢
      └─ 螺纹钢
```

**台账现在卡在第二层**，只能填"黑色金属"。
改完之后可以一直填到最底下那一层 —— 直接点名"螺纹钢"。

（补一句：**不是每根树枝都长到第四层**。有的类目到第三层就没了。
所以"最底下那一层"是每根树枝各不相同的，不能一刀切说"就是第四层"。）

## 那四条规则说的是同一句话

> **同一个爹底下的孩子，要么整个一起管，要么一个个点名，不许混着来。**

举例子：

✅ **可以**：台账里只写"型材" → 方钢、圆钢、扁钢、螺纹钢**全部**受管。（整个一起管）

✅ **可以**：台账里写"螺纹钢"、"方钢"、"圆钢"、"扁钢" → 一个个点名，清清楚楚。

❌ **不行**：台账里已经写了"螺纹钢"，又想再加一条"型材"。

**为什么不行？** 因为一旦你点名了螺纹钢，就等于宣告"型材这一层我要一个个管"。
这时候再写个"型材"，就矛盾了 —— 那圆钢到底是被"型材"那条管着，还是压根没人管？
说不清。所以系统直接不让你这么填。

**这条规则在第一层、第二层、第三层都适用，一模一样，所以需求里重复写了四遍。**

至于 6.1 那条：如果你要精确管到某个**具体的物料编码**（比如"HRB400 螺纹钢 Φ12"），
那这一行的类目必须写到最底层。不能写个"黑色金属"再挂一个具体物料，那样口径是打架的。

# 第五章：和之前做的那些需求有什么衔接

**有，而且衔接得非常紧。三条。**

## 衔接一：这个需求能顺手补上报表卡了很久的一个洞 ⭐

**这是最值钱的一条，开会建议主动说。**

还记得之前做的**集采统计报表**和**驾驶舱**吗？领导想在报表上看：

> "集团集采做了多少钱？二级集团集采多少钱？区域集采多少钱？"

当时做不出来。为什么？
因为系统里虽然**有**这个字段（叫"采购业务分类"，取值就是：集团集采 / 二级集团集采 / 区域集采 / 分散采购），
但是**没有任何地方让人填它** —— 全公司 17062 张采购方案里，**只有 5 张有值。**

当时那期的结论原话是：「**技术上没有第二条路**」。就卡死在这儿了。

**现在这个需求，正好把这个洞堵上。**

因为第三章第二句 —— 系统要在每张单子上自动盖「集采目录层级」这个章。
而这个章的三个取值（集团集采 / 二级集团集采 / 区域集采），
**跟那个一直没人填的字段几乎一模一样。**

也就是说：**这次改完，那个报表缺的数据自动就有了，不用再单独做一期需求。**

（一个提醒：只有**以后的新单子**才会有值。历史的 17000 多张补不了 —— 没有可靠依据能倒推。）

## 衔接二：之前驾驶舱那期，踩的就是这张台账的坑

做**驾驶舱取值**那期的时候，查出来一个问题：

云采（商城）那边的订单同步过来时，系统会把物料的细分类目**砍成粗类目**，
然后拿去台账里查 —— **查得到才收，查不到整条丢掉。**

这个逻辑是建立在"台账里全是粗类目"这个前提上的。

**这次台账要管到末级（细类目）了，这个前提就不成立了。**
台账一旦填了细类目，这条同步链路会**一条都对不上，数据静默丢失** —— 而且不报错，最阴险。

**同一张表，同一个坑，第二次遇到了。** 开会时得让后端同事知道这件事。

## 衔接三：云采那边，这套玩法早就跑起来了

需求文档里有三个字很关键：「**同云采**」。这不是随口写的。

云采（商城）那边**已经有一张一模一样的清单**，而且：
- 早就有"是否强管控"这个标签了
- 早就能按强管控与否走两套不同的审批流程了

**所以这次的活，本质上是"把云采那边成熟的玩法，搬到招采这边来"。**
这是个大好消息 —— 有现成的东西可以照抄，风险和工作量都小很多。

# 第六章：所以这次到底"要干啥"，一句话

> **把《集采范围台账》从一张"名单"，升级成一套"分级管理制度"。**

具体就四件事：

| # | 干什么 | 好比 |
|---|---|---|
| 1 | 清单能填得更细（管到末级） | 从"管所有钢材"细化到"只管螺纹钢" |
| 2 | 每条规矩标明是谁定的（三个层级） | 每份文件盖上发文单位的公章 |
| 3 | 每条规矩标明硬不硬（强/弱管控） | 硬的能破例但要惊动领导，软的自己看着办 |
| 4 | 规矩废止要留痕（失效时间 + 状态） | 文件作废归档，不是撕掉扔了 |

加上一件配套的：**下单时真正按"影响范围"判断该不该管你**（今天这一列是摆设）。

# 第七章：开会前，你心里要有数的三件事

**① 「区域集采」现在做不了 —— 不是代码问题，是数据问题。**

系统里压根**没有"区域"这一层组织**。区域只是贴在每家公司身上的一个标签。
而且 **854 家公司里有 622 家（73%）这个标签是空的**，已经填的还有错别字
（"邢台"写成"刑台"）、有编码和名称对不上的。

**功能可以做，但做出来一条数据也管不住。** 这是开会第一优先级。

**② 「管到末级」的前提是有人先梳理出清单。**

代码放开限制不难。难的是"哪些类目要管到第几级"这份清单 ——
**这只能业务出，开发出不了**。需求文档自己也在这儿打了四个问号。

清单不来，功能做完了也没数据可导。

**③ 加的这两个字段是必填的，历史 7343 条数据得先想好填什么。**

我的建议（会上顺口确认一下就行）：
历史数据统一填「集团集采」+「弱管控」+「生效」，
这样上线当天系统行为跟现在完全一样，**不会突然冒出一堆审批**，之后业务再慢慢调。
