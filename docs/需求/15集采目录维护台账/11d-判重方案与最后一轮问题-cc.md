# 2. 三个方案

## 2.0 先统一一个概念：「管辖域」

任何一条台账规矩，本质上都是在说 **"哪些东西 × 归哪些板块管"**：

```
管辖域 = 【节点】 × 【板块集合】

节点     = 有物料码就是物料码，没有就是类目码（类目码可以是任意层级）
板块集合 = 集团集采      → 全部板块（ALL）
           二级集团集采  → 影响范围里填的板块码，拆成集合 {BU002, BU003}
           区域·企业集采 → 影响范围里填的区域码，换算成它所属的板块 {BU002}
```

> 🟢 **区域→板块的换算已经验通了**：`ubm_organization_manage.belong_plate_code → belong_bu_code`，
> uat 实测 36 个区域**全部 1:1 挂唯一板块**，0 个跨板块（证据见 `12f` §8）。

**判重 = 两条规矩的管辖域重不重叠。**

## 2.1 方案 A（推荐）：管辖域重叠 + 集团单向祖先

```
两条规矩算冲突，当且仅当：
   ① 板块集合有交集
   且
   ② 节点满足下面任一条：
        a. 节点完全相等
        b. 已存在的那条是【集团集采】，且新配的节点是它的后代
           （集团配了 1701，就不许再配 170101 或 1701 下的任何物料）

明确不算冲突：
   - 已存在的是集团集采，新配的是它的【祖先】  ← R5，必须放行
   - 板块集合无交集                            ← R2/R4，跨板块随便配
```

**用产品自己举的 4 个例子验一遍：**

| 产品的例子 | 方案 A 的判定 | 对不对 |
|---|---|---|
| 集团管到 `1701`（范围 all），二级集团想在下面配 `170101` | ①ALL∩{BU002}≠∅ ②b 后代 → **拦** | ✅ 他要的就是拦 |
| 集团配 `170101`，水泥集团配 `1701`（上级） | ②a 不等、②b 是**祖先**不是后代 → **放行** | ✅ 他说"应该是能的" |
| 唐山区域（属水泥）配了物料 X，水泥集团还想配 X | ①{BU002}∩{BU002}≠∅ ②a 相等 → **拦** | ✅ 「同一板块下不能再重复」 |
| 唐山区域（属水泥）配了 X，**地产集团**配 X | ①{BU002}∩{BU006}=∅ → **放行** | ✅ 「这个是可以的」 |

**四个全对。这套规则是能落地的，不是拍脑袋。**

- 🟢 优点：五条规则全覆盖，产品的每个例子都对；判重和匹配用同一套心智模型，不容易写歪
- 🟠 成本：要能判"类目 A 是不是类目 B 的祖先"（查主数据类目树）+ 区域→板块换算
- ⏱ 估：**1.5 天**（含单测）

## 2.2 方案 B（省工版，谈不拢就上这个）

**去掉 ②b 那条祖先校验，只保留「节点完全相等 + 板块集合有交集」。**

- 🟢 优点：一次查询 + 一个集合交集就完事，**不需要类目树**，估 **0.5 天**
- 🟠 代价：R1 做不到——业务可以配出"集团管了 1701，二级集团又配了 170101"这种数据
- 🟢 **但系统行为仍然是确定的、不会出错**：匹配时是「物料 → 四级 → 三级 → 二级，从下往上找、找到即停」，
  所以 `170101` 那条会先命中，`1701` 那条走不到。**结果是"更细的规矩赢"，业务上说得通。**
- 📌 **B 是 A 的子集，代码结构一模一样**，以后补上 ②b 就升级成 A，不用重写

## 2.3 方案 C（不推荐）：任何血缘关系 + 板块交集都拦

- ❌ **直接违反 R5**（集团配了 170101，二级集团配 1701 会被拦），产品明确说这个要能配
- 列在这里只是为了让产品知道"最严"是什么样，别让他误以为 A 已经够严了

## 2.35 🟢 两个实测发现，让方案 A 便宜了一大截

**发现一：祖先判定不用查类目树，用字符串前缀就行。**

`mdm_material_class` 实测（uat，2026-09-08）：类目编码是 **2/4/6/8 位的严格前缀式四级树**
（27 个一级 / 230 二级 / 626 三级 / 562 四级；除 27 个顶级节点 `parent='0'` 外，**1418/1418 条父码都是子码的前缀**）。

```
17      一级
1701    二级      ← 1701 LIKE '17%'
170101  三级      ← 170101 LIKE '1701%'
17010101 四级
```

⇒ 「A 是不是 B 的祖先」= `B.category_code LIKE CONCAT(A.category_code,'%') AND LENGTH(B)>LENGTH(A)`
⇒ **方案 A 里最贵的那一段（递归查树）消失了。估算从 1.5 天降到 0.8 天，和方案 B 差不多。**
⇒ **所以直接上 A，不用退而求其次。**

**发现二：存量数据零冲突，新规则不会打到老数据。**

跑了 `sql/04-开工前体检.sql`（uat）：

| 检查 | 结果 |
|---|---|
| 同一 (类目, 物料) 多行 | **0 组** |
| 类目之间的祖先/后代关系 | **0 对** |
| 物料行落在某条只管类目的行下面 | **0 对** |

⇒ 期初那 7343 行**互相之间干干净净**，判重规则怎么定都不会把存量数据判成非法。
⇒ **11d §3 边界 7「存量冲突谁来发现」的答案：现在没有存量冲突，体检脚本已写好（`sql/04`），上线前再跑一次即可。**
⇒ 但这也说明：**7343 行全是 4 位类目 + 7340 个物料码，彼此不重叠**，
   所以 §3 边界 1（期初全填集团集采会锁死下级）**仍然成立**，那条还是要问。

# 3. ⚠️ 7 个他没想到的边界（这才是这次要谈的重点）

## 🔴 边界 1：期初一填「集团集采」，三级层级功能就等于没上线

**这是最要紧的一条，先问。**

- 期初：7343 行**全部**填「集团集采」（`12f` §2 ② 已确认）
- 这 7343 行覆盖了 **7 个类目、7340 个物料**（uat 实查）
- 按 **R1**：集团集采占位 → 这些类目及其下级，**任何层级都不许再配**
- ⇒ **业务上线后想配二级集团/区域的规矩，只能配这 7 个类目之外的东西**
- ⇒ 而这 7 个类目正是现在唯一在管的六大类

> **翻成一句话**：辛辛苦苦做的三级层级，上线当天对现有业务**一条都用不上**。

**三个出路，要他选一个：**

| 出路 | 做法 | 代价 |
|---|---|---|
| **① 期初不全填集团** | 产品在他那份 Excel 里，按类目分档填层级 | 他要多花时间填；**但他本来就要自己填这 7000 行，成本不高** |
| **② R1 只拦"同层级以下"，不拦跨层级细化** | 集团配了 `1701`，二级集团仍可配 `170101`（更细的补充） | 规则变松，和他 13:40 举的反例矛盾——**得他自己推翻自己** |
| **③ 认了，这期就是全集团统管** | 三级层级先做上、不用；等业务提出来再逐类目下放 | 最省事，但要跟业务讲清楚"上线不等于能用" |

> 💡 **我的建议是 ①**，理由：他反正要自己填那 7000 行，多填一列不多花多少工夫，而且这是**唯一能让新功能上线即可用**的路。

## 边界 2：集团自己能不能再配一条更细的？

集团配了 `1701`（整个三级类目），后来发现 `170101` 要特殊管——**集团自己能不能再配一条 `170101`**？

- 按 R1 字面意思：不能（"此类目及下级不允许再维护其他层级"——但这是**同一层级**，不是"其他层级"）
- 按方案 A 的 ②b：会被拦
- 👉 **要问**。默认按**允许**（同层级细化是合理需求），但要产品点头

## 边界 3：同层级之间的祖先关系

水泥集团（二级集团）配了 `1701`，唐山区域（也属水泥）配 `170101` —— 允不允许？

- 方案 A 判定：**放行**（②b 只对集团集采生效）
- 匹配结果：物料 `1701010001` → 从下往上找 → 命中 `170101` 唐山区域那条 → 停
- 👉 业务上说得通（区域的规矩比板块的细，细的赢），**但产品没说过**，要确认

## 边界 4：影响范围填多个板块，算不算重复？

- 规矩 A：二级集团，影响范围 = `BU002`
- 规矩 B：二级集团，影响范围 = `BU002/BU003`
- 四字段判重：影响范围字符串不同 → **放行**
- 按 R4「同一板块内不能重复」：`BU002` 出现了两次 → **应该拦**

> 👉 **这条决定实现方式**：判重必须按**"展开后的板块集合"**比交集，
> **不能按影响范围那个字符串比**。我按"拦"来做（符合 R4），但要他确认。

## 边界 5：失效的行占不占判重位置？

- 默认（`13` D1）：**不占**，只跟「状态=生效」的比
- 理由：不然业务作废一条之后，想重新录一条一样的都录不进来
- 👉 顺口确认一下就行

## 边界 6：73% 的组织没维护区域，区域层级的规矩对它们无效

- uat 实查：854 个组织**只有 232 个（27%）填了区域**；13 个板块里 **9 个一个区域都没有**
- ⇒ 配了区域层级的规矩，那些没维护区域的企业提单时**匹配不上**，会静默落到上一级
- 👉 要么先补区域主数据，要么这一档先关着（= `13` D9）

## 边界 7：判重只在导入时拦，存量冲突谁来发现？

- 3.2 的互斥校验**只在导入时生效**
- 期初那 7343 行、以及规则改之前录进去的行，**不会被回头校验**
- 👉 建议：**我做一个"冲突体检"SQL**，上线前跑一遍，把存量里已经冲突的行列出来给产品处理
- 成本：半天，**建议做**——不然上线后遇到冲突数据，代码得能兜底，兜不住就是线上事故
