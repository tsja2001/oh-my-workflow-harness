## 0. 读之前先建立一个心智模型

这套系统里发生的所有事，都在回答一个问题：

> **公司要花钱买东西。怎么保证「买得便宜、买得干净、买得有记录」？**

- **买得便宜** → 让尽可能多的供应商来竞争 → 招投标、比价、商城比价
- **买得干净** → 全程留痕、专家评分、公示、防止串标 → 评标匿名、电子签章、天眼查查股东、围串标 AI
- **买得有记录** → 每一笔都进系统、能统计 → 台账、报表、集采率

**这次 37 个需求，没有一个跳出这三条。** 你看每一项时可以先问自己："这是在解决便宜、干净、还是记录？"

## 1. 两个平台的分工（先分清这个，后面不会乱）

| | **招采平台**（招标采购） | **云采商城** |
|---|---|---|
| 像什么 | 像政府招标网站 | **像京东企业购** |
| 买什么 | 金额大、非标、需要谈的（工程、设备、大宗物资） | 金额小、标准品、随时要的（办公用品、五金、劳保） |
| 怎么买 | 发公告 → 供应商报名投标 → 专家评标 → 定标 → 公示 → 签合同 | 搜索 → 加购物车 → 下单 → 发货签收 |
| 一次交易耗时 | 几周到几个月 | 几分钟 |
| 网关路径 **【实测】** | `/e/business/...` | `/c/business/...` |
| 这次的需求 | **25 项**（P1–P6） | **11 项**（M1–M4） |

> 💡 **Node 类比**：招采平台像一个**流程引擎驱动的审批系统**（状态机 + 工作流），云采商城像一个**标准电商站**（商品/搜索/购物车/订单）。
> 这是两种完全不同的软件形态，**这也是为什么这份计划看起来"眼花缭乱"——它其实是两份计划订在了一起。**

## 2. 招采平台主流程：一笔采购从"想买"到"付钱"

下面这条线是**这个系统的脊椎**。每一步我标了：谁在操作 → 落在哪个后端模块 **【实测】** → 这次要改哪几项。

```
① 需求提报    ② 采购计划    ③ 采办方案(含标段/评分模板)   ④ 发公告
     │              │                    │                      │
     ▼              ▼                    ▼                      ▼
⑤ 供应商报名  ⑥ 交保证金/标书费  ⑦ 投标(上传投标文件)   ⑧ 开标
     │              │                    │                      │
     ▼              ▼                    ▼                      ▼
⑨ 评标(专家打分)  ⑩ 定标方案审批   ⑪ 中标公示        ⑫ 中标通知书
     │              │                    │                      │
     ▼              ▼                    ▼                      ▼
⑬ 签合同      ⑭ 下单/履约      ⑮ 退保证金        ⑯ 付款/开票
                                          │
                                          ▼
                              ⑰ 供应商评价 / 年审 / 黑名单
```

### 逐步拆解

#### ① 需求提报 → ② 采购计划
**谁**：用车间/部门的人说"我要买 200 吨钢材"。
**落在哪** **【实测】**：`scm-source-all/scm-source-require`（swagger 标签"需求计划管理"）、`scm-source-plan`（"采购计划管理"）。
**这次改**：无直接项。但 **M3-03（购物车采购计划字段）** 跟它有关——商城下单也要挂上"这是哪个采购计划的钱"。

#### ③ 采办方案（这是招采平台的**核心单据**）
**谁**：采购员编制方案——买什么、多少钱、用哪种寻源方式、分几个标段、怎么评分。
**落在哪** **【实测】**：`scm-source-scheme`（swagger 标签："采办方案管理""采办方案**标段**管理""采办方案**评分模版**管理"）。
**"标段"是什么**：一个大项目切成几块分别招标。比如"全厂电缆采购"切成"高压电缆标段/低压电缆标段"，可以分别定给不同供应商。
**这次改**：
- **P1-01 分阶段评标、分标段终止**（63 人天，最大的招采项）——让每个标段能**独立**启停/终止/归档，不再一荣俱荣一损俱损
- **P1-02 审批流程升级**（25）——方案要走审批，这次加"草稿保存""退回到原驳回节点"等

**寻源方式有 6 种** **【实测】**（后端各有独立模块）：

| 方式 | 通俗解释 | 后端模块 **【实测】** |
|---|---|---|
| 招标 | 最正规：公开发公告，谁都能来投 | 主流程 |
| 询价 | 发给几家问价，谁便宜要谁 | `scm-source-quote`（"寻源-报价管理""比价单管理"） |
| 竞争性谈判 | 边谈边压价，可以多轮 | `scm-source-negotiate` |
| 竞争性磋商 | 谈判 + 允许改方案 | `scm-source-consult` |
| 单一来源 | 只有一家能供（独家专利/原厂配件），不比价但要说明理由 | `scm-source-single` |
| 竞价 | 类似拍卖，供应商在线往下压价 | `scm-source-bid` |

> ⚠️ **一个容易搞混的点**：后端模块 `scm-source-bid` 里的 "bid" **不是"投标"，是"竞价"** **【实测】**（swagger 标签是"竞价管理-操作"）。
> 真正的**投标/开标/评标**在另一个仓 `scm-professor-all`。这个命名坑记一下，能省你几小时。

#### ④ 发公告
**落在哪** **【实测】**：`scm-source-notice`（"寻源发布公告接口"）。
**这次改**：**P3-01 电子签章**（38）——公示文件发布时可以选择自动盖公章，**默认盖**。
（现在的做法**【推测】**是人工把盖了章的文件扫描成图片上传，所以原文才写"防止盖章混乱或图片截图盖章"。）

#### ⑤ 供应商报名 → ⑥ 交保证金/标书费
**落在哪** **【实测】**：`scm-source-enroll`（"寻源-报名响应"）、`scm-source-cost`（"寻源-费用信息"）。
**保证金是什么**：供应商交一笔押金证明"我是认真来投标的"。没中标要**原路退回**，中标了转成履约保证金或退回。
**这次改**：**P1-06 保证金线上自动退费**（35，高优先级）——现在**【推测】**很可能是财务手工核对再退，这次要做成
"系统自动匹配中标结果 → 自动触发退费 → 校验退款账户和原缴费账户是同一个 → 留台账"。

> **【实测】这条路已经修了一半**：代码里已经有 `scm-source-ssc` 模块（SSC = 财务共享中心），
> 其中 `SourceSscSendServiceImplForDepositRefund` 就是"保证金退款推送财务共享"，
> 还有一个状态枚举 `SourceDepositPushStateEnum`：线下处理 / 待推送 / 推送中 / 已推送共享 / 推送失败。
> 也就是说**"推给财务"这一步已经通了，缺的是"自动判断该退了"这一步**。

#### ⑦ 投标 → ⑧ 开标 → ⑨ 评标（**整个流程最敏感的一段**）
**谁**：供应商上传投标文件（技术标 + 商务标）；到点开标；抽出来的专家给每一家打分。
**落在哪** **【实测】**：`scm-professor-all` 仓 ——
`scm-professor-extract`（专家抽取）、`scm-professor-check-tender`（"评标列表"）、`scm-evaluate-bid`（评标）、
`scm-professor-template`（"评审模版"）、`scm-professor-main`（专家库维护）。
前端在 `02zhaocai-front/scm-vue-all-bidevaluation` **【实测】**，页面如 `/bidEvaluationt/index.html#/bidEvaluationt/taskList`。

**技术标 vs 商务标**：技术标看"你的东西行不行"（方案、资质、业绩），商务标看"你的价格和条款"。
**这次要做的"分阶段评标"（P1-01）就是把这两段拆开走**：先评技术标，技术不过关的直接淘汰，不用再看报价。
**【推测】** 这么做的业务动因是**防止评委被价格影响技术判断**——这是招投标行业的通行做法。

**这次改（这一段最密集）**：
- **P1-01 分阶段评标**（63）——技术评标/商务评标分阶段；两个阶段都能"废标"
- **P1-04 评标功能优化**（51）——专家能看到投标文件；**评委匿名化**（只显示"专家 1 号"）；评标报告自动生成；对接电子签章让评委在线签字
- **P1-03 扩充特殊报价模式**（51）——支持负数报价、费率报价、折扣率报价；多品类差异化权重；AI 自动算商务分回填
- **P3-04 专家库优化**（13）——给专家打标签（比如"电气专业""华北地区"），方便抽取
- **P5-01 围串标 AI**（42）——比对几家投标单位的法人/授权人是不是同一个人、股权有没有关联、投标文件的 WPS 编辑人是不是同一个、上传电脑的 MAC 地址/CPU 序列号有没有重合、文件内容雷不雷同
- **P5-06 辅助评标 AI**（50）、**P5-03 异常报价 AI**（30）、**P5-02 资质核对 AI**（30）

> 💡 **"围串标"是什么**：几家供应商私下商量好，轮流让谁中标、故意报高价。这是采购领域最严重的违规。
> 上面那几个检测手段（MAC 地址重合、文件编辑人相同）都是行业里很成熟的取证套路——**说明这一项业务规则其实是清晰的**，
> 难的是技术实现（要能读出 Office 文件的元数据、要在上传时采集客户端指纹）。

#### ⑩ 定标方案审批 → ⑪ 中标公示
**落在哪** **【实测】**：`scm-source-deal`（"寻源-定标方案""成交方案""定标方案推送 OA 系统""定标方案推送 SRM 系统"）。
**公示**：把"谁中标、多少钱"挂出来晾几天，没人质疑就算定了。**公示时间是这套系统里最重要的时间戳之一**——
你之前做的 06 取值需求里，"集采金额"就是按公示时间算的。
**质疑澄清**：`scm-source-defence`（"寻源-质疑澄清"）**【实测】**——供应商觉得不公可以提异议。

**这次改**：
- **P1-05 定标公示功能重构**（34）——公示几家可配置（1–3 家 / 单一来源 1 家 / 不限）；按评分排名自动填充；AI 风险提示
- **P3-05 数据导出**（16）——招标/定标审批流程存成 PDF 归档，能按招标编号批量下载

#### ⑫–⑯ 中标通知书 → 合同 → 订单/履约 → 退保证金 → 付款
**落在哪** **【实测】**：合同在 `scm-contract-all`，订单在 `scm-order-all`，对外系统（ERP/财务）在 `scm-ifs-all`。
**这次改**：主要是保证金退费（P1-06）和商城侧的对账开票（M3-01）。

#### ⑰ 供应商评价 / 年审 / 黑名单（横切整条线）
见下一节。

## 3. 供应商生命周期（P2 这条主线的全貌）

这是一条**和主流程平行的线**。供应商不是想来就来的，要先"入网"。

```
供应商注册 → ② 入网申请 → ③ 资质审核（入围标准）→ ④ 入库成为合格供应商
                                                        │
                    ┌───────────────────────────────────┤
                    ▼                                    ▼
              ⑤ 参与招标/供货                      ⑥ 年度审核（年审）
                    │                                    │
                    ▼                                    ▼
              ⑦ 履约评价打分 ──────────────────→ ⑧ 分级评定（SRM 评级）
                    │
                    ▼
              ⑨ 不良行为记录 → ⑩ 冻结 / 拉黑
```

**落在哪** **【实测】**：`scm-srm-all` 仓（SRM = Supplier Relationship Management，供应商关系管理）；
页面在 `02zhaocai-front/scm-vue-all-emp`（供应商列表/冻结/拉黑/整改反馈）和 `scm-vue-all-ubm`（供应商信息管理）。

**这次改（6 项，195 人天）**：

| 项 | 干什么 | 通俗解释 |
|---|---|---|
| **P2-01** 多子账号权限体系（32） | 供应商能开子账号并配权限；打标签做差异化管控 | 现在**【推测】**一家供应商只有一个账号，业务员和财务共用；这次拆成多账号 |
| **P2-02** 入网功能优化（35） | **一次入网服务多个二级集团** | 现在**【推测】**同一家供应商要在水泥集团、地产集团各入一次网，这次改成入一次全集团通用 |
| **P2-03** 入围标准规则模板（40，高） | 集团统一底线（纳税、社保、资质、风险）+ **OCR 自动审纳税社保**；不符合自动拦截 | 把"人工看材料"改成"系统自动卡"。**这一项业务价值极高，因为它把合规风险前置了** |
| **P2-04** 评价及年审（38） | 自定义评价维度（采购环节/合同执行/质保期三大类）+ 权重 + 自动汇总评级 | 给供应商打分并排名 |
| **P2-05** 黑名单强化（15，高） | 黑名单供应商不能改基础信息 | 防止拉黑后改名字改法人洗白 |
| **P2-06** 天眼查对接（35） | 自动拉工商数据：失信被执行人、经营状态、股东、实际控制人 | **【实测】代码里已经有天眼查的服务和接口**（`scm-srm-all` 下的 `CompanyTianyanchaService` / `TianyanchaController`），这次是扩大使用场景 |

> 💡 **二级集团**：这家公司是三层结构——金隅集团（总部）→ 二级集团（水泥、地产、新材、投资物业、冀东发展、天津建材……）→ 成员企业。
> 系统里叫 `buCode`/`buName`（BU = Business Unit）。**"分二级集团管理"这个词在这次计划里反复出现**（P2-02、P2-03、M1-01），
> 本质都是同一个诉求：**集团定统一底线，二级集团在底线之上自己加规矩。**
> 详细背景见 `docs/需求/06取值需求/复盘与学习/04全套业务逻辑复盘-cc.md` 第一章。

## 4. 云采商城主流程（M 这条线）

```
① 商品目录分类(运营定)  ② 供应商上架商品  ③ 价格变动审批
        │                      │                 │
        ▼                      ▼                 ▼
   ④ 采购员搜索  →  ⑤ 比价  →  ⑥ 加购物车  →  ⑦ 下单(走审批)
                                                  │
                                                  ▼
                          ⑧ 推 ERP  →  ⑨ 发货  →  ⑩ 签收  →  ⑪ 对账开票  →  ⑫ 付款
```

**落在哪** **【实测】**：商品在 `scm-product-all`（服务 `scm-product-web`），订单在 `scm-order-all`（`scm-order-web`），
外部电商对接在 `scm-ifs-all/scm-ifs-external-*`（目录里能看到 `-jd`、`-zkh`、`-ofs`、`-xfs` 等，**【推测】**分别是京东、震坤行等外部商城）。
前端在 `scm-vue-all-mall`、`scm-vue-all-mall-portal`、`scm-vue-all-productmgt`、`scm-vue-all-order-purchase` **【实测】**。

**这次改（11 项，417 人天，占全盘 31%）**：

| 项 | 干什么 | 通俗解释 / 难点 |
|---|---|---|
| **M1-01** 商品目录分类（36，高） | 分二级集团管理商品目录，按分类限定可上架品类 | 相当于"每个集团有自己的京东频道" |
| **M1-02** 商品上架需求流程（43） | 用户提报"我要的东西商城没有" → 系统汇总 → 归集寻源 | **把商城的缺货变成招采平台的采购需求**，两个平台在这里接上了 |
| **M1-03** 价格变动审批与预警（35） | 简化调价审批；价格异常预警；触发条件前台可配 | 防止供应商偷偷涨价 |
| **M1-04** SPU 聚合模型（**90，全场最大**） | 同一个商品的不同规格聚合成一条 | **难点不在代码，在数据**——原文自己写了"需业务部门初始化数据梳理" |
| **M1-05** 同品类低价识别（19） | 标出"全网最低"，可直接下单 | |
| **M1-06** 一键批量比价（20） | 同款不同规格/不同商家放一起比 | |
| **M2-01** 搜索权重算法（32，高） | 精准匹配优先、关键词分层；屏蔽无关商品 | **搜索排序是电商的看家本领**，调不好业务天天骂 |
| **M3-01** 发票对账单导出（22） | 批量下载发票、导出对账单、标未签收/已结算 | 财务的活，纯导出 |
| **M3-02** 订单界面增强（34） | ERP 订单号检索、发货筛选、打印、深化 ERP 集成 | 涉及 ERP 对接 |
| **M3-03** 购物车采购计划字段（27） | 同物料不同采购计划**不合并**，统一下单 | 看着小，其实是购物车合并逻辑的核心改动 |
| **M4-01** 商城报表重构（59） | 帆软重做，新增 10 个以内报表 | 见下 |

> 💡 **SPU / SKU 是什么**（电商黑话）：
> **SPU** = 一款商品（"某品牌 A4 复印纸"）；**SKU** = 具体到能下单的那一条（"某品牌 A4 复印纸 70g 500张/包"）。
> 现在**【推测】**商城里每个规格都是一条独立商品，搜"A4纸"出来 30 条几乎一样的；做了 SPU 之后搜出来 1 条，点进去选规格。
> **改造代价大，因为要把已有的几万条商品重新归堆——这是人工活，不是代码活。**

## 5. 报表和 AI 这两块，为什么单独说

### 报表（P4-01 + M4-01，129 人天）
**要干的事**：现有报表全部推倒，改用**帆软**（一个国产 BI 报表工具）重做，加多层穿透下钻。
**【实测】** 全代码库搜"帆软"/"finereport" **零命中** —— 说明**这套工具现在根本没进系统**，是全新引入。
**【推测】** 帆软是"拖拽配置式"的报表工具，开发方式跟写 Java 完全不同，通常由帆软实施方或专门的报表工程师做。
**这跟你现有的技能栈没有交集**，是 `10d` 里必须问清楚归属的一块。

> 你之前做过的 `03采集管理业业务统计报表` 和 `06取值需求`，报表是**手写 Java + Elasticsearch 查询**做出来的
> （后端 `SourceQueryBuilderImpl_<Flag>`，前端 `#/reportForms/<flag>`）**【实测】**。
> "全体系报表重构"意味着**这些可能都要推倒重来**——这一点你要格外注意，因为那是你熟悉的地盘。

### AI 智能体（P5，7 项，295 人天）
7 项分别是：围串标审核、资质核对、异常报价识别、供应商异常预警、入网智能审核、辅助评标、智能问数。
**共同点**：3 项原文写明"基于**集团统一 AI 底座**"，实施阶段标的是"阶段二(**AI 预研**)"。

**说人话**：集团要建一个统一的 AI 平台，各业务系统在上面搭"智能体"。
**这块的不确定性不在于 AI 难不难，而在于**：
1. 底座什么时候能用？现在存在吗？
2. 你负责哪一段——是把业务数据喂过去，还是自己写提示词和规则，还是只负责把结果回填到页面？
3. "智能问数"（P5-07，85 人天）是让人用自然语言查采购数据（"去年水泥集团买了多少钢材？"）——
   **【推测】** 这类东西的难点是把自然语言翻译成正确的查询，而这套系统的数据口径极其复杂（MySQL + ES 混合、五路数据源、去重规则），
   **这 85 人天我个人判断是全表最乐观的估时。**

## 7. 业务黑话小词典（碰到就查这里）

| 词 | 说人话 |
|---|---|
| **寻源** | "找供应商买东西"这整件事的统称。招标/询价/竞谈/竞磋/单一来源/竞价都是寻源方式 |
| **采办方案** | 采购的正式计划书：买什么、预算多少、怎么招、怎么评分。**这是招采平台的核心单据** |
| **标段** | 一个大项目切成几块分别招标，可以分别定给不同供应商 |
| **废标** | 判定某家供应商的投标无效（材料不全、报价超限、串标） |
| **流标** | 整个标没招成（来投的家数不够、都不合格），要重招 |
| **技术标 / 商务标** | 技术标看方案资质业绩；商务标看价格和条款 |
| **围标 / 串标** | 几家供应商私下串通，轮流让谁中标、故意抬价。采购领域最严重的违规 |
| **入围 / 入网** | 入网 = 供应商注册进平台；入围 = 通过资质审核，有资格参与某类业务 |
| **年审** | 每年重新审一遍供应商资质还有没有效 |
| **SRM** | Supplier Relationship Management，供应商关系管理（本系统里 `scm-srm-all` 那个仓）**【实测】** |
| **SSC / 财务共享** | Shared Service Center，集团统一的财务处理中心。保证金收退、付款都推给它 **【实测】** |
| **保证金 / 标书费** | 保证金 = 投标押金（要退）；标书费 = 买招标文件的钱（一般不退） |
| **限价** | 招标方设的价格上限，超过直接废标（这次 P1-03 要加"询比价最高限价单价含税"限制） |
| **公示** | 把中标结果挂出来晾几天接受质疑。**公示时间是统计口径里最关键的时间戳** |
| **质疑澄清** | 供应商对结果有异议提出来，采购方答复 |
| **二级集团 / 板块 / BU** | 三个词一个意思：金隅集团下面的水泥集团、地产集团这一层 **【实测】** |
| **SPU / SKU** | SPU = 一款商品；SKU = 具体到能下单的那一条规格 |
| **驾驶舱** | 领导看的大屏看板 |
| **帆软** | 一个国产 BI 报表工具，拖拽式配报表 |
| **AI 底座** | 集团统一的 AI 平台，各系统在上面搭"智能体" |
| **电子签章** | 在电子文件上盖具备法律效力的电子公章 |
| **天眼查** | 查企业工商信息的商业数据服务（股东、失信记录、经营状态） |
