## 1.3 这个交付模式有正式名字

| 名字 | 是什么 | 谁在用 |
|---|---|---|
| **Branch-per-Customer**（按客户分叉） | 一套产品代码，每来一个客户拉一个分支，在分支上改。分支之间不再回流 | 中国绝大多数 To-B 项目型软件 |
| ↔ **Single-instance Multi-tenant**（单实例多租户） | 所有客户跑同一套代码，靠数据隔离区分 | Salesforce、Workday、Ariba |
| **Vertical Solution / Industry Template**（行业方案） | 厂商把一个行业的共性做成半成品，每个客户改 30–50% | 石化盈科、用友行业线、美云智数 |

**Branch-per-Customer 的代价，学术上叫 `divergence`（分叉），工程上的症状是三个：**

1. **产品的改进流不回你这**。厂商在别的客户身上做的新功能，你这条分支永远拿不到，除非再花一次钱做"升级"。
2. **你的定制流不回产品**。你出钱改的东西，厂商拿去卖给下一家，你也拿不到钱。
3. **原厂一撤，分支就变成孤儿**。谁都不认识这套代码了。

> **第 3 条你们已经在承受了**：`scm-share-aim-spring` 在 Nexus 上的 jar 停在 **2023-04-18**，
> 字节码里还含 fastjson 1.x 的 `TypeUtils.getClassFromMapping`（`ai-docs/代码库地图.md` §4 记的真实事故）。
> **底座组件三年没人动，不是因为它完美，是因为原厂已经不在了。**

## 1.4 反直觉：你们对"复制一套出来"这件事，其实是专家

会上美云列的三种方案，是这么说的：

- 方案一：把冀东那套完整复制，独立部署一套 → 这就是 **Branch-per-Customer**
- 方案二：同底座复制一套功能出来 → 这是 **Branch-per-Customer 的省钱版**
- 方案三：在冀东那套上加一层集团组织 → 这是**唯一一个朝"单实例多租户"走的方案，所以美云说它"代价最大"**

**美云那句"我们并不是传统的多租户平台"，翻译过来就是：我们也是 Branch-per-Customer。**

而你们的招采平台，当年就是这么被交付的。所以：

> **你们这次面对的不是一个陌生的技术选择，是同一个坑的第二次。**
> 第一次的账单现在还在付（底座没人维护、`groupId` 改不掉、SNAPSHOT 跨团队漂移）。

# 二 · 为什么是"数科公司"在负责

## 2.1 大集团的 IT 只有三种组织形态

这是企业架构里的标准分类（Gartner、MIT CISR 都用这套词）：

| 形态 | 英文 | 谁决定买什么 | 典型症状 |
|---|---|---|---|
| **集中式** | Centralized IT | 总部一个部门说了算 | 反应慢，但口径统一 |
| **分散式** | Decentralized IT | 各子公司自己决定 | 快，但一个集团里十套系统 |
| **联邦式** ← **金隅在这一档** | **Federated IT** | **总部管平台和标准，BU 管自己的业务系统** | **"总部平台永远慢一拍，BU 早就自己买好了"** |

**联邦式的经典失败模式有个说法叫 `pave the cowpaths`（沿着牛踩出来的路铺路）**：
等总部想统一的时候，各家已经踩出了各自的路，这时候要么承认既成事实（贵），要么强推（更贵，还得罪人）。

**0827 那场会，从头到尾就是这个失败模式的现场。**

## 2.2 数科公司在里面是什么角色

国际上这类公司叫 **Captive IT Subsidiary**（自有 IT 子公司），和 **Shared Service Center**（共享服务中心）是同一类东西。
国内叫「XX 数科 / XX 信息 / XX 科技」。同类：石化盈科（中石化）、宝信软件（宝武，已上市）、国电南瑞（国网，已上市）、中远海科。

**它的真实商业模型是这样的（这一段是理解你所有日常的钥匙）：**

```
集团 IT 预算
    │  立项、下预算
    ▼
【数科公司】  ← 你在这
    │  核心能力其实是三样：需求翻译、供应商管理、验收
    │  不是"写代码"
    ├──► 总包商（石化盈科这类，卖行业方案）
    │        └──► 分包/人力外包（按人天）
    └──► 少量自有开发  ← 你在这的这一层
```

**数科不是技术部门，是"甲方的技术翻译层 + 采购层"。** 它的收入来源在会计上叫 **Chargeback**（内部结算）——
集团把预算给它，它交付系统，收管理费和人天费。所以：

> **邵总在会上反复算"工作量""要多报人工"，不是抠门，是因为数科的收入单位就是人天。**
> 录音 50 里那句"你用 ABI 的话，对不起，你得多报人工"——这不是技术态度，这是**商业模式在说话**。

## 2.3 那数科为什么还要养自有开发（你的岗位为什么存在）

外包干不了四类活，这四类就是你的岗位定义：

| 干不了的活 | 为什么 |
|---|---|
| **改已经交付完、原厂撤了的老系统** | 没人认识这套代码，重新招标不划算 |
| **救火** | 线上炸了，走采购流程找厂商要三天 |
| **跨系统对接** | 接口两边归属不同厂商，谁都不肯当主责 |
| **需求太碎，不值得起一个项目** | 200 多条需求里有一大半是这种 |

**这四类活的共同点：技术含量不高，但离不开人。** ——这是**法则 4 的诚实部分**，先说短板：

- **技术栈会被冻结**。Java 8 / Vue 2 / Node 14.21.3 / Fastjson，这是 2021 年的选型，
  而你的系统上线于 2023 年、要再跑五年。**你在这个岗位上，技术栈的更新速度由预算周期决定，不由你决定。**
- **没有真实规模压力**。全库几百条采购计划，这个量级练不出任何性能功夫。
- **反馈回路极长**。你改的东西可能三个月后才有人用，一年后才知道设计得对不对。

## 2.4 但有两样东西是这个位置独有的、买不到的

（这两条不是安慰，是可以在简历上写清楚的）

1. **你见过一个真实的多法人集团的组织建模**。`ubm_member_job` 挂 `company_id`、切公司换整套菜单、
   供应商服务关系登记在 BU 层——这套东西没有公开教材，只有在真集团里待过才知道。
2. **你见过系统之间真实的政治边界**。DPS 工作流在公司外部、SRM 只对 BU004 生效、
   黑名单主控权吵不出结果——**这类"技术上很简单、但改不动"的事，是绝大多数程序员职业生涯里的盲区。**

# 三 · 为什么从 SCM 到 SRM 全都是外包

## 3.1 Build / Buy / 以及中国国企真正走的第三条路

教科书只讲两条路，但你们走的是第三条：

| 路 | 英文 | 做法 | 谁这么干 |
|---|---|---|---|
| 自建 | **Build** | 从零写 | 互联网公司 |
| 采购 | **Buy** | 买标准 SaaS，业务迁就系统（`fit-to-standard`） | 欧美中大型企业 |
| **买底座再改** ← 你们 | **Buy-then-Build**（也叫 `Heavily Customized COTS`） | 买一套行业半成品，改 30–50%，然后自己养 | **中国绝大多数国企** |

**为什么中国国企必然走第三条**（四条原因，第一条最硬）：

1. **人力成本结构相反**。美国雇一个开发的年成本可能是买一套 SaaS 的好几倍，所以买标准品是省钱；
   中国自养团队 + 找集成商，往往比买标准品便宜。**这条经济规律直接决定了你的岗位存在。**
2. **甲方话语权强，不接受 `fit-to-standard`**。会上邵总那句"集团管理模式和你们产品的精细化程度有根本性差异"——
   在欧美这句话的下一句通常是"那我们改流程"，在中国是"那你改系统"。
3. **合规要求是本地的**。招投标法、国招平台报送、等保三级，国际产品根本没有这些模块。
4. **数据不能出境、不能上公有 SaaS**（很多国企内控直接写死）。

## 3.2 外包的真实代价不是代码质量，是三个词

| 词 | 中文 | 你们的具体症状 |
|---|---|---|
| **Bus factor** | 公交车系数：几个人被车撞了项目就停摆 | 底座组件 `scm-share-aim-*` 现在的 bus factor **【推断】接近 0** |
| **Knowledge transfer gap** | 知识没转移 | AIM 四段寻址这种自研机制，**编译期看不见、IDE 点不进去**，只能靠人传人 |
| **Version drift** | 版本漂移 | 跨团队 `1.0.0-JDSN-SNAPSHOT` 比本地源码旧，**全量 `mvn compile` 本来就是坏的** |

**这三个词合起来的效果**：交付验收那天是这套系统状态最好的一天，之后一路衰减。
学术上这叫 **software entropy**（软件熵增），莱曼软件演化定律的第二条讲的就是这个。

> 反直觉：**外包最贵的不是外包费，是外包结束后的那五年。**

# 四 · 为什么冀东先用上了 SRM ★本文核心

## 4.1 先看一个大前提：这是并购，不是新建

**【公开信息，年份请自己核】** 北京金隅与冀东集团在 **2016 年前后**完成重组，金隅成为冀东水泥的实际控制人。
也就是说——**冀东不是金隅生出来的，是娶进来的。**

娶进来的时候，冀东带着自己的：ERP（用友 NC65）、自己的物料编码体系、自己的采购部门、自己的 IT 团队、自己的预算。

**并购之后的系统整合，咨询业有专门的名字：`PMI`（Post-Merger Integration，并购后整合）。**
业内的经验值大致是这样**【公开信息，量级】**：

| 整合的东西 | 通常多久 | 完成率 |
|---|---|---|
| 财务报表合并 | 立刻，法定要求 | 100% |
| 人事、品牌 | 1–2 年 | 高 |
| 采购集中（谈判层面） | 2–3 年 | 中 |
| **IT 系统整合** | **5 年以上** | **低，很多集团永远做不完** |

**IT 永远排最后。** 因为它不影响报表、不影响股价，而且换一次系统整个业务要停摆。

## 4.2 所以"冀东先用上 SRM"的正确读法

> ### **不是冀东跑得快，是冀东本来就有，而且金隅一直没能力收编它。**

会上冀东侧那句"我们这边跟 NC65、包括各个企业的 ERP 都已经集成了"——
翻译过来是：**我这套东西是自成体系的，你别想轻易动。**

而 `BU004` 那两处硬编码（`SourceEnrollServiceImpl.java:1899`、`DealToSRMTaskConsumerAdapater.java:90`），
就是这段组织史在代码里的字面投影：

> **康威定律（Melvin Conway, 1967）**：系统的结构会长成组织沟通结构的样子。
> 通常讲这条定律都很鸡汤，但你们这儿有一个**能指到行号的例子**：
> **一个集团有 11 个板块，代码里只认 1 个，就是那个"娶进来时自带系统"的板块。**

## 4.3 更扎心的一层：SRM 和招采平台的基因不同

这是**全文最值钱的一条**，它一句话解释了前面所有现象：

> ## **合规驱动的系统天然集中，经营驱动的系统天然分散。**

| | **招采平台** | **SRM / ERP** |
|---|---|---|
| 存在的理由 | **合规**：《招标投标法》要求留痕、公示、报送国招平台 | **经营**：把货买到、按时到、质量对、钱付对 |
| 谁强制的 | 法律 + 集团纪检审计 | 没人强制，是业务自己要的 |
| 天然形态 | **集中**（统一口径才能审计） | **分散**（每家厂的物料、交期、质量标准都不一样） |
| 覆盖范围 | 寻源到定标，然后交出去 | 从需求一路管到付款 |
| 绩效指标能不能自动算 | **不能**（没有履约数据） | **能**（有收货、交期、合格率） |

**所以这次要做的事，本质上是：把一个经营系统，塞进一个合规系统的模具里。**

会上所有的痛点都是这一条的分身：
- 品类为什么对不上 → 经营要细（四级），合规只要粗（二级）
- 绩效为什么算不出来 → 经营有 ERP 取数，合规系统没有履约数据
- 黑名单为什么定不下主控 → 合规的黑名单是"一黑俱黑"，经营的冻结是"这单不跟你玩"，**根本不是一个东西**

> **反直觉**：邵总说"不如自己开"，从技术上看是对的，但从这个框架看更准确的说法是——
> **不管谁来开，把 SRM 提到集团层面这件事，缺的都不是软件，是"一个集团级的采购经营组织"。**
> 现在集团层面只有"招标合规"这一个抓手，没有集团采购部、没有集团品类经理、没有统一物料。
> **软件解决不了这个。**

# 五 · 为什么不能直接移植到全平台

会上给的理由是"品类粒度不一样"。对，但那只是症状。下面是完整的机理。

## 5.1 主数据的四种架构风格（MDM Implementation Styles）

这是 Gartner / Informatica 教材里的标准四分法，**每个大集团都必须在这四个里选一个**：

| 风格 | 做法 | 代价 | 谁适合 |
|---|---|---|---|
| **Registry**（注册表） | 主数据留在各系统，中间只存一张**编码映射表** | 最便宜，但查一次要跨系统 | 刚并购完 |
| **Consolidation**（汇总） | 各系统数据抄一份到中心，**只读，只为报表** | 便宜，但改不了源头 | 想先看清全貌 |
| **Coexistence**（共存）★ | 中心有一份主数据，**和各系统双向同步**，各系统仍可自己建 | 中等，但同步逻辑复杂 | **绝大多数中国大集团** |
| **Centralized / Transaction Hub**（集中） | **主数据只能在中心创建**，各系统只能用 | 最贵，业务要重训 | 单一业务、强管控的集团 |

**你们在哪一档：Coexistence。** 两条实证：

1. **公司主数据**：报名校验前要拿供应商编码去 MDM（`mdmSysCode = "BBMG"`）换成集团统一编码，再发给 SRM
   （`SourceEnrollServiceImpl.java:1908-1919`）——**这是典型的 Registry/Coexistence 映射动作**。
2. **物料主数据**：会上冀东侧讲的"集采物料码"——建一个统一集采物料名，多对一映射各企业 ERP 的物料码，
   对外用集采码，回来再映射回各企业码。**这是 Coexistence 的教科书写法。**

> **反直觉**：不统一物料**不是懒，是一个算得清的经济决策。**
> 统一物料的成本 = 编码映射 × 存量数据清洗 × 各厂业务重训 × 长期治理组织（要养一个主数据团队，永久性支出）。
> 收益 = 集采议价空间 + 统计口径。
> **多数中国大集团算下来是负的**，所以选 Coexistence。邵总那句"集团以前讨论过大一统物料，
> 基于成本还有很多管理复杂度，最终还是没有这样做"——这是一次做过的决策，不是遗漏。

## 5.2 美云的"奇瑞案例"是标准打法，但前提条件金隅一条都不满足

美云在会上举的例子（商用车上线成熟 → 复制给乘用车 → 再推第三个事业部），
在 SAP 全球部署方法论里叫 **Template Rollout / Core Model**，是大集团铺系统的标准做法。

**但 Template Rollout 成功有两个硬前提：**

| 前提 | 英文 | 金隅满不满足 |
|---|---|---|
| 模板要**冻结**，各单位不许乱改 | Core Model Freeze | ❌ 会上明确说各二级集团管理模式不同、规则要**分别配置** |
| 各单位接受**改自己去迁就系统** | Fit-to-Standard | ❌ 会上明确说不做物料统一、不接 ERP、集团是粗放式管控 |

**奇瑞能成，是因为商用车和乘用车是同一家公司的两个事业部，物料体系是一套。**
**金隅的 11 个板块是并购拼出来的，物料体系是 11 套。** ——不是同一个题。

## 5.3 把会上的三种方案，翻译成一张标准表

SaaS 多租户有一套业界通用的分档（AWS SaaS Factory 的 **Silo / Bridge / Pool** 模型，
Microsoft 的说法是 `Deployment Stamps`）。会上那三种方案正好一一对应：

| 会上的说法 | 标准名 | 隔离程度 | 每加一个客户的成本 | 统一升级 |
|---|---|---|---|---|
| 方案一：完整复制、独立部署 | **Silo（筒仓）** | 最强 | **线性增长**（每家一套机器一套运维） | 不可能 |
| 方案二：同底座、复制一套功能 | **Bridge（桥接）** | 中 | 中 | 很难 |
| 方案三：加一层集团组织维度 | **Pool（池化）** | 靠权限 | **趋近于零** | 可以 |

**这张表把会上的争论说清楚了：**
- 美云说"方案一最快、IP 风险最低" → **对，因为 Silo 不用改架构，只要复制**
- 美云说"方案三代价最大、所有功能表要动、冀东全量数据要初始化一次" → **对，因为那是把 Silo 改成 Pool，是架构手术**
- 集团说"部署多套没法集中管控" → **对，Silo 天生反集中管控**

> **反直觉：这三个方案不是三个选项，是一条演进路径上的三个点。**
> 行业里从 Silo 走到 Pool 的标准打法叫 **Strangler Fig Pattern**（绞杀榕模式，Martin Fowler 2004）：
> 不推倒重来，而是在旁边长出新的、逐个把老路由切过去、老的自然枯萎。
> **谁也没在会上提这条路——因为它要跨预算年度，而这个项目只有一年。**

## 5.4 更根本的一句

> **"能不能移植"这个问题本身问错了。**
> 移植的是软件，但**卡住的是"金隅有没有一个能对 11 个板块下命令的采购经营组织"**。
>
> 这在企业架构里叫 **Inverse Conway Maneuver（逆康威机动）**：想要什么样的系统架构，先去改组织结构。
> 金隅现在做的是反过来——**想用系统架构去倒逼组织统一。** 这条路全球都极少成功。

# 六 · 为什么还有 SAP（以及 NC65、以及各企业自己的 ERP）

## 6.1 先破一个常见误解

很多人的第一反应是"为什么不都做进 SAP"。**答案是：全球主流已经明确不这么干了，而且这个转向有名字。**

**`Postmodern ERP`（后现代 ERP）——Gartner 2014 年提出的概念。**

| | 传统单体 ERP | Postmodern ERP |
|---|---|---|
| 思路 | 一套 ERP 干所有事 | **核心 ERP 只留财务和记账，周边用最好的专项产品** |
| 周边怎么办 | 都做进去 | 用 **best-of-breed**（各品类选最好的）+ 集成 |
| 代价 | 改一次动全身，升级地狱 | **集成成本变成主要成本** |

**所以"招采平台在 SAP 外面"不是没整合好，是标准分工。**
对应到 `52-企业系统全景-cc.md` 里已经讲过的那对词：
**SAP = System of Record（记录系统，账要准，变化慢）；招采平台 = System of Engagement（交互系统，人天天点，变化快）。**

## 6.2 但金隅的 ERP 局面确实不正常，问题不在 SAP

真正的问题是**多套 ERP 并存**。这在 Gartner 的词里叫 **Two-tier ERP**（双层 ERP）或 `Multi-instance ERP`：

```
金隅集团
├─ BU002 冀东水泥 ────► SAP        （2023-04 起对接招采平台，实测 60 条计划）
├─ BU004 冀东发展 ────► 用友 NC65 + 美云 SRM （2025-10 起对接，实测 149 条计划）
├─ 其他 9 个板块  ────► 各自的 ERP / 或没有
└─ 集团层面      ────► 只有招采平台（合规）+ 财务共享（付款）
```

**Two-tier ERP 本身是一个合法的、被推荐的策略**——总部用重型 ERP，子公司用轻量的，靠接口对账。
**它的适用前提是：总部和子公司的边界清晰、接口标准化。**

**金隅不满足的是第二条**：这两条通道是**分别定制**的——
SAP 那条走一套接口，SRM 那条走 ESB 且只认 `BU004`。**每加一个板块就要再定制一次。**

> ⚠️ **一个特别容易搞混、而且会让你在会上说错话的点：**
> **"两个冀东"是两个不同的板块、两条不同的通道。**
> - **BU002 冀东水泥** → SAP 通道，2023-04 起
> - **BU004 冀东发展** → SRM 通道，2025-10 起
>
> 会上有人说"冀东用的"，指的其实是 BU004。**在集团开会时把这两个说混，会被当场纠正。**

# 七 · 集成层：ESB 这个选择在说什么

## 7.1 企业集成的三代演进

| 代 | 名字 | 长什么样 | 年代 |
|---|---|---|---|
| 一 | **Point-to-Point**（点对点） | A 直连 B，N 个系统要 N² 条线 | 2000 前 |
| 二 | **ESB**（Enterprise Service Bus，企业服务总线） | 中间放一根总线，所有系统只连总线（**Hub-and-Spoke** 星型） | 2005–2015 |
| 三 | **API Gateway + iPaaS + Event Mesh** | 网关管流量、iPaaS 管编排、事件总线管异步 | 2015 后 |

代表产品：ESB 时代是 IBM Integration Bus、Oracle Service Bus、TIBCO、Mule ESB；
iPaaS 时代是 MuleSoft（Salesforce 收）、Boomi、Informatica、国内谷云和轻易云。
MuleSoft 把第三代的方法论包装成一个词叫 **API-led Connectivity**（分 System/Process/Experience 三层 API）。

## 7.2 你们的 SRM 对接走的是第二代

`SrmESBConfig` 里的报文头是这样的：`Basic Auth` + `sysid` + `syncode` + `synname` + `puuid`。

**这四个头是 ESB 的身份证**：
- `sysid` = 调用方系统编号（谁在调）
- `syncode` / `synname` = 服务编号和服务名（调的哪个服务）
- `puuid` = 每次调用的唯一流水号（**出事了能回溯到具体这一次**）

> **反直觉：ESB 在国企活得好好的，不是因为落后，是因为它解决的是治理问题不是效率问题。**
>
> API Gateway 时代把"谁能调谁"的决定权还给了各团队，效率高了，但**审计视角丢了**。
> 而国企要的恰恰是：任何一次跨系统调用，都要能查出来是哪个系统、哪个服务、哪一次、谁授权的。
> `puuid` 这个字段的存在，比任何架构文档都更能说明这套系统服务的是什么样的组织。

## 7.3 但这一代集成有个固有代价，你们已经踩上了

**同步阻塞**。`checkEnroll` 是同步调用，SRM 返回"不合格"就直接
`throw new BusinessException(result.getData())` 抛给前端弹窗（`SourceEnrollServiceImpl.java:1941-1946`）。

现在只有 BU004 一个板块走这条路，所以 SRM 挂了只影响一个板块。
**推到 11 个板块之后，SRM 挂 = 全集团报名功能瘫痪。**

对应的行业解法有名字，一个都还没做：
**Circuit Breaker（熔断，Netflix Hystrix / Resilience4j）**、**Bulkhead（舱壁隔离）**、**Graceful Degradation（优雅降级）**。

# 九 · 所以这次 SRM 选型，真实难度在哪

把前八节压成一句话：

> ### **这个项目要在一年内，用软件补上一件金隅十年没做的事——把 11 个并购来的板块的采购经营，统一到一个口径。**

**如果我是决策者，会先问这三个问题**（顺序不能换）：

| # | 问题 | 为什么这个顺序 |
|---|---|---|
| 1 | **集团层面有没有一个能对 11 个板块下命令的采购部门？** | 没有 → 买什么系统都会退化成"冀东专用系统 + 10 个板块不用" |

| 3 | **供应商评价要不要客观取数？** | 要 → 必须接各板块 ERP（项目范围外）；不要 → 人工打分，一年只能评一次，功能做了也没人用 |

**这三个问题一个都不是技术问题。** 而 0827 那场会上，它们一个都没被正面回答。

本期缩成"给 BU004 + 一两个板块做供应商评价"，用 Silo 或 Bridge 落地，其余板块推到下一个预算年度。
**这不是失败，这是 Federated IT 的常态。**

# 十二 · 接着可以钻的三个方向

1. **「Ariba / Coupa 的产品长什么样」** —— 按模块讲界面和流程，你可以直接对着自己的系统看差距。
   这是把"我做的东西在全球是什么水平"这个问题回答清楚的最快路径。

2. **「一次真实的 Silo → Pool 改造是怎么做的」** —— Strangler Fig 的具体施工步骤：
   影子表、双写、灰度路由、旧路枯萎。**这是你能在这个项目里真正做出技术含量的唯一一块。**

3. **「甲方 IT 怎么在组织里证明价值」** —— 你手上那条 `BU004` 已经是个很好的例子（会上没人提、你能指到行号）。
   但从"发现一个事实"到"让领导记住是你发现的"中间有一整套做法。
