# 二 · 上游：谁在喂它数据

## 2.1 SAP —— 这家公司的账本

| | |
|---|---|
| **它是什么** | ERP（企业资源计划）。**企业的账本和骨架**：物料主数据、库存、成本、财务凭证 |
| **国际品类** | **ERP** —— 全球最大的一块企业软件市场。同类：Oracle Fusion、用友、金蝶、浪潮 |
| **和我们的关系** | ① **推采购计划过来**（库存低于安全线自动触发补货）② **煤炭采购流水每天推过来**（这条线你在 03/06 需求里做过）③ **商城订单回推给它记账** |
| **证据** **【实测】** | 采购计划里有一批的来源标着 SAP，名字直接叫"SAP计划-xxx"；订单状态里有一整套 SAP 相关状态（SAP订单待提交/发送失败/发送成功/校验中）|

> 🔑 **这是全图最重要的一条关系，值得单独理解：**
>
> **SAP 是 system of record（记录系统），招采平台是 system of engagement（交互系统）。**
>
> - **记录系统**：那本不能错的账。要求准确、一致、可审计，**变化慢**。
> - **交互系统**：人天天在上面点的那层。要求好用、流程灵活，**变化快**。
>
> 这个分层是企业架构里的经典模式。**理解它，你就明白为什么不能"把招采平台的功能做进 SAP"**——
> 账本要稳，前端要变，把它们焊在一起，两边都做不好。

## 2.2 SRM —— 另一个供应商数据来源

**【实测】** 采购计划里还有一批标着来源 SRM，名字叫"SRM计划-xxx"；定标结果也要**推回 SRM**（有专门的推送任务表）。

**【推断】** 集团层面可能有一套更早的、或者更偏"供应商主数据"的 SRM 系统，
和招采平台这套 SRM 模块是**并存关系**——招采平台里也有 SRM 模块（供应商管理），
但集团那套是更上位的。**这一条值得跟同事确认，我只看到了数据往来，没看到全貌。**

## 2.3 MDM —— 主数据

| | |
|---|---|
| **它是什么** | Master Data Management，管"什么是一个物料""什么是一个采购组织" |
| **国际品类** | **MDM**。同类：Informatica MDM、SAP MDG |
| **管什么** **【实测】** | 物料管理、物料类别、工厂管理、采购组织管理、专业管理、采购申请类型 |

> 🤔 **【推断】为什么主数据要单独一套系统？**
>
> 因为**同一个东西在不同系统里必须是同一个东西**。
> "螺纹钢 HRB400 直径 12mm"——在 SAP 里叫什么码、在招采平台里叫什么码、在商城里叫什么码，
> **必须一致，否则所有跨系统的统计都是错的。**
>
> 这就是为什么你在 06 需求里踩过"同一家公司在 4 个系统里有 4 个编号"的坑——
> **那正是主数据没打通的典型症状。**

## 2.4 统一门户 —— 待办聚合

**【实测】** 有一个专门的模块叫"统一门户待办"，往外推送待办事项。

**【推断】** 集团有一个统一的门户/工作台，员工每天登录那里，
**各个系统的待办（采购审批、报销审批、请假审批）都汇总到一个列表**。
招采平台产生的审批待办要推过去。

> 💡 **这是大集团的标配。** 一个员工可能同时是采购审批人、报销审批人、合同会签人——
> **让他每天登五个系统找待办，是不可能被接受的。**

# 三 · 下游：谁在消费它的产出

## 3.1 合同系统

定标之后进合同。**国际品类叫 CLM（Contract Lifecycle Management）**，同类：Icertis、DocuSign CLM。

## 3.2 财务共享 SSC

| | |
|---|---|
| **它是什么** | Shared Service Center，集团统一的财务处理中心 |
| **国际品类** | **Financial Shared Services**，大集团标配 |
| **和我们的关系** **【实测】** | 保证金的缴纳确认、**退款推送**、银行信息、认领台账，都推给它 |

> 🤔 **【推断】为什么财务要"共享"？**
>
> 一百多家成员企业，如果每家都养一套财务班子做付款、开票、对账——**成本极高且标准不统一**。
> 集中到一个共享中心，用统一流程处理，**既省人又统一口径**。
>
> 代价是：**业务系统必须把财务动作"翻译"成共享中心能处理的标准任务推过去**。
> 你看到的那套"待推送→推送中→已推送共享→推送失败"的状态机，就是这个翻译层。

## 3.3 OA / SRM 回写

**【实测】** 定标方案有两条专门的推送任务：**推 OA 系统**、**推 SRM 系统**。

**【推断】** 推 OA 是走公司的办公审批或归档；推 SRM 是同步"这家供应商中标了"这个事实，
影响它的绩效评价。

> 🔑 **这解释了一件事**：为什么改定标相关的功能风险高。
> **定标数据是下游好几个系统的输入源**，改一个字段可能影响五个地方。

## 3.4 云采商城

严格说商城不算"下游"，它是**并列的另一条采购通道**。但有两个接头：

1. **合同推送商城** **【实测：有这个菜单】** —— 招采招出来的框架协议供应商，推到商城让员工直接下单
2. **商品上架需求 → 归集寻源**（本次规划新增）—— 商城缺货 → 汇总 → 回到招采去寻源

**这两条把两个系统串成了闭环：商城暴露需求，招采解决供给，供给回到商城。**

# 四 · 旁挂：提供单项能力的

这一圈的特点是：**它们不参与业务流程，只提供一种能力**。

## 4.1 DPS 工作流引擎 —— 全图最容易被忽略的一个

| | |
|---|---|
| **它是什么** | **所有审批流程实际跑在它上面**，招采平台这边只是个代理 |
| **国际品类** | **BPM / Workflow Engine**。同类：Camunda、Flowable、Activiti |
| **证据** **【实测】** | 配置里写着一个外部服务地址，本仓代码全程用 HTTP + 签名去调它 |

> 🔑 **对你最实际的影响**：**审批能配成什么样，是 DPS 决定的，不是你写 Java 决定的。**
>
> 本次规划里"审批流程功能升级"那一项（直退、逐级退回、自定义分支、会签、抢单、撤回），
> **大概率是 DPS 的配置能力**，这也解释了为什么它只给了 8 个开发人天。
>
> 🤔 **【推断】为什么工作流要放外面？** 因为**流程是全集团共用的资产**。
> OA、报销、人事都要审批。做一个统一引擎，各系统调它——审批体验一致、配置集中、审计口径统一。
> **代价就是：很多"审批相关的需求"不在你能改的地方。**

## 4.2 天眼查 / 企查查 —— 外部工商数据

**【实测】** 天眼查在供应商模块已经有服务和接口；企查查有独立模块。

**国际对应**：Dun & Bradstreet（邓白氏）、Moody's 的企业风险数据。**大公司都买这类数据。**

**用途**：入围审核自动拉失信被执行人、经营状态；开标时自动拉股东和实际控制人（查串标关联）。

## 4.3 电子签章（引入中）

**国际品类**：**e-Signature**。同类：DocuSign、Adobe Sign、e签宝、法大大、契约锁。

**【实测】** 目前代码库里基本零痕迹，是全新对接。

## 4.4 帆软 BI（引入中）

**国际品类**：**BI / 数据可视化**。同类：Power BI、Tableau、Qlik。

**【实测】** 全代码库搜"帆软"零命中——**还没进来**。

> 💡 **帆软在国内 BI 市场占有率常年靠前**（厂商口径，我没法独立核实）。
> 它的开发方式是**拖拽配置**，跟写 Java/Vue 完全是两回事——**这是另一个工种。**

## 4.5 短信 / 消息、AI 底座（规划中）

短信是通知通道；AI 底座是集团规划中的统一 AI 平台，七个智能体都要架在它上面。

# 五 · 对外：国招平台（这一条最有中国特色）

**【实测】** 系统里有一整套"国招平台信息录入 / 发布 / 查询 / 报表"的菜单和后台模块。

| | |
|---|---|
| **它是什么** | **国家招标投标公共服务平台**（业内简称"国招平台"、CEB）|
| **和我们的关系** | **招标公告、中标结果要按规定报送到国家平台** |

> 🔑 **这一条是理解"为什么国企采购系统这么重"的关键证据。**
>
> **【推断】** 依法必须招标的项目，公告要在国家指定媒介发布——**这是法定动作，不是公司选择。**
> 所以系统里必须有一条通往国家平台的报送管道，还要能查报送状态、出报送报表。
>
> **欧美有完全对应的东西**：欧盟的 TED（Tenders Electronic Daily）、美国联邦的 SAM.gov。
> **只要是"花公众的钱"，全世界都要求公开发布。**

# 六 · 全局横切：数据是怎么变成报表的

**【实测】** 这套平台是"**写 MySQL、查 Elasticsearch**"的形态：
业务表在 MySQL，列表和报表查询走 ES，中间靠定时任务同步。

```
业务操作 → 写 MySQL → 定时任务（每天凌晨）→ 同步进 ES → 报表/驾驶舱查 ES
```

> 🤔 **【推断】为什么要这么绕？**
> 因为写和查的要求是矛盾的：**写要事务和强约束（MySQL 擅长），查要多条件组合和快（ES 擅长）。**
> 报表页面动辄十几个筛选条件，用 MySQL 硬扛会把库拖死。
>
> **代价是延迟**：今天录的数据明天凌晨才进 ES。
> **所以"页面看不到刚录的数据"，第一反应应该是"同步任务还没跑"，而不是"有 bug"。**

# 七 · 把名字抹掉，这张图长什么样

**这才是带得走的部分。** 把"SAP""帆软""DPS"这些具体名字换成品类，你会发现**任何一家大公司都是这张图**：

```
        ┌──── 监管/合规报送（政府平台、交易所、行业主管）
        │
  ┌─────┴─────────────────────────────────────────┐
  │  主数据 MDM ── 定义"什么是一个物料/客户/组织"    │
  └───────────────────┬───────────────────────────┘
                      │
   ERP（记录系统）─────┼─────  业务前端（交互系统）
   账、物、成本         │       流程、审批、协作
   变化慢、不能错       │       变化快、要好用
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
   财务共享        合同 CLM      商城/自助服务
        │
        └──── 数据仓库 / BI ──── 给领导看的数字

  【横向挂着】工作流引擎 BPM ｜ 电子签章 ｜ 外部数据服务 ｜ 消息通道 ｜ AI 能力层
```

## 认识这张图之后，你能做三件事

**① 接到需求时，先定位它落在哪一格。**
"保证金自动退费"→ 我们和财务共享之间的那条线；
"审批加会签"→ 工作流引擎那一格，可能不归我改；
"报表重构"→ BI 那一格，另一个工种。
**光是这一步，就能省掉大量方向性返工。**

**② 排查问题时，知道往哪个方向找。**
数据不对 → 先问是不是上游推来的；页面没数据 → 先问同步任务跑没跑；
审批不动 → 先问工作流引擎那边配了什么。

**③ 跟人聊的时候接得住话。**
别人说"我们上了 Ariba"，你知道那是 S2P，跟你做的是同一格；
别人说"我们在做主数据治理"，你知道那是最上面那一层，你踩过它没做好的坑。

# 最后：三句话带走

1. **招采平台是"闸门"，不是起点也不是终点。** 上游 ERP 说要买什么，它决定跟谁买，下游签约付钱记账。

2. **记录系统（ERP）要稳，交互系统（业务前端）要变，所以它们必须分开。** 这是企业架构里最基础的一条分层原则。

3. **把这张图上的名字抹掉，任何一家大公司都是同一张图。**
   你现在学的不只是金隅的系统，是**一整类系统长什么样**——这部分知识换公司也带得走。
