# 一、先看懂骨架：三个工作台 = 三种人

这套系统**不是一个网站，是三个门户**。同一件事在三个门户里长得完全不一样。
**【实测】** 从菜单地图（`ai-docs/前端页面地图.tsv`）能直接看出来：

| 工作台 | 谁在用 | 他关心什么 | 菜单规模 **【实测】** |
|---|---|---|---|
| **我的工作台（企业端）** | **采购员、审批人、管理员** —— 也就是金隅自己的员工 | 我要买东西、我要审批、我要看报表 | 最大，约 130 个页面：报表查询 23、审批待办 21、采购寻源 16、供应商管理 14、平台管理 13…… |
| **我的工作台（供应商）** | **外部供应商的业务员** | 有什么活能接、我要投标、我中标了吗、我的订单 | 13 个页面：入网申请、公司档案、子账户管理、投标管理、中标管理、订单列表 |
| **我的工作台（专家）** | **评标专家**（企业内部专家 + 外部专家） | 有没有叫我去评标、我要打分 | 9 个页面：评审响应、项目评审、专家档案维护、我的邀请 |

> 💡 **这是理解一切的第一把钥匙。**
> 你以后看任何一个需求，先问："**这是给三种人里的哪一种做的？**"
> 比如 **P1-04"评委匿名化"是给专家端和企业端做的**（专家之间互相看不到名字）；
> **P2-01"多子账号"是纯供应商端的**；**P3-02"检索状态缓存"三个端都受益**。

还有两个不太起眼但很重要的角色 **【实测：菜单里有独立分组】**：

- **监标人**（菜单"专家|监标人管理"下有"监标人列表""监标任务""设置监标人"）——
  **【推测】** 相当于纪检监督员，全程盯着开标评标过程，防止舞弊。代码里有 `BidSuperviseStateEnum`：无需选择 / 待选择 / 已选择 / 需补选 **【实测】**。
- **运营/平台管理员**（菜单"平台管理""系统配置""运维中心"）——配字典、配模板、配菜单。**很多需求最后落地成"给管理员加一个配置项"，而不是写死逻辑。**

# 二、主线：一个寻源单的一生

现在开始讲主线。**为了好记，我们跟着一笔真实的采购走一遍。**

> **例子**：唐山冀东水泥要买 **200 吨螺纹钢**，预算 80 万，决定走**公开招标**。

整个过程在数据库里就是一条 `sc_source` 记录（寻源单），它的 `state` 字段会从头变到尾。
**【实测】** 这个状态机一共有 **24 个状态**，全在 `SourceStateEnum` 里
（`01zhaocai-end/scm-source-all/scm-source-source-api/.../enums/SourceStateEnum.java`）：

```
099 待发布采购公示     101 待发布公告        102 待发送邀请函      103 响应中
104 报名中             105 报价中            106 待开标            108 强制揭示审批中
115 磋商中             116 谈判中            117 评审中            118 待录入评审结果
119 待编制定标方案     122 定标方案审批中    123 定标方案审批拒绝  124 待发布公示
125 待发送中标通知     126 已流标            127 已公示            128 已终止
129 竞价中             130 进行中            131 暂停中            132 上传预审资料中
```

> ⚠️ **先记住三个数字，以后看数据库能立刻反应过来**：
> **127 = 已公示（正常走完的终点）｜ 126 = 已流标（没招成）｜ 128 = 已终止（中途叫停）**。
> 你之前做的集采统计报表，筛的就是 `state=127` —— 因为**只有公示了的采购才算数**。

下面按七幕展开。

## 第一幕 · 立项：从"我想买"到"方案批下来"

### 发生了什么

车间说要 200 吨螺纹钢 → 采购部门把它编成一个正式的**采办方案**（买什么、多少钱、怎么招、分几个标段、怎么打分）→ 走审批 → 批了才能往下走。

### ⭐ 先把三个词分清：采购计划 / 采办方案 / 标段

（2026-08-25 补：用户读到这里卡住，这一段是回写。下面全部用 test 库里一条**真实数据**讲。）

#### 一句话版

| 词 | 一句话 | 回答的问题 | 主表 **【实测】** |
|---|---|---|---|
| **采购计划** | **要买哪些东西的清单** | **买什么？买多少？** | `sc_plan` + `sc_plan_product` |
| **采办方案** | **这批东西打算怎么买的方案书** | **怎么买？谁来买？什么规矩？** | `sc_scheme` + `sc_scheme_product` |
| **标段** | **把一个方案切成几块，分别招、分别定** | **拆成几笔生意？** | `sc_scheme_tender`（标段号在物料行的 `tender_num` 上） |

> 💡 **Node 类比**（注意边界）：
> **采购计划 ≈ 一堆待处理的 issue**（各部门报上来的需求，一条一条躺在那）；
> **采办方案 ≈ 你把其中几个 issue 打包成一个 sprint**，并且给这个 sprint 定了规则（用什么流程、谁验收、评分标准）；
> **标段 ≈ sprint 里的子任务分组**，可以分别指派、分别验收、**分别取消**。
> **边界**：issue 是你自己建的，但**采购计划大部分不是在这个平台上建的**——见下面第 ② 条。

#### ③ 标段：一个方案切成几笔生意

**看一条真实的三标段招标** **【实测：test 库 `13110000-ZB-2024-0274`】**：

```
采办方案  13110000-ZB-2024-0274
          吉林金隅冀东环保科技有限公司招标评审模板招标
          采办方式=招标   状态=审批通过   采购人=张超
   │
   ├── 标段 1 ─┬─ 行000001  150101010005  方钢          32 吨
   │           └─ 行000002  150101010006  方钢          54 吨
   │
   ├── 标段 2 ─┬─ 行000003  150101010016  钢坯          32 吨
   │           ├─ 行000004  150101010017  镀锌方钢管     4 吨
   │           └─ 行000005  150101010018  镀锌方钢管    54 吨
   │
   └── 标段 3 ─┬─ 行000006  150101020028  圆钢          54 吨
               ├─ 行000007  150101020029  圆钢          78 吨
               └─ 行000008  150101020030  圆钢          98 吨
```

**为什么要分标段？** **【推测：业务常识，可拿去和产品验证】**
1. **品类不同**：钢坯和圆钢不一定是同一批供应商的强项，分开招能招到更专业的
2. **分散风险**：一家供应商出问题，不至于三个标段全瘫
3. **保持竞争**：三个标段可以有三家中标，下一次采购时它们互相压价

**标段在数据里长什么样** **【实测】**：
- `sc_scheme_tender` 一个标段一行，字段有 `tender_num`（标段号 1/2/3）、`tender_name`、`category_name`（物料分类）、`state`
- 物料行 `sc_scheme_product` 上带一个 `tender_num`，表示"我属于第几标段"
- **标段已经有自己的状态机了** **【实测：test 库分布】**：`101 进行中`(1104) / `104 已流标`(381) / `102 已终止`(17) / `103 已完成`(14)

```
   ┌─ SAP / SRM / SCM 推送 ──┐        ┌─ 人在页面上编 ─┐
```

> 这就是"集中采购"在系统里真实发生的样子。

#### ⑤ 于是回头看 P1-01 这个需求，就懂它为什么值 63 人天了

需求原文：**"多标段独立启停、终止、归档（含评分退回）"**。

**【实测】现状**：
- 标段**已经有**自己的状态机（进行中/已终止/已完成/已流标），而且 test 库里已经有 17 条"已终止"的标段
- 但**主流程的寻源单 `sc_source` 是整单一条**，它身上有 `divide_tender`（是否分标段：分标段 370 条 / 不分 552 条 / 老数据为空 1789 条），
  却**没有一条"按标段拆开"的寻源单**（`tender_id` 字段填充数为 **0**）
- test 库里能看到好几个叫"分标段终止""分标段流标再次寻源"的测试方案 **【实测】**，说明**这块业务同事已经试过了**

**【推测】翻译成人话**：现在标段能各自标记状态，**但整个流程（公告、开标、评标、定标、公示）还是整单一起走的**。
要做到"每个标段独立启停终止归档"，等于**要让流程本身能按标段分叉**——
这不是加个按钮，是**主流程状态机的改造**。63 人天（其中方案设计 20、开发 30）这个估法就说得通了。

> **给未来的你**：拿到 P1-01 的详细需求时，第一个要问清楚的是——
> **"标段独立走流程"是指公告也分开发、开标也分开开，还是只有评标和定标分开？** 这两种的工作量差好几倍。

### 数据里发生了什么 **【实测】**

采办方案是另一张表（`sc_scheme` 系列），有**自己的一套状态** `SchemeStateEnum`：

```
101 待提交 → 102 待审批 → 103 审批中 → 104 审批通过 → 106 待提交招标
                              ↓ 105 审批拒绝        → 107 招标项目编制中
                                                    → 108 采办方案退回
                                                    → 109 招标项目待提交
                                                    → 110 已关闭
```

**方案下面还挂着三样东西** **【实测：swagger 标签 + 表名】**：
- **标段**（"采办方案标段管理"）—— 一个方案可以切成几个标段分别招
- **评分模板**（"采办方案评分模版管理"，表 `sc_appraise_template` / `sc_appraise_template_content` / `..._norm`）—— 决定专家怎么打分
- **物料明细**（`sc_scheme_tender_product`）

> 🔑 **"方案 → 标段 → 物料"这个三层结构，是招采平台数据模型的地基。**
> 后面所有的报价、评分、定标、中标，全都是挂在"某方案某标段某供应商某物料"这四个维度上的。
> **【实测】** 你之前做的集采统计报表里，ES 主键就是"方案编号 + 标段号 + 供应商编码 + 物料编码"——
> 因为**同一个物料在同一个方案里可以被分标给好几家供应商**，少一个维度就会互相覆盖、金额算少。

### 这次新需求动这一幕的

- **P1-01 分阶段评标、分标段终止（63 人天）** —— "多标段独立启停、终止、归档"。
  现在**【推测】**标段是跟着主单一起走的，这次要让每个标段能单独终止而不影响别的标段。**这是数据模型层面的改动，不是加个按钮。**
- **P1-02 审批流程功能升级（25）** —— "采购方案保存草稿及删除"。对应上面的 `101 待提交` 状态要能存草稿、能删。
- **P1-03 扩充特殊报价模式（51）** —— 评分模板里要能配"负数报价 / 费率 / 折扣率"三种格式，以及多品类差异化权重。

## 第二幕 · 挂出去：发公告 / 发邀请函

### 发生了什么

方案批了，把这笔生意公之于众。公开招标就**发公告**（`101 待发布公告`）；
邀请招标/竞谈这类只找几家的，就**发邀请函**（`102 待发送邀请函`）。

### 公告一共有 8 种 **【实测：`SourceNoticeTypeEnum`】**

| 码 | 类型 | 什么时候发 |
|---|---|---|
| 01 | **招采公告** | 一开始，招人来投 |
| 07 | **邀请函** | 定向邀请时用 |
| 03 | **延期公告** | 报名/投标截止时间要往后推 |
| 04 | **澄清公告** | 招标文件写错了或有歧义，补充说明 |
| 05 | **结果公告** | 定标之后公示中标结果 |
| 06 | 单一来源公示 | 单一来源要先公示"我打算只找这一家"，接受质疑 |
| 02 | **终止公告** | 中途不招了 |
| 08 | **流标公告** | 没招成 |

**这四种公告都要走审批** **【实测：菜单里各有一个审批入口】**：
延期公告审批 `#/approveMgt/extensionApproval`、澄清公告审批 `#/approveMgt/clarifyNotice`、
终止公告审批 `#/approveMgt/applyCloseApproval`、定标方案审批 `#/approveMgt/calibrationScheme`。

### 这次新需求动这一幕的

- **P3-01 电子签章（38）** —— "公示文件发布环节用户选择是否盖章（**默认是**）"。
  **【推测】** 现在的做法是人工盖章后扫描成图片上传，所以原文才写"防止盖章混乱或**图片截图盖章**"。
- **P1-05 定标公示功能重构（34）** —— 动的是上表里的 **05 结果公告**。

## 第三幕 · 供应商响应：报名、买标书、交保证金、报价

### 发生了什么

公告挂出去，供应商在**供应商工作台**看到了，决定参加。这一幕状态在 `103 响应中 / 104 报名中 / 105 报价中 / 132 上传预审资料中` 之间流转。

### 供应商这边的状态 **【实测：`EnrollStateEnum`】**

```
00 待响应 → 01 已参与 / 02 不参与 / 03 已撤回 / 04 超时未响应 / 05 已报名 / 10 已关闭
```

**"超时未响应"是个自动状态** ——**【实测】** 另有 `EnrollPreStateEnum`：正常 / 报名已截止。
说明系统里有定时任务在卡时间点。

### 钱：标书费和保证金 **【实测】**

`CostTypeEnum` 只有两种：**`00` 标书费、`01` 投标保证金**。

- **标书费** = 买招标文件的钱，**一般不退**。供应商状态 `SupplierBidStateEnum`：`101 未购买标书 / 102 已购买标书 / 103 已退款`。
- **保证金** = 押金，证明你是认真的，**要退**。

费用单自己有一套状态 `CostStateEnum` **【实测】**：

```
101 待支付 → 102 待确认 → 103 已支付 → 105 开票中 → 106 已开票
              ↓ 104 支付失败              ↓ 107 开票失败
              109 已关闭
```

**注意"待确认"这一步**——**【推测】** 说明这里有人工核对环节：供应商说我打钱了，财务要确认到账。
**这正是 P1-06"保证金线上自动退费"想干掉的人工环节之一。**

保证金还有独立的审核状态 `BidMemberDepositStateEnum` **【实测】**：`101 未提交 / 102 审核中 / 103 审核通过 / 104 审核拒绝`。

### 屏幕上在哪 **【实测】**

- 供应商端：用户中心 / 入网申请、投标管理 `#/procurementSourcingProcessMgt`
- 企业端审批：审批待办 / **保证金审批** `#/approveMgt/enrollManage`、**标书费审批** `#/approveMgt/responseManage`、
  **保证金/标书费审批** `#/dynamicMultipleTabs/source/costpayqudicts`
- 企业端台账：采购寻源 / **保证金台账** `#/marginLedger`；运维中心 / 保证金日志管理 `#/marginLedger/log`

### 这次新需求动这一幕的

- **P1-03 扩充特殊报价模式（51）** —— 报价录入和计算逻辑重构。**这一幕就是报价发生的地方。**
  另外"询比价最高限价单价（含税）限制"也在这里：报价超过限价直接拦。
- **P1-06 保证金线上自动退费（35）** —— 详见第五章。
- **P3-03 文件批量处理与容量扩容（16）** —— 供应商传投标文件动辄几百 MB，现在**【推测】**传不上去或者只能一个一个传。

## 第四幕 · 开标：到点了，当众拆封

### 发生了什么

投标截止时间一到，状态变成 `106 待开标`。到开标时间，在**开标大厅**里当众解密所有投标文件。

### 开标大厅是一个独立的东西 **【实测：表 `sc_bid_lobby` / `sc_bid_member` / `sc_bid_log`】**

`BidLobbyStateEnum`：`101 未开始 → 102 竞价中 → 103 已结束 / 104 流标 / 105 暂停中 / 106 终止中 / 107 已终止`

**开标大厅会记录每个参与者是否在线** **【实测：`BidMemberStateEnum`】**：`101 在线 / 102 离线 / **103 违规**`。

> 💡 **"违规"这个状态很有意思。** **【推测】** 说明系统会检测供应商在开标过程中的异常行为（比如中途掉线、重复登录、
> 同一 IP 多家投标）。**这正好是 P5-01 围串标 AI 智能体的数据基础之一** —— 那些"MAC 地址重合""同一台电脑上传"的线索，
> 就应该在这个环节采集。

### 还有一个特殊状态：`108 强制揭示审批中` **【实测】**

**【推测】** 正常开标需要所有投标人都在线解密自己的文件；如果有人不来，采购方可以申请"强制揭示"（强行解密），
但这个动作**必须走审批**，因为它涉及打开别人的密封文件。**这是一个典型的"合规设计"——权力必须留痕。**

### 三种不圆满的结局，都在这一幕前后决定

| 结局 | 状态码 | 什么情况 |
|---|---|---|
| **流标** | `126 已流标` | **来投标的有效供应商家数不够**（见第三章的硬规则）、或者都不合格 |
| **终止** | `128 已终止` | 采购方主动叫停（预算没了、需求变了）。**要走终止公告审批** |
| **暂停** | `131 暂停中` | 临时冻结，还能恢复 |

**【实测】** 终止是一个独立的单据，有自己的状态 `SourceCloseStateEnum`：`101 待提交 → 102 待审批 → 103 审批中 → 104 审批通过 / 105 审批拒绝 / 106 已关闭`，
表 `sc_source_close` / `sc_source_close_record` / `sc_source_close_task`。

### 这次新需求动这一幕的

- **P1-01 分标段终止** —— 现在终止是整单终止，要改成能按标段终止。
- **P2-06 天眼查（35）** —— "**开标环节自动拉取持股股东、实际控制人**"。
  也就是开标那一刻自动去天眼查查一遍所有投标人的股权结构，看有没有互相持股（那就是串标嫌疑）。
- **P5-01 围串标 AI（42）** —— 数据采集点就在这一幕和上一幕。

## 第五幕 · 评标：专家来打分

**这一幕是整个系统最敏感、也是这次改动最密集的地方。**

### 5.1 先抽专家

**【实测】** 专家抽取是独立单据，表 `pro_professor_extract`，状态 `ExtractStatusEnum`：

```
101 待抽取 → 102 已抽取 → 103 待补抽（人不够，再抽）
             104 待指定抽取审批通过（想指定某个专家，要审批）
             105 参加评标的专家人数不足
             106 已终止
```

**抽取方式** `ExtractTypeEnum` **【实测】**：`12 随机抽取` / `13 指定专家`。
> 💡 **"随机"是默认，"指定"要审批** ——**【实测：菜单里有"专家抽取审批" `#/approveMgt/expertExtraction`】**。
> 这又是一个合规设计：能随机就随机，想挑人就得留痕。

**抽取范围** `ExtractRangeEnum` **【实测】**：`0 本企业专家` / `1 区域专家` / `2 外部专家`。

**专家是分专业的** **【实测：`ProfessorTypeEnum` 有 15+ 个专业】**：
高低压电气、自动化仪表、工程、环境能源、经济、协同处置、信息智能、安全、法务与审计、矿山、烧成、粉磨、质检、机械、发电……
**这些专业名一看就知道是水泥行业的**（烧成、粉磨、矿山都是水泥工艺环节）。

### 5.2 专家打分

**【实测：表名】** 评标这块的表全在 `scm-professor-all`，前缀 `ev_`：

| 表 | 装什么 |
|---|---|
| `ev_evaluation` | 评标主表 |
| `ev_evaluation_package` | **按标段（包）评** |
| `ev_expert` | 这次评标有哪些专家 |
| **`ev_expert_score`** | **每个专家给每一项打了多少分** ← 核心 |
| `ev_bidding_company` | 参与的投标单位 |
| `ev_bidding_file` | 投标文件 |
| `ev_choose_director` | **选评标组长** |
| `ev_again_score` | **重新打分** |
| `ev_review_process` / `ev_review_category` | 评审过程 / 评审分类 |

评标主状态 `EvaluateTenderStatusEnum` **【实测】**：`0 待开标 → 1 已开标 → 2 已开标(进行中) → 3 评审完成 / 4 已流标 / 5 已终止 / 6 暂停中`。

还有个投票 `EvaluateRateEnum`：`1 已投票 / 0 未投票` **【推测：选组长或表决用】**。

### 5.3 中标候选人

评完分排出名次，产生**中标候选人** **【实测：表 `sc_scheme_wincandidate`，状态 `WincandidateStateEnum`】**：

```
100 已保存 → 110 待确认 → 120 已确认 → 130 公示中 → 140 已完成 / 999 异常
```

### 屏幕上在哪 **【实测】**

### 这次新需求动这一幕的（**最密集**）

| 需求 | 具体动什么 |
|---|---|
| **P1-01 分阶段评标（63）** | 把评标拆成**技术评标**和**商务评标**两个阶段，技术不过关的直接淘汰，不用再看报价。两个阶段都要支持**废标**。**【推测】** 业务动因是防止评委被价格影响技术判断——这是招投标行业通行做法 |

## 第六幕 · 定标：谁中标，白纸黑字定下来

### 发生了什么

评标结果出来 → `118 待录入评审结果` → `119 待编制定标方案` → 编好提交审批 `122 定标方案审批中` →
批了就 `124 待发布公示` → 公示出去 → **`127 已公示`（终点）**。
中途被否就是 `123 定标方案审批拒绝`，打回重编。

### 数据 **【实测】**

定标方案有自己的状态 `DealStateEnum`：`101 待提交 → 102 待审批 → 103 审批中 → 104 审批通过 / 105 审批拒绝 / 106 已关闭`。

**表结构（这是你以后查数据最常用的一串）** **【实测：`@TableName`】**：

```
sc_deal_result    定标方案主表
  └─ sc_deal_detail    中标供应商（一个方案可以有多家）
       └─ sc_deal_product   中标物料（每家供应商中了哪些料、多少钱）
sc_deal_attach    附件
sc_deal_to_oa_task    推送 OA 系统的任务
sc_deal_to_srm_task   推送 SRM 系统的任务
```

**中标供应商还有自己的小状态** `DealSupplierStateEnum` **【实测】**：`201 已中标 → 202 已发送（中标通知书）→ 203 已回执（供应商确认收到）`。

### 定标之后，数据要往外推 **【实测：有专门的推送任务表和状态枚举】**

- **推 OA**（`DealPushToOAStateEnum` / `sc_deal_to_oa_task`）—— **【推测】** 走公司的办公系统再审一道或归档
- **推 SRM**（`DealPushToSRMStateEnum` / `sc_deal_to_srm_task`）—— 同步给供应商管理系统，记一笔"这家中标了"

> 💡 **这就是为什么改定标相关的东西风险高**：定标数据是**下游好几个系统的输入源**。
> 你改一个字段，可能影响 OA、SRM、合同、订单、统计报表五个地方。

### 这次新需求动这一幕的

- **P1-05 定标公示功能重构（34）** ——
  ① **重构公示数量限制的底层代码**（1-3 家 / 单一来源 1 家 / 不限，改成灵活配置）
  ② **新增"采购单位、中标供应商"关联字段，支持一对多** ← **这是表结构改动，要考虑存量数据**
  ③ 发布中标公示时按评分排名**自动填充**
  ④ 定标时调取供应商异常预警（AI 风险提示，对应 P5-04）
- **P3-05 数据导出（16）** —— "招标/定标审批流程 **PDF 归档**并保存到采购寻源查询界面，支持按招标编号批量下载"。
  **【实测】** 已有模块 `scm-source-pdf` 和表 `scm_pdf`，这次是扩场景。

## 第七幕 · 收尾：发通知书、退保证金、进合同

### 发生了什么

`125 待发送中标通知` → 发中标通知书 → 供应商回执 → 签合同 → 下单履约 →
**没中标的退保证金**、**中标的转履约保证金或退**。

### 退保证金：这次的重点需求 **【实测】**

有两套状态在这一段：

**① 退款进度** `SourceDepositRefundStateEnum`：`101 待退款 → 102 退款中 → 103 已退款`
**② 推给财务共享的进度** `SourceDepositPushStateEnum`：
```
100 (空) / 101 线下处理 / 102 待推送 / 103 推送中 / 104 已推送共享 / 105 推送失败
```

**【实测】** 对接财务共享的代码在 `scm-source-all/scm-source-ssc`，其中：
- `SourceSscSendServiceImplForDepositRefund` —— **保证金退款推送**
- `SourceSscSendServiceImplForDepositClaimLedger` —— 保证金认领台账
- `SourceSscSendServiceImplForBankInfo` —— 银行信息
- 任务表 `sc_source_ssc_task` / `sc_source_ssc_task_detail`，台账表 `sc_deposit_ledger`

> 🔑 **注意那个 `101 线下处理`。** **【推测】** 它的存在说明：**现在有相当一部分保证金是财务在系统外手工退的**，
> 系统只记一笔"这个走线下了"。
> **P1-06"保证金线上自动退费"的本质，就是把这些"线下处理"变成"自动推送"。**
> 需求原文里那几句——"系统自动匹配中标结果、项目状态""自动触发退费流程""校验退费账户与原缴费账户一致性""资金流转反向溯源台账"——
> 每一句都对得上现有的一个零件。**这一项是典型的"地基已有，补自动化"，不是从零做。**

### 这次新需求动这一幕的

- **P1-06 保证金线上自动退费（35，高优先级）**
- **P1-03 报价模式**里提到的"财务共享 + 履约管理"接口，也在这一段

# 三、六种寻源方式的分岔

第二幕到第六幕之间，**走哪条路取决于"采办方式"**。**【实测：`PurchaseMethodEnum`】** 一共 7 个值：

| 码 | 方式 | 通俗解释 | **最少有效供应商家数** |
|---|---|---|---:|
| **101** | **招标** | 最正规：公开挂公告，谁都能来投，专家评标 | **3** |
| **102** | **单一来源** | 只有这一家能供（独家专利/原厂配件），不比价但要先公示接受质疑 | **1** |
| **103** | **询价采购** | 发给几家问个价，谁便宜要谁。也叫"询比价" | **3** |
| **104** | **竞争性谈判** | 边谈边压价，可以多轮 | **2** |
| **105** | **竞争性磋商** | 谈判 + 允许供应商调整方案 | **2** |
| **106** | **竞价** | 类似拍卖，供应商在线往下压价（对应状态 `129 竞价中`） | **3** |
| **107** | **资格预审** | 先审资格再让投标（对应状态 `132 上传预审资料中`） | **3** |

## ⭐ "最少家数"是一条硬规则，不是摆设

**【实测，这条我特意追到了调用处】**：
`PurchaseMethodEnum` 的第三个参数就是最少家数，`SourceScheduleServiceImpl.java` 里有：

```java
if (validSupplierSize < PurchaseMethodEnum.getNum(x.getPurchaseMethod())) { ... }
```

配套的提示文案 **【实测：`SourceUpdateSourceNoticeConsumer.java`】**：
> "有效**报价**供应商不满足 N 家！" / "有效**报名**供应商不满足 N 家！" / "有效**提交预审文件**供应商不满足 N 家！"

**翻译成人话：定时任务到点检查，有效供应商不够 N 家，这个标就自动流标（`126`）。**

> 💡 **这就是"流标"最常见的原因**，也是为什么业务部门老抱怨"招不上来"。
> **【推测】** 三家这个数字是国内招投标的通行下限（《招标投标法》要求投标人不少于三个）。
> **单一来源之所以是 1，是因为它本来就只有一家** —— 这也解释了为什么单一来源有个专属状态 `099 待发布采购公示`：
> **它不用招标，但必须先公示"我要独家采购"，接受别人质疑。**

## 不同方式走的岔路 **【实测：状态码 + 代码里的分组常量】**

```
招标(101)     → 报名 → 上传投标文件 → 106 待开标 → 117 评审中 → 定标
资格预审(107) → 132 上传预审资料中 → 审资格 → 再走招标那一套
询价(103)     → 105 报价中 → 比价 → 定标（不一定抽专家）
竞谈(104)     → 116 谈判中 → 多轮报价 → 定标
竞磋(105)     → 115 磋商中 → 多轮 → 定标
竞价(106)     → 129 竞价中（开标大厅在线竞价）→ 定标
单一来源(102) → 099 待发布采购公示 → 公示无异议 → 直接定标
```

**【实测】** 代码里还有三个分组常量，名字很有暗示性：
`getProfessorCodes()` = 招标 + 竞磋 + 资格预审；`getOpenCodes()` = 招标 + 资格预审；`getTenderCodes()` = 招标 + 竞磋 + 资格预审。
**【推测】** 分别是"要抽专家评标的""要公开开标的""要交投标文件的"这三组。
**具体语义你开工碰到时看调用处，别照我这句下结论。**

> 🔑 **对你写代码的意义**：**几乎每个功能都要按 `purchaseMethod` 分支。**
> 你以后接到任何一个需求，先问一句："**这六种方式都要支持吗？还是只针对某几种？**"
> 这一句能帮你省掉一半的返工。**这次的 P1-03 特殊报价模式就是典型——负数/费率/折扣率报价大概率只适用于询价和竞谈，不适用于招标。**

```
采购计划审批   采购方案审批   定标方案审批   保证金审批   标书费审批
```

## 4.2 审批状态在全系统是同一套模式

**【实测】** 我对比了 `SchemeStateEnum`、`DealStateEnum`、`SourceCloseStateEnum`、`ApproveStateEnum`、
`SrmApplyStatusEnum`、`ProductApplyStatusEnum`、`OrderApplyStatusEnum`，
它们**长得几乎一模一样**：

| 通用含义 | 寻源侧常见码 | 供应商侧 | 商城侧 |
|---|---|---|---|
| 待提交 / 未提交 | 101 | 101 | — |
| 待审批 | 102 | 102 | 102（审核中）|
| 审批中 | 103 | 104 | — |
| 审批通过 | 104 | 106 | 103 |
| 审批拒绝 | 105 | 105 | 104 |
| 已关闭 / 作废 | 106 / 109 / 110 | 103（已撤销）| 105 |

> ⚠️ **坑：码值不统一。** 同样是"审批通过"，寻源侧是 `104`，供应商侧是 `106`，商城侧是 `103`。
> **不同模块的状态码不能互相套用**，跨模块写代码时一定要翻对应的 Enum。

## 4.3 但真正的流程引擎不在这个代码库里

**【实测】** 我们仓里的 `scm-workflow-all` **只是代理层**：
- `scm-workflow-springboot/src/main/resources/bootstrap-dev.yml:39-42` 配着 `dps.url: http://dps.scmflow-dev.jdsn.com/dps-service`
- `scm-workflow-base/.../DPSProcessServiceImpl.java` 全程用 HttpClient + HMAC 签名去调那个外部服务

**翻译**：**审批能配成什么样，是 DPS 那个系统决定的，不是你写 Java 决定的。**

**这次的 P1-02"审批流程功能升级"要的那一堆能力**——直退 / 退回逐级审批 / 修改后返回原驳回节点 /
自定义分支审批条件 / 多人会签 / 抢单 / 下一节点审批前撤回 / 退回流程归档——
**大概率是 DPS 的配置能力，而不是我们写代码实现的。** 这也解释了为什么它只给了 8 个开发人天。

> 🔑 **对你的意义**：拿到 P1-02 的详细需求文档时，**第一件事是找出哪几条是 DPS 配的、哪几条是我们代码做的。**
> 这两类混在一份需求文档里，是很常见的事。分不清就会出现"我照着写了但根本不生效"。

# 十、你写代码时最容易踩的 8 个业务坑

这一节是**给未来的你**的。等你拿到细化需求文档开工时，回来看一眼。

### 坑 1 · 状态码绝对不能猜，一定要翻 Enum
同样是"审批通过"，寻源侧 `104`、供应商侧 `106`、商城侧 `103` **【实测】**。
**动手前先 `find <仓> -name "*Enum*.java"` 把相关枚举全列出来。**

### 坑 2 · 一个需求先问"六种寻源方式都要支持吗"
几乎所有寻源功能都要按 `purchaseMethod` 分支。**这一问能省一半返工。**

### 坑 3 · "方案 → 标段 → 供应商 → 物料"四个维度，少一个就算错
**【实测：你在 06 需求踩过】** 同一个物料在同一个方案里可以分标给三家供应商。
主键少了"标段"或"供应商"维度，数据会互相覆盖，金额算少。

### 坑 4 · 改列表/搜索/导出前，先确认字段在 MySQL 还是 ES
只改 MySQL 不改 ES 映射和同步任务，**页面上什么都不会变**。
另外 **ES 分页/导出默认上限 10000，超了是静默截断** **【实测：系统地图】**——
**M3-01 发票和对账单批量导出要特别盯这一条。**

### 坑 5 · 定标数据是下游好几个系统的输入
定标一改，OA、SRM、合同、订单、统计报表都可能受影响 **【实测：有 `sc_deal_to_oa_task` / `sc_deal_to_srm_task`】**。

### 坑 6 · 审批相关的需求，先分清哪部分是 DPS 配的
DPS 是外部引擎。**照着需求写代码但根本不生效**，是这类需求最常见的翻车方式。

### 坑 7 · 时间戳口径别用错
统计口径用的是**公示时间**（`127 已公示` 那一刻），不是签合同、不是付款、不是收货 **【实测：你在 06 需求确认过】**。
**【推测】** 因为公示是法律意义上"这笔采购落地"的唯一确定时点。

### 坑 8 · 跨服务调用（AIM）在编译期看不见
**【实测：代码库地图】** 公司自研的 AIM 机制不是标准 Feign，注解必须贴在接口上，
**改接口签名不会报错，只会运行时炸**。改任何 `@TypeMapping` 接口前先全库搜调用方。

# 十二、这个系统为什么长这样：设计推测集

> **本章整章都是 【推测】。** 是我根据代码里的证据反推的设计意图，**不是官方口径**。
> 我把每条的"证据"都写出来了，你可以判断我推得合不合理，也可以拿去和产品对。

## 12.1 为什么审批角色小得离谱（一个只有 2 个菜单）

**证据** **【实测】**：`采购方案审批` 86 菜单、`定标方案审批` 14、`费用审批` 21、
`专家抽取审批` / `终止公告审批` / `澄清公告审批` / `延期公告审批` / `供应商入围审批` **各只有 2 个**。
而 `采购管理` 一个角色 3896 个菜单。

**推测**：**这是"职责分离"（Segregation of Duties）在权限模型上的落地。**
审批权是**风险权**，必须能**精确地、单独地**授予某个人，而且**不能顺带给他别的权力**。
如果把"审批方案"塞进一个大角色里，那么授权给某人审批时，就顺手给了他一堆别的能力——这在审计上是不可接受的。

**反过来，"干活"的角色可以做得很大**，因为**干活本身不产生风险，产生风险的是"批准"**。

**佐证** **【实测】**：`企业-采购员` 岗位身上**一个采购审批角色都没有**；
`企业-采购主管经理` 岗位身上**一个 `采购管理` 都没有**。**系统从设计上就不允许同一个账号既编又批。**

## 12.2 为什么要"岗位"和"角色"两层，直接给用户配角色不行吗

**证据** **【实测】**：`ubm_member_job`(3880) → `ubm_job_role`(768) → `ubm_rbac_role_menu`(6409)。

**推测**：**因为人会变，岗位不会变。**
张三调走了、李四来接他的班——如果权限直接挂在人身上，就要一条条重配；
挂在岗位上，只要把李四放进"企业-采购员"这个岗位，权限自动继承。

**更重要的是审计视角**：出事时要回答"**当时是什么岗位的人批的**"，而不是"张三批的"。
**岗位这一层是给合规看的，角色这一层是给系统看的。**

## 12.3 为什么审批分"一级/二级"，规则却看不到

**证据** **【实测】**：有 `采购审批（一级）`(558 菜单) 和 `采购审批（二级）`(171)，
主管经理拿二级、业务负责人拿一级；但**代码里找不到"多少钱走几级"的判断**。

**推测**：**这个规则配在 DPS 工作流引擎里，不在我们的代码里。**
金额阈值、分支条件这类东西天生适合配置化——今天 50 万以上走一级，明年改成 100 万，
**如果写在 Java 里就要发版，配在流程引擎里改个参数就行。**

**这条推测对你很重要**：以后接到"审批规则要改"的需求，**先问是不是 DPS 配置**，别一上来就找代码。

## 12.4 为什么采购计划大半来自 SAP / SRM

**证据** **【实测】**：test 库 633 条计划中，招采自建 303、SRM 149、SCM 119、SAP 59、ERP 3。

**推测**：**因为这个平台不是"需求的源头"，是"寻源的执行器"。**
"要买什么"是在生产系统（SAP）和主数据系统（SRM）里产生的——车间提物料需求、库存低于安全线自动触发补货。
招采平台的职责是**接过这些需求，把它们变成一次合规的采购**。

**这解释了为什么"计划"这块的功能相对薄弱**（这次 37 个需求里几乎没有动采购计划的），
**而"方案→评标→定标"那一段功能密度极高**——**那才是这个平台的立身之本。**

## 12.5 为什么"随机抽专家"不用审批，"指定专家"要审批

**证据** **【实测】**：`ExtractTypeEnum` = `12 随机抽取` / `13 指定专家`；
`ExtractStatusEnum` 里有 `104 待指定抽取审批通过`；菜单里有独立的"专家抽取审批"。

**推测**：**"随机"本身就是一种防腐设计**——机器抽的，谁也操纵不了，所以不用额外监督。
**一旦人可以挑，就出现了寻租空间**（挑一个跟供应商有关系的专家），所以必须补一道批准。

**这条规律在整个系统里反复出现，你可以拿它当"预测器"**：
凡是**"人可以自由选择"**的地方，去找找是不是有一道审批。
比如：强制揭示（打开别人的密封文件）要审批、终止公告要审批、指定邀请供应商要审批。

## 12.6 为什么保证金有个"线下处理"状态

**证据** **【实测】**：`SourceDepositPushStateEnum` 里有 `101 线下处理`，和"待推送/推送中/已推送共享/推送失败"并列。

**推测**：**这是"系统对不上现实"时的逃生舱。**
财务共享接口不通、账户信息缺失、金额有争议——总有系统处理不了的情况，
这时候人工去线下退，系统只记一笔"这个走线下了"。

**没有这个状态，业务就会被卡死；有了这个状态，它就会变成一个黑洞**——
只要有逃生舱，人就会走逃生舱。**P1-06"保证金线上自动退费"本质上就是在堵这个洞。**

> 💡 **这类"逃生舱状态"在企业系统里非常常见**，看到就要警惕：
> **它往往是下一个需求的来源。**

## 12.7 为什么每一种公告都要单独审批

**证据** **【实测】**：延期公告审批、澄清公告审批、终止公告审批各有独立菜单和独立角色（各 2 个菜单）。

**推测**：**因为公告是"对外的、不可撤回的"。**
一旦挂出去，所有供应商都看到了，改口就是失信。
**延期**改变了游戏规则（有人来不及、有人正好赶上）；**澄清**可能实质性修改招标要求；**终止**直接取消了别人的机会。
**这三件事都可能被人拿来操纵结果**，所以每一件都要单独批。

## 12.8 为什么要有"监标人"这个角色

**证据** **【实测】**：菜单有"监标人列表""监标任务""设置监标人"；有角色 `采购寻源监标`；
有 `BidSuperviseStateEnum`（无需选择/待选择/已选择/需补选）。

**推测**：**采购员和专家都是"局内人"，需要一个"局外人"在场。**
监标人不打分、不决策，只是**在场并留痕**。
**"需补选"这个状态说明监标人是必须凑齐的**——**【推测】** 大概率是"某些金额以上的项目必须有监标人才能开标"。

## 12.9 为什么状态码从 101 开始，不是从 1

**证据** **【实测】**：几乎所有状态枚举都是 `101, 102, 103...`；报名状态是 `00, 01, 02...`；商城订单是 `101...115`。

**推测**：**三位数留了扩展空间，而且避开了"0/1 容易和布尔混淆"。**
从 101 起步还有个隐含好处：**`099` 可以塞在最前面**——
实际上 `SourceStateEnum` 里真有一个 `099 待发布采购公示`（单一来源专用）**【实测】**，
**明显是后来加的，为了排在 101 前面才用 099。**

> 🔑 **这个小细节告诉你一件事：状态码的数字顺序 ≈ 流程顺序。**
> 看到一个陌生状态码，先按数字大小猜它在流程的哪一段，八九不离十。

## 12.10 为什么不同模块的状态码不统一

**证据** **【实测】**：同样是"审批通过"，寻源侧 `104`、供应商侧 `106`、商城侧 `103`。

**推测**：**因为这几个模块是不同团队、不同时期做的。**
微服务的代价：各库各表各枚举，没有一个全局字典强制统一。

**对你的意义**：**这不是可以"顺手统一一下"的东西。**
状态码已经落在几十万行历史数据里，改一个值意味着刷全表 + 改所有查询 + 改所有前端。
**看到不一致，接受它，翻枚举表就好。**

## 12.11 为什么统计口径是"公示时间"

**证据** **【实测：你在 06 需求确认过】** 集采统计取 `state=127 已公示` 且按 `final_time` 公示时间落账。

**推测**：**因为公示是唯一一个"确定的、公开的、单一的"时点。**
合同可能拖几个月才签，付款可能分期跨年，收货可能延期——只有公示是钉死的。
而且从考核角度，集团问"今年做了多少集采"，要的是"**今年定下来多少**"，不是"今年付了多少钱"。

## 12.12 为什么商城要聚合京东、震坤行这些外部渠道

**证据** **【实测】**：`ProductChannelEnum` 有 ZY 自有框架 / JD 京东 / ZKH 震坤行 / XFS 鑫方盛 / OFS 欧菲斯 / XY 西域 / DL 得力 / IN 内部协同。

**推测**：**因为小额零星采购走招投标是不划算的。**
买 20 个订书机走一遍"公告→报名→开标→评标→定标→公示"，流程成本远超货值。
**所以集团的策略是：大额非标走招采平台，小额标准品走商城直接下单**——
而商城自己不备货，**它是个"带审批和对账的企业版比价下单入口"**，货从京东、震坤行那边来。

**这解释了 M 线那 11 个需求的共同主题**：搜索准不准、比价方不方便、目录管不管得住、对账顺不顺——
**全是"怎么让员工在商城上少花钱、财务少费事"，没有一个是"怎么招标"。**

## 12.13 为什么工作流引擎放在外面（DPS）

**证据** **【实测】**：`scm-workflow-all` 只是代理层，真引擎是 `dps.scmflow-*.jdsn.com/dps-service`。

**推测**：**因为流程是全集团共用的资产，不是招采平台一家的。**
OA、报销、人事……都要审批。做一个统一的流程平台，各业务系统调它，
好处是**审批体验一致、流程配置集中、审计口径统一**。
代价就是你现在感受到的：**很多"审批相关的需求"不在你能改的地方。**

## 12.14 为什么"写 MySQL、查 ES"

**证据** **【实测：系统地图】** 业务表在 MySQL，列表/报表查 ES，中间靠 XXL-JOB 同步。

**推测**：**因为这两件事的要求是矛盾的。**
写要求事务、一致、强约束（MySQL 擅长）；
查要求多条件组合、全文检索、跨表聚合、快（ES 擅长）。
**报表页面动辄十几个筛选条件，用 MySQL 做会把库拖死。**

**代价是"延迟"和"不一致"** —— 今天录的数据明天凌晨才进 ES。
**你以后碰到"页面上看不到刚录的数据"，第一反应应该是"同步任务还没跑"，而不是"代码有 bug"。**

## 13.3 卡住了怎么办

| 现象 | 最可能的原因 | 一条命令定位 |
|---|---|---|
| 左边菜单**根本没有**这一项 | 当前公司下的岗位不带对应角色 | `bash scripts/perm.sh can <菜单名>` → 告诉你该切哪家公司 |
| 想知道**这菜单要什么角色** | — | `bash scripts/perm.sh whichrole <菜单名>` |
| 菜单有、**列表是空的** | 角色有了但**数据权限**范围不对 | 换一家公司试；或看 `ubm_organization_*` |
| **审批待办里没有那条单子** | 流程没走到你这个节点 | 这是 **DPS** 外部引擎的配置，本代码库看不到 |
| **按钮点了没反应** | 状态机不允许（如方案没批就想发公告）| 查 `sc_scheme.state` / `sc_source.state` 对照第二章状态表 |
| **进不去专家门户** | 不在专家库 or 当前公司没挂专家岗位 | `bash scripts/perm.sh now admin` |
| **供应商看不到公告 / 报不了名** | 没入网、没入围、或不在邀请名单 | 查 `srm_apply` 状态是不是 `106 审核通过` |
| **突然变成"已流标"** | 有效供应商不够最少家数 | 招标/询价/竞价要 3 家，竞谈/竞磋 2 家，单一来源 1 家 |

## 13.5 这一章想让你带走的三句话

1. **"我该用哪个账号"这个问题，正确的问法是"我该用哪个账号 + 切到哪家公司"。** 岗位挂在公司上，切公司就是换身份。
2. **每做一步就跑一次那条查 `sc_source.state` 的 SQL。** 看着状态码从 101 一路走到 127，比读十遍流程图都管用。
3. **菜单看不见 ≠ 功能没做。** 九成是角色没配。先 `perm.sh can`，再去找人。
