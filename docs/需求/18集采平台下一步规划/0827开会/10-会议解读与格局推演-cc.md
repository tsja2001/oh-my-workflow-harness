## 2.3 ★ 招采平台 ↔ 冀东 SRM 现有集成链路（本次最值钱的一段情报）

这条链路以前你只能从代码里看到零碎的推送任务，**这次是双方当事人现场口述的完整版**：

```
① 供应商在【招采平台】入网
      ↓  招采只做"初审"（基础资质、基础信息）
② 审核通过 → 传【集团 MDM 主数据平台】
      ↓  SRM 定时拉取
③ 【冀东 SRM】落地为"潜在供应商"（无合作权限）
      ↓  走准入流程：资质审查 / 现场评审 / 样品确认 / 物料试用
④ 生效 → 形成【供应商-品类关系】（挂在三/四级末级品类上）

—— 以下是业务发生时的实时校验 ——

⑤ 冀东侧需求：ERP 建的生产物料（NC65 等）或 SRM 建的非生产物料 → 需求池
      ↓  采购按"品类分工"看自己权限内的需求 → 勾选 → 【推送阳光招采平台】
⑥ 招采生成需求/计划 → 转单 → 发布寻源 → 供应商【报名】
      ↓  招采把「供应商 + 物料明细行」推给 SRM
⑦ SRM 用物料反查末级品类 → 查「供应商-品类关系」的合作状态
      ↓  返回 合格 / 不合格
⑧ 招采【弹窗提示】不合格供应商 + 不合格的品类名称
      → 供应商可去 SRM 侧补充资料、追加合格品类，重新审
      → 否则报名审核不通过，不能报价
⑨ 定标 → 结果回推 SRM → SRM 继续走合同 / 订单 / 对账 / 付款（跟各企业 ERP 打通）
⑩ 绩效结果按周期取平均值传回集团
```

**这条链路解释了三件你以前只能猜的事：**
1. 为什么招采平台里有"SRM 计划"这个来源——第 ⑤ 步推过来的。
2. 为什么定标要推 SRM——第 ⑨ 步，SRM 要接着走履约。
3. 为什么入围审核这么绕——**因为品类粒度不一样**：招采按二级分类控，SRM 按三/四级控，所以"招采能看到 10 家都能报名，报完名才去 SRM 问合不合格"。邵总当场就说了：*"他有很多流程，一听就明显是为了两个系统。"*

### 这五条合起来意味着什么

> **现在这条"招采 ↔ SRM"链路，不是一个平台级能力，是一次一对一的板块定制。**

所以这次会上讨论的三种方案，**代价的一大半其实在招采平台这边**，会上没人说：

1. 两处 `BU004` 硬编码要改成**按板块可配**（哪些板块走 SRM 校验、哪些不走）
2. 每个板块的**品类粒度不同**（BU004 是三/四级，其他板块只到二级）→ `checkEnroll` 传的 `categoryCode` 语义要按板块分叉
3. 每个板块的**业务实体编码 `orgCode`** 和 MDM 映射要各自打通
4. 报名校验现在是**同步阻塞**（`throw new BusinessException(result.getData())` 直接把 SRM 返回的不合格信息抛给前端弹窗）——多板块之后，SRM 挂了会**卡死所有板块的报名**

> 💡 **这是你在这件事上最有价值的一句话，比会上任何人说的都具体：**
> *"现在招采和 SRM 的对接是给冀东发展（BU004）一个板块硬编码的，两个接口里都写死了 `BU004`。要推到集团 11 个板块，招采这边至少要做：板块可配、品类粒度按板块分叉、MDM 编码映射逐板块打通、以及给同步阻塞的报名校验加降级——**这部分工作量现在的 37 项计划里一条都没有**。"*

## 2.4 集采：一个会上没对上的隐性需求

甲方产品一号位提了**集团现在的三级集采体系**：

| 层级 | 谁在集采 |
|---|---|
| 一级 | 集团级集采 |
| 二级 | 各二级集团集采（冀东 SRM 里那个"集采目录"就是这一级） |
| 三级 | 区域 / 二级管理单位 / 单个企业的多项目打包集采 |

美云的回答是"靠 组织搭建 + 品类分工 + 用户权限 三件套实现"，甲方当场回了一句 **"和我刚刚说的需求不是很一样，行，那咱们继续吧"** —— **这条没对上，是个坑，会后要补。**

**但冀东侧白送了一个现成打法（值得记下来）**：
> 各企业 ERP 的物料编码各管各的（NC65 是集团级 ERP，但物料编码也分开管）。冀东在 SRM 里建了一套**「集采物料码」**：统一起一个集采物料名称 → 挂各企业 ERP 的多个物料码（多对一映射）→ **对外推招采用集采码，回来再映射回各企业自己的码**。

**这是解决"集团做不到物料大一统"的标准解法。** 不管最后买不买美云，这个思路你都能用。

## 2.5 会上白送的三份产品设计（不管买不买都能抄）

美云为了证明能力，把三块产品的**设计细节**当场讲完了。这三块正好对着你 CSV 里的三项：

**① 入围/准入标准 → 对应 CSV `P2-03 入围标准规则模板`（40 人天）**
- 把门槛做成**指标项**（注册资金、合规报告…），每个指标下配**分级**（100–500 万 / 1000–2000 万…），分级关联分数
- 供应商填完 → **系统自动评分**
- **AI 证照核验**：从工商局官网抓取的证照 vs 供应商填写的内容做一致性比对，把人工审核变成机器审核
- **策略加分项**：战略品类可加分，用于"自动准入前 N 名候选"

**② 供应商风险 → 对应 CSV `P2-06 天眼查对接`（35 人天）+ `P5-04 异常预警智能体`（29 人天）**
- 风险分**外部**（天眼查等三方）+ **内部**（跨系统：比如这家供应商在集团金融平台连续三个月贷款未按时还）
- 抓到后**分类打标签**（高/中/低）
- **每日简报**推送到责任人看板 / 系统首页
- **单据级闭环**：高风险在资格审核环节**直接阻断**；中低风险**填备注原因 + 挂审批附件**才放行

**③ 围串标识别 → 对应 CSV `P5-01 围串标审核智能体`（42 人天）**
美云现场投屏的规则清单（8 条）：
1. 同一供应商反复参与**同一发起人**发起的寻源（记次数）
2. **多个供应商组合**反复同时出现在同一标的
3. 同一标的**异常高分**（和第二名差距过大）
4. **定标总是同一家**（系统自动评分选 A，最终定了 A 以外的，发生过几次）
5. 人脸识别（已很少用）
6. **IP 地址**重合
7. 组织者与参与者**成对出现**
8. **投标资料 / 标书相似度**比对

美云还说了实现方式：*"目前是程序写死的，如果要，可以做成一个 AI 智能体单独部署，或者我们出方案交给招采的开发去实现。"*
→ **这等于免费给了你 P5-01 的需求规格书。**

**冀东天眼查的实际用法**（可对标你们现在的做法）：
- 股权穿透**上三层 + 下三层，共六层**；第四层数据量太大、重合度没意义，不查
- **不实时查**：先抓一次全量，之后业务量大就每天抓增量，业务量小就**每周抓一次增量**（因为接口按次收费）
- 只在**寻源阶段**卡关联关系，合同签订后不再控

# 三 · 真正的矛盾在哪（这场会的技术内核）

会上兜兜转转两个多小时，**其实一直在绕同一个矛盾的五个面**。

## 3.1 矛盾一：品类粒度 —— 全场最要命的一条

| | 金隅集团 / 招采平台 | 冀东 / 美云 SRM |
|---|---|---|
| 物料分类统一到 | **二级** | 在集团模板上**自己往下扩了三级、四级** |
| 供应商认证挂在 | 二级分类 | **末级品类（三/四级）** |
| 品类的作用 | 基本只是个标签 | **贯穿全平台**：准入审查项、绩效模型适用范围、寻源策略、物料匹配、采购人员分工，全挂在它上面 |

**三个致命细节：**
1. 美云的产品是**"基于品类管理的思维"**——"你的寻源需求 100 万做 IT 服务，通过金额+品类决定走什么寻源方式"。品类是这个产品的地基。
2. **金隅本次项目明确不做物料统一**。邵总原话：*"我们这次项目没有要把物料统一化的目标……集团以前讨论过大一统物料，基于成本和管理复杂度，最终还是没有这样做。"*
3. **更糟的一点**（江总指出的）：不同二级集团的**二级分类编码是一样的，但含义不同** —— 所以**根本没法共用同一棵品类树**。

**推论**：要么每个二级集团一棵独立品类树（= 必须真多租户），要么强行统一（集团不干）。**这一条直接决定了三种方案里哪个可行。**

## 3.2 矛盾二：管控模式（粗放统管 vs 精细直管）

- **招采平台**：集团统管，但**只管到寻源阶段**。定标之后的采购订单、履约数据，集团不统控。
- **冀东 SRM**：从需求管到付款，粒度细得多，且跟各企业 ERP 打通。

邵总的判断很直白：*"金隅冀东现在用这个平台，它的采购精细化管理程度其实是比集团招采平台要细的。集团统一化的话，这块确实是有矛盾，怎么权衡这两个事情，这是管理层面的问题，不光是软件的问题。"*

**把冀东退回粗放** → 不合适（人家已经用得好好的）。
**把集团升到精细** → 做不到（没有统一物料，也没打算接各企业 ERP）。

## 3.3 矛盾三：美云不是"真"多租户

美云的原话很关键：*"其实是可以做到多租户的权限管理，**只是说我们并不是传统的多租户的平台**，我们是通过集团级的组织去管理业务架构。"*

邵总在会后私聊里翻译成大白话：***"他妈没有严格的租户，他没这能力。"***

→ 所谓"隔离"是靠 **组织 + 功能权限 + 数据权限** 拼出来的，不是架构级租户隔离。这就是为什么会上要列三种方案。

## 3.4 矛盾四：供应商状态的"主控权"分散在两套系统

现在集团制度里其实是**三层**状态，散落在两边：

| 状态 | 严重度 | 谁触发 | 现在管在哪 |
|---|---|---|---|
| **黑名单** | 最重（围串标、徇私舞弊）→ 一黑俱黑，连准入都封 | 集团制度 | **招采平台** |
| **冻结** | 中（单笔业务配合不好、企业级）→ 只在该企业不能开新业务 | 企业 | **冀东 SRM** |
| **不良行为** | 轻（评价衍生结果）→ 打个标记，影响后续业务动作 | 评价 | 目前**两边都不完整** |

会上定的原则（邵总）：***"你得定一个主控的地方，主控的地方肯定是以细的那边儿为主，另外一边儿粗的地方是给他提供判断的依据数据。"***
江总更激进：***"所有的操作都移过来，因为你状态要统一管理。"***

**但没收口**。因为招采平台**必须**在寻源阶段拦截，SRM **必须**在履约阶段拦截 —— 结论大概率是「**两边都存一份，以细的那边为源，另一边订阅状态**」。

## 3.5 矛盾五：绩效要客观取数，就得接 ERP，而集团不接

冀东侧当场提了：*"合格率、准时交付这些节点，有了系统控制以后可以直接系统取数……当前这个模式，那就相当于这些取不到，需要人工去打分。"*

邵总的算账（**这段你要记住，将来会用上**）：
> *"这个评价的工作量会很大，按品类打分，如果是手动的话，我觉得**按年评一次就了不得了**……外头做得好的都是按季度或半年评一次，那是因为他们接了 ERP 能自动控很多数据。你没系统的话，就需要巨大的采购人力投入——采购部门得扒层皮，真没开玩笑。"*

**这直接影响 CSV `P2-04 供应商评价及年审功能`（38 人天）的可行性**：功能做出来了，但**没人有精力用**，最后就是一年评一次走过场。

## 3.6 一句话把五个矛盾串起来

> **金隅在采购上是"只管寻源的松管控"，美云 SRM 是"从需求管到付款的紧管控"。紧管控的地基是统一物料 + 统一品类 + 统一 ERP —— 这三样金隅都没有，而且本次项目也不打算做。**

邵总最精准的一句话是这个：
> *"咱们不用纠结他们所谓的 SRM 和咱们理解的 SRM 是不是一个 SRM。他这个东西我理解是个**采购平台**，不是一个真的供应商关系管理平台。你如果要集成的话，你要做很多流程上的拆解和处理。"*

# 四 · 三种落地方案（会上锁定，9 月出报价）

美云自己在会上把方案收敛成三条，甲方要求**三条都要报工作量和成本**（录音 49 明确）。

| | **方案一：独立部署** | **方案二：同底座、复制一套（≈ 租户）** | **方案三：在冀东这套上加一层集团** |
|---|---|---|---|
| **做法** | 把冀东这套完整复制，给金隅**独立部署一套** | 共用产品底座，**复制一套功能和数据**出来给金隅，金隅独立配置、独立二开、独立运维 | 不复制。在现有功能上**加一层"二级集团"组织维度**，冀东降为其中一个二级集团 |
| **美云自评** | **IP 风险和工作量最低、最快**。引用奇瑞案例：商用车上线成熟 → 复制给乘用车 → 再推第三个事业部 | 中等 | **代价最大**："涉及它所有的功能表"，冀东**全量数据要初始化一次**，冀东要**再切换一次**，影响在用业务 |
| **满足集团"集中管控"** | ✗ 部署多套没法统管 | ○ 一套应用两个租户，勉强 | ✓ 最符合 |
| **服务器** | 需迁回集团（现在在冀东"装备"机房；招采在阿里云，会上确认**不强制同云**） | 沿用冀东机房存疑，可能要迁 | 同左 |
| **你们内部真实态度**（录音 50） | — | 产品一号位："**咱们就用个租户嘛，最多就是用个租户**" | 邵总："**改造成本巨大无疑**""所有的单据数据都得初始化一次，你觉得这多少工作量？" |

**邵总对报价结果的预判（原话，很值得记）：**
> *"要么报价很高，要么他估错了，到最后他支持不了你，就只能慢慢地给你凑合着做。"*

**一个关键数字**：会后私聊里提到美云自己说**定制率 40%** —— 说明这产品**不是纯配置型**，大部分页面是开发出来的。邵总：*"招采和供应链平台基本上都是这样的，供应商评价那些绩效表，靠配置是配不出来的。"*

# 五 · 拆解需求：会后职责边界会怎么切

## 5.1 已经口头切定的（八九不离十）

| 能力 | 落在哪 | 依据（原话） |
|---|---|---|
| 寻源 / 开标 / 评标 / 定标 / 公示 | **招采平台，完全不动** | "后边的都不动""寻源我们现在的招采平台已经把所需要的寻源场景做完了" |

| 供应商**评价 / 年审 / 绩效 / 不良行为** | **全部搬到 SRM**，**替换**招采平台现有的评价功能 | 录音 49：*"评价是在 SRM 去做……包括年审、绩效管理那些东西全都在 SRM"* / 美云确认：*"评价要替换现有在招采的评价功能"* |

| ERP 对接 | **本期不做** | 邵总："你要 ERP 对接，集团那就更热闹了，我们这边有 SAP 有 NC" |
| **系统集成方式** | **只挂一个入口链接 + 单点登录**，不做菜单级深度集成 | 邵总（说得非常死）：*"招采菜单里只有一项，就叫供应商管理系统或平台，就那一项，**你别想把他这个目录给搬过去，你别想了**"* |

> **为什么不做菜单级集成**（邵总的理由，技术上完全成立）：菜单底层带着权限控制，搬目录 = 搬两套权限体系。*"要不然就让人家平台按咱们的权限控制改一遍，要不然招采平台的权限也按人家的。否则你就别这么搞了。"*

## 5.2 会上提出、但清单里没有的**新增需求**

1. **集团集采 / 二级集团集采的供应商库模型**（录音 49 结尾，甲方要求美云单独记一条）
   > *"可能会涉及到搭模型……集团集采供应商和二级集团集采供应商的管理，你们可能要单独搭出来一套模型。那个库在哪管、入口在哪。"*
2. **绩效指标的两层体系**（集团一级指标 + 二级集团细分指标）
   - 集团制度里定了 **3 个一级指标**，集团只要这 3 个一级指标的总分
   - 二级集团要按自己业务往下分二级、三级指标
   - 会上讨论到"给指标打标签/加指标层级"，美云说要在数据字典里加
   - **邵总当场承认没想好**：*"这两类指标儿怎么揉在一起，我现在没想好。"*
3. **集采物料码映射**（见 2.4）
4. **SRM 对接接口一整套**（招采侧要新写）

# 九 · 名词表（会上出现、你可能不熟的）

| 名词 | 大白话 |
|---|---|
| **SRM** | Supplier Relationship Management，供应商关系管理。但**美云这套实际是"采购全流程平台"**，比字面意思大得多 |
| **MDM** | 主数据平台。招采入网通过后先进 MDM，SRM 再从 MDM 定时拉 |
| **NC65** | 用友的集团级 ERP。冀东在用，但各企业还有自己的 ERP，物料编码不通 |
| **末级品类** | 品类树最底下一层。冀东是三/四级，集团是二级。**供应商认证挂在末级上** |
| **供应商-品类关系** | "这家供应商在哪些品类下是合格的"。招采校验报名资格时调的就是这张表 |
| **绩效模型** | 一套可配的评分表：适用哪些品类 + 适用哪些公司 + 几个维度 + 每个维度的权重 + 每个维度下的指标和权重 |
| **品类分工** | "哪个采购员管哪些品类"。冀东靠它控制谁能看到哪些需求、谁能寻源 |
| **集采物料码** | 建一个统一的集采物料名，多对一映射各企业 ERP 的物料码。解决"物料不统一"的标准打法 |
| **冻结 / 解冻** | 比黑名单轻一级的管控：临时不让这家供应商发生新业务，改善完再解冻 |
| **等保三级** | 国家网络安全等级保护第三级，政企系统的常见硬门槛。美云称已过 |
| **DMZ / 双域名隔离** | 供应商走外网域名（只开白名单接口），采购员走内网域名，两套接口互不可见 |
| **多租户** | 一套系统给多家客户用、数据互相看不见。**美云不是真多租户**，是靠组织+权限拼的 |
| **ABI** | 集团想统一用的 BI 工具（对应你们原计划里的帆软）。目前功能受限 |
| **定制率 40%** | 美云自称：这产品 40% 的功能是给客户定制开发的，不是配置出来的 |

# 十 · 写给你的一段大白话

**这场会你听着云里雾里是正常的**，因为会上有三层话在同时进行：

1. **产品层**（美云在讲他们能做什么）——这层最好懂，也最不重要，因为都是标准话术。
2. **架构层**（邵总在拆台）——这层最有价值。他一直在说同一件事：**这产品的地基（统一品类）金隅没有，硬接会很痛。**
3. **政治层**（会后私聊）——这层决定结果。核心是：**预算不高、需求没细化、领导要 9 月报价、技术负责人倾向自研、产品负责人想借力**。

**你需要在意的只有四件事：**

1. **供应商评价这块，很可能不归你写了**（搬去 SRM）——但**接口和拦截逻辑一定归你**。
2. **报表那两项（129 人天）的技术底座可能要换**（帆软 → ABI），**工作量会涨**。这条比 SRM 那摊子对你更直接。
3. **别指望这次会减少你的工作量。** 邵总那句"改造成本巨大无疑"是对美云说的，但对招采平台同样成立——**两套系统协同的成本，CSV 里一个人天都没估。**

4. ⭐ **你手上有一张会上谁都没打出来的牌**：现在的 SRM 对接是**给冀东发展一个板块硬编码的**（代码里两处 `BU004`），而平台有 **11 个板块**。
   这条不是判断、不是推测，是能指到文件行号的事实。会上所有人都在讨论"美云那边要改多少"，**没有一个人说招采这边要改多少**。
   把这条讲出来，你在这件事里就从"听会的开发"变成"提供关键输入的人"。

**最后一条建议**：录音 50 里邵总教了你们领导一招，你也可以学——
> **"做出来美不美观跟我没关系，跟我有关系的是工作量。你要用那个，对不起，你得多报人工。"**
>
> 把技术选型的**决策权和责任**交回给提要求的人，自己只负责**如实报代价**。这是在大集团里干活最实用的一条自保原则。
