# 大白话：本地把 source 跑起来，我到底做了什么

> 给谁看：你（不用懂 Java）。目的：看完知道"本地运行"是怎么回事、我干了哪几件事、中间有哪些坎、怎么迈过去的。
> 一句话结论：**你的 source 服务已经能在你自己电脑上跑起来了，连的是测试环境的配置和数据，跑的是你 `feature/taizhang-yang` 分支的代码，而且一行公司代码都没改。**

---

## 1. 先打个比方

把一个"服务"想成一台**咖啡机**：

- **源码** = 咖啡机的设计图纸和零件（`scm-source-all` 这个仓库）。
- **打包** = 把零件组装成一台能插电的成品机（打成一个 `.jar` 文件）。
- **运行环境** = 水、电、豆子从哪来（配置、数据库、缓存……这些不在你电脑上，在"测试环境"那栋楼里）。
- **点火启动** = 插上电、按开机键，机器转起来对外服务（监听 `8110` 端口）。

"本地运行"＝把这台咖啡机搬到**你自己桌子上**开机，而不是只能在机房里开。好处：改了图纸能马上在桌上试，不用每次都送回机房重装。

---

## 2. 你昨天最担心的那个问题：要依赖字典、身份、订单一堆模块，怎么办？

**答案：这些模块我根本没在你电脑上启动，而是直接"借用"测试环境里已经在跑的那几台。**

再用比方说：你只在自己桌上开了 **source 这一台咖啡机**。它偶尔需要"牛奶"（字典）、"门禁卡"（身份认证）、"糖包"（订单）——这些东西，测试环境那栋楼里本来就有现成的供应点，而且**你电脑的网络能直接连到那些供应点**（这一点我实测过，能连通）。所以 source 需要的时候，就顺着网线去测试环境那边现拿，用完就用完了。

- ✅ 好处：你电脑上只跑一台机器，轻，简单。
- ✅ 这也是为什么不用你把十几个服务都在本地开起来——那样电脑根本扛不住，也没必要。

> 一句话：**别的模块不在本地起，走测试环境现成的。**

## 3. 本地运行遇到的一串坎，和我怎么迈过去的

这套系统平时是"机房流水线（Jenkins）统一组装"的，**同事从来不在自己电脑上组装**。所以我一在本地组装，就接连撞上几个坎：

| 坎 | 大白话是啥意思 | 我怎么解决 |
|---|---|---|
| ① 下载零件被门卫拦了 | 组装要先下载一堆零件，公司的下载站被一道安全策略默认拦住了 | 给门卫递了张"通行条"（只改我自己电脑的一个设置文件，不动仓库） |
| ② 别的组给的零件是旧型号，对不上 | 你的代码用了新款接口，但我电脑缓存里存的还是别的团队的**旧版零件**，装上去对不齐 | 把这些零件换成**测试线上正在用的那批新版**（同样只换我电脑缓存里的，换之前都留了备份） |
| ③ 零件都装上了，机器却打不着火 | 组装（编译）通过了，一按开机却报"缺个零件"。因为开机时要把每根线都过一遍，才发现还有几根旧线没换 | 把机器**实际用到的所有旧零件一次性全换新**，再打火就着了 |
| ④ 别把临时机器并进正式电网 | 机器一开机，默认会"上报"说"我也能对外供电"，这样测试环境可能把真实请求导到你电脑上，很危险 | 开机时加了个开关：**只许它用电、不许它并网供电**（它能去调用别人，但不会把自己登记进去顶替线上那台） |

全部迈过之后，机器就在你桌上稳稳转起来了：`8110` 端口能访问，日志打印"启动成功"。

## 4. 最后交代三件你会关心的事

1. **一行公司代码没改。** 上面所有"换零件、递通行条"都发生在**你自己电脑的缓存和开机参数**这一层，两个代码仓库检查过都是干净的，不会污染提交。
2. **可回滚。** 换掉的零件都留了原件备份，随时能还原。
3. **连的是共享测试数据。** 你在本地的增删改，是**真写进测试库**的——查看没问题，删除/批量改这类要小心（详见同目录《12-日常运行与安全注意》）。

## 5. 附：技术要点

都知道"这套代码本地全量编译是坏的、大家从不本地编译"。所以真正会好奇的是：**你怎么绕过依赖版本对不齐、还能连着 test 跑起来、又没动代码？**

### 5.1 一段可以直接说的话（口头版）
> "没在本地起那一堆依赖服务，是让本地这台**指到 test 的 Nacos**，配置、库、中间件全从 `scm-jdsn-test` 拉，别的服务（认证/字典/订单）直接调 test 集群现成的——集群 pod IP 从本机能通。启动加了 `register-enabled=false`，**只做消费者、不注册进服务发现**，所以不会抢流量。编译那关，就是你们说的跨团队 SNAPSHOT 漂移——我把用到的跨团队包的 **`-TEST-SNAPSHOT` 版用 `install:install-file` 塞进 plain 坐标**，没动 pom 也没动 BOM。还有个坑是编译过了启动照样报 ClassNotFound，因为 Feign 启动要解析整个接口，所以我把 fat jar 里**捆绑的跨团队包一次性全对齐**到 test，才起来。全程两个仓库 0 diff。"

### 5.2 技术要点
- **运行环境**：`APP_PROFILE=test` 走 `scm-jdsn-test` 命名空间；`-Dnacos.ip=10.0.54.16:30996` 顶掉代码里那个集群内、本机 DNS 解析不了的 nacos 地址。配置/DB/ES/Redis/MQ 全来自 Nacos，本机 resources 只有 bootstrap。
- **不污染服务发现**：`-Dspring.cloud.nacos.discovery.register-enabled=false` → 本机只订阅、不注册。日志里服务名册只有集群实例（`172.50.29.139`），本机不在内，测试流量不会被导过来。
- **跨团队 SNAPSHOT 漂移的解法**：Nexus 每个 `com.pcitc` 包并存 `plain / -TEST / -UAT / -PROD-SNAPSHOT` 四条线；plain `1.0.0-JDSN-SNAPSHOT` 早就陈旧，而分支代码是按 test 线的跨团队 API 写的。做法 = 把这些包的 `-TEST-SNAPSHOT` 内容 `mvn install:install-file -Dversion=1.0.0-JDSN-SNAPSHOT` 装进 **plain 坐标**（改本机 `.m2`，`.orig-bak` 备份），reactor 解析到的就是自洽的一套。**不改 pom、不改 BOM、不改 version。**
- **编译过 ≠ 能启动**：`mvn install` 只校验被引用到的符号；Feign 在启动时 `parseAndValidateMetadata` 会解析接口**所有方法**的入参/返回类型，Spring 也会实例化全部 bean，于是暴露编译期没碰到的类（本次 `ProfessorDTO`）。所以对齐范围要覆盖 **fat jar `BOOT-INF/lib/` 里捆绑的全部跨团队 `com.pcitc` 包**（实测约 120 个里 75 个有 test 版），不能只补编译报错那几个。
- **http-blocker**：本机 Maven 3.8.7 默认 `maven-default-http-blocker` 拦公司私服 http，在 `~/.m2/settings.xml` 加了个同名覆盖的 mirror 放行（只动个人 settings，非仓库）。
- **代码零改动**：适配全部落在三处——本机 `.m2` 缓存、外部 `-D`/环境变量、分支切换。两个业务仓 `git status` 全程干净。

### 5.3 
- **"那你不会把流量引到你机器上吧？"** → 不会，`register-enabled=false`，只消费不注册；名册里没有本机。
- **"改 pom/BOM/配置了吗？"** → 没有。跨团队包是用 `install:install-file` 把 test 版塞进 plain 坐标，坐标名没变，pom 不用动。
- **"依赖那么多服务你都本地起了？"** → 没有，一个都没在本地起，全调 test 集群现成的（pod IP 本机可达）。
- **"定时任务、MQ 会不会影响 test？"** → 完整实例确实带 xxl-job 执行器和 MQ 能力，做长期本地开发时会用启动参数把这两个关掉（仍不改代码），日常读接口不触发。见《12》。
- **"这套能沉淀吗？"** → 能，可复现步骤在《10 §A》，对齐脚本都在，换台机器照做即可。
