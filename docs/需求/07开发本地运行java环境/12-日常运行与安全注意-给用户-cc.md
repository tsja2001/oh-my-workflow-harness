## 一、平时怎么用（这些基本都是 AI 帮你做，你只需知道流程）

日常一个来回就三步，**你负责说要改啥、看效果；技术活我全包**：

1. **改代码** —— 你提需求，我改 source 里对应的代码。
2. **重新编译 + 打包 + 点火** —— 我来：把改动重新编译成新包，再启动。
   - 你想自己按也行，命令都在《10 号 §A.3 / A.4 / A.5》，一条条能跑。
3. **看效果** —— 服务跑在 `http://localhost:8110/scm-source-web`。
   - 直接调业务接口要带 **token**（跟你平时用系统一样，需要登录凭证）。你告诉我要试哪个接口，我用你的 test token 帮你调，把结果给你。

> 要停：让我停，或关掉那个运行终端即可。要重启：让我重启（或照 §A.5）。

## 二、⭐ 会不会在服务端被发现"异常访问"？（老实说明）

结论：**不会做"偷偷摸摸/越权"的事，但因为连的是共享测试环境，会留下一些正常痕迹，个别后台联动要留个心。** 分四点说清：

### ✅ 1. 不会顶替线上、不会把测试流量导到你电脑
开机时我加了"只用电、不并网"的开关（技术上叫关掉服务注册）。所以：
- 你的电脑**不会**被登记进测试的"服务名册"；
- 测试环境**不会**把真实请求派发到你电脑上；
- 也不会顶替机房里那台正牌 source。
- （我在成功日志里确认过：服务名册里只有集群那台 `172.50.29.139`，没有你电脑。）

### ⚠️ 2. 你的增删改是"真的"写进共享测试库
本地连的是**共享的测试数据库 / 搜索引擎**。你在本地点的"新增/修改/删除"，都是**真写进测试库**的，而且会以你登录用的那个账号留下痕迹（谁创建的、操作日志里记着）。
- **看数据、调查询接口** → 随便，几乎无影响。
- **删除、批量改、审批流转** → 动手前想清楚，最好先跟我说一声。这不是"异常访问"，但确实会改动大家共用的测试数据。

### ⚠️ 3. 两个"后台联动"可能会碰到测试环境（要用时先告诉我）
一台完整的 source 实例，除了对外服务，还带两个后台能力，理论上会和测试环境联动：
- **定时任务（xxl-job）**：本地实例启动后，可能被测试的"定时任务调度台"当成一个可用执行器，从而被派活（在你电脑上跑某个定时批处理）。
- **消息队列（MQ）**：本地实例可能加入测试的消息消费组，**分走一部分本该给测试的消息**。
- 影响面：日常"点点看、调查询接口"一般**不会**触发这两个；但如果你要专门测"定时跑批""发消息触发"的功能，就可能碰到。
- 👉 **要更干净很简单**：你要测这类功能时先告诉我，我给本地**关掉这两个联动**（只加启动参数，依然不改代码），就完全不影响别人了。
- 说明：这次那台已经停了；MQ 那次的日志尾巴我没抓全、日志现已清掉，所以我用"可能"来讲——真要长期本地开发，我建议默认就把这两个关掉，最保险。

### ✅ 4. 调字典/身份/订单，就是正常接口调用
source 需要这些服务时，是带着你的 token 走正常接口去调的，跟你平时用系统本质一样，只是"发起方"从机房变成了你电脑。不是越权、不是异常。

> 一句话总结：**读随便、写小心、批处理/消息类要测先招呼一声；要绝对干净我能一键关掉那两个联动。**

## 三、推代码要注意什么

1. **本地那些"换零件、递通行条"的操作不会跟着代码走。** 它们只在你电脑的本地缓存和开机参数里，**不进 git、不会污染提交**，放心。
2. **提交仍走你们原来的规矩**：feature 分支开发 → 合并进 test → Jenkins 部署。我会按团队的 `enterprise-dev-workflow` 流程来，你的习惯不用变。
3. **我提交前会核一遍**：只提交真正的业务改动，不夹带本地运行产生的临时文件（编译产物、缓存等本来就被忽略）。
4. **分支别搞混**：现在源码在 `feature/taizhang-yang`。要切别的分支跑，告诉我，我确认工作区干净再切，不会弄丢你的东西。

## 四、出问题怎么办

- 起不来、报错、接口不通 → 让我看日志，我能定位卡在哪一步（编译缺零件 / 启动缺类 / 连不上某服务，各有明显信号）。
- 想确认"本地这次有没有影响测试环境" → 让我查启动日志里的注册/消费情况，我如实告诉你。
- 想把本地跑法配进 IDEA（点个按钮就启动）→ 告诉我，我一步步带你配（参数见 §A.5）。
