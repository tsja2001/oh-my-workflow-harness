## 0. 先看一张总图（心里有个骨架再往下读）

```text
   你（或Postman/前端）发一个 HTTP 请求
        │  POST /api/centralized-procurement-report/sync  {startTime,endTime}
        ▼
 ① Controller  （门口/按钮）      CentralizedProcurementReportController
        │  把参数交给下一层
        ▼
 ② Service 接口（能力清单）        CentralizedProcurementReportService
        │  声明"我能同步"，但不写怎么做
        ▼
 ③ ServiceImpl（真正干活的厨房）   CentralizedProcurementReportServiceImpl
        │   ├─ 用 Mapper 查 MySQL（主单表 + 物料表）
        │   ├─ 用 Feign 查板块字典
        │   ├─ 把每条物料拼成一个"ES记录对象"(Model)
        │   └─ 用 Repository 一次性写进 ES
        ▼
 ④ Model（ES记录的模子）+ ⑤ Repository（写ES的手）
        ▼

  另外还有 ⑥ SourceChaseConfig（配置搬运工）：告诉 Model 到底往哪个 ES 索引写，
```

一句话概括这次做的事：**加了一个"按一下，就把数据库里的非平台采购单搬进 ES"的按钮**，以及它背后的一整套配套零件。

## 1. 新手第一疑惑：为什么要新建这么多文件？一个不行吗？

你在 Node 里，可能一个 `index.js` 就把"路由 + 逻辑 + 查库"全写完了。Java（Spring）不这么干，原因有两条：

**(1) Java 的硬规矩：一个 `public class`（类）必须单独一个同名文件。**
`CentralizedProcurementReportModel` 这个类，就必须放在 `CentralizedProcurementReportModel.java` 文件里，文件名和类名一字不差。所以"有几个类"基本就等于"有几个文件"。这不是我们讲究，是 Java 语言强制的。

**(2) 企业项目讲究"分层"，每层各司其职。** 用开餐厅打比方：

| 角色 | 餐厅比喻 | 我们的文件 |
|---|---|---|
| Controller | 服务员：只负责接单、报菜名，不下厨 | `...Controller.java` |
| Service 接口 | 菜单：写着"本店能做哪些菜" | `...Service.java` |
| ServiceImpl | 厨师：真正按菜谱做菜 | `...ServiceImpl.java` |
| Mapper / Repository | 库管：只负责从仓库取货/放货 | 复用现成的 Mapper + 新建的 Repository |
| Model | 菜品摆盘规格：一盘菜长什么样 | `...Model.java` |

为什么非要拆这么细？因为**改动可控、谁坏了一眼看得出来**。以后要改"查询条件"，只动厨师（ServiceImpl）；要改"接口地址"，只动服务员（Controller）；互不牵连。这也是这个项目里所有功能的统一写法，我们照着来，别人一看就懂，不会觉得"这段代码是外人写的"。

> 小结：**5 个新文件不是我随意拆的，是 Java 规矩（一类一文件）+ 项目统一分层习惯的自然结果。** 我们只是照葫芦画瓢，跟旁边的"老交易报表"长得一模一样。

## 2. 逐个文件：它是谁、为什么要有它、关键在哪

下面**按"从外到内"的调用顺序**讲（请求先到谁、再到谁）。

### 2.1 ① Controller —— 对外的"门口 / 按钮"

文件：`controller/CentralizedProcurementReportController.java`

- `@RestController`：告诉 Spring"这个类是对外的 HTTP 接口集合"。≈ Express 里你用 `router` 挂路由。
- `@PostMapping("/api/centralized-procurement-report/sync")`：定义一个 POST 接口和它的路径。≈ `app.post('/api/.../sync', ...)`。
- `@RequestBody(required=false) DateRangeParam param`：把请求体里的 JSON（`{"startTime":"...","endTime":"..."}`）自动变成一个 Java 对象 `param`。`required=false` 表示"不传也行"。
- 里面那个 `DateRangeParam` 小类 + `@JsonFormat(pattern="yyyy-MM-dd HH:mm:ss")`：规定日期字符串长什么样，方便 JSON 自动转成 Java 的 `Date`。

**这个文件只做一件事**：拿到参数 → 转手交给 Service → 把结果（写了多少条）包成统一格式 `Result` 返回。它不查库、不写 ES，就是个"传话的门童"。

### 2.2 ② Service 接口 —— "能力清单 / 菜单"

文件：`service/CentralizedProcurementReportService.java`

它里面只有一行"声明"：`int syncCentralizedProcurementData(Date startTime, Date endTime);`——只说"我能同步，给我起止时间，我还你一个写入条数"，**但不写具体怎么同步**。

≈ TypeScript 里的 `interface`。你可能会问：既然啥都不干，为什么还要单独一个文件？两个原因：
1. 这是 Spring 项目的通用写法（面向接口），别人都这么写，我们保持一致。
2. **以后加"定时任务"时**，定时框架（XXL-JOB）就是靠在这个接口上打标签来找到方法的。现在先留个位置，阶段二再往上加标签，不用回头动结构。

新手阶段：**你就把它理解成"菜单占位"，照抄即可，不必纠结。**

### 2.3 ③ ServiceImpl —— "真正干活的厨房"（这是核心，重点看）

文件：`service/impl/CentralizedProcurementReportServiceImpl.java`

**先说 `@Autowired` 是什么**（新手必懂）：
类顶部有一堆 `@Autowired private XxxMapper xxx;`。这叫"依赖注入"——你只要声明"我需要这个工具"，Spring 启动时会**自动帮你 new 好、塞进来**，你直接用就行。≈ Node 里 `const db = require('db')` 然后就能用，只不过这里是框架自动"require + 实例化"。

这个厨房手里有 5 样工具（都是自动注入的）：

| 工具 | 干嘛的 | 类比 |
|---|---|---|
| `supplierGreenChannelMapper` | 查 MySQL 的"主单表" | 查库的 DAO |
| `supplierChannelProjectsMapper` | 查 MySQL 的"物料明细表" | 查库的 DAO |
| `dictFeignService` + `innerFeignService` | 去别的服务查"板块字典" | 调用别的微服务的 HTTP 客户端 |
| `centralizedProcurementReportRepository` | 往 ES 写数据 | 写库的 DAO |

**核心方法 `syncCentralizedProcurementData` 的五步**（这就是整个功能的灵魂）：

1. **定时间**：没传日期就默认"昨天一整天"；传了就用传入的范围。（`calculateYesterdayDate/getStartOfDay/getEndOfDay` 这几个私有小方法就是干这个的。）
2. **查主单**：用 `LambdaQueryWrapper`（≈ 查询构造器，像 knex 的链式 `.where()`）拼出条件——审批通过(101) + 采购分类是集采(101/102/103) + 审批时间在范围内——然后 `selectList` 查出一批主单。
3. **查物料**：把这些主单的 id（`channelId`）收集起来，**一次性**把所有物料查回来（而不是"一个单查一次"，避免慢）。再用 `groupingBy` 按 `channelId` 把物料分到各自主单名下。
4. **查板块字典**：调一次 UBM 字典服务，拿到"板块编码→标准名称"的对照表（`queryOwningplateDictMap`）。为什么要它？因为主单表里存的板块名是脏的（同一个板块有好几种叫法甚至空的），得用编码去字典里换成统一的标准名。
5. **拼装 + 写入**：双层循环——**每个主单 × 它的每条物料 = 一条 ES 记录**。挨个 `model.setXxx(...)` 把字段填好（字段对照见下面第 3 节），塞进一个大 `List`，最后 `repository.saveAll(list)` **一次性全写进 ES**。

几个私有小方法（都是打杂的）：
- `buildId(...)`：拼主键 = 采购业务编号 + 物料编码。
- `resolvePurchaseType(isJc)`：是集采→"集团集采"，否→"分散采购"。
- `resolveBuName(...)`：用编码去字典换标准板块名，换不到就用原名兜底。

### 2.4 ④ Model —— "ES 里一条记录的模子"（和 ES 的关系全在这）

文件：`model/CentralizedProcurementReportModel.java`

这个类不干活，它只是**规定"存进 ES 的一条记录长什么样"**，一共 18 个字段（板块、企业、供应商、物料、金额、时间……）。≈ 前端你熟悉的 **Mongoose 的 Schema**：定义好结构，数据库就按这个结构存。

三个关键注解：
- `@Document(indexName = "...")`：说明"这类对象存到 ES 的哪个索引里"。（索引 ≈ MySQL 的一张表。）
- `@Field(type = FieldType.Keyword/Text/Date/Double/Integer)`：每个字段在 ES 里是什么类型。
- `@Id`：**哪个字段是主键**。我们用 `id`（=业务编号+物料编码）。主键的作用很关键：`saveAll` 写入时，**主键相同就覆盖、不同才新增**——所以同一条物料重复同步只会覆盖自己，不会变两条。这就是"幂等"，也是我们能放心重复跑的原因。

其中 `@Document` 里那串 `#{@sourceChaseConfig.getCentralizedProcurementReportIndex()}` 很重要——它表示"索引名不写死在代码里，而是运行时去配置里取"。**这正是要配 Nacos 的根源**，第 4 节细讲。

### 2.5 ⑤ Repository —— "往 ES 写的那只手"

文件：`repositories/CentralizedProcurementReportRepository.java`

它是个**空接口**，只写了 `extends ElasticsearchRepository<Model, String>`，里面一个方法都没有。为什么空的也能用？因为 Spring Data 会**自动帮你生成实现**，`saveAll`、`findById` 这些方法凭空就有了。≈ Mongoose 里 `const Model = mongoose.model(...)` 之后，`Model.save()` 自带，你没写过它的代码。

新手阶段：**你就理解成"声明一下就白得一个写 ES 的工具"，照抄即可。**

### 2.6 ⑥ SourceChaseConfig —— "配置搬运工"（这次是改，不是新建）

文件：`config/SourceChaseConfig.java`

这个类**本来就存在**，我们只加了一行字段：`private String centralizedProcurementReportIndex;`。
它头上有 `@ConfigurationProperties(prefix = "source.chase.es")`，意思是"把配置里 `source.chase.es.` 开头的值，自动填到这个类的同名字段上"。所以配置里写 `source.chase.es.centralizedProcurementReportIndex = xxx`，这个字段就会自动等于 `xxx`。

配合 `@Data`（Lombok）自动生成的 `getCentralizedProcurementReportIndex()` 方法，第 2.4 节 Model 上那串 SpEL 就能取到真正的索引名了。链条是：

```text
Nacos 里配的值  →  填进 SourceChaseConfig 的字段  →  getter 取出来  →  Model 的 @Document 拿到索引名  →  知道往哪个 ES 索引写
```

## 3. 字段对照表：一条物料是怎么变成一条 ES 记录的

这是第 2.3 节第 5 步"拼装"的明细。左边是 ES 字段，右边是从哪取的：

| ES 字段 | 从哪来 |
|---|---|
| `id`（主键） | 主单.采购业务编号 + 物料.物料编码（直接拼） |
| `buCode` / `buName` | 主单.bu_code / 用 bu_code 查字典得到的标准名 |
| `purchaseCompanyName/Code` | 主单.company_name / company_code |
| `supplierName` / `supplierCode` | 主单.supplier_name / three_in_one_id_code（统一社会信用代码） |
| `planCode` / `planName` | 主单.purchase_business_code / purchase_business_name |
| `materialCode` / `materialName` | 物料.product_code / product_desc（长描述） |
| `categoryCode` / `categoryName` | 物料.category_code / category_name（可空） |
| `taxTotal` | 物料.total_price（每条物料自己的含税总价） |
| `bookTime` | 主单.update_time（审批结束时间） |
| `isCentralized` | 主单.is_jc（1 是 / 0 否） |
| `purchaseType` | 由 is_jc 派生：是→集团集采，否→分散采购 |
| `dataSource` | 固定 `FP`（非平台录入） |

## 4. 我们的代码和 ES 到底是什么关系

**ES（Elasticsearch）是什么？** 你就理解成一个"专门为查询和搜索优化过的数据仓库"，像一个超强的搜索引擎版数据库。

**为什么报表不直接查 MySQL，非要多一个 ES？** 因为这张大报表要汇总 5 类来源，数据分散在不同的表、甚至不同的微服务里，页面临时跨库现查会又乱又慢。所以做法是：**每类来源各自把数据"复制+翻译"成统一格式，堆到同一个 ES 索引（公共货架）上**，以后页面只查这一个货架。

**我们这次的代码，在整条链路里只干"往货架上摆货"（写入）这一段**：

```text
MySQL(非平台的主单+物料)  ──我们的ServiceImpl复制并翻译字段──►  ES 的集采报表索引
                                                                    ▲
                          （以后阶段三：report 服务从这里查、前端展示）
```

注意：**"复制"不是"搬走"**。MySQL 里的原始业务数据一直都在、是真身；ES 里只是为报表准备的一份副本。报表只读 ES，不会反过来改业务数据。

Spring 这边的分工也就对上了：**Model = 货品标签（长什么样）**，**Repository.saveAll = 摆货动作**，**索引名 = 摆到哪个货架**（来自配置）。

## 5. 为什么要配 Nacos？我该怎么配？

### 5.1 Nacos 是个啥

**Nacos = 一个"集中放配置的服务器"（配置中心）。** 类比：与其把 `.env` 塞在每个项目里，公司把所有服务的配置统一放到一个远程中心，服务一启动就去那里把自己的配置拉下来。

**为什么索引名不写死在代码里，非要放 Nacos？** 因为有三套环境：test / uat / prod，每套的索引名后缀不一样（比如测试是 `..._test`）。如果写死在代码里，就没法"同一份代码，部署到不同环境用不同索引"。放 Nacos 就能"代码不变，各环境配各自的值"。

### 5.2 这次为什么"必须"配（不配会怎样）

回顾第 2.4/2.6 节那条链子：Model 的索引名 ← `sourceChaseConfig` 的字段 ← Nacos 的值。
**如果 Nacos 里没配这个值**，那字段就是空（null），Model 就不知道该往哪个索引写，**服务启动时会直接报错、或建不出索引**。所以这一步是部署前的硬前提。

### 5.3 一步步怎么配

1. **打开 Nacos 控制台**。地址/账号见 `ai-docs/creds.env`（配置服务器是 `10.0.54.19:8848`，控制台一般是它的 `/nacos` 页面；不确定就问同事要一下入口）。
2. **选对环境**：命名空间（namespace）选 **`scm-jdsn-test`**，分组（group）是 **`common`**。
3. **找到对的那份配置文件（dataId）**：最稳的办法是——在配置里**搜 `tradeDataReportIndex`**（那是已有的"老交易报表"索引名）。它在哪个文件里，我们要加的新配置就加在**同一个文件、同一段 `source.chase.es:` 下面**。
4. **加一行**（注意 YAML 靠缩进对齐，要和上面 `tradeDataReportIndex` 那行对齐）：
   ```yaml
   source:
     chase:
       es:
         tradeDataReportIndex: index_web_trade_data_test          # ← 这行是已有的，别动
         centralizedProcurementReportIndex: index_centralized_procurement_report_test   # ← 加这行
   ```
   （实际文件里多半是紧凑写法，你就找到 `tradeDataReportIndex` 那一行，在它下面照着缩进加一行即可。）
5. **点"发布"保存。**
6. 建议：改完配置后**让服务重新部署一次**再验证（索引名这种启动时才用到的配置，重启生效最稳）。

> 如果你在 Nacos 里怎么都找不到 `tradeDataReportIndex`，说明它可能在共享配置 `global-config.yaml` 里，或者需要同事给你看具体是哪个 dataId——这时候把这段发给同事问一句就行。

## 6. 把所有文件串成一场"电影"（60 秒回放）

```text
1. 你 POST /api/centralized-procurement-report/sync  {startTime,endTime}
2. Controller 收到，转成 Date，交给 Service
3. ServiceImpl 开工：
     算时间 → 查主单(Mapper) → 查物料(Mapper) → 查板块字典(Feign)
     → 每个主单的每条物料拼成一个 Model → saveAll
4. Repository 把这批 Model 写进 ES（索引名来自 Nacos → SourceChaseConfig → Model）
5. ES 里出现一条条报表记录；主键相同的会覆盖（重复跑不重复存）
6. Controller 返回："同步成功，写入 N 条"
```

## 7. 名词小抄（Java/Spring/ES ↔ 你熟悉的 Node/前端）

| 这里的名词 | 作用 | Node/前端类比 |
|---|---|---|
| `class` + 一类一文件 | 代码的基本组织单位 | 一个模块，但强制单独文件 |
| `@RestController/@PostMapping` | 声明 HTTP 接口 | Express 的 router / app.post |
| `@RequestBody` | 请求体 JSON → Java 对象 | `req.body` 自动解析 |
| Service 接口 + Impl | 先声明能力，再写实现 | TS interface + class |
| `@Autowired` | 自动把依赖塞进来 | require 并自动实例化 |
| `LambdaQueryWrapper` | 拼 SQL 查询条件 | knex 链式 query builder |
| Mapper | 查/写 MySQL 的入口 | DAO / ORM 方法 |
| `@Document/@Field/@Id` | 定义 ES 记录结构和主键 | Mongoose Schema |
| `ElasticsearchRepository` | 自带 save/saveAll 写 ES | Mongoose Model 自带 .save() |
| `@ConfigurationProperties` | 把配置值注入字段 | 读 .env / config 对象 |
| Nacos | 远程集中配置中心 | 远程 .env 服务 |
| ES 索引 | 存一类数据的地方 | 约等于一张表 / 一个集合 |
