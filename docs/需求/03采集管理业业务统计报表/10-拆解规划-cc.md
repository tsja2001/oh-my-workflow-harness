```text
JD 机电四大类 ┘
```

## 2. 招采平台的数据长什么样（用大白话讲一遍）

一笔招采平台的业务，在系统里是这么一层层套下去的：

| 层 | 页面上叫什么 | 库里的表 | 一条代表什么 |
|---|---|---|---|
| 1 | 招标/询价/谈判/磋商/单一来源 的列表行 | `sc_source` | 一个**采购方案**（谁采购、什么名字、什么时候公示的） |
| 2 | 详情页里的"定标方案"列表 | `sc_deal_result` | 一份**定标方案**（有审批结果，可能被拒绝后重做，所以一个方案可能有好几份） |
| 3 | "定标结果展示"里合并单元格那一行 | `sc_deal_detail` | 一家**中标供应商**（带这家的中标总金额、第几标段） |
| 4 | "定标结果展示"里的每一行物料 | `sc_deal_product` | 一条**中标物料**（物料编码、描述、物料组、这条的含税金额） |

**报表一行 = 第 4 层的一条中标物料。** 你在页面上看到的"阶段1/阶段2/阶段3"，库里叫 `tender_num`（标段号）。

## 3. 14 个字段的最终取值（每条都核实过）

| 报表列 | 从哪取 | 证据 |
|---|---|---|
| 板块名称 | `sc_source.bu_code` → 查 `Owningplate` 字典取标准名 | 同 FP；主表 `bu_name` 是脏的（BU004 有"冀东集团"/"冀东发展"多种写法） |
| 板块编码 | `sc_source.bu_code` | 实测有值 |
| 采购企业 / 编码 | `sc_source.purchase_company_name` / `purchase_company_code` | 列表页"采购企业"列绑 `requestPurchaseCompanyName`，后端两个分支都赋 `purchaseCompanyName` |
| 供应商 / 编码 | `sc_deal_detail.supplier_name` / `supplier_code` | 定标结果里的"中标供应商"，实测形如 `JYJT0003481` |
| 采购方案/订单编号 | `sc_source.scheme_code` | 列表页"采购方案编码"列 |
| 采购方案名称 | `sc_source.scheme_name` | 列表页"采购方案名称"列 |
| 物料编码 | `sc_deal_product.product_code` | 导出代码 `productItemArr[0]=getProductCode()` |
| 物料描述 | `sc_deal_product.product_desc` | 导出代码 `productItemArr[1]=getProductDesc()` |
| 类目描述 | `sc_deal_product.category_name` | 导出代码 `productItemArr[2]=getCategoryName()`，表头就叫"物料组名称" |
| 类目编码 | `sc_deal_product.category_code` | 上一条的相邻字段，实测 100% 有值 → **不用调 mdm 接口** |
| 交易金额（含税） | `sc_deal_product.tax_total`（**待确认，问题 2**） | 需求原文写的是供应商级的"中标总金额" |
| 公示/下单时间 | `sc_source.final_time` | 列表页"公示时间"列绑 `finalTimeStr` |
| 是否集采 | `sc_scheme.is_collection` | 需求指定的详情页字段，第一期已核实同一链路 |
| 采购业务类型 | 由上一条派生：1→集团集采，0→分散采购 | 同 FP 规则 |
| 数据来源 | 固定 `ZC` | 读侧已支持转成"招采平台" |

**过滤条件**

```text
sc_source.state = '127'（已公示）
sc_source.purchase_method IN ('101' 招标, '102' 单一来源, '103' 询价, '104' 竞争性谈判, '105' 竞争性磋商)
sc_source.final_time 在同步区间内（首次补数从 2026-01-01 起）
sc_deal_result.state = '104'（审批通过），同一方案取最新一份
sc_deal_detail.is_win_bid = 1
```

## 5. 两个问题会影响什么（说明为什么值得问）

- **问题 1（主键）**：不改的话，那 9 单里有 1 单会从 3 行变 1 行，金额从 1070.9 元变成只剩一笔。等真实业务上来，多供应商分标是招采平台的常态，丢的会更多。
- **问题 2（金额）**：如果按需求字面取"中标总金额"，一家供应商中 3 个物料就把钱算 3 遍。目前 test 里 2026 年的 9 单每家供应商恰好只中 1 个物料，所以**用哪个口径结果都一样，看不出差别**——这正是必须提前问清楚的原因。

## 3. 同步算法

```sql
-- 1. 主单
SELECT * FROM sc_source
WHERE state='127' AND purchase_method IN ('101','102','103','104','105')
  AND final_time BETWEEN :start AND :end;

-- 2. 是否集采
SELECT scheme_id, is_collection FROM sc_scheme WHERE scheme_id IN (:schemeIds);

-- 3. 定标方案（审批通过，同方案取 create_time 最新一份）
SELECT * FROM sc_deal_result WHERE scheme_id IN (:schemeIds) AND state='104';

-- 4. 中标供应商
SELECT * FROM sc_deal_detail WHERE deal_result_id IN (:dealResultIds) AND is_win_bid=1;

-- 5. 中标物料
SELECT * FROM sc_deal_product WHERE deal_detail_id IN (:detailIds);
```

`delete_sign` 不用手写：`bootstrap.yml` 配了全局逻辑删除字段 `deleteSign`，MyBatis-Plus 自动加条件（FP 实现也是这么写的）。

## 6. 已知边界

- `final_time` 只是"公示时间"。若一个单子公示后又改了定标数据，按公示时间扫增量会漏掉这次修改——和 FP 用 `update_time` 是同类边界，本期不额外处理。
- test 里 2026 年后只有 9 单 11 行，页面数据会很少，这不是代码问题。
- 一个采购方案若有多份"审批通过"的定标方案（目前实测没有），只取最新一份，历史那份不进报表。
- 招采平台不加"采购业务分类"过滤，范围比非平台录入宽（见问题 3.2）。
