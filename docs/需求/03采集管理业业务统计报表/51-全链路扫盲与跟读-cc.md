# 第一部分：先回答你的问题

## 1.1 你的理解对不对？

你说的是：

> 先在 source 里取数据（同事写了从 order 里取数据），然后存到 es 里，然后再 report 里查数据

**主干完全正确。** 这就是这套东西的骨架，你抓住了最重要的东西。

要补三个细节，补完你的图就完整了：

**补充一：不是"两个服务"，是"五个搬运工"**

不是 source 和 order 两家。是**五个数据来源，各写各的搬运代码**，但都往同一个 ES 索引里写：

| 来源 | 编码 | 谁写的 | 在哪个服务 | 从哪张表捞 |
|---|---|---|---|---|
| 非平台录入 | FP | 你（AI 代写） | `scm-source-all` | `sc_supplier_green_channel` + 物料明细表 |
| 招采平台 | ZC | 你 | `scm-source-all` | `sc_source` → `sc_deal_*` 四张表 |
| 煤炭SAP | MT | 你 | `scm-source-all` | `sc_source_collection`（`data_source='SAP'`）|
| 机电四大类 | JD | 你 | `scm-source-all` | `sc_collection_daily_amount_ledger` |
| 云采平台 | YC | 同事 | `scm-order-all` | 订单相关表 |

你负责 4 个，同事负责 1 个。你们在**两个不同的 Git 仓库**里各写各的，互不影响，唯一的约定是「往同一个索引写、字段名和类型必须一模一样」。

**补充二：中间那步不只是"存"，是"摊平 + 翻译"**

数据从 MySQL 到 ES 不是原样搬。做了两件事：

1. **摊平**：MySQL 里是一层套一层的（一个采购方案 → 几家中标供应商 → 每家几个物料），ES 里是**一条物料一行**，全部拍平成一张大表。
2. **翻译**：把编码翻成人看得懂的名字（`BU002` → `水泥集团`），把 `1/0` 翻成业务含义（`is_jc=1` → `集团集采`）。

这是整个设计的核心。后面 3.5 节会讲为什么必须这么做。

**补充三：还有第四段，前端**

完整是四段：

```
MySQL ──①写入──→ ES ──②查询──→ report 服务 ──③HTTP──→ Vue 页面
        (source)         (report)                    (前端仓库)
```

你参与了①②③全部。

## 1.2 那个"笑话"其实不是笑话

你说你问同事「SQL 要手动执行吗，不会自动建表吗」，觉得丢人。

**这个问题问得完全合理**，而且你恰好踩在一个真实存在的不一致上：

| | 要不要手动 | 为什么 |
|---|---|---|
| **MySQL 建表** | **要手动执行 SQL** | 这个项目没装自动迁移工具 |
| **ES 建索引** | **不用，自动的** | 代码里 `@Document` 注解一写，服务启动时框架自动去 ES 建好 |

**同一个需求里，一半自动一半手动**。你会困惑太正常了。

再说 Node 那边：Prisma / Sequelize / TypeORM 都自带 migration，`npx prisma migrate deploy` 一条命令，表就建好了。你的直觉「不是应该自动吗」来自那个世界，没错。

Java 也有对应的东西（Flyway、Liquibase），**只是这个项目没用**。为什么不用，两个现实原因：

1. **生产库权限是分开的**。开发碰不到 prod 库，只有 DBA/运维能执行。自动迁移意味着"应用一启动就改生产库结构"，很多公司不接受这个风险。
2. **团队习惯**。发版时 SQL 是一个单独的交付物，交给负责人统一执行、统一回滚。

所以这个项目的规矩是：**代码你提交，SQL 你写好存档，发版时人工执行。** AGENTS.md 里"发版纪律"那条说的就是这个 —— 每条执行过的 SQL 都要存进需求文件夹的 `sql/`，因为上生产时要交给别人重放一遍。

> 记住这句话，以后不会再问错：
> **这个项目里，数据库结构靠人手动执行 SQL；ES 索引结构靠代码自动创建。**

# 第二部分：业务扫盲 —— 这报表到底在解决什么问题

## 2.1 一句话

**领导想知道：全集团这段时间，从哪些供应商、买了什么东西、花了多少钱。**

问题在于这些钱花在五个完全不同的系统里：

- 走招标流程的（招采平台）
- 线下谈完了补录进系统的（非平台录入）
- 电商化直接下单的（云采平台）
- 从 SAP 拉过来的煤炭采购（煤炭SAP）
- 机电公司每天报的汇总台账（机电四大类）

五个系统，五套表结构，五种叫法。领导要的是**一张表**。

这就是这个需求的全部意义：**把五种形状的数据，捏成同一个形状，放进同一个筐，让人能一起查、一起导出。**

## 2.2 "一行"到底代表什么（最容易搞错的地方）

报表的一行**不是**一笔采购业务，而是 **"某一笔业务里，某个供应商中标的某一个物料"**。

举个真实例子（test 库里的真数据）：

```
采购方案 12870012-XJ-2026-0001（一次询价采购）
  └── 中标物料"倒焰窑85矾土块料"，3 家供应商分着中标：
        ├── 江苏鱼跃医疗设备股份有限公司   300.00 元
        ├── 中国工艺集团有限公司           100.00 元
        └── 唐山明诚矿业有限公司           670.90 元
```

**这一笔业务，在报表里占 3 行。** 三行的方案编号一样、物料一样，只有供应商和金额不同。

为什么这么设计？因为报表要按供应商统计金额。合并成一行的话，另外两家供应商的钱就没地方放了。

**这个认知直接决定了主键怎么设计**，也是我这次开发发现的两个大坑的根源（后面 4.4 节）。

## 2.3 五个来源的"形状差异"有多大

这是为什么这个需求"看起来简单做起来复杂"的真正原因：

| | 招采平台 ZC | 非平台 FP | 煤炭SAP MT | 机电 JD |
|---|---|---|---|---|
| 一条原始数据是 | 一个采购方案 | 一个补录业务 | **一天的一条收发流水** | 一天的一条汇总 |
| 要展开几层才拿到物料 | **4 层** | 2 层 | 0 层（本身就是物料级）| 0 层（**根本没有物料**）|
| 有没有业务名称 | 有 | 有 | **没有，得拼** | **没有，得拼** |
| 有没有板块名称 | 有（但是脏的）| 有（但是脏的）| **全是 NULL** | 有 |
| 时间字段叫什么 | `final_time` 公示时间 | `update_time` | `final_time` | `statistic_date` 统计日期 |
| 是否集采从哪来 | 查 `sc_scheme` 表 | 主表 `is_jc` 字段 | **固定"是"** | **固定"是"** |

五个来源，五种取法。**代码里那五个 `syncXxData` 方法，差异全在这张表上。**

# 第三部分：技术扫盲 —— 用你熟悉的 Node 世界做锚点

这一部分是你说的"非代码类技术知识"。每个概念我都给一个 Node 类比，**并说明类比在哪里会失效**（类比用错比不用更危险）。

## 3.1 微服务：为什么有几十个仓库

你的 Koa 项目大概是一个 repo、一个进程、一个 `npm start`。

这套系统是**几十个独立的服务**，每个是一个独立的 Java 进程，跑在自己的容器里：

```
scm-source-all     采购寻源服务   ← 你主要在这里干活
scm-report-all     报表查询服务   ← 你也改了这里
scm-order-all      订单服务      ← 同事的地盘
scm-ubm-all        用户/组织/字典服务
scm-gateway-all    网关
... 还有 20 多个
```

**Node 类比**：像你把一个 Koa 大项目拆成 20 个小 Koa 服务，各自 `npm start`，互相通过 HTTP 调用。

**类比边界**：Node 微服务通常各自有各自的数据库。这套系统里**多个服务共用同一个 MySQL 库**（`scm_source_test`）。所以你会看到 `scm-report-all` 也能读到 source 的表 —— 这在纯粹的微服务架构里算"不规范"，但企业系统里非常常见。

## 3.2 一个仓库里的几十个"模块"

打开 `scm-source-all`，你会看到 47 个子目录：`scm-source-bid`、`scm-source-deal`、`scm-source-chase`……

**这些不是 47 个服务**，它们最终打包成**一个** Java 进程。

**Node 类比**：像 monorepo 里的 workspace packages。`packages/user`、`packages/order`……最后一起构建成一个 app。

它们的关系在 `pom.xml` 里声明（相当于 `package.json` 的 `dependencies`）：

```
scm-source-chase/pom.xml 里写了依赖 scm-source-source、scm-source-deal、scm-source-scheme
→ 所以 chase 模块的代码可以 import 那三个模块的类
→ 这就是为什么这次我不用改 pom：要用的 Mapper 早就在依赖里了
```

**为什么你的代码写在 `scm-source-chase`**：chase = "追数据"，这个模块专门放"从业务表捞数据同步到 ES"的逻辑。同目录下 `TradeDataReportServiceImpl` 就是同事以前写的同类东西。

## 3.3 Maven ≈ npm，但有个大坑

| npm | Maven |
|---|---|
| `package.json` | `pom.xml` |
| `node_modules/` | `~/.m2/repository/`（**全机器共用一份**，不是每个项目一份）|
| `npm install` | `mvn install` |
| npm registry | 公司私服 Nexus |
| `1.0.0-beta.3` | `1.0.0-JDSN-SNAPSHOT` |

**SNAPSHOT 是那个大坑。** 它相当于 npm 的 `latest` tag —— 版本号不变，内容随时会变。

于是就出现了工作规范里那条：**"同事从不本地编译"**。

原因：你本地 `~/.m2` 里的 `scm-source-source-1.0.0-SNAPSHOT.jar` 可能是三个月前下载的，而别人的源码早就改了。你本地全量编译，会在**别人的文件**里报一堆错 —— 不是你的问题，是你手里的 jar 过期了。

**所以我们验证代码的方式是"隔离编译"**：不管整个项目编不编得过，只把**我们改的那几个文件**拿出来，对着真实依赖单独编一遍。零报错 = 我们的代码是健全的，剩下的交给 Jenkins（它每次都拉最新的构建）。

这次三期开发，每次收工我跑的就是这个，退出码 0。

## 3.4 Spring 注解：那些 `@` 符号是干嘛的

Koa 里你要手动组装：

```js
const service = new UserService(db)
router.post('/users', ctx => service.create(ctx.request.body))
```

Spring 里你不组装，**你贴标签，框架自己组装**：

| 注解 | 意思 | Koa 对应 |
|---|---|---|
| `@RestController` | 这个类是对外的接口入口 | `router` |
| `@PostMapping("e/business/...")` | 这个方法处理这个 POST 路径 | `router.post('/path', fn)` |
| `@Service` | 这个类是干活的，**请框架帮我造一个实例** | `new XxxService()` |
| `@Autowired` | **请框架把那个实例塞给我** | 手动 `require` + 传参 |
| `@Data`（Lombok） | 自动生成 getter/setter | JS 对象天然就有属性 |

**核心区别叫"依赖注入"**：你从来不写 `new`，框架启动时扫描所有 `@Service`，造好实例，然后按类型塞进所有 `@Autowired` 的字段里。

**在哪扫描的？** [SourceWebConfig.java:16](01zhaocai-end/scm-source-all/scm-source-web-jar/src/main/java/com/pcitc/scm/source/webconfig/SourceWebConfig.java:16)：

```java
@ComponentScan(basePackages = {
    "com.pcitc.scm.source.*.controller",
    "com.pcitc.scm.source.*.service",   // ← 你的 ServiceImpl 因为这行被扫到
    ...
})
@MapperScan(basePackages = {"com.pcitc.scm.source.*.repositories"})  // ← Mapper 因为这行
```

**这解释了一个你可能困惑的事**：为什么我写完 `@Service` 就能直接用，不用在任何地方"注册"一下？因为包路径匹配上了，框架自动扫到。反过来，**如果你把类放错包**（比如放到 `com.pcitc.scm.source.chase.util`），它就不会被扫描，运行时报"找不到 bean"。

## 3.5 MySQL vs ES：为什么要两套，不能直接查库？

这是整个架构里最值得理解的一个决策。

**MySQL** = 你熟悉的关系型数据库，业务系统的"真相源头"。所有增删改都在这。

**Elasticsearch** = 搜索引擎。可以粗暴理解成"一个为查询优化过的、极其快的大 JSON 集合"。

**为什么不直接查 MySQL 出报表？** 三个理由，从弱到强：

1. **要跨 5 个系统**。五个来源的表结构完全不同，直接 join 出一张统一报表，SQL 会写成噩梦，而且云采的数据根本在另一个服务的表里。
2. **要展开成一行一物料**。招采平台要 4 层展开（方案→定标方案→供应商→物料），每次查报表都实时 join 四张表 + 翻字典，慢且重。
3. **报表查询会拖垮业务库**。领导拉一次全年报表，扫几十万行，正在下单的人跟着卡。

所以做法是：**把"算好、拍平、翻译好"的结果预先存进 ES，报表只读 ES，完全不碰业务库。**

**Node 类比**：像你在 Koa 里为了首页性能，把几张表 join 好的结果预先算进 Redis，前端只读 Redis。

**类比边界**：Redis 是纯 KV，ES 能全文搜索、能分页排序、能聚合统计 —— 它更像"一个只读的、超快的、能模糊搜中文的数据库"。

**代价**（这个必须知道）：ES 里的数据是**快照，不是实时的**。MySQL 改了，ES 不会自己变，要等下次同步任务跑。所以报表数据永远比业务系统"晚一点"。这是这类设计的固有取舍，不是 bug。

## 3.6 ES 里的东西长什么样

不用背术语，看一条真实的（我从 test 上查出来的）：

```json
{
  "_index": "index_centralized_procurement_report_test",   // 索引名 ≈ 表名
  "_id": "10930000-XJ-FPT-2026-00285467890",               // 主键
  "_source": {                                             // 真正的内容
    "buName": "水泥集团",
    "purchaseCompanyName": "唐山市盾石信息技术有限公司",
    "supplierName": "北京金隅数智科技有限公司",
    "planCode": "10930000-XJ-FPT-2026-0028",
    "materialName": "电脑",
    "taxTotal": 339000.0,
    "bookTime": "2026-07-10T01:20:10.000+00:00",
    "dataSource": "FP"
  }
}
```

对照记忆：

| ES | MySQL |
|---|---|
| index 索引 | table 表 |
| document 文档 | row 行 |
| field 字段 | column 列 |
| `_id` | 主键 |
| mapping | 表结构 |

**`_id` 是理解这次两个大坑的钥匙**：ES 写入时，**`_id` 相同就覆盖，不同就新增**。没有"重复主键报错"这回事，它默默覆盖。

所以主键设计错了 → 数据被悄悄吃掉 → **不报错，你还以为成功了**。这两个坑后面 4.4 讲。

## 3.7 网关：为什么接口路径长成那样

前端不直接连 20 个服务，只连一个**网关**（`10.0.54.16:32740`）。网关看路径，转发给对应的服务。

```
浏览器 → http://10.0.54.16:32740/gateway/e/business/source/centralizedProcurementReport/syncZc
                                          └─ 网关看这段，转发给 scm-source-web 服务
```

**Node 类比**：nginx 反向代理，或者 API Gateway。

**这里有个已经踩过的坑**（写在工作规范 §3）：网关**不剥前缀**。Controller 里必须把完整路径写全：

```java
@PostMapping("e/business/source/centralizedProcurementReport/syncZc")   // ✅ 网关能路由到
@PostMapping("/api/trade-data-report/sync")                             // ❌ 路由不到，404
```

`scm-source-chase` 里那个老的 `TradeDataReportController` 用的就是 `/api/...`，**那是同事留的本地调试入口，网关根本走不到**。写新接口别照抄它。

**还有一个更阴的坑**：往网关发一个不存在的路径，可能返回

```json
{"status":true,"code":"000000","data":"ok"}
```

看着像成功，其实是网关的兜底响应。**判断接口通没通，要看返回内容是不是你自己接口该返回的东西**，不能只看 `status:true`。

## 3.8 Nacos：配置中心

代码里索引名不是写死的：

```java
@Document(indexName = "#{@sourceChaseConfig.getCentralizedProcurementReportIndex()}")
```

这个值从 **Nacos** 里读。Nacos 是个网页，运维在上面填配置，服务启动时去拉。

**Node 类比**：`.env` 文件 + dotenv，但是**放在服务器上集中管理的**，改完不用重新打包，服务能热更新。

**为什么要这样**：test / uat / prod 三套环境的索引名不一样（`..._test` / `..._uat` / `..._prod`）。写死的话每个环境得打包三次。

配置在哪：[bootstrap-test.yml:5-8](01zhaocai-end/scm-source-all/scm-cloud-source/src/main/resources/bootstrap-test.yml:5) 指明了 Nacos 地址和命名空间 `scm-jdsn-test`。

## 3.9 XXL-JOB：定时任务

**Node 类比**：`node-cron`，但是**独立的一个管理后台**，谁都能在网页上配、能看执行日志、能手动触发一次。

这个项目的调用方式有点绕，值得知道（不然你看不懂那串参数）：

XXL-JOB 后台配一个任务，handler 填 `simpleJobHandler`，参数填：

```
source-centralizedProcurementReportService-syncZcData-{}
```

这串东西被 [XxlJobExecutorServiceImpl.java:28](01zhaocai-end/scm-assemblies-all/scm-scheduling-all/xxl-job-executor/src/main/java/com/pcitc/scm/xxljob/executor/service/impl/XxlJobExecutorServiceImpl.java:28) 按 `-` 切成 4 段：

| 段 | 值 | 含义 |
|---|---|---|
| 1 | `source` | 发给哪个服务 |
| 2 | `centralizedProcurementReportService` | 哪个 Service（对应代码里 `@TypeMapping`）|
| 3 | `syncZcData` | 哪个方法（对应 `@MethodMapping`）|
| 4 | `{}` | 参数 JSON |

**这解释了代码里那两行注解为什么存在**：

```java
@TypeMapping("centralizedProcurementReportService")   // 类上
@MethodMapping("syncZcData")                          // 方法上
```

没有它们，XXL-JOB 找不到该调谁。

**也解释了为什么参数只能传 `{}`**：按 `-` 切割，而日期 `2026-01-01` 里全是 `-`，传进去会被切碎。所以定时任务固定同步前一天，指定日期补跑只能走手动接口。

## 3.10 Jenkins / Docker / K8s：代码怎么变成线上服务

你点一下 Jenkins 的"构建"，背后发生的事（从 [Jenkinsfile](01zhaocai-end/scm-source-all/scm-cloud-source/Jenkinsfile) 里读出来的）：

```
1. 拉代码        git clone，切到 test 分支
2. 编译          mvn clean install -U          ← 打成 jar 包
3. 镜像构建      docker build                  ← jar + JDK + 配置 → 一个"集装箱"
4. 镜像推送      docker push 到公司镜像仓库
5. 部署          kubectl apply                 ← K8s 拉新集装箱，替换旧的
```

**Node 类比**：
- **Docker 镜像** ≈ 把 `node_modules` + Node 运行时 + 你的代码，一起冻成一个文件，保证"在我机器上能跑"= "在服务器上能跑"
- **K8s** ≈ pm2 的集群版，管着几十个容器的启动、重启、扩容、滚动更新
- **Jenkins** ≈ GitHub Actions，只不过是公司自己搭的

**为什么必须是你点，不是我点**：Jenkins 要登录、有权限，而且部署是**对外有影响的动作**。这也是 AGENTS.md 里那条红线的由来。

**排错去哪看**：KubeSphere（K8s 的网页控制台），能看容器日志。服务起不来、报错，去那看。


**为什么 Service 要拆成"接口 + 实现"两个文件？** 你在 Node 里不会这么写。原因有二：一是 Spring 的很多能力（事务、AOP）依赖接口；二是 XXL-JOB 的 `@MethodMapping` 注解贴在接口上。**照着现有代码的样子写就行，不用纠结。**

**四个 `syncXxData` 方法的共同套路**（读一个就懂全部）：

```
1. 处理时间参数    没传 → 默认昨天；只传开始 → 补当天结束
2. 查主数据        LambdaQueryWrapper 拼条件 → mapper.selectList()
3. 查关联数据      分批查（500 一批），避免 IN 条件太长
4. 转换            for 循环，一条一条 new Model()，setXxx() 赋值
5. 写 ES           分批 saveAll（1000 一批）
6. 返回条数
```

**`LambdaQueryWrapper` 是什么**（MyBatis-Plus 的查询构造器）：

```java
LambdaQueryWrapper<Source> q = Wrappers.lambdaQuery();
q.eq(Source::getState, "127");          // WHERE state = '127'
q.in(Source::getPurchaseMethod, list);  // AND purchase_method IN (...)
q.ge(Source::getFinalTime, start);      // AND final_time >= ?
List<Source> list = sourceMapper.selectList(q);
```

**Node 类比**：knex 的链式调用 `knex('source').where('state', '127').whereIn(...)`。

**类比边界**：`Source::getState` 这个写法是 Java 的"方法引用"，框架靠它反查出数据库列名 `state`。好处是改字段名时编译器会报错，不像字符串拼 SQL 那样运行时才炸。

**有个隐藏行为必须知道**：`bootstrap.yml` 里配了全局逻辑删除

```yaml
logic-delete-field: deleteSign
logic-delete-value: 1
logic-not-delete-value: 0
```

意思是：**只要实体类里有 `deleteSign` 字段，MyBatis-Plus 会自动在每条查询后面加 `AND delete_sign = 0`**，你不用写。

这次做煤炭SAP 时这条差点要命：`sc_source_collection` 表的 `delete_sign` 列**全是 NULL**（2792 行无一例外）。如果实体类里有这个字段，自动加上 `delete_sign=0` 之后 **一条都查不到**。万幸 `SourceCollection.java` 里没定义这个字段，所以不会加。我实测确认过才敢往下写。

**在 IDEA 里怎么验证这类事**：打开 `SourceCollection.java`，`Ctrl+F` 搜 `deleteSign`，搜不到 = 不会自动过滤。

`Ctrl+B` 点进 `getCentralizedProcurementPageList`，到 [SourceMetaQueryServiceImpl.java:1618](01zhaocai-end/scm-report-all/scm-report-source/src/main/java/com/pcitc/scm/report/source/service/impl/SourceMetaQueryServiceImpl.java:1618)。

这个方法就干一件事：**把前端传的条件，翻译成 ES 的查询语句**。

```java
BoolQueryBuilder bl = QueryBuilders.boolQuery();   // 一个"条件容器"

// 数据权限：只能看自己有权限的公司
if (Boolean.TRUE.equals(sourceChaseConfig.getUsePerssion())) {
    List<String> r = reportFacedAdapter.getPermissionCompanyIds();
    if (!r.isEmpty()) {
        bl.must(QueryBuilders.termsQuery("purchaseCompanyCode", r));
    }
}

// 企业名称：模糊匹配
if (StringUtils.isNotBlank(param.getPurchaseCompanyName())) {
    bl.must(QueryBuilders.matchQuery("purchaseCompanyName", param.getPurchaseCompanyName())
            .operator(Operator.AND));
}

// 板块：精确匹配
if (StringUtils.isNotBlank(param.getBuCode())) {
    bl.must(QueryBuilders.termQuery("buCode", param.getBuCode()));
}
```

**`must` = SQL 的 AND。** 每个 `if` 判断"前端传了这个条件吗"，传了才加进去。

**`matchQuery` 和 `termQuery` 的区别 —— 这是 ES 最核心的概念，务必搞懂：**

| | `termQuery` | `matchQuery` |
|---|---|---|
| 含义 | **精确相等** | **分词后匹配** |
| SQL 类比 | `= 'BU002'` | 类似 `LIKE '%唐山%'`（但更聪明）|
| 用在什么字段 | `keyword` 类型 | `text` 类型 |
| 本报表里 | `buCode`、`dataSource` | `purchaseCompanyName`、`supplierName` |

**为什么名称类字段要用 match**：ES 会把"唐山市盾石信息技术有限公司"用中文分词器切成「唐山 / 市 / 盾石 / 信息 / 技术 / 有限公司」这些词存起来。你搜"盾石"，能命中。如果用 `termQuery`，必须一字不差输入整个公司名才能查到 —— 那就没法用了。

`.operator(Operator.AND)` 的意思是：**你输入的词必须全部命中**。搜"唐山盾石"，切成「唐山」「盾石」，两个词都得有。不加这个默认是 OR，搜"唐山盾石"会把所有带"唐山"的公司都查出来。

> 这一条是踩过坑改过来的：早先的实现用了短语查询，导致输入公司简称查不到。现在实测简称能查到，不存在的名字返回 0 条。

## 4.4 重点：这次开发发现的两个"会悄悄吃数据"的坑

这两个是这次开发最有价值的部分，也最能体现"为什么需要人去核实数据而不是照着需求写"。

### 坑一：招采平台，同一物料多家供应商分标

**表面**：主键定为「采购方案编号 + 物料编码」，看起来天经地义。

**真相**：同一个方案的同一个物料，**可以被多家供应商分着中标**。

实测 test 库：方案 `12870012-XJ-2026-0001` 的物料 `260101010002`，3 家供应商各中 300 / 100 / 670.9 元。历史数据里同一组合最多重复 **7 次**。

**后果**：3 条数据主键完全相同 → 写进 ES 互相覆盖 → 只剩 1 条 → 报表少 2 行，金额从 1070.9 变成只剩一笔。**而且不报任何错。**

**解法**：主键改成「方案编号 + 标段号 + 供应商编码 + 物料编码」。

### 坑二：煤炭SAP，按天拉的流水

**表面**：跟其他来源一样，「订单号 + 物料编码」。

**真相**：SAP 数据是**按天拉的收发流水**，同一订单的同一物料**每天一条**。

实测：订单 `4500931416` 的「烟煤^4500~5000kcal」，从 1 月 9 日到 27 日 **18 条**，每天金额 2.9 万到 40 万不等。

**后果**：18 条压成 1 条。全量算下来 503 条会掉到 375 条。

**解法**：主键加上公示日期 → 「订单号 + yyyyMMdd + 物料编码」。加完实测 503 条 → 503 个不同主键，0 碰撞。

### 这两个坑教给你的方法论

**需求文档描述的是"页面上看到什么"，不是"数据库里长什么样"。** 产品看到详情页一个物料一行，不会知道底下是三家供应商分标。

所以拿到需求后必须做的一件事：**用真实数据验证主键会不会重复**。一条 SQL 的事：

```sql
SELECT 主键的那几个字段, COUNT(*) c
FROM 表 WHERE 过滤条件
GROUP BY 主键的那几个字段 HAVING c > 1;
```

返回空 = 安全。返回有数据 = 会丢行。

**以后遇到任何"往 ES/Redis 里按主键写"的需求，这条 SQL 都该跑一遍。**

```
          浏览器 → /procurementScheme/index.html#/reportForms/centralizedProcurement

【第 5 步】前端发查询
          POST /e/business/report/source/centralizedProcurementPageList
          { currentPage:1, limit:10, model:{ purchaseCompanyName:"唐山" } }
                    ↓ 网关转发给 scm-report-web 容器（注意：另一个服务）

【第 6 步】SourceMetaQueryServiceImpl.getCentralizedProcurementPageList()
          ① 拼 ES 查询条件：权限过滤 + matchQuery(企业名) + 时间范围
          ② 按 bookTime 倒序、分页
          ③ elasticsearchOperations.search() 执行
          ④ 返回 PageList

【第 7 步】前端拿到 JSON，渲染表格
          dataSource: "MT"  → dataSourceMap 转成 "煤炭-SAP"
          isCentralized: 1  → 显示 "是"
          bookTime          → moment 格式化成 "2026-01-27 00:00"

【第 8 步】用户点导出
          POST .../centralizedProcurementDownload
          → 复用第 6 步的查询（limit 改成 10000）
          → convertDataSource("MT") → "煤炭-SAP"
          → EasyExcel 生成 xlsx → 浏览器下载
```

**整条链路跨越**：2 个 Java 服务 + 1 个 Vue 前端 + 1 个 MySQL + 1 个 ES + 1 个网关 + 1 个字典服务 + 1 个定时任务平台。

这就是为什么你觉得复杂 —— **它确实复杂**，这是企业系统的常态。

# 附：名词速查

| 名词 | 一句话 | Node 类比 | 类比边界 |
|---|---|---|---|
| Spring Boot | Java 的 Web 框架 | Koa / Express | 靠注解自动装配，你不写 `new` |
| Maven | 依赖管理 + 构建 | npm | `~/.m2` 全机器共享一份 |
| SNAPSHOT | 会变的开发版本号 | `latest` tag | 是本地编译坏掉的元凶 |
| MyBatis-Plus | 操作数据库的库 | knex / Sequelize | 用方法引用而非字符串指字段 |
| Mapper | 一张表的操作接口 | knex 的 `table()` | 只写接口不写实现，框架生成 |
| Entity / Model | 一张表一个类 | 无直接对应 | Java 必须先定义结构 |
| Elasticsearch | 搜索引擎 / 查询库 | Redis 缓存（弱）| 能全文搜、能分页排序聚合 |
| index / document | 表 / 行 | — | `_id` 相同会**静默覆盖** |
| 网关 | 统一入口 + 转发 | nginx 反代 | 不剥前缀，路径要写全 |
| Nacos | 配置中心 | `.env` + dotenv | 集中在服务器，可热更新 |
| XXL-JOB | 定时任务平台 | node-cron | 有网页后台，参数按 `-` 切割 |
| Jenkins | 自动构建部署 | GitHub Actions | 公司自建，你点按钮 |
| Docker 镜像 | 程序+环境打包 | — | 保证各环境跑得一样 |
| K8s / KubeSphere | 容器编排 / 它的网页 | pm2 集群版 | 排错看日志去这 |
| Feign | 调别的服务的接口 | axios 调内部 API | 写个接口就能调，框架实现 |
| Lombok `@Data` | 自动生成 getter/setter | JS 对象天然有属性 | **隔离编译时必须显式列出源文件，否则不生成** |
| DTO / VO | 传输对象 / 展示对象 | 接口的 response 类型 | Java 要显式定义类 |
