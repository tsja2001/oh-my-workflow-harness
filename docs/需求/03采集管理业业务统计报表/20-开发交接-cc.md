## 一、大白话：这一步做了什么

在后端 `scm-source-all` 里加了一个**手动同步接口**。你（或 AI）调用它、传一个日期范围，它就会：

1. 从数据库里把这段时间内**审批通过的、属于集采分类的**非平台录入业务单捞出来；
2. 把每个单子下面的**每一条物料**都摊开；
3. 按照同事定的那套统一字段，把**每条物料变成 ES 里的一条报表记录**存进去。

一条物料 = ES 里一条记录。存进去用的主键是"采购业务编号 + 物料编码"，所以同一条物料重复同步只会覆盖自己、不会变成两条。

这一步**只做"手动写入"**，还没做每天自动跑、也没做查询页面——那是后面阶段二、阶段三的事。

## 四、新代码跟读（照着 50 文档那套"定时间→查数据→转字段→存 ES"看）

核心方法：`CentralizedProcurementReportServiceImpl.syncCentralizedProcurementData(Date, Date)`。

**第一块 · 决定查哪段时间**（和旧交易报表一样的三种情况）
- 都不传 → 昨天一整天；只传一个 → 那天一整天；都传 → 用传入区间。
- 区别：本报表**按"审批结束时间"`update_time` 扫**，不是旧报表的 `create_time`（否则"上周建、昨天才审批"的单会漏）。

**第二块 · 查符合条件的主单**（表 `sc_supplier_green_channel`）
- 条件：`approve_status=101`（审批通过）+ `purchase_business_type IN (101,102,103)`（集团/二级集团/区域集采）+ `update_time` 在范围内。
- **不加** `is_inner=1`：内部、外部供应商全量统计（口径见 12 答复第 3 条）。

**第三块 · 一次性批量查物料明细**（表 `sc_supplier_channel_projects`）
- 收集这些主单的 `channel_id`，一次 `IN` 查询把所有物料捞回来，再按 `channelId` 在内存里分组。
- 这样避免"一单查一次"的 N+1；旧订单侧就有这个 N+1 毛病，我们不重犯。

**第四块 · 板块名查字典**
- 调 UBM 字典（`Owningplate`）拿到 `bu_code → 标准名` 的对照表，一次取好放内存。
- 存进 ES 的板块名用**字典标准名**（按 `bu_code` 查），不用主表 `bu_name`（主表同一板块有多种脏名甚至 NULL）。

**第五块 · 一单 N 条物料 → N 条 ES 文档 → 写入**
- 双层循环：每个主单 × 它的每条物料 = 一条 `CentralizedProcurementReportModel`。
- 填完字段 `saveAll` 一次写 ES；主键相同则覆盖（幂等）。

### 字段怎么填的（一条 ES 记录 = 一条物料）

| ES 字段 | 取值 |
|---|---|
| `id`（主键） | 主单 `purchase_business_code` + 物料 `product_code` 直接拼接 |
| `buCode` / `buName` | 主单 `bu_code` / 按 bu_code 查字典的标准名 |
| `purchaseCompanyName` / `Code` | 主单 `company_name` / `company_code` |
| `supplierName` / `supplierCode` | 主单 `supplier_name` / `three_in_one_id_code`（统一社会信用代码，非平台无独立供应商编码） |
| `planCode` / `planName` | 主单 `purchase_business_code` / `purchase_business_name` |
| `materialCode` / `materialName` | 物料 `product_code` / `product_desc`（物料"描述"取的是长描述，不是 product_name） |
| `categoryCode` / `categoryName` | 物料 `category_code` / `category_name`（允许空） |
| `taxTotal` | 物料 `total_price`（每条物料自己的含税总价，不用整单金额） |
| `bookTime` | 主单 `update_time`（审批结束时间） |
| `isCentralized` | 主单 `is_jc`（1 是 / 0 否） |
| `purchaseType` | 由 `is_jc` 派生：是→集团集采，否→分散采购 |
| `dataSource` | 固定 `FP`；页面/导出层以后转成"非平台录入" |

### 过程中修掉的一个坑（重要经验）

首版接口路径照抄了同模块旧的 `TradeDataReportController` 的 `/api/trade-data-report/...` 风格，**实测网关根本路由不到**（404，报错 path 显示 `/scm-source-web/e/business/source/api/...`）。
本项目真实规矩是：**网关不剥前缀，Controller 必须自己写完整路径** `e/business/source/<业务>/<方法>`。已改为 `e/business/source/centralizedProcurementReport/sync`（提交 `5bebc94af`）。
另注：往网关发不存在的路径可能返回 `{"status":true,"code":"000000","data":"ok"}`，**不要把它当调用成功**，要看返回内容是不是自己接口的。该经验已写进 `ai-docs/工作规范与习惯.md` §3。

### 遗留观察（留给阶段三）

`bookTime` 在 ES 里按 UTC 存储（比北京时间早 8 小时）。阶段三做查询/导出/前端时，展示要按 +08:00 渲染，否则页面上会少 8 小时。

## 八、要盯的点 / 已知边界

- **`bookTime` 是 Date 类型且没写 format**：这是照同事公共合同来的，也是本项目其他报表模型的惯例。由于现在**索引由我们创建**，服务首次启动会按模型自动建 mapping；若启动日志报日期格式相关错误，属于公共合同问题，届时和同事一起给 `bookTime` 补 format，不要各写各的。
- **索引自动创建**：我方模型 `createIndex` 用默认（true），启动即建索引。若以后同事的订单侧也指向同一索引，先起的一方建、后起的复用，不冲突。
- `update_time` 只是当前约定的"审批结束时间"，审批后若还改主表会漂移（12 已接受该口径）。
- 主键 `业务编号+物料编码` 不做空值/重复兜底（用户已确认），异常数据按拼接结果直接写。
- 按当前 test 数据，符合条件的单子很少（个位数），页面初期数据少属正常，不是代码问题。

### 隔离编译踩的坑（下次直接照抄）

**javac 只对显式列出的源文件跑注解处理器。** `Source`/`DealDetail`/`DealProduct`/`DealResult`/`Scheme` 都是 Lombok `@Data`，
只靠 `-sourcepath` 让 javac 隐式加载它们的话，**getter 全都不会生成**，会报一大片 `invalid method reference` / `cannot find symbol`，
看起来像是我们自己代码写错了（第一次跑就是这样，372 行报错）。正确做法：把用到的实体源码一并**显式列在 javac 命令行上**。
另外 `-sourcepath` 用 `find -maxdepth 4`（`模块/src/main/java` 是第 4 层，用 3 会静默取空，导致 argfile 参数错位报 `invalid flag`）。
完整可复用脚本：`/tmp/zcjc2.sh`。
