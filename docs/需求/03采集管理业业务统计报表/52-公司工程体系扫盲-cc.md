# 第一部分：AIM 是什么

## 1.1 一句话

**AIM 是公司自研的"服务内部调用总线"** —— 让一段代码能用**字符串**调用另一段代码，而不需要拿到 Java 类型。

源码位置：`01zhaocai-end/scm-assemblies-all/scm-share-aim-all/`（公司自己写的，不是开源框架，网上搜不到）

## 1.2 解决什么问题

正常 Java 调用是这样，**编译期就绑死了**：

```java
@Autowired private DealService dealService;   // 我必须能拿到 DealService 这个类
dealService.getDealInfo(param);
```

但有三种场景**拿不到类**：

| 场景 | 为什么拿不到 |
|---|---|
| XXL-JOB 定时任务 | 配置是网页文本框，只能填字符串 |
| 跨模块调用 | 模块 A 想调模块 B，但不想在 pom 里依赖 B（会导致依赖循环）|
| 跨服务调用 | 对方在另一个容器里，类根本不在同一个进程 |

AIM 的解法：**给每个 Service 起个字符串外号，按外号调用。**

```java
@TypeMapping("dealService")        // 贴在接口上 = 服务外号
public interface DealService {
    @MethodMapping("getDealInfo")  // 贴在方法上 = 方法外号
    List<DealDetailVO> getDealInfo(DealQueryParam param);
}
```

调用方（[DealExportServiceImpl.java:114](01zhaocai-end/scm-source-all/scm-source-deal/src/main/java/com/pcitc/scm/source/deal/service/impl/DealExportServiceImpl.java:114)）：

```java
sourceAIMService.request(new AIMRequest<>(dealParam, "dealService", "getDealInfo"));
//                                                    ↑外号        ↑方法外号
```

## 1.3 四段寻址

AIM 的核心接口只有一个方法（`AIMConsumerHandler.doBusiness`）：

```java
R doBusiness(String app, String businessModule, String businessAction, T param, boolean enApi);
//           哪个服务      哪个Service           哪个方法              参数
```

这就是 XXL-JOB 参数那串东西的由来：

```
source - centralizedProcurementReportService - syncZcData - {}
  ↑app        ↑businessModule                    ↑action    ↑param
```

- `source` 定义在 [SourceAIMService.java](01zhaocai-end/scm-source-all/scm-source-api/src/main/java/com/pcitc/scm/source/api/SourceAIMService.java)：`APP_ROOT = "source"`
- 后两段就是 `@TypeMapping` / `@MethodMapping` 的值

**聪明的地方在 [AIMConsumerHandlerFeign.java:25](01zhaocai-end/scm-assemblies-all/scm-share-aim-all/scm-share-aim-feign/src/main/java/com/pcitc/scm/share/aim/feign/controller/AIMConsumerHandlerFeign.java:25)**：

```java
AIMService aimService = aimFactory.getAIMService(app);
if (aimService != null) {
    resp = aimService.request(req);          // 本服务内 → 直接方法调用
} else {
    resp = aIMFeignFactory.exetute(req, app); // 别的服务 → 发 HTTP
}
```

**同一行调用代码，目标在本进程就直接调，在别的服务就自动走 HTTP。** 调用方不用关心对方在哪。这是 AIM 存在的最大价值。

**Node 类比**：像你封装了一个 `call('user', 'getById', {id})`，内部判断 user 模块是本地引入还是远程服务。

## 1.4 注册机制（为什么注解必须贴接口上）

[MethodHandlerServiceImpl.java:36](01zhaocai-end/scm-assemblies-all/scm-share-aim-all/scm-share-aim-spring/src/main/java/com/pcitc/scm/share/aim/spring/impl/MethodHandlerServiceImpl.java:36)：

```java
Map<String, Object> maps = applicationContext.getBeansWithAnnotation(TypeMapping.class);
for (Object object : colls) {
    cs = object.getClass().getInterfaces();        // 拿 bean 实现的所有接口
    for (Class<?> c1 : cs) {
        tm = c1.getAnnotation(TypeMapping.class);  // ← 从【接口】上读注解
        if (tm != null) {
            map.put(tm.value(), new MethodHandler(tm.value(), object, c1));
            break;
        }
    }
}
```

服务启动时建一张 `外号 → 实际对象` 的表。**注解从接口上读，贴在 Impl 类上不生效。**

这也回答了"为什么 Service 非要拆接口 + 实现两个文件"——**接口是这套机制的挂载点，不是形式主义。**

## 1.5 代价（这个要知道）

AIM 让调用变灵活，代价是**把编译期检查换成了运行期**：

| | 普通调用 | AIM 调用 |
|---|---|---|
| 方法名写错 | 编译不过 | **运行时才报错** |
| 参数类型不对 | 编译不过 | **运行时才报错** |
| IDEA 里 `Alt+F7` 查引用 | 找得到 | **找不到**（字符串没有引用关系）|
| 改方法名重构 | IDEA 自动改全 | **字符串不会跟着改** |

**这就是为什么 AIM 那个 `JsonServiceImpl` 会成为 fastjson 事故的爆点** —— 它要在运行时把 JSON 转成任意类型，全靠反射和 JSON 库，一旦 JSON 库的方法没了，整条 AIM 调用链全断。下一部分讲这个。

## 2.2 `scm-cloud-parent` 是干什么的

打开它的 pom，描述写得很清楚：

> 顶级项目，管理编译环境、SpringCloud版本以及第三方框架版本，**应用项目中禁止直接引用第三方JAR包及版本号**

里面全是版本号声明：

```xml
<spring.boot.version>2.7.0</spring.boot.version>
<mybatis-plus.version>3.4.2</mybatis-plus.version>
<fastjson.version>2.0.62</fastjson.version>     ← 就是它
```

**Node 类比**：像 monorepo 根目录的 `package.json` 里的 `resolutions` / `overrides` —— **全公司统一钉死每个第三方库的版本**。

**为什么要这样**：475 个模块，如果各自写 `fastjson 1.2.x`、`1.2.83`、`2.0.x`，同一个 JVM 里只能有一个版本，最后加载哪个全看运气。这叫 **依赖地狱**。统一在 parent 里管，所有人继承同一个版本。

**代价**：**改一个版本号，影响全公司 475 个模块。** 这就是 fastjson 那次的规模。

## 2.3 一个陷阱：Git 仓库 ≠ Maven 项目

这个我第一次看也绕了一下，你肯定也被坑过。

`scm-assemblies-all` **是一个 Git 仓库**（有 `.git`），但它**根目录没有 pom.xml**。它下面的 11 个 `xxx-all` **各自是独立的 Maven 项目**：

```
scm-assemblies-all/          ← 1 个 Git 仓库，无 pom.xml
├── scm-common-all/          ← 独立 Maven 项目（有自己的 pom）
├── scm-share-aim-all/       ← 独立 Maven 项目
│   ├── scm-share-aim/
│   ├── scm-share-aim-api/
│   ├── scm-share-aim-spring/    ← 7 个子模块
│   └── ...
├── scm-scheduling-all/      ← 独立 Maven 项目
└── ...
```

**后果**：
- `git commit` 一次可以同时改好几个 Maven 项目（fastjson 那次就是，一个提交改了 `scm-common-json` 和 `scm-share-aim-spring` 两个不同项目的文件）
- 但 `mvn deploy` **必须一个 Maven 项目一个 Maven 项目地跑**，因为根目录没有 pom，Maven 不知道从哪开始

**这解释了你当时的困惑**：改一次代码，要分别 deploy 好几个地方。

# 第三部分：Jenkins vs `mvn deploy` —— 你问的核心问题

## 3.1 它们产出的东西根本不一样

| | Jenkins | `mvn deploy` |
|---|---|---|
| 用在 | **业务服务**（第 3 层）| **公共库和地基**（第 1、2 层）|
| 产物 | **Docker 镜像** | **jar 包** |
| 送到哪 | 镜像仓库 → K8s **运行起来** | Nexus（私服）**供别人依赖** |
| 结果 | 一个跑着的服务 | 一个躺在仓库里的文件 |
| 谁消费 | 用户通过浏览器访问 | 别的 Maven 项目 |

**关键认知：公共库不是"服务"，它跑不起来。**

`scm-share-aim-spring` 里没有 `main` 方法、没有端口、没有 Controller。它就是一堆类，打成 jar 给别人用。**你没法"部署"一个 jar，只能"发布"它。**

**Node 类比**：

| Java | Node |
|---|---|
| 业务服务 → Jenkins → Docker → K8s | 你的 Koa 应用 → 部署到服务器 |
| 公共库 → `mvn deploy` → Nexus | 你的工具库 → `npm publish` → npm registry |

**`mvn deploy` ≈ `npm publish`。** 你不会说"把 lodash 部署到服务器上"，同理你也不会 Jenkins 一个公共库。

## 3.2 那为什么公共库没有 Jenkins 任务？

理论上可以配（Jenkins 也能跑 `mvn deploy`），**但这个公司没配**——实测 6 个地基/公共仓库 Jenkinsfile 数量全是 0。

现实原因大概是：公共库改动频率低（一年几次），配 Jenkins 任务的收益不如业务服务。改一次就找人手动 deploy 一次。

**所以你的理解是对的**：那次 `mvn deploy` **确实代替了 Jenkins 的"编译 + 发布产物"那一步**。只不过 Jenkins 发布的是镜像，你发布的是 jar。

## 3.3 发布出去的 jar 长什么样

工作日志里记的产物版本号：`1.0.0-JDSN-20260722.013718-3`

拆解：
- `1.0.0-JDSN-SNAPSHOT` 是声明的版本
- deploy 时 Nexus 自动加时间戳 `20260722.013718`，序号 `-3`（当天第 3 次发布）

**这就是 SNAPSHOT 的含义**：同一个版本号，内容可以被覆盖。别人 `mvn install` 时会拉最新的那个时间戳。

**Node 类比**：像 npm 的 `next` / `beta` tag，版本号不动但内容在变。

# 第四部分：fastjson 那场事故，完整因果链

现在把你经历的那件事从头串一遍。**这一节值得慢慢读，它是理解企业项目"为什么这么乱"的最好样本。**

## 4.1 事故起点

安全部门通知：fastjson 1.x 有漏洞，全公司升级到 2.x。

于是有人在 `scm-cloud-parent` 改了一行（提交 `256a2be fastjson升级到2.0.62`）：

```xml
<fastjson.version>2.0.62</fastjson.version>
```

**一行改动，影响 475 个模块。**

## 4.2 第一个坑：fastjson 2.x 删掉了方法

fastjson 2.x 不是 1.x 的小版本升级，它**删除了一批 API**。其中就有：

```java
com.alibaba.fastjson.util.TypeUtils.getClassFromMapping(String)
```

而公司的公共库里有两处在用它——**其中一处正是 AIM 的 JSON 转换器**：

| 文件 | 属于 |
|---|---|
| `scm-common-all/scm-common-json/JsonTransferUtil.java` | 通用 JSON 工具 |
| `scm-share-aim-all/scm-share-aim-spring/JsonServiceImpl.java` | **AIM 的序列化核心** |

**这就是第一部分末尾说的"AIM 是爆点"**：AIM 要把任意 JSON 转成任意类型，重度依赖 JSON 库的反射能力。JSON 库一改，AIM 直接断。

你的修复提交 `80e24fa 处理fastjson2.x缺失方法问题` 改的就是这两个文件。看 diff 里 AIM 那处：

```java
// 改之前（fastjson 1.x 写法）
JSON j = (JSON) JSONObject.toJSON(content);
Class<?> c = TypeUtils.getClassFromMapping(type.getName());   // ← 2.x 里没有这个方法
if (c != null) { return (T) content; }

// 改之后（不依赖那个方法）
if (type.isInstance(content)) { return (T) content; }          // ← 用 Java 原生判断
JSON j = (JSON) JSONObject.toJSON(content);
return j.toJavaObject(type);
```

**改法的本质**：原来用 fastjson 的内部映射表判断"这个类型认不认识"，现在改用 Java 原生的 `isInstance` 判断"这个对象是不是这个类型"。功能等价，不再依赖被删的 API。

## 4.3 第二个坑：为什么 `mvn deploy` 时别的库报错

这是你问的重点。**两种完全不同的报错，得分开看：**

### 情况 A：编译期报错 —— "别的模块也用了被删的方法"

`mvn deploy` 在 `scm-share-aim-all` 目录跑时，Maven 会构建它下面**全部 7 个子模块**（这叫 **reactor 反应堆**）：

```
scm-share-aim, scm-share-aim-api, scm-share-aim-factory,
scm-share-aim-spring, scm-share-aim-dubbo, scm-share-aim-feign, scm-share-aim-web-jar
```

**任何一个编译失败，整个 deploy 就失败**，即使你只想发布其中一个。

如果某个兄弟模块也调用了被删的 fastjson 方法，它就会报 `找不到符号 getClassFromMapping`。

**Node 类比**：monorepo 里 `npm run build` 构建所有 workspace，一个包挂了全挂。

> 实测佐证：`scm-share-rule-all/JsonUtils.java:84` 里那行 `getClassFromMapping` **是被注释掉的**——
> 说明当时确实有人挨个模块去找、去改/去注掉这个方法。你不是唯一一个被它绊住的人。

### 情况 B：运行期报错 —— `NoSuchMethodError`（更阴险）

这个是工作日志里记的那个真实问题：

> Nexus 上原 jar 停留在 2023-04-18，字节码仍含 fastjson 1.x 的 `TypeUtils.getClassFromMapping`，会在运行时抛 `NoSuchMethodError`

**这是 Java 特有的坑，Node 里几乎不会遇到**，务必理解：

Java 是**编译型**的。源码 `.java` 编译成字节码 `.class` 时，**方法调用被写死成了一条指令**：

```
调用 com/alibaba/fastjson/util/TypeUtils.getClassFromMapping(String)Ljava/lang/Class;
```

这条指令**烙在 jar 里**了。所以：

```
源码改好了 ✅  →  但 Nexus 上的 jar 是 2023 年编译的，字节码里还是老指令 ❌
          ↓
业务服务启动时，从 Nexus 拉这个旧 jar
          ↓
运行到那行，JVM 去 fastjson 2.x 里找 getClassFromMapping
          ↓
找不到 → NoSuchMethodError → 整条 AIM 调用链崩溃
```

**关键点：编译能通过，启动也能成功，跑到那行才炸。** 因为 JVM 是**用到才加载**（懒加载）。

**这就是为什么必须重新 `mvn deploy`** —— 不是为了改源码（源码早改好推上去了），**是为了让 Nexus 上那个 jar 的字节码重新生成一遍**。

**Node 对比**：JS 是解释执行的，`require` 拿到什么就是什么。你改了源码重新发包，别人装到的就是新代码，不存在"字节码里烙着旧调用"这回事。这是 Java 独有的复杂度。

## 4.4 第三个坑：证书过期（顺带说，你会再遇到）

工作日志记的：

> Nexus 证书 `*.jdsn.com.cn` 已于 2026-06-16 过期，`~/.m2/settings-zc.xml` 第 83 行下载地址由 https 改为 http 才能构建

**这类"跟你的代码毫无关系但就是构建不了"的问题，在企业环境里占了排错时间的一大半。** 心里有个准备。

## 4.5 整件事的因果链（一张图）

```
安全部门：fastjson 有漏洞，升级
        ↓
scm-cloud-parent 改一行版本号（影响 475 个模块）
        ↓
fastjson 2.x 删了 getClassFromMapping 方法
        ↓
公司两个公共库用了它 → 编译报错
   ├─ scm-common-json（通用 JSON 工具）
   └─ scm-share-aim-spring（AIM 的序列化核心）← 你改的
        ↓
改完源码提交推送 ✅
        ↓
但公共库没有 Jenkins 任务 → 没人自动构建 → Nexus 上还是旧 jar
        ↓
旧 jar 字节码里还烙着已删除的方法调用
        ↓
业务服务运行时 NoSuchMethodError
        ↓
必须手动 mvn deploy 重新生成 jar ← 你做的这一步
        ↓
deploy 时 reactor 构建全部兄弟模块，别的模块也报错 ← 你被绊住的地方
        ↓
（外加）Nexus 证书过期，https 连不上，改 http 才能传
```

**你当时觉得"什么乱七八糟的"——现在看，这条链上每一环都有它的道理，但它们叠在一起就是很难受。这就是企业级项目的真实状态。**

# 第五部分：以后遇到类似情况怎么办

## 5.1 判断"该用 Jenkins 还是 mvn deploy"

```
我改的这个仓库里有 Jenkinsfile 吗？
├─ 有 → 业务服务 → 提交推送，点 Jenkins
└─ 没有 → 公共库/地基 → 提交推送，还要手动 mvn deploy 发到 Nexus
                        ↓
                  然后所有依赖它的业务服务都要重新构建一次
                  （否则它们手里还是旧 jar）
```

**最后那句是最容易漏的**：公共库 deploy 完不等于生效，依赖它的服务得重新构建才会拉到新 jar。

## 5.2 看到 `NoSuchMethodError` 的排查套路

这个错误的含义永远是：**编译时有这个方法，运行时没有了。**

| 步骤 | 做什么 |
|---|---|
| 1 | 看报错里的方法全名，确定是哪个库的 |
| 2 | 查这个库最近是不是升过版（看 `scm-cloud-parent` 的 git log）|
| 3 | 如果升过 → 找出**哪个 jar 在调这个方法** |
| 4 | 那个 jar 的源码改了吗？改了但 Nexus 上是旧的 → **重新 mvn deploy** |

**和 `ClassNotFoundException` 的区别**：
- `ClassNotFoundException` = 整个类都找不到（jar 没引进来）
- `NoSuchMethodError` = **类在，方法没了**（版本不匹配）——几乎总是版本问题

## 5.3 心态：不要试图理解全部

475 个模块、7993 个 Java 文件。**没有人全懂，包括写了十年的老员工。**

企业项目的正确用法是：

| 你需要 | 深度 |
|---|---|
| 自己那 3 个文件 | **精通** |
| 直接依赖的东西（Mapper、Model、AIM 怎么调）| **会用、知道边界** |
| 公共库内部实现 | **知道它在哪、出事了能找到** |
| 其他 24 个业务服务 | **知道有这么个东西就行** |

**这次 fastjson 你被迫下潜到了第 3 层**——那是意外，不是常态。而且你处理完了，这本身就说明能力够用。
