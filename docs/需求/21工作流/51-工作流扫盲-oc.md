# 工作流扫盲——这套审批流到底是什么、怎么运转（大白话版）

## 一句话版本

**DPS 是一个独立的"审批流引擎"产品**（石化智云系的公司级产品，跟我们的 Java 代码库是两回事）。
我们把单子"递"给它，它按事先画好的流程图一层层派人审批，审完再"通知"我们改单子状态。

## 一个比喻：快递系统

把审批流想象成寄快递：

| 快递世界 | 我们的系统 |
|---|---|
| 你把包裹交给快递公司 | 业务代码调 `processStart`，把单据 ID + 几个关键字段递给 DPS |
| 快递公司内部有分拣路线 | DPS 按**流程图**走（谁审→谁审→通过/驳回） |
| 收件地址由面单决定走哪条线路 | 流程图里的**分支条件**看我们传的变量（比如"是否集采=是"就走多一级审批） |
| 每到一站有人签收 | 每个审批节点生成一条**待办**，落在审批人的"我的待办"里 |
| 签收完成后系统给你发通知 | DPS **回调**我们，我们把单子状态改成"已通过/已驳回" |
| 快递公司有自己的管理后台 | **工作流控制台**（dps.scmflow-test.jdsn.com），产品/实施在那里画流程图 |

## 关键认知一：审批几级、谁审，**不归开发管**

- 这些信息**不在代码里**，是产品/实施在**工作流控制台**上画出来的（画流程图、配每个节点谁来审）。
- 开发的活只有两块：
  1. **把分支要用的变量传准**（比如"是否集采""集采目录层级""是否强管控"——15集采需求第二期你就是要给华姐提供这几个字段）；
  2. **接住审批结果回调**（通过→单子变"已审批"，驳回→变"已驳回"）。
- 所以遇到"流程要加一级审批"这种需求，答案通常是：**产品去控制台画图，不是改代码**。

## 关键认知二：一张流程图都不止"一张"

- 每个环境（test / uat / prod）的 DPS 是**独立部署、独立数据库**，流程图是**手工逐环境配的，不会自动同步**。
  所以"test 和 uat 流程不一样"是常态不是 bug。
- 同一个业务（比如采购方案）在 DPS 里不止一张图：按集团（BU）各配了一张
  （`SCHEME-BU001` 金隅集团、`SCHEME-BU002` 冀东水泥……）。系统起流程时按**发起企业属于哪个集团**
  自动挑图，挑不到才用兜底的那张。这就是代码里说的"四级降级"。
- 改了流程图要**发布新版本**，已经在途的老单子继续走老版本图——所以"改了流程但老单没变"也是正常的。

## 关键认知三：整个链路是"两家公司三个系统"在配合

```
[我们的业务服务] --递单子--> [我们的工作流代理(scm-workflow-web)] --转发--> [DPS 引擎]
       ^                        |                                       |
       |                     落库存证                              派待办、推进节点
       |                        |                                       |
       +---------审批结果回调(经MQ+AIM)-------------------------------------+
```

- **DPS 引擎**：真正管流程推进的外部产品，自己有库、有控制台、有自己的账号体系（admin）。
- **工作流代理（scm-workflow-web）**：我们这边的"翻译+邮局"。业务服务不直接碰 DPS，
  都通过它。它还负责：记流水（哪张单用了哪个模板）、审批完成后把消息可靠地送回业务服务（发 MQ，丢了能补）。
- **业务服务**（采购方案、采购计划、合同、供应商、商品、订单……全平台 8 个业务域都在用审批流）。

## 关键认知四：为什么"提交成功了却没有待办"不算稀奇

起流程是**异步**的：业务提交 → 代理先落库、发个消息就返回"成功" → 后台消费者才真正去调 DPS。
中间任何一环（MQ、DPS 网络）抖一下，单子就停在"提交了但流程没起来"。排查口诀（AI 已经封装好）：

```bash
bash scripts/wf.sh trace <单据ID> test    # 一条命令看：流程起没起、用哪张图、回调到哪
bash scripts/wf.sh todo test              # 现在全平台谁的单子卡在谁手里
```

## 你（用户）自己上手看的话

```bash
bash scripts/wf.sh open test
```
会打印控制台地址和登录填法（帐号密码在 creds.env 里，应用Id 填 `jdsn`，**用户Id 必须填 `1001`**，
不填或填错会报"用户Id校验失败"——这是本次研究踩出来最隐蔽的一个坑）。

进去以后最常用的三个页面：
- **模板管理→机构模板**：看/画流程图（左边选集团，右边列表，点进去是图形编辑器）；
- **流程管理→待办监控**：所有环境的在途审批（比业务页面的待办全）；
- **流程管理→实例详情**：按单据 ID 搜某张单走到哪了、看过谁的手。

**红线提醒**：控制台里任何"保存/发布/重置/转移/补救"按钮都是写操作，会直接改测试环境流程。
看可以，点之前想清楚；AI 侧的工具（wf.sh）已经做成纯只读，没有写能力。

## 常见问题快答

**问：DPS 是哪家公司的产品？**
答：PCITC（石化盈科）的"石化智云"工作流服务。代码里一堆 `com.pcitc`、页面标题"石化智云|工作流服务"都是它。我们只是采购/集成方，引擎内部实现改不了（只能控制台配 + 它暴露的接口）。

**问：为什么 AI 说"这个要在工作流平台配"？**
答：因为分支条件、审批人、几级审批都画在 DPS 的流程图里，不在我们的代码库里。开发改代码够不着那里。

**问：审批人列表从哪来？**
答：DPS 每到一个要选人的节点，会**反过来调我们暴露的接口**查组织/人员/角色（"这个人所在部门的领导是谁"之类）。所以组织架构数据变了但审批人还是老的，通常是缓存或接口数据没刷新。

**问：这套东西的数据我们能查吗？**
答：能。业务侧流水在 `scm_ubm_<env>` 库（`scm_wf_template` / `scm_wf_template_record` / `wf_instance` 三张表）；
DPS 侧的模板/待办/变量走控制台 API（wf.sh 已封装）。⚠️ 唯一的坑：本机能看到的老 `dps_test` 库是 2023 年就停更的旧库，别拿它当线上真相。
