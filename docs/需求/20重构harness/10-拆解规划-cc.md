# 第一部分：这次要改什么，为什么

## 1. 一句话

这套 harness 的**结构方向是对的**（人写的分层文档 + 索引表 + 按需加载），
问题全部集中在**两处**：**该被索引的东西没被索引**，和**写进去的东西没有退出机制**。

不需要引入任何新产品。六项改造全部靠 markdown 约定和 shell 脚本完成。

## 2. 这套设计对应的行业标准叫什么（便于以后自查）

| 你已经在做的 | 标准名字 | 出处 |
|---|---|---|
| `AGENTS.md` 唯一入口 | **AGENTS.md 开放规范** | 2025-08 由 OpenAI 牵头、Google/Cursor/Factory 参与制定；2025-12 捐给 Linux Foundation 的 Agentic AI Foundation。6 万+ 项目采用，20+ 工具原生读。规范见 agents.md |
| §3 索引表 + 「按需查不要通读」 | **Progressive Disclosure 渐进式披露** | 源自 1990s 交互设计（Jakob Nielsen 一派），2025 年被 AI 上下文工程整体借用 |
| skill 的 `description` → 正文 → `references/` | 同上，三级披露 | Anthropic Agent Skills |
| `系统地图.md` / `工作日志.md` / `SKILL.md` / `校准记录.md` 的分工 | **记忆四分法**：语义 / 情景 / 程序性 / 偏好 | 认知心理学（Tulving 情景-语义之分，1970 年代初），被整个 agent memory 赛道借用 |

| 层 | 定义性属性 | 本仓库对应 |
|---|---|---|

| **Recall Memory** | 不常驻，**全自动落盘的原始流水** | **无**（`工作日志.md` 是人写的摘要，不是流水）。真正的流水在 `~/.claude` `~/.codex` 里，见 §5 |
| **Archival Memory** | 不常驻，**内容经过筛选** | `系统地图.md` `代码库地图.md` `经验教训.md` |

### 改造 2（P0，~1 小时）：`docs/需求/INDEX.md`

现状 364 个文件分布：

```
01台账 24 │ 02台账需求2 19 │ 03采集管理业业务统计报表 34 │ 04和生产环境运维对接需求1-4 26
05fastjson升级 82 │ 06_2取值需求2-驾驶舱取值需求 14 │ 06取值需求 36 │ 07开发本地运行java环境 4
08jsonBUG解决 1 │ 09自动登录获取Token 6 │ 10WSL-Clash网络间歇断网 2 │ 11部分git仓库需要账号密码 2
12deepseek-harness迁移 2 │ 13数据库考试 4 │ 14和生产环境对接报表取值 7 │ 15集采目录维护台账 7
16安全 11 │ 17网络 65 │ 18集采平台下一步规划 10 │ 19新需求 10
```

**为什么是 P0**：这是仓库最大的无 L0 区域。
渐进式披露的失败模式是**盲区不是噪音**——AI 判断"这个目录跟我无关"之后，整个子树永远进不去，
**不报错、无征兆，只表现为"AI 好像不知道这事"**。364 个文件目前全在这个状态。

**做法**：新建 `docs/需求/INDEX.md`，一主题一行，按 L0 四条规则写：

1. 写**"什么时候该开我"**，不写"里面有什么"
2. 触发词用**用户会说的原话**，不用规范术语
3. **写负向边界**（"什么时候别开"），防止误触发
4. 兄弟条目**必须互斥**，一眼能分开

样例：

```markdown
| 主题 | 什么时候该开 | 状态 |
|---|---|---|
| 17网络 | VPS / Cloudflare Tunnel / SSH 域名迁移 / WSL 断网。**与招采业务无关，做需求时别进** | 2026-08 活跃 |
| 18集采平台下一步规划 | 未来一年 37 项计划、业务全景扫盲、企业系统全景图。**问"这系统整体干嘛的"先看这里** | 已完成 |
| 05fastjson升级 | 安全升级，82 份全是过程记录 | 已收口，只做考古时开 |
```

然后 `AGENTS.md` §3 加一行：`| 想知道某个需求以前做过没有、历史方案在哪 | docs/需求/INDEX.md |`

**依赖用户**：19 个主题的一句话定性，见 `10-待确认问题-cc.md` 问题 1。

### 改造 3（P0，~30 分钟 + 持续）：`工作日志.md` 拆职能

**现状**：46,694 字符，单条 500~1500 字符，只增不删，**且结论内容与权威文档重复**。

08-25 那条自己写着「`ai-docs/系统地图.md` 新增 §6 权限模型」——
**同一份权限模型结论，日志一份、系统地图一份，没有任何标记说哪份是权威。**

**为什么是问题**：一个文件同时承担了 Recall（流水）和 Archival（结论）两种职能，
两者的正确处置方式相反——流水可丢、结论要留且必须唯一。
后果是记忆设计检查清单的第 3 条（冲突消解）和第 7 条（可归因）同时失效：
**`系统地图.md` §6 以后改了，日志那份不会跟着改，两份分叉，AI 无法判断信哪个。**

**做法三步（可只做前两步）**：

**a. 新条目的结论部分改成指针，不复述内容**

```
❌ 现在：… ｜ 实测权限模型：岗位挂在 ubm_member_job 且带 company_id，切公司=换整套菜单 …
✅ 改成：… ｜ 权限模型结论 → 权威副本 ai-docs/系统地图.md §6 …
```

日志只留三件事：**做了什么、在哪验证的、动没动远程 git**。
（旧条目不动，只增不覆盖。）

**b. 顶部加 L1 索引段**——这是全仓库**唯一**需要 L1 的文件
（其余 md 都在 2,410~8,130 字符，L0 + 全文两级足够，硬做 L1 是浪费）：

```markdown
## 索引（读这里就够；全文只在考古时读）
| 时间段 | 主线 | 相关目录 |
|---|---|---|
| 2026-08 下旬 | VPS / Cloudflare SSH 域名迁移 | docs/需求/17网络 |
| 2026-08 中旬 | 集采平台下一步规划扫盲、权限模型摸底 | docs/需求/18集采平台下一步规划 |
```

**c. 归档改按月，且归档文件必须登记进 §3**
（现在 `工作日志-归档-2607.md` 在 `AGENTS.md` 命中 0，归档 = 失联。）

### 改造 5（P1，~15 分钟）：加"失效标记"约定 —— 补上淘汰机制

`经验教训.md` 头部已有严格的**准入控制**（"只收还会再犯的"、"这份文件长了就没人读了"），
**但全仓库没有任何一条规定：什么时候把一条标记为失效。**

**准入 ≠ 淘汰。** 当前状态是：进去了就永远有效、永远权重相同——
2026-08 的环境地址和三个月后改过的地址，在文档里长得一模一样。

（对照：这是记忆设计里公认最难的一条。业界主流做法是衰减权重而非删除，
因为删错不可逆、且没人能定义"这条以后肯定用不到"。所以下面取最轻的做法：**不删，只标**。）

**做法**：`AGENTS.md` §5 加一条约定：

```markdown
**事实失效了不要删，改成划掉 + 标注：**
~~旧内容~~ 【失效 2026-09-xx：原因 / 新值在哪】
```

好处：可 `grep -rn "【失效"` 批量审计；历史可追；AI 读到划掉内容会知道别用。
**最该先上这条的是 `系统地图.md`**——环境地址、表结构、菜单变得最快。

---

### 改造 6（P1，~15 分钟）：【推断】统一标记 —— 补上可信度分级

红线 5 要求"推断必须显式标注"，`industry-perspective/SKILL.md` 法则 5 重申。
**但没有统一格式**，所以不同 AI 写法不一（"推测""可能""【推断】"混用），**无法批量审计**。

例：`com.pcitc = 石化盈科` 这个推断在多份文档出现过，目前无法一条命令列全。

**做法**：`AGENTS.md` §5 写死：

```markdown
**未证实的结论一律写成** `【推断】结论内容（无法证实的原因：xxx）`
之后 `grep -rn "【推断】" docs/ ai-docs/` 即为完整的未证实结论清单。
```

## 5. 全量对话日志（Recall Memory）：要做，但不用 OpenViking

### 5.1 现状：原始流水已经存在，约 3.8 GB

```
~/.claude/projects/-home-t-projects-work-wsl/   16M    9 个 jsonl 会话（本项目）
~/.codex/                                      3.3G
~/.opencode/ + ~/.local/share/opencode/        489M
```

这些文件包含**每一次工具调用、每一次失败的尝试、每一次用户打断和纠偏**，
信息量远超 `工作日志.md` 的人工摘要。**缺的从来不是记录，是从里面挖东西的工具。**

### 5.2 为什么不能交给 OpenViking

> **【2026-08-27 更新】用户已明确解除数据出境顾虑**（原话：「不用担心那么敏感出网……你更应该考虑最佳实践，而不是戴着镣铐跳舞」）。
> 下表前两行（凭据出境 / 业务数据出境）**不再作为阻断理由**。重新评估后结论不变，但理由是纯技术的——见 `10b-目录结构与生命周期方案-cc.md` §5。


| 阻断 | 说明 |
|---|---|
| **凭据出境** ★决定性 | 建向量索引要把全部内容过 embedding 模型（外部 API）。而 `工作日志.md` 2026-08-26 条目自述：「**该账号密码已出现在聊天记录里，建议测完改密**」。**把对话日志送去 embedding = 把出现过的凭据送出去**，直接违反红线 2 |
| **业务数据出境** | 日志含内网地址、表名、组织架构、供应商真实名称、uat/prod 信息 |
| **AGPLv3** | 国企子公司法务通常直接禁用 |
| **v0.4.x** | 未到 1.0，API 会变；515 open issue |
| **解决的不是本仓库的问题** | 它的价值在十万文件规模的自动检索。本仓库 17 + 3 + 364，手写索引足够。上面六项缺口它一项都补不上 |

### 5.3 正确形态：产出**指标**，不是**内容**

关键判断：**不要把原始对话喂给 AI 当上下文。**
Recall Memory 的正确用法是**按需搜索，不是常驻**——原始对话的噪音比 `ai-docs/` 高一到两个数量级。

正确做法是**离线挖掘**：新增 `scripts/retro.sh`，从本地 jsonl 里算三类指标，产出**候选条目**交人审核。
（这正好落在 §6 那条判据上：机器要重复的事归脚本，人要理解的事归文档。）

| 想回答的问题 | 从日志里怎么算 | 产出去哪 |
|---|---|---|
| **同一个坑踩了几次** | 统计重复出现的报错特征串 / 同一文件被反复试错修改 | 判断 `经验教训.md` 某条**是否生效**；这是淘汰机制的输入 |
| **AI 在哪一步反复走弯路** | 统计单个任务内工具调用轮次异常高的环节 | §6 说"做到第二遍还要回忆参数 = 工具缺口"，**这条判据目前靠人感觉，可以改成从日志自动检出** → 该补哪个脚本 |
| **用户纠偏都发生在什么时候** | 提取用户消息中的否定/纠正类表达及其上下文 | `校准记录.md` 的候选来源（**仍需人工审核后才写入**） |

**边界（重要）**：
- 脚本**只读本地**，不发任何东西出网
- 产出的是**候选清单**，写入 `ai-docs/` 前必须人工过一遍——保持"人对文档有最终写权限"这个前提不变
- 第三类（纠偏挖掘）涉及原始对话内容，**先只跑本项目的 16M，不碰 `~/.codex` 的 3.3G**，避免误扫到含凭据的历史会话

**这一项建议放在六项改造之后做**，因为它的价值依赖前面几项先立起来（挖出来的候选得有地方放）。

## 6. 不该做的（防过度工程）

| 别做 | 理由 |
|---|---|
| 引入 OpenViking / 任何向量库 | 见 §5.2。瓶颈不在检索 |
