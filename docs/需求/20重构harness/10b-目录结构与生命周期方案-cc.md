## 3. 四个结构性问题

### 问题 A：同一套两位数字，被当成两种东西在用

- **规范意图**：段号 = **阶段分类**（00 输入 / 10 想清楚 / 20 动过 / 30 别人验 / 50 交还理解 / 90 其它）
- **实际用法之一**：`01台账需求追问回答.md`、`02问题.md`、`03全套业务逻辑复盘.md` —— 这是**发生顺序编号**

两种体系混在同一个命名位上，**AI 无法判断 `03xxx.md` 是"第三个文件"还是"30 段的变体"**。
86 个无段号文件（32%）也大多是早期用顺序编号留下的。

**修法**：段号位**只允许表示阶段**。需要顺序的用轮次后缀（`10b` `10c`）或写进文件名中段。
旧文件不改名（只增不覆盖原则），只在 `INDEX.md` 里注明"本主题早期文件用顺序编号，非段号"。

**所以对你那个问题——"理想是线性，现实一定会返工，该如何提前规划目录结构"——答案是：**

> **别把返工当成主流程的一个分支去规划。返工是一棵子树，用和主树完全相同的段号体系，只是降一层。**
> 这样任何 AI 进到任何一层，看到的都是同一套规则，不需要学第二套。

**当前的实际问题不是结构，是命名不统一。** 同一类事情有六个名字：

```
02台账需求2/问题解决/          06取值需求/问题解决/
04.../bug处理/                04.../导出模板id问题/
03.../测试反馈/               05fastjson升级/02漏洞问题/、03ifs模块新问题/
```

**修法**：统一为两个名字，写进 §5 规范：

| 子目录名 | 什么时候开 |
|---|---|
| **`问题解决/`** | 交付后发现的 bug、测试反馈、生产问题。**内部沿用完整段号**（00 问题描述 → 10 调查/方案 → 20 开发交接 → 30 验证） |
| **`sql/`** | 保持现状（7 个主题已在用） |

一次返工内如果又有多个独立问题，用 `问题解决/01-<短名>/`、`问题解决/02-<短名>/` 再降一层，规则不变。

旧目录**不改名**（只增不覆盖），在 `INDEX.md` 注明别名即可。

## 5. 关于引入外部服务（用户已明确解除数据出境顾虑）

用户原话：「不用担心那么敏感出网……你更应该考虑最佳实践，而不是戴着镣铐跳舞」。
按此重新评估，**结论不变但理由完全不同**：

### 5.1 OpenViking：仍然不建议，理由纯技术

| 理由 | 说明 |
|---|---|
| **它不解决本仓库的问题** | 扫描出的问题是「32% 文件不合规、段号漂移出 50 种前缀、返工目录 6 个名字、10 个孤儿脚本、2 个目录零索引」——**这些全是"约定没有强制机制"，不是"检索不到"**。装向量库一条也补不上 |
| **规模不够** | 它的价值在十万文件级自动检索。本仓库 267 份 md + 17 份 ai-docs，手写索引绰绰有余 |
| AGPLv3 / v0.4.x | 次要，但仍是维护成本 |
| 要跑常驻 server | 增加一个必须活着的依赖，harness 的价值恰恰在于**纯文件、无依赖、任何 AI 工具都能读** |

**明确的触发条件**（到了再回来看它）：`docs/需求/` 超过 2000 个文件，或你需要**跨项目**（work + personal + 5 个 harness 项目）统一检索。

### 5.2 真正的最优解：把规范变成可执行的检查

**你的瓶颈是「规矩写在文档里，靠人和 AI 自觉遵守」。** 267 份文件里 32% 不合规就是证据。

最佳实践在软件工程里已经有成熟答案了，叫 **linter + pre-commit hook**——
不是数据库，是**让违规在发生的那一刻就报错**。

新增 `scripts/harness-lint.sh`，检查项：

| 检查 | 现在会查出 |
|---|---|
| 每个 `docs/需求/*/` 是否在 `INDEX.md` 登记 | 21 个主题全部未登记 |
| 每个 `ai-docs/*.md` 是否在 `AGENTS.md` §3 索引 | `工作日志-归档-2607.md` 漏了 |
| 每个 `scripts/*` 是否在 `工具箱.md` 登记 | 10 个孤儿脚本 |
| 文件名是否符合 `<段号>-<短名>-<工具>.md` | 86 个无段号（**旧文件加白名单，只管新增**） |
| 段号是否在允许集合内 | 40/41 等规范外段号 |
| 顶层目录是否都在 `AGENTS.md` 出现 | `note/`、`deepseek-harness/` 零命中 |
| `【推断】` 后面是否跟了"无法证实的原因" | —— |
| `【失效` 标记是否超过 90 天未清理 | —— |

配 git `pre-commit` hook（只对**新增/修改**的文件生效，不追溯历史）。
**这条落地之后，前面所有约定才真正有牙齿**——否则三个月后一定重新漂移。

**这才是"最优解"，不是妥协方案。** 它符合 `AGENTS.md` §6 那条判据：

我觉得个人项目上lint有点繁重了，先仅靠文档限定吧，先不做这些lint

## 6. 关于开发交互流程的观察

从 267 份文档的分布看到的三点，供参考：

### 6.1 多 AI 并行做同一份文档，是这套流程最独特的地方

`06取值需求/` 里 `10-拆解规划` 有 cc 和 codex 两份、`11-待确认问题` 有 cc 和 codex 两份、
`40-评审报告` 有 codex 和 oc 两份 + `41-独立复评-cc`。

**这实际上是「多模型交叉验证」**，在你的场景里价值很高——因为你无法自己复核 Java 代码，
让第二个 AI 独立复评是唯一的质量兜底。

**但现在没有规范约束**：什么时候该做双份、双份不一致时怎么裁决、裁决结果写哪，全靠临时决定。
**建议**：在 `enterprise-dev-workflow` 里写死一条——
「**10（拆解）和 40/30（评审）两个阶段做双 AI，其余单 AI**；不一致时新开 `<段号>x-分歧裁决-<工具>.md` 记录取舍理由」。

回答：这个先不用

### 6.2 codex 是主力（112 : 54 : 8），但工作日志显示 cc 承担了文档和分析

工具分工事实上已经形成了，但**没有写进任何文档**。新接手的 AI（或三个月后的你）不知道这个分工。
**建议**：`AGENTS.md` §4 加两行说明各工具的实际分工，这属于"团队规矩"的一部分。

回答：这个先不用

### 6.3 `13-需求定稿-开发基线` 这个段位应该强制化

`06取值需求` 用了它，别的主题没有。
它的作用是给"讨论期"画句号——**在它之前所有讨论都是草稿，在它之后改需求就是变更**。
没有这个锚点，`10b` `11b` `10c`…… 会一直滚下去（实测最高滚到 `20k` = 第 11 轮）。

**建议**：写进 §5，作为进入 20 段（开发）的前置条件。
