## 五、口径落地细节

**七个品类**（`CATEGORIES` 常量），每格三个条件：指定数据来源 + 四位大类前缀（含下级细类）+ `isCentralized=1`

| 品类 | dataCode | 数据来源 | 类目前缀 |
|---|---|---|---|
| 煤炭 | 1001 | MT 煤炭-SAP | 1001 |
| 钢材 / 润滑剂 / 电线电缆 / 轴承及备件 | 1501 / 1701 / 2302 / 2502 | JD 机电台账 | 同 dataCode |
| 办公设备 / 办公文具 | 2102 / 2113 | YC 云采平台 | 同 dataCode |

**五个时间窗**，统一右开到查询日 00:00（即统计到前一天 24:00）：`day` 前一日 ｜ `month` 当月1日 ｜ `quarter` 当季首日 ｜ `year` 当年1月1日 ｜ `cumulative` 固定 2026-01-01。

> `year` 和 `cumulative` **分开实现**：2026 年内两者相同，2027-01-01 起「年度集采」归零重算、「累计总金额」继续累加。
> 集采首页 `CentralizedProcurementPortalServiceImpl.java:100` 的 `BUSINESS_START_YEAR = 2026` 写死，那边跨年会不归零——**本次没动首页，属于遗留项**。

**需求里的 b/c/d 三个扣减项没有实现**，因为在本口径下取数范围里根本没有它们：非平台录入不在任何品类的来源里（b、c 无可扣）；云采只取 2102/2113，机电四大类进不来（d 无可扣）。这一点在实现类的类注释里写了。

**前端契约（dataCode 不能改名）**：`centerHeader` = companyCount/taxTotal/day/month/quarter/year/sumCount；`categoryAmount` = 七个类目码；`situA` = situA1/2/3；
`doRate` = doRate1 响应率、doRate2 完成率、**doRate3 滞后率、doRate4 执行率**（3 和 4 反直觉，已按 `sc_collection_data` 实测契约实现）。

**两个取值决定**（都可一行改回）：
- 金额一律**万元两位小数**（老驾驶舱是整数）。理由：与集采首页一致，且七格四舍五入后仍能加出头部总额。
- `companyCount` 沿用老 SQL 里的 **485**（需求："这两个数不用管，就写死就行了"）。注意 `sc_collection_data` 静态表里那行是 483，两者本来就不一致，本次不动。

**顺带清掉的死代码**：四个 typeCode 全部提前分流后，`collectionShow` 字典开关（`categoryAmount=0`、`situA=0`）已无人读取，
该字典查询整段删除——它是这个方法里唯一的读取点（全代码库 grep 只此一处）。**字典行留在库里不用管，也不用改成 1。**

> `SourceCollectionMapper` 里的 `queryCenterHeader` / `queryCategoryAmount` / `querysituA` 三段老 SQL 现在没有调用方了，
> 本次**故意没删**（共享 Mapper 文件，删了扩大 diff）。将来清理时可以一并删掉。

## 七、为什么没有动 scm-order-all（踩过一次）

第一版方案是在 `scm-order-feign` 里加一个 DTO 和一个方法，让 source 直接用 `FeignOrderClientService`。
**编译直接失败**：`package com.pcitc.scm.order.feign.ao does not exist`——`scm-source-all` 依赖的是 Nexus 上的 `scm-order-feign` **jar**，
新加的类不发包就看不见。而 `mvn deploy 到私服` 是红线（AI 不碰），还会给别的服务引入一次跨仓发布依赖。

改成**在消费侧自带 DTO + 自带 Feign 接口 + 复用同一个配置前缀**，一个仓就能编译，也不用发包、不用改 Nacos。
`scm-source-feign-consumer` 里调 ubm 用的就是这套写法（`UbmFeignWebConfig`），照它写的。
