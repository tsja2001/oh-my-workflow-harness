# 集采日计划台账负滞后率 · 根因调查

> 日期：2026-08-11  
> 工具：codex  
> 当前状态：已用 UAT 运行接口和 UAT 数据库原始行完整复现 `已滞后数量/率 = 220.00 / -1.30%`，根因已确定。  
> 下一步：先由产品确认“滞后率是否应直接使用已滞后数量”；确认后再改单一计算口径并补前后端录入校验，当前调查不修改 UAT 数据。

## 一、结论

`-1.30%` 不是部署、缓存或四舍五入错误，而是下面三件事共同造成的：

1. 需求明确写的是 `滞后率 = 响应率 - 执行率 - 完成率`，见 `02临时需求.md:8-10`；代码也一字不差地执行了这个公式。
2. 页面显示的“已滞后数量 220”是直接累加数据库的 `delayed_quantity`，**计算滞后率时完全没有使用这 220**。
3. UAT 被纳入累计的手工台账数据不自洽：执行中、已完成、已滞后没有与响应数量形成可相减的关系，因此公式的结果可以与滞后数量不一致，甚至为负数。

所以当前实现虽然“照着需求公式写了”，但需求没有规定录入约束，系统也没有校验，最终出现了业务上无法解释的 `220 / -1.30%`。

## 三、负数是怎样算出来的

代码分别先算三个率，再相减：

```text
响应率 = 19082 ÷ 19302 × 100% = 98.86%
执行率 =  1057 ÷ 19302 × 100% =  5.48%
完成率 = 18275 ÷ 19302 × 100% = 94.68%
滞后率 = 98.86% - 5.48% - 94.68% = -1.30%
```

换成数量看更直接：

```text
公式隐含的“滞后数量” = 响应数量 - 执行中数量 - 已完成数量
                       = 19082 - 1057 - 18275
                       = -250

-250 ÷ 19302 × 100% ≈ -1.30%
```

数据库实际存的“已滞后数量”却是 `220`。若使用它计算，结果应为：

```text
220 ÷ 19302 × 100% ≈ 1.14%
```

也就是说，当前页面左边的 `220` 与右边的 `-1.30%` 本来就不是同一个分子算出来的。

## 四、是哪几条数据造成的

当前 UAT 累计 SQL 实际纳入 3 条记录：2026-07-31 两条手工台账，加 2026-08-10 一条云采自动同步。

| 统计日 | 执行单位 | 计划 | 响应 | 执行中 | 已完成 | 已滞后 | `响应-执行中-已完成` |
|---|---|---:|---:|---:|---:|---:|---:|
| 2026-07-31 | 北京分公司 | 19000 | 18800 | 800 | 18000 | 200 | 0 |
| 2026-07-31 | 机电公司 | 280 | 260 | 255 | 255 | 20 | **-250** |
| 2026-08-10 | 云采平台 | 22 | 22 | 2 | 20 | 0 | 0 |
| **合计** |  | **19302** | **19082** | **1057** | **18275** | **220** | **-250** |

直接触发负数的是“机电公司”这条：响应只有 260，但执行中 255、已完成又是 255，两者相加为 510，已经超过响应数量。北京分公司那条虽然不会产生负数，但 `响应-执行中-已完成=0`，与录入的已滞后 200 同样不一致。

## 五、为什么系统允许录成这样

目前只有“必填、不能小于 0”的单字段校验：

- 前端 `dailyPlanStatisticsLedger/index.vue:146-171,241-249` 只设置了 `min=0` 和 required；
- 后端 `CentralPurchaseDailyStatisticsServiceImpl.java:84-104` 的新增/修改直接 `save/updateById`；
- 前后端都没有校验 `响应数量 = 执行中数量 + 已完成数量 + 已滞后数量`，也没有校验各数量之间是否存在包含/互斥关系。

因此单个数字都大于等于 0 就能发布，组合起来是否合理没人拦。

## 六、代码与需求的对应证据

| 位置 | 事实 |
|---|---|
| `02临时需求.md:5-10,15-19` | 产品公式：三个率都除以计划总数量；滞后率再用三个率相减 |
| `CentralPurchaseDailyStatisticsServiceImpl.java:136-172` | 响应/执行/完成分别除计划总量；滞后率严格做三率相减 |
| `CentralPurchaseDailyStatisticsServiceImpl.java:217-223` | `delayedRate` 入参只有三个率，没有 `delayedQuantity` |
| `CentralPurchaseDailyStatisticsMapper.xml:78-92` | `delayed_quantity` 作为独立字段累加，形成页面左侧的 220 |

## 七、建议的最终处理

技术上不建议简单把负数强制显示成 0，因为那只是把脏数据藏起来，数量与率仍然对不上。

推荐产品在下面两种完整口径中选一个：

### 方案 A：数量和率使用同一个分子（推荐）

```text
滞后率 = 已滞后数量 ÷ 计划总数量 × 100%
```

当前 UAT 会显示 `220.00 / 1.14%`，数量和率直观一致。系统仍应增加数量关系校验，避免其他三率失真。

### 方案 B：保留产品现在的相减公式

那么发布台账时必须保证：

```text
已滞后数量 = 响应数量 - 执行中数量 - 已完成数量
```

建议页面不再让人单独填写已滞后数量，而是自动计算；后端再次校验，结果小于 0 时禁止发布。UAT 的两条 07-31 手工记录也必须由业务人员重新给出正确数字，技术人员不能猜着改。

## 八、给产品的逐字确认话术

> UAT 现在显示“已滞后数量 220、滞后率 -1.30%”。原因是需求要求滞后率用“响应率减执行率减完成率”，但已滞后数量是数据库单独累加的，两者不是用同一个数计算。当前累计数据是计划 19302、响应 19082、执行中 1057、已完成 18275，所以相减实际对应的是负 250，除计划数后就是负 1.30%；而数据库录入的已滞后数量是正 220。请确认最终口径：是否改成“滞后率=已滞后数量÷计划总数量”，页面显示 220/1.14%；还是保留相减公式，并要求录入时强制满足“已滞后=响应-执行中-已完成”？我建议前者，数量和率能保持同一个口径。
