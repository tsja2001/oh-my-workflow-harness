# 第一部分：写给你看的

## 1. 这个需求到底是做什么

给招采平台加一本“煤价日报账本”：执行单位每天录入最多 5 个坑口/港口的含税煤价，提交就算发布；账本可以查、改、删、导出。领导驾驶舱右侧那张“煤炭重点坑口日指标”表继续用原地址，但以后应该自动显示这本账里最新一版的 5 个价格。

这不是“每天 24 点自动抄数”的定时任务。需求原文是执行单位在 24 点前完成录入，系统要做的是提交后立刻发布并让驾驶舱能读到，截止时间本身是对人的要求（`台账需求2.md:5`）。

## 3. 现有驾驶舱到底有没有接口

结论：**接口已经有，页面也已经在调用；但它现在只读 5 条人工/历史缓存，和本次要建的新台账没有连接。**

证据链如下：

1. 现有驾驶舱页面右侧表格字段就是“坑口名称 / 今日含税单价 / 单位”，逐行渲染 `planData`（`02zhaocai-front/scm-vue-all-cockpit/src/views/procurementCatalogMgt/index.vue:149-170`）。需求截图 `驾驶舱页面截图.png` 与该区域一致。
2. 页面已经调用 `GET /e/business/source/source/cockpit_collection_data_kengk`，并把 `dataDesc` 映射为坑口名、`dataValue` 映射为价格、单位固定为“元/吨”（同文件 `:492-507`）。
3. 后端统一入口真实存在：`SourceQueryController.java:555-558` 接收 `typeCode` 并调用 `queryCollectionData(typeCode)`。
4. 类型枚举已预留 `KENGK("kengk", "煤炭重点坑口日指标")`（`CollectionDataTypeEnum.java:3-10`）。
5. 当前服务只有中心头部、类目金额和情况分析走实时查询；其他类型直接按 `data_type` 读取 `sc_collection_data`（`SourceCollectionDataServiceImpl.java:43-62`）。专门的 `queryKengk()` 仍返回 `null`（同文件 `:81-83`）。
6. 2026-07-10 查询 `scm_source_test.sc_collection_data WHERE data_type='kengk'` 返回 5 行：`60001~60005`，价格分别为 `575/677/650/660/730`，名称与截图完全一致。`SHOW CREATE TABLE` 同时确认该表只有通用 `data_desc/data_value` 和扩展字段，没有发布日期、发布时间或操作人，无法自己判断“哪一天最新”。
7. 2026-07-10 查询 `scm_ubm_test` 的 `collectionShow` 字典，只存在 `centerHeader/categoryAmount/situA` 三个开关，没有 `kengk` 项；所以 `kengk` 当前确定走第 5 点所述的缓存分支。
8. 运行态 curl 还差一步：`scripts/api.sh` 检测到本地 TOKEN 为空，故本阶段没有声称“test 接口已经实际请求成功”。

因此，产品说的“自动更新”不需要再造一个驾驶舱 API，也不需要定时任务；需要把现有 `kengk` 分支接到新台账的最新有效记录。推荐直接查询新台账，以免同一份价格同时存两张表后出现对不上；首次新台账发布前可继续回退显示现有 5 条缓存。这个方案需由负责驾驶舱的后端同事确认（问题 5）。

组织控件不新增专用后端接口：前端复用平台已有控件，只把选中的 `executeUnitId/executeUnitCode/executeUnitName` 传给台账接口。上一版台账曾新增又删除专用组织查询接口；`test` 最近合入的相关 feature 提交 `435d0f6b5` 正是“删除台账专用组织查询接口”，本次不要重复走弯路。

## 4. 特殊逻辑

1. **流水号**：照 `CollectionDailyLedgerCodeSequence` 写 `JCKK` 版本；日期取服务器提交当天，序号每天从 `001` 重置，沿用项目 GID 服务生成，并用数据库唯一索引兜底防重。
2. **直接发布**：不增加草稿/发布状态；insert 成功即成为候选最新记录。
3. **修改防越权**：复制 DTO 后必须把流水号、创建信息、删除标记和前端传入的发布人/发布时间置空，再由服务器重填发布信息。
4. **价格校验**：非空价格必须大于等于 0、最多两位小数；名称和价格必须成对出现；至少有 1 组有效明细。
5. **驾驶舱转换**：按确认后的“最新记录”规则取一条，把非空的坑口 1~5 按序转成 `SourceCollectionData`；没有新台账记录时返回原 `sc_collection_data` 的 5 条 `kengk` 数据。
6. **删除影响**：直接实时查新台账时，逻辑删除当前记录后自然回退到下一条有效记录，不需要反向改写缓存。

## 6. 自测清单

1. 新增返回 `JCKK-当天-001`；同日第二条为 `002`。
2. 未传/伪造发布时间、操作人时，库里仍以服务器当前登录人和当前时间为准。
3. 流水号、单位、发布时间区间都能正确筛选；分页和导出结果口径一致。
4. 只填 1~3 个坑口也能保存，列表空位不报错；名称无价格或价格无名称时明确报错。
5. 修改后业务字段、发布时间、操作人变化，流水号和创建信息不变。
6. 删除后列表、详情、导出均不可见，数据库记录仍保留且 `delete_sign=1`。
7. 驾驶舱原 GET 地址返回最新有效记录的非空坑口，字段仍为 `dataDesc/dataValue`。
8. 删除当前驾驶舱记录后按产品确认规则回退；删到没有新台账时按确认规则处理旧缓存。
9. 新增 Java 文件和共享服务修改必须按工作规范走隔离 javac；不以全量 Maven 漂移报错代替自身验证。
