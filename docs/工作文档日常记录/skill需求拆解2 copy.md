# 文件日志和阅读文档规则
有时候可能只是让AI帮忙改一下接口，可能就改几行，或者让ai帮忙找个项目位置很简单，就没必要让她完整读完整个文档，跟着文档来执行工作了。
我觉得跟着读项目介绍相关的文件是有必要，只要AI操作项目肯定要知道项目组成和背景。这时候有涉及两种情况，比如让AI只是帮我找个功能，找个问题，就不需要按照完整文档事无巨细的分析和留下来记录和交接文档了；如果AI帮忙简单改一改需求或者功能，还是需要落下来文档作为日志的。这样同时我也就得和你确定一下当前记录和交接文档规则是什么，我希望AI每次执行都会写一篇类似日志的文档记录干了什么，简单复盘一下情况，目的是之后的AI知道之前的AI大概做了什么，类似一种共享记忆/上下文的操作。

# git分支问题
现在分支名太有AI味了，之后不要改一个需求就提一个分支，最好是在一个大场景完成一个大需求下，在下面无论改什么都用同一个分支。分支名尽量写的像人写的，也能够确保在当前大任务下当前分支名都能用。也参考同事提交过的分支名。比如最近在改台账功能，分支名就和台账相关，然后后面加个-yang（我的名字），确保这个分支名能用比较长时间。

# SQL语句问题
现在流程是最后会把SQL给维护的人他上生产环境，所以开发修改过程终究要考虑到，如果给到生产环境，sql需要考虑周全，尤其和前端配合的话，如果只建表没插入数据，会不会前端某些情况不好看？尤其是驾驶舱（dashboard）这种场景，也插入几条测试数据，让大屏有数据。

# 你表述的能新增文件就不修改文件感觉有点绝对了
我理解说这样不容易有冲突，容易回滚，但这样的话有时候开发的代码观感会差一点。这样吧，初次需求分析的时候，我把整个项目组的需求文档都发出来，这样可以让AI分析一下会不会有冲突。我觉得可以要求为了防止冲突啥的，开发过程中尽量保持代码集中和简洁，别这改一点那改一点的。
