# fastjson 升级带来的一系列事情

> 记录时间：2026-07-22
> 写给：不懂 Java、不熟 Maven/Nexus 的人（比如三个月后的我自己）
> 目标：把这件事的来龙去脉、公司这套技术架构、以及每一个坑背后的道理讲明白

---

## 〇、一句话说清这件事

> 公司所有 Java 服务用的一个 JSON 工具库（fastjson）有安全漏洞，需要把它从 1.2.83 升到 2.0.62。
> 理论上只要改一行配置，实际上牵出了 7 个坑，花了两天。

这份文档就是把那 7 个坑和它们背后的原理讲清楚。

## 一、先补基础：几个概念（拿前端的东西类比）

如果你写过 Node，下面这张表能省你一半时间。**Java 这套东西和 npm 那套是一一对应的**，只是名字不一样。

| Java 世界 | 前端里的对应物 | 干什么的 |
|---|---|---|
| Maven | npm / pnpm | 包管理工具 |
| `pom.xml` | `package.json` | 声明"我要用哪些包、哪个版本" |
| `~/.m2/repository` | pnpm store / npm 缓存 | 下载过的包存在本地这里 |
| `~/.m2/settings.xml` | `.npmrc` | 配置"去哪个仓库拉包、账号密码是啥" |
| `mvn deploy` | `npm publish` | 把我做的包发布出去 |
| Nexus | 公司自建的私有 npm registry | 存包的服务器 |
| jar 包 | 已经打包压缩好的 npm 包 | 编译好的二进制产物 |

### 1.1 什么是 jar 包（这个概念后面特别重要）

`.jar` 文件本质上**就是个 zip 压缩包**，里面装的是编译好的 `.class` 文件。

关键点：**`.class` 是二进制，不是源码。** 它已经是"编译完成态"了。

打个比方：
- 源码 `.java` = 菜谱
- `.class` / `.jar` = 已经做好的预制菜

你把预制菜买回来直接下锅，**不会再看一遍菜谱**。这个特性后面会咬人一口（见坑 6）。

### 1.2 SNAPSHOT 是什么

版本号后面带 `-SNAPSHOT` 的，是"开发版"。

它和 npm 最大的区别是：

> **SNAPSHOT 是覆盖式的。同一个版本号，每次发布都把上一次盖掉。**

npm 里 `1.0.0` 发过就不能再改了，你得发 `1.0.1`。Maven 的 SNAPSHOT 不是，`1.0.0-JDSN-SNAPSHOT` 这个号可以被反复覆盖，永远指向"最新的那次"。

公司这套全是 SNAPSHOT。**这是坑 2 的根源。**

## 二、公司这套架构长什么样

### 2.1 Nexus：公司的包仓库

地址 `nexus.jdsn.com.cn`（内网 IP `10.0.54.19`）。它内部长这样：

```
maven-public  ← 唯一入口，所有人的配置文件里只填这一个地址
   ├── maven-central（代理仓）  → 转发到公网/阿里云，拉 fastjson 这类第三方包，拉完在本地存一份
   ├── maven-releases（宿主仓）→ 公司自己的正式版包
   └── maven-snapshots（宿主仓）→ 公司自己的开发版包
```

`maven-public` 是个"组"，本质是个**转发路由**：你只配一个地址，它内部按顺序去这三个仓里找。

由此得出两个重要结论：

1. **第三方包（fastjson 的 jar）你既不需要、也不能"上传"。** Nexus 会自己去公网拉。你能改的只是"用哪个版本号"这个声明。
2. 公司自己的包，是靠人或 Jenkins 执行 `mvn deploy` 推上去的。

### 2.2 25 个仓库，分成两类

本地克隆下来的公司仓库有 25 个，它们不是平等的：

**第一类：7 个"地基库"——Jenkins 里没有任务，只能手动发**

```
scm-cloud-parent            ← 最重要，全公司的"版本宪法"
scm-cloud-bom
scm-cloud-dependencies
scm-cloud-assemblies
scm-assemblies-all          ← 这次改代码的地方
scm-all
scm-sino-approve-attach-all
```

**第二类：18 个业务库——Jenkins 里有任务**

```
auth  contract  datacenter  devops  file  gateway  ifs  mdm  order
platform  product  professor  report  source  srm  template  ubm  workflow
```

### 2.3 `scm-cloud-parent` 是什么：全公司的"版本宪法"

这个东西前端没有完全对应物，最接近的是 `package.json` 里的 `overrides`。

它的 `pom.xml` 里写着：

```xml
<properties>
    <fastjson.version>2.0.62</fastjson.version>   <!-- 定义一个变量 -->
</properties>

<dependencyManagement>
    <dependency>
        <artifactId>fastjson</artifactId>
        <version>${fastjson.version}</version>     <!-- 声明：谁用 fastjson 就用这个版本 -->
    </dependency>
</dependencyManagement>
```

然后下游 27 个项目在自己的 `pom.xml` 里只写：

```xml
<dependency>
    <artifactId>fastjson</artifactId>
    <!-- 注意：不写版本号！ -->
</dependency>
```

**版本号从 parent 继承。所以改 parent 一行 → 发布一次 → 全公司下次构建自动生效。**

这就是为什么这活儿看着只改一行却很敏感：**它是单点，改错了全公司一起崩。**

### 2.4 Jenkins：两类任务，先 all 后 web

公司 Jenkins（`jenkins.jdsn.com`）里有 168 个任务，其中后端 test 相关的 40 个。规律是死的：

| 任务名 | 拉哪个仓库 | 分支 | 干什么 |
|---|---|---|---|
| `xxx-all-test` | 对应的业务仓库 | `test` | `mvn versions:set 1.0.0-JDSN-TEST-SNAPSHOT` + `mvn clean deploy`<br>→ **把 jar 发到 Nexus** |
| `xxx-web-test` | **全部都是 `scm-cloud-starters-web`** | `test` | `mvn clean install` + 打 Docker 镜像 + `kubectl apply`<br>→ **上 K8s 真正跑起来** |

**两个反直觉的点：**

1. **19 个 `-web-test` 任务全都构建自同一个仓库 `scm-cloud-starters-web`。** 那是个"壳工程"单体仓库，里面一个服务一个目录。它不在你本地的 25 个仓库里，不用管，Jenkins 自己拉。

2. **每个服务要跑两个任务，顺序不能反。** `-all` 先把 jar 发到 Nexus，`-web` 再从 Nexus 把 jar 拉下来打成镜像。反了就是拿旧 jar 打镜像。

> 补充：有些仓库的代码里能翻到 `Jenkinsfile-Test` 之类的文件，那是**历史残留副本**，实际任务不读它。真正的配置在 Jenkins 网页上。

### 2.4.1 ⭐ 19 个 `-web-test` 用同一个仓库，靠什么区分？

这是最容易懵的一个点。答案是 **`PROJECT_DIR` 这个环境变量**。

把几个任务的配置拉出来对比，除了三个变量，其余**完全一样**：

| 任务 | git 仓库 | **PROJECT_DIR** | **APP_NAME** | **JAR_FILE** |
|---|---|---|---|---|
| scm-source-web-test | scm-cloud-starters-web | `scm-cloud-source` | scm-source-web | scm-source-web.jar |
| scm-order-web-test | scm-cloud-starters-web | `scm-cloud-order` | scm-order-web | scm-order-web.jar |
| scm-srm-web-test | scm-cloud-starters-web | `scm-cloud-srm` | scm-srm-web | scm-srm-web.jar |
| scm-gateway-web-test | scm-cloud-starters-web | `scm-cloud-gateway` | scm-gateway-web | scm-gateway-web.jar |
| scm-gateway-mall-web-test | scm-cloud-starters-web | `scm-cloud-gateway-mall` | scm-gateway-mall-web | scm-gateway-mall-web.jar |

完整环境变量块 11 行里，只有 `APP_NAME` / `JAR_FILE` / `PROJECT_DIR` 三行不同。Harbor 地址、命名空间、凭据 ID、K8s 配置全都一样。

**`scm-cloud-starters-web` 是个单体仓库，一个服务一个目录，任务只是 `cd` 进不同的目录构建。**

### 2.4.2 什么是「壳工程」

那 19 个目录里装的是"壳"——几乎没有业务代码，只有三样东西：

1. 一个 `main()` 启动入口
2. 配置文件（连哪个数据库、哪个注册中心）
3. `Dockerfile` 和 K8s 部署 yaml

**业务代码不在这儿**，在 `scm-source-all` 那些仓库里。

用 Node 类比：

| | 对应物 |
|---|---|
| `scm-source-all`（业务仓库） | 你写的业务 npm 包，`npm publish` 发出去 |
| 壳目录 `scm-cloud-source` | 极薄的 `server.js`，内容基本是 `require('业务包')` + `app.listen(8080)`，再配个 Dockerfile |

所以两类任务的分工：

```
scm-source-all-test   把业务代码编译成 jar，发到 Nexus
                              ↓
scm-source-web-test   cd 进壳目录 → 从 Nexus 拉业务 jar
                      → 壳 + 业务 jar 打成一个能跑的大 jar
                      → Docker 镜像 → K8s
```

**这就是为什么必须先 all 后 web**——反了就是拿旧的业务 jar 打镜像。

**为什么要这么拆？** 三个好处：

1. **业务和部署解耦** —— 运维改 Dockerfile、改 K8s 配置，不用碰业务仓库
2. **规范统一** —— 19 个服务的启动方式、镜像构建、部署流程全在一个仓库管，改一处全部生效
3. **一套业务代码可配多个壳** —— 证据：`scm-cloud-gateway` / `scm-cloud-gateway-mall`、`scm-cloud-ubm` / `scm-cloud-ubm-mall`。同一业务域，一个对内一个对商城，配置不同、镜像不同、Pod 不同，业务 jar 共用

### 2.4.3 ⚠️ 只点 `-all-test`，线上是不会变的

**这条最实用，务必记住。**

`-all-test` 只是把 jar 发到 Nexus 这个"仓库"里，**K8s 上跑的 Pod 完全没动**。必须再点对应的 `-web-test`，才会重新打镜像、重新部署。

> 如果遇到"我明明改了、Jenkins 也绿了、怎么测试环境没变"——十有八九就是**只点了 `-all-test`**。

例外：`scm-platform-all`、`scm-mdm-all`、`scm-datacenter-all`、`scm-template-all` 这四个纯粹是给别人用的库，没有自己的服务，所以只有 `-all-test`。

**回到 fastjson**：最终镜像里带的是哪个 `fastjson.jar`，是在 `-web-test` 这一步打包时决定的——壳工程 `mvn clean install` 读 parent pom 拿到 `2.0.62`，和所有业务 jar 一起塞进大 jar。所以 **`-web-test` 才是真正让 fastjson 2.0.62 上线的那一步**。

### 2.5 完整链路：从你改一行，到线上服务真的换了库

```
你在本地改 pom.xml / 改代码
   │
   ├── git push ──────────→ GitLab（源码存档，给人看的、可追溯的）
   │
   └── mvn deploy ────────→ Nexus（构建产物，给机器拉的）
                                │
                                ↓
                       Jenkins  xxx-all-test
                       拉 test 分支 → mvn clean deploy
                       把业务 jar 发到 Nexus
                                │
                                ↓
                       Jenkins  xxx-web-test
                       从 Nexus 拉全部 jar → 打成一个大 jar
                       → Docker 镜像 → 推到 Harbor
                                │
                                ↓
                       K8s 集群（KubeSphere 是它的管理网页）
                       服务真正跑起来的地方
```

**`git push` 和 `mvn deploy` 是两条完全独立的腿**，这点前端也一样（`git push` ≠ `npm publish`）：

- 只 push 不 deploy → 代码库里有了，但下游 Jenkins 拉到的还是老 jar
- 只 deploy 不 push → 线上生效了，但代码库里查不到是谁改的

## 三、⭐ 为什么有的要手动 `mvn deploy`，有的去 Jenkins 点

这是最容易懵的一个点，单独拿出来讲。

**先说结论：`mvn deploy` 这个动作，两边都在做。区别只在于"谁来按这个按钮"。**

| | 谁执行 | 为什么 |
|---|---|---|
| 7 个地基库 | **人手动在本地敲 `mvn deploy`** | 历史上**没人给这几个仓库建 Jenkins 任务**。就这么简单，没有技术原因 |
| 18 个业务库 | **Jenkins 点一下，它替你敲 `mvn deploy`** | 有人建了任务 |

Jenkins 任务的本质，就是**一台服务器帮你自动执行那几条命令**：拉代码 → 敲 mvn → 打镜像。它并没有什么魔法，你在本地敲的和它在服务器上敲的是同一套命令。

**为什么当年没给地基库建任务？** 合理推测：地基库改动频率极低（`scm-share-aim-spring` 上一次发布是 **2023 年 4 月**，三年没动过），一年动不了一次，建任务的收益不大，就一直手动了。

**这带来一个后果**：地基库的更新完全依赖"有人记得去手动发"。这次差点就漏了一个（见坑 6）。

## 四、fastjson 是什么，为什么非升不可

**fastjson 是阿里做的一个 JSON 处理库**，作用相当于前端的 `JSON.parse()` / `JSON.stringify()`，只是功能多得多。

**1.x 版本有个要命的漏洞，叫 autoType。**

这个功能是这样的：JSON 报文里可以写一个特殊字段 `@type`，指定"把这段数据变成哪个 Java 类"：

```json
{ "@type": "com.example.User", "name": "张三" }
```

fastjson 看到 `@type` 就会照着去实例化这个类。听起来很方便，但——

> **攻击者只要能往你的接口传 JSON，就能塞一个恶意类名进去，让你的服务器替他执行代码。**

用前端的话说：**这相当于对用户传来的字符串做了 `eval()`。** 这是最高危的那一档漏洞（远程代码执行 RCE）。

fastjson 2.x 重写了整个实现，**默认关闭 autoType**，所以升级到 2.x 就解决了。

**为什么不打补丁而要跨大版本？** 查过了，Nexus 上 1.x 最高就到 1.2.83，官方没有 1.2.84+。要么升 2.x，要么用 `1.2.83_noneautotype`（物理阉割版）。最后选了 2.0.62，因为它是"兼容包"，`import` 语句不用改。

## 五、⭐ 完整经过：7 个坑，一个一个讲

### 坑 1：IDEA 一直卡在"正在解析 Maven 依赖"

**现象**：改完 pom，IDEA 转圈半天不动。

**原因**：`~/.m2/settings-zc.xml` 里有一行

```xml
<localRepository>/Users/zhangyingle/maven-repo/repo/</localRepository>
```

`/Users/xxx` 是 **macOS 的路径格式**。这个配置文件是从一位用 Mac 的同事那儿拷来的，在 Linux/WSL 上这个路径根本不存在。

**后果**：本地已经下载好的 662MB 缓存全部作废，每次都从 Nexus 重新全量下载。

**处理**：改成 `/home/t/.m2/repository`。

**教训**：**别人的配置文件拿来直接用，先检查里面的路径。**

---

### 坑 2：从错误的分支 deploy，覆盖掉了同事的东西

这是最值得记住的一个坑。

**现象**：改完 parent 发布出去后，`scm-platform-all` 的 Jenkins 构建报错：

```
'dependencies.dependency.version' for com.alibaba:easyexcel:jar is missing
```

**发生了什么**（一步步看）：

1. `scm-cloud-parent` 有好几个分支，`prod` 是主线
2. `prod` 分支上，同事最近提交了 4 个改动：加了 easyexcel（两次）、swagger v3、springdoc
3. 但我是从 `dev` 分支执行的 `mvn deploy`
4. `dev` 分支**落后 prod 4 个提交**，里面根本没有 easyexcel 的版本声明
5. 因为 **SNAPSHOT 是覆盖式的**，这一发直接把 Nexus 上那份"完整的 parent"盖成了"缺 4 项的 parent"
6. 下游项目要用 easyexcel，但新 parent 里查不到版本号 → 构建失败

**用 npm 的话说**：相当于你在一份旧代码上 `npm publish` 了同一个版本号，把同事刚发的内容覆盖了。

**处理**：切回 `prod` 分支，只改 fastjson 那一行，重新 deploy。

**教训（红线级）**：

> **全公司公共模块的 deploy，必须基于最新的主线分支。**
> deploy 前先 `git pull`，先确认自己在哪个分支上。

### 坑 3 和坑 4：Jenkins 报"找不到某个 jar"

**现象**：

```
Failure to find com.pcitc:scm-source-cebpubservice:jar:1.0.0-JDSN-SNAPSHOT
package com.pcitc.scm.plateform.importdata.enums does not exist
```

**原因**：这两个都**和 fastjson 完全无关**，是结构性问题：

1. Jenkins 的任务配置里写了 `PROJECT_DIR`，**它只构建仓库里的某一个子目录**，同仓库的兄弟模块不在构建范围内
2. 跨仓库、跨模块的依赖，只能从 Nexus 拉
3. 如果某个模块从来没被 deploy 过，或者 SNAPSHOT 过期被 Nexus 清理了，就会"找不到"

**教训**：**要学会分辨两种失败。**

| 报错长这样 | 性质 | 怎么办 |
|---|---|---|
| `cannot find symbol` / `package does not exist`（找不到**方法/类**） | **真实代码问题** | 必须改代码，Jenkins 也救不了 |
| `Failure to find xxx:jar`（找不到**包**） | 环境/发布顺序问题 | 补发布或调整构建顺序 |

这个分辨能力，是这次最值钱的收获。

### 坑 5：fastjson 2.x 把一个方法删了，代码编译不过

**现象**：

```
cannot find symbol: method getClassFromMapping(String)
  in com.alibaba.fastjson.util.TypeUtils
```

**原因**：`TypeUtils.getClassFromMapping()` 是 fastjson **1.x 的内部工具方法**，2.x 重写实现时把它物理删除了。

全工程扫描后，用到它的地方有 3 处：

| 文件 | 状态 |
|---|---|
| `scm-common-json/JsonTransferUtil.java:73` | 活跃，要改 |
| `scm-share-aim-spring/JsonServiceImpl.java:70` | 活跃，要改 |
| `scm-share-rule/JsonUtils.java:84` | 已被注释掉，不用管 |

**改法**（用标准写法替代内部 API）：

`JsonTransferUtil.java`：
```java
// 原来：靠 fastjson 内部方法判断"这个对象是不是已经是目标类型了"
Class<?> c = TypeUtils.getClassFromMapping(g.getClass().getName());
if (c != null) { return (T) g; }
return JSONObject.toJavaObject((JSON) g, returnClass);

// 改后：用 Java 自带的 instanceof 判断
if (g instanceof JSON) {
    return JSONObject.toJavaObject((JSON) g, returnClass);
}
return (T) g;
```

`JsonServiceImpl.java`：
```java
// 原来
JSON j = (JSON) JSONObject.toJSON(content);
Class<?> c = TypeUtils.getClassFromMapping(type.getName());
if (c != null) { return (T) content; }
return j.toJavaObject(type);

// 改后
if (type.isInstance(content)) {
    return (T) content;
}
JSON j = (JSON) JSONObject.toJSON(content);
return j.toJavaObject(type);
```

顺便也扫了其他已知的 2.x 不兼容 API（`addAccept`、`autoTypeSupport`、`setAutoTypeSupport`、`ParserConfig.getGlobalInstance`），全工程都没用到。

### 坑 6：⭐ 差点漏掉的"运行时地雷"

**这是整件事里最危险、也最值得学的一个坑。**

#### 问题是什么

坑 5 里改好的两个文件，提交了、推送了。但**改完代码只是第一步，还得把改完的 jar 发到 Nexus 上去**。

结果：
- `scm-common-json` —— 发了 ✅（提交后 2 分钟就发了）
- `scm-share-aim-spring` —— **忘了发** ❌

Nexus 上那个 jar 还停留在 **2023 年 4 月 18 日**的版本。

#### 为什么这个特别危险

回想 1.1 节说的：**jar 是编译好的二进制，用的时候不会再看一遍源码。**

所以会发生这样一件事：

```
下游服务构建时：
   拉到 fastjson 2.0.62（新的，没有 getClassFromMapping）
   +
   拉到 scm-share-aim-spring 的旧 jar（里面写死了"去调 getClassFromMapping"）
        ↓
   编译 ✅ 通过     ← javac 只检查你写的源码，不会拆开别人的 jar 看里面
        ↓
   打成镜像 ✅ 成功
        ↓
   K8s 里 Pod ✅ 正常启动
        ↓
   真实业务请求打进来，走到那段代码
        ↓
   💥 java.lang.NoSuchMethodError
```

**打个比方**：

> `JsonServiceImpl` 是个翻译官，他的小抄上记着"这个词去查词典第 387 页"。
> 公司把词典从第 1 版换成第 2 版，第 2 版删掉了第 387 页。
> 但翻译官是张"照片"（编译好的 jar），换词典的时候没人检查他的小抄。
> 一切看起来都正常——直到真有人来找他翻译，他翻到 387 页，发现没了，当场傻眼。

**这比编译失败危险得多**：编译失败你当场就知道；这个是**构建全绿、镜像推上去、Pod 起来了，等真实业务流量进来才炸**。

#### 影响范围

`scm-share-aim-spring` 被这些地方依赖：
- `scm-ifs-all`（batch / bi / cebservice / log / message / sms / ssc / sse / tymh，共 9 个模块）
- `scm-srm-all`（apply-qualification / apply-sitevisit / web-jar / srm，共 4 个模块）
- `scm-cloud-assemblies/scm-assembly-oauth2`

#### 怎么发现的

不是靠猜，是靠**把 Nexus 上的 jar 下载下来，直接拆开看字节码**：

```python
import zipfile
z = zipfile.ZipFile('scm-share-aim-spring-xxx.jar')
for n in z.namelist():
    if n.endswith('.class') and b'getClassFromMapping' in z.read(n):
        print("★ 还在调这个方法:", n)
```

结果确实打印出来了 → 地雷坐实。

**这个技巧记住：怀疑 Nexus 上的 jar 是不是旧的，就把它下下来拆开搜字符串。比看时间戳可靠得多。**

#### 一个附带的知识点：Maven 的时间戳是 UTC

排查时差点判断错。Nexus 上显示 `scm-common-json` 的发布时间是 `20260721.081424`，看起来是"上午 8 点 14 分"，而代码是下午 16:12 才提交的——好像发布在提交之前，说不通。

实际上 **Maven 快照的时间戳是 UTC 时间**，加 8 小时才是北京时间：

```
08:14 UTC  =  16:14 北京时间
代码提交    =  16:12 北京时间
```

正好晚 2 分钟，完全说得通。**看 Nexus 时间戳记得 +8。**

### 坑 7：Nexus 的 HTTPS 证书过期了

**现象**：手动 `mvn deploy` 时直接报错：

```
PKIX path validation failed: validity check failed:
NotAfter: Tue Jun 16 07:59:59 CST 2026
```

**原因**：Nexus 的 HTTPS 证书 `*.jdsn.com.cn`（RapidSSL 签发）**已于 2026-06-16 过期**，当时已经过期五周多了。Maven 下载依赖时走 `https://`，撞上过期证书直接中断，连编译都没开始。

**处理**：把 `~/.m2/settings-zc.xml` 里的下载地址从 `https://` 改成 `http://`。

**为什么这样改是安全的**（不是偷懒绕过检查）：

> 公司自己的 parent pom 里，`distributionManagement`（上传地址）**本来就写的 `http://`**。
> 也就是说，**Nexus 密码在每次 deploy 时早就是明文过网的**。
> 把下载也统一成 http，安全性没有任何实际变化，但 IDEA、命令行所有地方一次性都通了。

**这个要报给运维换证。** 同事大概率也踩过这个坑，或者各自偷偷改成了 http。

## 六、⭐ 划重点：这次学到的几条硬道理

### 1. `git push` 和 `mvn deploy` 是两件事

- `git push` → 源码进 GitLab，给**人**看
- `mvn deploy` → 产物进 Nexus，给**机器**拉

**改完代码只 push 不 deploy，等于没改**（对下游构建而言）。坑 6 就是栽在这。

### 2. SNAPSHOT 是覆盖式的，所以 deploy 前必须站在最新分支上

从落后的分支 deploy = 把同事的东西回滚了。坑 2。

### 3. 会分辨"该修的失败"和"噪音失败"

- `cannot find symbol`（找不到方法/类）→ **真实代码问题，必须改**
- `Failure to find xxx:jar`（找不到包）→ 环境/顺序问题，重发或调顺序

### 4. 编译通过 ≠ 运行时没事

二进制 jar 不会在编译时被重新检查。**换了底层库之后，所有依赖它的旧 jar 都得重新编译发布一遍**，否则就是坑 6 那种"构建全绿、上线才炸"。

### 5. 仓库之间的依赖是有环的

用全部 pom 算过依赖图，`scm-source-all ↔ scm-ifs-all ↔ scm-order-all ↔ scm-srm-all` 互相依赖。

**意味着不存在一个"完美顺序"。** 好在都是 SNAPSHOT，Nexus 上永远有上一版兜底，跑一遍就行，个别失败的重跑一次即可。

### 6. 要验证"真的生效了"，别只看 Jenkins 绿灯

绿灯只说明"构建没报错"，不说明"跑起来是对的"。真正的验证是：

```bash
# 进 K8s pod 里
jar tf /opt/app/scm-source-web.jar | grep fastjson    # 应该看到 2.0.62
```

然后翻服务启动日志和首批请求日志，**专门搜 `NoSuchMethodError`**。
