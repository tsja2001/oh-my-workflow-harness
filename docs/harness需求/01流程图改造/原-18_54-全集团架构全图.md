# 一 · 为什么要画六张图，而不是一张

架构图画不成一张，这不是画图能力问题，是行业共识。

**`ISO/IEC/IEEE 42010`** 这个国际标准专门规定了一件事：架构描述必须**按不同干系人的关注点分成多个视图（Views）**。
最有名的落地版本是 **Kruchten 的 `4+1 View Model`**（逻辑/开发/进程/物理 + 场景），
企业级建模语言 **`ArchiMate`** 则分成 Business / Application / Technology 三层。

**为什么一张图必然失败**：领导要看"哪个板块上了没有"，你要看"改这个字段影响谁"，运维要看"跑在哪台机器上"——
**这三个问题的正确画法完全不同**，硬塞一张图上，三个人都看不懂。

本文按这个思路拆六张：

| 视图 | 回答谁的问题 | 关注点 |
|---|---|---|
| **1 组织视图** | 领导 | 11 个板块，谁上了、谁没上 |
| **2 应用覆盖矩阵** | 项目经理 | 板块 × 系统，哪些格子是空的 |
| **3 数据流视图** | 你 | 一笔业务跨了哪些系统，在哪断开 |
| **4 集成视图** | 你 | 12 条对外接口，各走什么协议 |
| **5 技术视图** | 运维 | 微服务、中间件、部署在哪 |
| **6 治理视图** | 决策者 | 合规管什么、经营管什么——**这张最少人画，但决定项目成败** |

## 这张图最该看出来的三件事

**① 这个"集团平台"实际上是一个板块在用。**
BU002 冀东水泥占了 **约 90%** 的方案量，BU004 冀东发展 6%，剩下 9 个板块加起来不到 5%。

> **【推断】** 这不代表那三个板块不采购，而是他们的采购**没走这个平台**。
> **无法证实的原因**：平台外的采购行为不会在平台库里留任何痕迹。

**② "11 个板块"和"11 个租户"是两回事。**
BU005/BU007/BU009/BU010/BU011 各自只有 **1 家公司**——这些是集团的职能型子公司（财务公司、研究院、人才中心），

> 这条对 SRM 选型直接有用：会上讨论"要不要支持 11 个板块的多租户"，
> **按实际用量看，真正的题目是"要不要支持 4 个"。** 这会显著改变方案二和方案三的成本估算。

**③ 冀东系（BU002 + BU003 + BU004）合起来占了平台 96% 的业务量**（3486 / 3644 条带板块编码的方案）。
换句话说——**这个"金隅集团招采平台"，事实上是一个冀东系的平台。**
这和 `53` 里那条并购史（2016 年前后重组冀东【公开信息，年份自核】）完全对得上。

## 这张矩阵暴露的结构性问题

```
                    招采平台（集团统一，合规驱动）
                            ▲       ▲
              ┌─────────────┘       └──────────────┐
              │ 定制通道 A                          │ 定制通道 B
              │ 2023-04 上线                        │ 2025-10 上线
              │ 60 条计划                           │ 149 条计划
        ┌─────┴─────┐                        ┌──────┴───────┐
        │  SAP      │                        │  美云 SRM     │
        │ (BU002)   │                        │  (BU004)     │
        └───────────┘                        └──────┬───────┘
                                                    │
                                             ┌──────┴───────┐
                                             │  用友 NC65    │
                                             └──────────────┘

        另外 9 个板块 ──── 没有上游通道，全靠人在页面上手工建计划
```

> ### **这就是"每加一个板块，就要再定制一次一条通道"的图形化版本。**
>
> 两条通道是**分别做的、互不复用**：
> - SAP 那条走 `scm-ifs-outservice/sap`
> - SRM 那条走 `scm-ifs-outservice/srm` + **ESB**，而且**两个入口都用 `if("BU004".equals(...))` 卡死**
>   （`SourceEnrollServiceImpl.java:1899`、`DealToSRMTaskConsumerAdapater.java:90`）**【实证】**
>
> **这个反模式有名字：`Point-to-Point Integration`（点对点集成）。**
> 代价是连线数按 **N²** 增长——3 个系统 3 条线，6 个系统 15 条线。
> 企业集成的整个演进史（ESB → iPaaS → Event Mesh）都是在解决这一件事。

## 一个数据质量问题，顺手记下来

**【实证】** `sc_plan` 里 149 条 SRM 来源的计划，**`bu_code` 全部是 NULL**。
也就是说：**SRM 推过来的计划不带板块编码。**

后果：任何按板块统计的报表都会漏掉这 149 条，或者把它们算进"未知"。
**推到多板块之后，这个字段必须补上，否则集团级看板从第一天就是错的。**

## 三条值得记住的观察

**① ESB 只用在"集团级、要审计"的接口上。**
走 ESB 的三家：**冀东发展 SRM、集团财务共享（BBMG BIP）、SAP**。
其余全是点对点 HTTP。**这不是随意的——ESB 报文头里的 `sysid`/`syncode`/`synname`/`puuid`
就是为了"任何一次跨系统调用都能查出是谁、调的什么、哪一次"。**

> **`puuid` 这一个字段，比任何架构文档都更能说明这套系统服务的是什么样的组织。**

**② 财务共享有两条路，不是一条。**
`scm-ifs-ssc`（保证金相关）和 `scm-ifs-outservice/bbmgbip`（集团财务共享收款单）是两个模块。
**【推断】** 前者是早期做的保证金专用通道，后者是后来接的集团统一财务共享（用友 BIP）。
**无法证实的原因**：两个模块的上线时间和职责边界在代码注释里没写。**这条值得问一下同事**，
因为下一年计划里 `P1-06 保证金线上自动退费`（35 人天）要动的正是这块。

**③ 工作流引擎在平台外面，但部署在金隅域名下。**

## 这张图一句话解释了 0827 那场会的所有争执

> ### **合规域天然集中，经营域天然分散。**
> ### **而 SRM 是一个经营域的产品，现在要把它塞进合规域的模具里。**

| 会上吵不出结果的问题 | 用这张图看 |

# 八 · 这张图上的 9 个空格

**架构图的价值不在画满的格子，在空着的格子。** 按对下一年计划的影响排序：

| # | 空格 | 影响 |
|---|---|---|
| 1 | **9 个板块没有上游通道**，全靠人工建计划 | 集团级数据永远不全，任何驾驶舱都是残的 |
| 2 | **经营域集团层是空的**——没有集团采购部、没有集团品类经理、没有统一物料 | **SRM 提到集团层最大的障碍，不是软件** |
| 3 | **SRM 推来的计划不带 `bu_code`**（149 条全 NULL） | 多板块后集团看板从第一天就是错的 |
| 4 | **两条上游通道各定制一次**，没有抽象成"通道适配层" | 每加一个板块就再定制一次 |
| 5 | **`checkEnroll` 同步阻塞，无熔断/舱壁/降级** | 推到多板块后，SRM 挂 = 全集团报名瘫痪 |
| 6 | **供应商评价在合规域算不出来** | `P2-04`（38 人天）做出来也只能人工一年评一次 |
| 7 | **黑名单/冻结/不良行为三层状态没有单一事实源** | 会上没收口，两边都存、各管各的 |
| 8 | **报表底座未定**（帆软 vs 集团 ABI） | `P4-01`+`M4-01` 共 129 人天悬空 |
| 9 | **底座组件无人维护**（`scm-share-aim-spring` 的 jar 停在 2023-04-18） | 任何涉及公共层的改动都要先趟一遍雷 |

**其中第 1、2 条不是技术问题**，但它们决定另外 7 条值不值得做。

# 九 · 三句话把六张图串起来

1. **组织上**，这是一个"金隅集团"的平台，但实际上 **96% 的业务量来自冀东系**（BU002+BU003+BU004，3486/3644）。
2. **技术上**，两条上游通道（SAP / SRM）各定制一次、点对点、其中一条还用 `BU004` 硬编码写死——
   **"支持多板块"这件事在架构上还没开始做。**
3. **治理上**，集团在合规域有完整抓手，在经营域**几乎没有抓手**。
   而这次要买的 SRM 是经营域的产品——**这才是整件事真正的难度所在。**
